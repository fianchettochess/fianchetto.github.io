    accuracy¶

    Per-move win-probability losses, per-move accuracies, quality labels, band counts with their ply indices, phase splits, and both game-accuracy aggregates — for one side, from a White-POV eval array. Every formula is a linked AccuracyAggregator call; the command only shapes JSON.

    stdin¶

    One JSON object per line.

    Field Type Required Default Meaning
    id String yes — echoed on the response line
    white_pov_evals [Double] yes — the annotate output array; needs at least 2 entries
    start_is_white Bool yes — which color moved at ply 0
    color String yes — "white" or "black", case-insensitive; whose moves are graded

    There are no optional fields.

    stdout¶

    Field Type Meaning
    id String the request id
    accuracy Double per-move-average accuracy — the number the app's Review pane shows
    accuracy_mean_loss Double mean-loss aggregate — what calibration and EloEstimator use
    sample_moves Int how many moves this side made
    move_plies [Int] 0-based ply index of each of this side's moves
    move_wp_losses [Double] per-move win-probability drop, mover POV, on the 0…1 scale
    move_accuracies [Double] per-move accuracy, 0…100
    move_qualities [String] "best" / "excellent" / "good" / "inaccuracy" / "mistake" / "blunder"
    blunders, mistakes, inaccuracies Int band-exclusive counts, not cumulative
    blunder_plies, mistake_plies, inaccuracy_plies [Int] the plies behind those counts
    phase_accuracy [String: Double] keyed opening / middlegame / endgame, over the phases this side actually played

    The four parallel arrays (move_plies, move_wp_losses, move_accuracies, move_qualities) are index-aligned and always have sample_moves entries.

    Flags¶

    None at all. Any argument is an error, including an unrecognized one — --help and -h are intercepted by the dispatcher before the command runs.

    The formulas¶

    All constants live in AccuracyAggregator and appear nowhere else in the codebase:

    winProbability(cp) = 1 / (1 + exp(-0.00368208 * cp))

mover POV        wp        for white
                 1 - wp    for black
wpDrop_i         = max(0, wpBefore_i - wpAfter_i)              // 0…1
moveAccuracy_i   = clamp(103.1668 * exp(-0.04354 * (wpDrop_i * 100)) - 3.1668, 0, 100)

accuracy             = mean(moveAccuracy_i)                    // per-move average
accuracy_mean_loss   = clamp(103.1668 * exp(-0.04354 * meanLoss) - 3.1668, 0, 100)
    where meanLoss   = mean(min(100, wpDrop_i * 100))

    The two aggregates differ by more than rounding. Applying a convex curve to each move and then averaging is not the same as averaging the losses and applying the curve once — by Jensen's inequality the per-move average is always the higher of the two. Both are emitted because both are load-bearing: the Review pane shows the first, and every calibration row was labeled with the second, so mixing them would silently bias every Elo estimate.

    Labels come from the same win-probability drop:

    classifyMoveQuality(wpDrop:playedBestMove:)
    playedBestMove   -> .best        // never fires here
    wpDrop >= 0.20   -> .blunder
    wpDrop >= 0.10   -> .mistake
    wpDrop >= 0.05   -> .inaccuracy
    wpDrop >= 0.02   -> .good
    else             -> .excellent

    playedBestMove is hardwired false in this command. An eval array carries no best-move identity — knowing the position was worth +43 before and +35 after says nothing about which move the engine preferred — so the .best override cannot be evaluated here. The app applies it only where best-move UCIs are stored alongside the evals. A move labeled "best" therefore never appears in this command's output.

    Counting is band-exclusive: a blunder is not also counted as a mistake and an inaccuracy. Sum the three fields to get "moves worse than good".

    Phases split by full move number, derived as (ply / 2) + 1:

    moves  1–10  -> opening
moves 11–30  -> middlegame
moves 31+    -> endgame

    A phase key is absent when this side made no moves in it — callers should skip it rather than read it as 0.

    Errors¶

    An unknown color, an array with fewer than 2 entries, a side that made no moves in the array, or a nil return from AccuracyAggregator.accuracy(evalsJSON:…) each emit {"id", "error"} and continue.

    Worked example¶

    Taking the Scholar's-mate eval array straight from annotate and grading Black:

    printf '%s\n' \
  '{"id":"scholars-mate","white_pov_evals":[43,35,35,-59,-40,-46,100000,100000],"start_is_white":true,"color":"black"}' \
  | .build/debug/fianchetto-cli accuracy

    {"accuracy":66.3538,"accuracy_mean_loss":42.6294,"blunder_plies":[5],"blunders":1,
 "id":"scholars-mate","inaccuracies":0,"inaccuracy_plies":[],"mistake_plies":[],"mistakes":0,
 "move_accuracies":[100,92.4963,6.5652],"move_plies":[1,3,5],
 "move_qualities":["excellent","excellent","blunder"],
 "move_wp_losses":[0,0.0173437,0.5422430],
 "phase_accuracy":{"opening":66.3538},"sample_moves":3}

    (Floats are rounded here for width; the real line carries full double precision and is emitted as a single line.) Ply 5 is Nf6??, allowing mate: the win-probability drop of 0.54 is well past the 0.20 blunder threshold and drives the per-move accuracy to 6.6. Note how far the two aggregates separate on a short game with one catastrophe — 66.35 per-move-average against 42.63 mean-loss. Grading White on the same array instead reports one inaccuracy at ply 2 and an overall 90.50.

    Seam provenance¶

    Fully linked to AccuracyAggregator:

    Behavior Kit surface
    the logistic AccuracyAggregator.winProbability(cp:)
    per-move accuracy AccuracyAggregator.moveAccuracy(wpBefore:wpAfter:)
    per-move-average accuracy, phases, sample counts AccuracyAggregator.accuracy(evalsJSON:startIsWhite:color:)
    mean-loss aggregate AccuracyAggregator.accuracy(fromMeanLoss:)
    labels AccuracyAggregator.classifyMoveQuality(wpDrop:playedBestMove:)
    the label strings themselves ChessCore MoveQuality raw values

    Nothing is mirrored. The per-move sweep the command runs to build the parallel arrays uses the identical mover-POV flip and wpDrop convention as the kit's own accuracy(evalsJSON:) walk, and the game-level number is taken from that kit call rather than recomputed — the arrays and the scalar cannot disagree.

    guard let gameAccuracy = AccuracyAggregator.accuracy(
    evalsJSON: evalsJSON,          // white-POV centipawns, plies + 1 entries
    startIsWhite: true,
    color: .black
), let overall = gameAccuracy.overall else { return }

gameAccuracy.phases[.opening]      // nil when the side made no moves in that phase
gameAccuracy.overallSampleCount
