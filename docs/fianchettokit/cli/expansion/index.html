    CLI expansion (proposed)¶

    fianchetto-cli runs the app's own validated logic headlessly, so every FianchettoKit seam that decides a number without a view attached is a candidate for a subcommand. This page ranks the candidates a full survey of the kit turned up, sketches wire contracts for the strongest, and records which seams are honestly not worth exposing.

    Everything on this page is a proposal

    The CLI implements exactly six subcommands today: annotate, estimate, maia, accuracy, project, track. Nothing below is implemented. Command names are proposals and may change; the seams are real and every signature, argument label, and constant quoted here was read out of the kit source.

    Why expand at all¶

    The CLI is not a reimplementation — it links the same package the app builds against, so a number it prints is the number the app would have computed. That property is what makes a subcommand worth more than a script, and it buys four things a running app cannot:

    What it buys
    Research throughput Corpus-scale answers — feature matrices, yield counts, distributions, inference budgets — over a library instead of one game at a time
    Batch QA A pass/fail gate over a fixture directory that a CI job can run, rather than a manual sweep through a UI
    Regression baselines A golden output file, diffable on every change, pinning a constant that today only a running app exercises
    App parity One canonical answer both the Apple and Android shells can diff against, instead of two independent derivations that drift

    The fourth is the one with a track record. Several kernels in the kit exist because the two shells disagreed, and their source comments name the divergence they were extracted to kill. A CLI turns each of those from a one-time fix into a standing check.

    What counts as a candidate¶

    A seam qualifies when three things hold at once: it is public, it is a function of values a JSON line (or a PGN) can reconstruct, and it has a consumer that is not a view. The third test eliminates most of the kit — a great deal of it decides a label or a color for exactly one SwiftUI surface, and a subcommand around that is a maintenance liability rather than a capability.

    Candidates are ranked by value over effort, both scored on stated ladders so the ordering can be argued with:

    rank = (research value + QA/parity value) / implementation effort

research value  corpus-scale answers the app cannot give — feature matrices,
                distributions, inference budgets, dataset generation,
                train/test hygiene
QA value        Apple/Android parity, golden fixtures, and regression pinning of
                a constant that today only a running app can exercise

effort  1  public pure statics over scalars, strings, and value types;
           JSON plumbing only
        2  needs a PGN replay (ChessCore Position / MoveGenerator), a
           multi-field nested request object, or a filesystem shim
        3  needs the MoveNode / Game object graph, a bundled resource, or
           the network
        4  needs an engine process, a tablebase service, or a Maia
           inference backend
        X  blocked — the seam is not public

    Effort 1 and 2 is the interesting band. Everything at effort 4 already has a precedent in annotate and maia, and it is a precedent that costs an engine handshake or a model compile per run.

    Below the line¶

    Real seams, worth building eventually, but the ratio does not justify going first:

    Proposal Seam Why it waits
    drill-replay DrillFlowCore — the full state machine behind Tactics/Trap/Punish/Study/Endgame on both platforms The highest-leverage QA target in the Train module and the least JSON-Lines-natural: it is an interactive reducer, not a batch transform, so the command would test the script format as much as the kernel
    board-replay EBoardSessionCore.handle(event:game:orientationFlipped:) over a .replay script Turns a field diagnostic capture into a diffable effect trace. Real regression value, zero research value, and it needs three things the CLI does not have: a .replay-text-to-BoardEvent adapter, a GameView conformer to pass as game:, and a synchronous stand-in for the async resolution coordinator
    endgame-verify EndgameMiningV2ValidatedGeneration.validate(expectedCoverage:loadObjectJSON:), EndgameMiningValidatedGeneration.validate(loadShardJSON:) The validators are already pure functions over injected (String) -> String? load closures, so a directory-backed shim is the whole job — but EndgameMiningValidatedGeneration's initializer is fileprivate, so the V1 half is only reachable through a resolver. Fold into store as a verify-mining op rather than shipping alone
    material MaterialBalance.compute(from:) Self-contained and correct, but it is a starting-count subtraction over five piece types. The right artifact is a golden fixture, or an extra field on a command that already holds a Position
    clock-sim ClockCore.start(color:) / .stop() / .reset() / .switchTurn() / .advance(byElapsed:) Scriptable in principle, but the inputs only exist inside a running session driven by wall time. Niche game-logic QA, no research value

    Blocked by access level¶

    Three seams the survey wanted and could not have. Each needs a one-word source change, and the CLI is a separate SPM package, so internal is as unreachable as private.

    Seam Access What it would have enabled
    EloCalibrationData internal A calibration-dump command emitting coefficients, feature means and standard deviations, residual bands, and the Elo grid per (time control, model version). Tools/elo-calibration/generate_swift.py bakes these into Swift from JSON artifacts under a "DO NOT EDIT" header, and nothing currently re-reads the baked values to confirm they still match the source after a regen. This is the missing round-trip check for that generator
    StatsKernel.isOTBClassicalTC(tag:tc:) private An is_otb_classical field on classify. The rule is tc == .classical && estimatedSeconds(fromPGNTag:) >= 6000, and it selects a widened CI and a different estimate label
    TimeControlClass.estimatedSeconds(fromPGNTag:) internal The staged-clock duration behind both classifiers. classify can emit the resulting class but not the seconds that produced it, which is the field a mis-bucketing investigation actually wants

    Note

    Mirroring a non-public seam in the CLI is possible under the file:line citation convention the CLI index documents, but it is the wrong trade here: all three are load-bearing numeric logic, and a mirrored copy of numeric logic is a copy that can drift silently.

    Wire contracts for the top candidates¶

    All sketches follow the protocol the six shipped commands already implement: one JSON object per line in, one per line out, explicit snake_case CodingKeys, nil fields omitted rather than written as null, per-line failures emitted as {"id", "error"} without stopping the stream.

    chart¶

    The strongest proposal on this page, because its bug class already shipped. The source comment on EloChartPresentation records the divergence verbatim: Apple's domain unioned the anchored intervals, the actual ratings, and the per-game evidence dots; Android's unioned only the intervals and ratings, so every dot outside that band drew flat against the chart edge — measured at 2.3% of points on the reference account and 7.1% on the worst. The dots are the varying series; the anchored line barely moves.

    EloChartPresentation.domain(points:showsComparableRating:)

    values = for each point:
                 displayedInterval(for: point).lowerBound
                 displayedInterval(for: point).upperBound
                 point.actualRating          // ONLY if showsComparableRating
    no values at all                      -> 0...3_000

    performances = points.map(unclippedPerformance).sorted()
    count >= 20 -> lower = min(lower, performances[count / 20])
                   upper = max(upper, performances[count * 19 / 20])
    count <  20 -> lower = min(lower, performances.first)
                   upper = max(upper, performances.last)

    padding = max(30, (upper - lower) * 0.05)
    domain  = (lower - padding)...(upper + padding)

EloChartPresentation.clipped(_:to:)
    inset = max(1, (domain.upperBound - domain.lowerBound) * 0.01)
    min(upper - inset, max(lower + inset, value))

displayedInterval(for:)  / unclippedPerformance(for:)
    calibration == .chessComPersonalized && gameProjection != nil
        -> projection.interval68        / projection.mappedPerformance
    otherwise
        -> point.strengthCI             / point.performance.elo

    The 5th/95th percentile trim is the load-bearing line: it is what stops one wild game rescaling the chart and flattening everything else, and it is exactly the kind of rule two independent implementations get subtly different.

    {"id":"p1","date":"2026.03.01","calibration":"chessComPersonalized","actual_rating":1180,"performance":{"elo":1240.0,"ci_low":980.0,"ci_high":1500.0},"strength_ci":[1150.0,1280.0],"game_projection":{"mapped_performance":1305.0,"interval68":[1210.0,1400.0]}}

    {"domain_high":1547.0,"domain_low":947.0,"point_count":1}
{"clipped_performance":1305.0,"displayed_interval_high":1400.0,"displayed_interval_low":1210.0,"id":"p1"}

    let domain = EloChartPresentation.domain(
    points: points,
    showsComparableRating: showsComparableRating
)
for point in points {
    let interval = EloChartPresentation.displayedInterval(for: point)
    let raw = EloChartPresentation.unclippedPerformance(for: point)
    let drawn = EloChartPresentation.clipped(raw, to: domain)
}

    Warning

    unclippedPerformance must not itself be clipped to the domain — the domain is derived from it, and clipping first makes the derivation circular. A CLI that emits both values keeps that ordering visible in the output, which is the point.

    classify¶

    Two classifiers deliberately disagree, and every mis-bucketed game silently changes which calibration artifact serves it and which provider rating pool it belongs to. The command emits both, plus the derived fields, one game per line.

    TimeControlClass.classify(baseSeconds:incrementSeconds:)   // estimator artifact
    baseSeconds == nil -> .correspondence
    total = base + 40 * increment
    total <  180 -> .bullet        total < 1500 -> .rapid
    total <  480 -> .blitz         else         -> .classical

StatsKernel.classifySpeed(tags:event:)                     // provider rating pool
    TimeControl tag non-empty AND classifies .correspondence -> .daily
    event contains "bullet" / "ultrabullet"                  -> .bullet
    event contains "blitz"                                   -> .blitz
    event contains "rapid"                                   -> .rapid
    event contains "classical"                               -> .classical
    event contains "correspondence" / "daily" /
                   "let's play" / "lets play"                -> .daily
    tag empty                                                -> .rapid
    base = staged duration when the tag contains ":" or "/",
           else Int(text before "+"), else 0
    base <  180 -> .bullet        base <= 1800 -> .rapid
    base <  600 -> .blitz         else         -> .classical

    A 300+5 game is .rapid to the estimator (300 + 40 × 5 = 500) and .blitz to the rating pool (base = 300). That is intentional, and it is exactly the pair a census wants to count. Three named failures are pinned by this pair: a Chess.com Daily clock spelled 1/86400 read as bullet by a naive + split, a - tag falling through to rapid, and a staged OTB control like 40/7200:3600+30 read as its first stage.

    {"id":"g1","tags_json":"{\"TimeControl\":\"300+5\"}","event":"Rated blitz game"}

    {"display_speed":"blitz","estimator_tc":"rapid","id":"g1","starts_with_white":true}

    let tags = StatsKernel.parseTags(tagsJSON)
let estimatorTC = TimeControlClass.classify(
    fromPGNTag: tags["TimeControl"] ?? ""
)
let displaySpeed = StatsKernel.classifySpeed(tags: tags, event: event)
let startsWhite = StatsKernel.startsWithWhiteToMove(tags: tags)

    identity¶

    Every cross-platform identity question and every corpus-dedup question reduces to "what keys does this game produce?", and there is no way to answer it today without launching the app.

    GameIdentity.canonicalProviderID(_:)
    "lichess:<id>"      -> suffix (split on / ? #), 8...12 ASCII alphanumerics
                           -> "lichess:" + first 8 characters
    "chesscom:<id>" /
    "chess.com:<id>"    -> suffix (split on / ? #), all ASCII digits
                           -> "chesscom:" + suffix
    a recognized web location -> the same canonical form
    anything else             -> nil

GameIdentity.stableID(gameID:link:site:contentID:)
    first non-empty of:
        the persisted remote ID derived from gameID / link / site
        gameID itself, when it is already a content ID
        contentID()                            // autoclosure — computed last

    Lichess's stable component is the first eight case-sensitive characters, so the canonical form is not the raw string, and the two representations are what a dedup pass across differently-sourced corpora has to reconcile.

    {"id":"r1","game_id":"","link":"https://lichess.org/abcd1234/white","site":"lichess.org","white":"alice","black":"bob","date":"2026.03.01","result":"1-0","event":"Rated blitz game","opening":"B90","move_text":"1. e4 c5","tags_json":"{}"}

    {"canonical_provider_id":"lichess:abcd1234","id":"r1","is_remote_id":true,"stable_game_id":"lichess:abcd1234"}

    combo¶

    Stage 1 of combination mining is pure Foundation and ChessCore over stored annotation — no engine call at all. Both the admission gate and the ranking score are short enough to state completely, which is what makes offline threshold retuning practical.

    CombinationMiningKernel.candidates(in:userIsWhite:)  — admission gate
    naiveCp <= sacrificeThresholdCp   (-150)   // looks like a sacrifice
    evalCp  >= winningThresholdCp     ( 150)   // actually winning
    evalCp  <= decidedBandCp          ( 900)   // not already decided

CombinationMiningKernel.score(naiveCp:seeCp:evalCp:sharpnessCp:foundIt:)
    total  = min(-naiveCp, 900)                     // how bad it looks
    total += min(max(0, seeCp - naiveCp), 900) / 2  // blind-spot gap
    total += min(evalCp, 600) / 2                   // winning, not runaway
    total += min(sharpnessCp ?? 0, 400) / 2         // uniqueness
    if foundIt { total -= 500 }                     // penalised, not filtered

CombinationMiningKernel.validateLine(startingFEN:uciMoves:)
    forcedReplies counts opponent turns with
        legalMoves.count <= forcedReplyMaxLegalMoves   (2)
    dipped     = maxDeficitCp <= minimumDeficitCp      (-150)
    longEnough = solverMoves  >= minimumSolverMoves    (3)

    endsInCheckmate && longEnough -> .combination
    !dipped || !longEnough        -> .notACombination
    netGain >= 0                  -> .combination
    otherwise                     -> .truncated   // re-probe deeper, do NOT discard

    .truncated is the case that must not be treated as a rejection: the line dipped and ran out before recovering, so the resolution is past the probe horizon rather than absent.

    {"id":"g1","white":"alice","black":"bob","username":"alice","move_text":"1. e4 c5","tags_json":"{}","annotation_evals_json":"[...]","second_best_evals_json":"[...]"}
{"id":"v1","mode":"verdict","fen":"...","moves":["d1h5","g7g6","h5e5"]}

    {"candidates":[{"eval_cp":420,"move_number":14,"mover_is_white":true,"naive_cp":-400,"played_san":"Nf3","position_fen":"...","score":1085,"see_cp":100,"sharpness_cp":180,"engine_best_san":"Qxc8","engine_best_uci":"d1c8"}],"id":"g1"}
{"ends_in_checkmate":false,"final_material_cp":100,"forced_replies":2,"id":"v1","max_deficit_cp":-400,"opponent_turns":2,"outcome":"combination","solver_moves":3}

    // Stage 1 from an annotated game — no engine, no async.
let candidates = CombinationMiningKernel.candidates(from: input)

// Or judge one hand-supplied line.
let verdict = CombinationMiningKernel.validateLine(
    startingFEN: fen,
    uciMoves: moves
)

    Note

    candidates(from:) returns [] for a game with no engine annotation, and for a game whose eval array length is not moves.count + 1. Both are honest answers rather than errors, so a CLI should report the empty result with its reason rather than emitting a per-line error.

    glyphs¶

    annotate emits only white-POV evals, and accuracy derives only quality labels from them. Nothing exposes the glyph cascade users actually see, which depends on three inputs an eval array cannot carry: the rank-2 gap, the best-move match, and sacrifice detection.

    AnnotationKernel.classifyGlyph(wpDrop:wpBefore:wpAfter:gap:playedBestMove:
                               opponentMissed:involvesSacrifice:absEvalCp:)

    wpDrop >= 0.20                                        -> .blunder
    wpDrop >= 0.10                          -> opponentMissed ? .miss : .mistake
    wpDrop >= 0.05                          -> opponentMissed ? .miss : .dubious

    wpDrop < 0.02 && gap >= 0.15 && absEvalCp < 50_000
                  && wpBefore < 0.75 && involvesSacrifice -> .brilliant
    wpDrop < 0.02 && gap >= 0.08 && wpBefore < 0.40       -> .great
    wpDrop < 0.02 && gap >= 0.08 && wpBefore < 0.55
                  && wpAfter > 0.60                       -> .great
    playedBestMove && gap >= 0.03                         -> .best
    wpDrop < 0.02 && gap >= 0.03                          -> .excellent
    wpDrop < 0.05 && gap >= 0.06                          -> .good
    otherwise                                             -> nil

    wpBefore       = winProbability(evals[i].bestCp)
    wpAfter        = 1 - winProbability(evals[i+1].bestCp)
    wpDrop         = max(0, wpBefore - wpAfter)
    gap            = winProbability(bestCp) - winProbability(secondBestCp),
                     0 when no rank-2 line was recorded
    opponentMissed = (prevWP - (1 - wpBefore)) >= 0.10 && wpBefore > 0.55

    Sacrifice is the only non-eval predicate in the cascade and the sole gate on .brilliant, so a --sacrifice-only mode over {fen_before, uci} is worth having: it is board-only, needs no evals, and lets the brilliant precondition be measured over an arbitrary corpus.

    let results = AnnotationKernel.computeAnnotations(
    inputs: inputs,   // [AnnotationComputeInput(positionBefore:positionAfter:move:)]
    evals: evals,     // [AnnotationEval]; evals[0] is the start position
    startIsWhite: true
)
for result in results {
    result.glyph          // MoveAnnotation?
    result.moveQuality
    result.moveAccuracy
    result.engineBestMoveUCI
    result.engineEval     // white-POV formatted string
}

    Warning

    computeAnnotations breaks at evals.count - 1 inputs. A caller supplying n moves must supply n + 1 evals, or the tail is silently dropped. The CLI should reject a length mismatch as a per-line error rather than emit a short array — the same discipline CombinationMiningKernel.candidates(from:) already applies internally.

    store¶

    FileJSONBlobStore is the portable persistence substrate, and nothing in the six shipped commands inspects one. A store command makes a blob directory a debuggable artifact: enumerate keys by namespace, dump one key's raw JSON, snapshot the whole directory, or validate the routing invariants without decoding any progress schema.

    namespaces routed by FileJSONBlobStore.fileURL(forKey:)
    flat                <root>/<key>.json
    authored heads      <root>/authored-heads/
    authored revisions  <root>/authored-revisions/
    authored index      <root>/authored-index/
    authored witnesses  <root>/authored-frontier-witnesses/
    import checkpoints  <root>/import-checkpoints/
    endgame mining      <root>/endgame-mining/<content address, 3-4 components>

enumeration ceiling  FileJSONBlobStore.maximumEnumeratedJSONKeys = 1_000_000
    Payload reads never begin after this bound is exceeded.

snapshotJSONByKey excludes, unconditionally:
    authored infrastructure keys
    endgame-mining infrastructure keys
    legacy flattened "personalEndgames_" keys
    and fails — rather than returning a partial map — if an enumerated file
    disappears between the listing and the read

    let store = FileJSONBlobStore(directory: URL(fileURLWithPath: path))

switch store.storedJSONKeysReportingError() {
case .value(let keys):   // [String]
    for key in keys {
        switch store.loadJSONReportingError(forKey: key) {
        case .value(let json): break
        case .missing:         break
        case .failure(let message): break
        }
    }
case .failure(let message):
    break
}

let snapshot = store.snapshotJSONByKey(
    excludingKeys: [],
    includingAuthoredRecords: true
)

    Note

    The read APIs deliberately return three-case results rather than String?. A CLI must not collapse .failure into .missing: the whole reason the distinction exists is that an unreadable blob and an absent blob call for opposite recovery decisions.

    The storage seam makes every Codable store CLI-reachable¶

    Worth stating plainly, because it changes what the stateful proposals cost: FileJSONBlobStore is a public struct conforming to JSONBlobStore, imports only Foundation, and has a public initializer that takes a directory. Every parameter after directory has a default, so a CLI constructs one in a line and gets the same persistence the app uses on any non-Apple platform.

    let store = FileJSONBlobStore(directory: URL(fileURLWithPath: path))

var ratings = TacticsRatingStore.load(from: store)
let delta = ratings.recordAttempt(
    puzzleKey: key,
    difficulty: .medium,
    outcome: .correct,
    in: store
)

var srs = DrillSRS.load(from: store)
srs.recordCorrect(key: key, to: store)
srs.isDue(key: key, now: Date())

    load(from:) and save(to:) come from a protocol extension on BlobBackedStore, so any conformer works with no per-store wiring. The public conformers, with their verified blob keys:

    Store Blob key
    TacticsRatingStore tacticsRating
    TacticsPerformanceStore tacticsPerformance
    DrillSRS drillSRS
    RepertoireDrillStats repertoireDrillStats
    CombinationPuzzleStore combinationPuzzles
    VoiceTranscriptLog voiceTranscriptLog
    EBoardDiagnosticCapture eBoardDiagnosticCapture

    Two more stores are stateless namespaces that read and write a blob directly rather than conforming: BlunderMasteryStore (key blunderMastery, masteryThreshold = 3) and TrainProgressCache (key trainProgress.<PracticeMode.rawValue>).

    Six of these keys are semantically mergeable, which is what makes the merge-progress proposal testable at all:

    ProgressBlobSemanticMerger.mergeableKeys
    tacticsRating          tacticsPerformance     drillSRS
    repertoireDrillStats   blunderMastery         endgameHistory

mergedResult(forKey:candidates:)
    candidates sorted by (updatedAt descending, json ascending)
        — the json tiebreak is what makes the choice independent of fetch order
    only consumer-decodable candidates contribute
        — a syntactically valid but wrong-schema sibling cannot lend its
          newer timestamp to the merged union

    The consequence for this page: progress, merge-progress, and the stateful half of authored need no new persistence design. They need a directory path and a flag.

    Note

    FileJSONBlobStore also has an init(subdirectory:) that resolves against the user's document directory. That is the app-shaped initializer; a CLI should use init(directory:) so the store location is an explicit argument rather than an environment-dependent default.

    What is deliberately not worth exposing¶

    Being able to wrap a seam is not a reason to. Four classes should stay out of the CLI permanently.

    Presentation policies whose only consumer is a view. StatsChartPresentationPolicy.servingPathLabel(for:) returns "Move-quality model", "Exact-opponent Maia", or "Neutral-1500 Maia (provisional)". EstimatedStrengthServingCoverage.label assembles a sentence like "Maia-refined: 12 of 40 games (9 exact, 3 neutral-1500 provisional)". TacticsExtractionMode.displayName and .prompt return "Punish" and "Your opponent erred — find the punishing move.". BoardCatalog.displayName(key:) names a hardware brand. These are real cross-platform contracts and they are worth pinning — as fields inside a command that already computes the underlying value, never as a command of their own. This is why coverage is proposed around estimatedStrengthServingCoverage(for:), which returns counts, and not around the label that formats them. A subcommand whose entire output is a noun phrase is a string table with a process around it.

    Mode and selection policies that exist to keep a control populated. StatsChartPresentationPolicy.normalizedMode(_:) and .effectiveMode(storedMode:canShowEstimated:) map a persisted string onto one of two segmented-control values, failing safely to the rating chart. normalizedEstimatedSpeed(_:) folds any speed outside estimatedStrengthSpeeds down to .rapid. Correct, portable, and completely uninteresting outside a view that has a segment to select.

    Anything that needs live hardware. The BLE transports and the live half of the e-board stack cannot run in a batch process at all: they need a radio, a paired board, and a human moving pieces. Only the pure kernels underneath are proposed — BoardCatalog's static tables, and BoardDiffResolver / BoardTakebackDetector driven from synthetic occupancy arrays. That split is deliberate: board-catalog and board-diff are in tier 2, and board-replay, which needs a captured session transcript and a Game conformer, is below the line.

    Anything that mutates an object graph. AnnotationKernel.computeAnnotations is pure and returns value types; applyAnnotations writes onto MoveNode through a Game. The CLI wants the pure half. The rule generalizes: when a kernel splits into a pure compute and a thin write pass, the CLI wraps the compute and stops. The same reasoning keeps drill-replay and board-replay below the line — both are reducers that expect a caller owning mutable board state.
