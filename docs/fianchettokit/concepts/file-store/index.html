    FileJSONBlobStore & the Persistence Machinery¶

    How JSONBlobStore gets a real, Foundation-only body: directory layout and key routing, atomic and durable writes, deterministic fault injection for tests, and the type-aware merge policy that reconciles two replicas that both wrote progress offline.

    Overview¶

    Stores & the storage seam covers the two-protocol boundary — JSONBlobStore (key → JSON-string get/set) and BlobBackedStore (a single-row Codable keyed by a stable blobKey, with load(from:) / save(to:) supplied by a protocol extension) — and the five stat stores that persist through it. This page covers the one concrete backend that ships in the kit: FileJSONBlobStore, a Sendable struct that stores one JSON file per key under a directory.

    It's Foundation-only — no SwiftData, no CloudKit, no UIKit/SwiftUI, no app process. That's the headline: any store or namespace in the kit that talks through the seam — BlobBackedStore conformers like tactics rating, tactics performance, and repertoire drill stats, as well as direct-JSONBlobStore namespaces like blunder mastery — round trips through FileJSONBlobStore unchanged, which means it round trips through a plain command-line tool unchanged too. Construct one, hand it to TacticsRatingStore.load(from:) / .save(to:), and you have working, crash-safe persistence with nothing else running. This is exactly what would let a headless tool persist and reload rating/SRS state between invocations: build one FileJSONBlobStore pointed at a chosen directory and hand it to the same BlobBackedStore calls shown on this page.

    fianchetto-cli does not do this today. Its six shipped subcommands — annotate, estimate, maia, accuracy, project, track — are all JSON-lines pipes over stdin/stdout with no persisted directory. track in particular replays StrengthTracker, a pure value type, over a stream of per-game Elo estimates: its entire state is one var the caller re-assigns on each line, and it never touches a blob store. A store subcommand that would exercise FileJSONBlobStore directly — enumerate keys, dump one key's raw JSON, snapshot a directory — is proposed but not implemented.

    let store = FileJSONBlobStore()                   // "blobs" under the
                                                    // documents directory
var rating = TacticsRatingStore.load(from: store)  // decode, or a fresh Self()
_ = rating.recordAttempt(
    puzzleKey: "startFEN:e4",
    difficulty: .medium,
    outcome: .correct,
    in: store                                      // recordAttempt persists too
)

    Everything below this line is FileJSONBlobStore-specific: it is not part of the portable JSONBlobStore protocol, and nothing outside this file backend needs to know about it.

    Directory layout & key routing¶

    A FileJSONBlobStore owns one directory: URL (a "blobs" subdirectory under .documentDirectory for the default init(subdirectory:), or any URL you supply for init(directory:...) — the latter is what a CLI or a test uses to point the store at an arbitrary path). Every key routes through fileURL(forKey:) into exactly one of three namespaces.

    Directory constant Value Holds
    (blob root) — ordinary flat blobs: <key with "/" → "_">.json
    authoredHeadDirectoryName "authored-heads" compact per-replica authored heads
    authoredRevisionDirectoryName "authored-revisions" immutable authored revision facts
    authoredIndexDirectoryName "authored-index" keys prefixed authoredFrontierIndexPrefix
    authoredWitnessDirectoryName "authored-frontier-witnesses" keys prefixed authoredFrontierWitnessPrefix
    importCheckpointDirectoryName "import-checkpoints" the one lichessHistoryImportCheckpointKey
    RepertoireExpansionCheckpointStorage.directoryName "expansion-checkpoints" keys prefixed RepertoireExpansionCheckpointStorage.keyPrefix ("local.repertoireExpansionCheckpoint.v1.")
    endgameMiningDirectoryName "endgame-mining" derived personal-endgame mining proofs

    The routing decision, in order:

    fileURL(forKey: key):

  1. EndgameMiningStorageNamespace.isInfrastructureKey(key)
       — key has prefix "personalEndgames/" (or the legacy flat
         "personalEndgames_")
     → split key on "/"; a valid route needs exactly 3 or 4 components,
       each passing the safe-component check below
     → endgame-mining/<c1>/.../<cN-1>/<cN>.json   (every component nests,
       including the leading "personalEndgames" segment)
     → e.g. "personalEndgames/head/v1"
            → endgame-mining/personalEndgames/head/v1.json
        "personalEndgames/head/v1/deviceA"
            → endgame-mining/personalEndgames/head/v1/deviceA.json

  2. AuthoredBlobRecordCodec.kind(of: key)
       .compactHead — exactly 5 dot-separated parts, namespace
         "authoredHead.v1." ("authoredHead.v1.<field>.<game>.<replica>")
           → authored-heads/<field>/<game>/<replica>.json
       .immutableRevision — exactly 8 dot-separated parts, namespace
         "authoredRevision.v1." ("...v1.<field>.<game>.<replica>.<counter>.<sha256>.<proof>")
           → authored-revisions/<field>/<game>/<replica>/<counter>.<sha256>.<proof>.json
       either kind, with a part count that doesn't match
           → a flat legacy file in the same directory (`<key>.json`),
             never a route into a parent directory

  3. anything else → flat "<key with "/" → "_">.json" in the blob root,
     except four fixed-prefix keys routed to their own directory, checked
     in this order:
       key == lichessHistoryImportCheckpointKey        → import-checkpoints/
       RepertoireExpansionCheckpointStorage
         .isCheckpointKey(key)                          → expansion-checkpoints/
         ("local.repertoireExpansionCheckpoint.v1.")
       key.hasPrefix(authoredFrontierIndexPrefix)       → authored-index/
         ("local.authoredFrontierIndex.v1.")
       key.hasPrefix(authoredFrontierWitnessPrefix)     → authored-frontier-witnesses/
         ("local.authoredFrontierWitness.v1.")

    fileURL(forKey:) is public and does no filesystem work by itself — only a save prepares the parent directory, and it reports preparation failures rather than creating silently.

    An interrupted repertoire-expansion walk's cursor gets the same routed-away treatment as the Lichess import cursor, and for the same reason: it is non-portable per-device state, not authored library state a second device should inherit, so it must stay out of the flat key enumeration a backup inventory walks. Directory routing is only half the guard — RepertoireExpansionCheckpointStorage's own doc comment notes that LibraryStoreKernel.reservedBlobKeys membership does the other half, since the "local." prefix on the key enforces nothing by itself.

    Path-component safety and depth bound¶

    Every slash-separated component of an endgame-mining key must pass a whitelist before it is allowed to become a directory or file name:

    isSafeEndgameMiningPathComponent(component):
  non-empty, not "." or "..", <= 255 UTF-8 bytes, and every byte in:
    0x30–0x39  '0'–'9'
    0x41–0x5A  'A'–'Z'
    0x61–0x7A  'a'–'z'
    0x2D  '-'     0x2E  '.'     0x5F  '_'

    maximumEndgameMiningPathComponents = 4: a logical key must split into 3 or 4 components (a singleton head/receipt is 3; a content address or per-replica head is 4), and the recursive directory walk used by storedEndgameMiningObjectsReportingError throws once components.count + 1 >= 4 — it refuses to descend past the depth any valid key could use, independent of how many entries are down there. Bounding depth separately from entry count stops a hostile or corrupted skinny tree from turning a bounded inventory into an unbounded recursive walk.

    NAME_MAX and legacy-key migration¶

    fallbackFileURLs(forKey:) — the list of legacy candidate paths a read falls back to when the routed URL is missing — filters every candidate to lastPathComponent.utf8.count <= 255 before ever touching the filesystem. NAME_MAX is 255 on both Android app storage and Apple filesystems, and Linux and Darwin surface different errno domains for exceeding it, so the store never issues a call it already knows will fail in a platform-specific way.

    At store initialization (init(subdirectory:) and init(directory:...) alike), removeLegacyFlattenedEndgameMiningFiles deletes every regular (not directory, not symlink) personalEndgames_*.json file directly in the blob root — proof files written by a retired slash-to-underscore flat router, one release prior. It fails closed on anything that isn't a plain file, and logs [FileJSONBlobStore] <message> on any cleanup failure rather than throwing from the initializer.

    Reads, writes, and tri-state results¶

    Method Returns Behavior
    loadJSON(forKey:) String? the JSONBlobStore conformance; collapses the tri-state result into nil
    loadJSONReportingError(forKey:) FileJSONBlobReadResult .value(String) / .missing / .failure(String)
    loadDataReportingError(forKey:) FileJSONBlobDataReadResult byte-preserving variant for recovery evidence
    saveJSON(_:forKey:) — the JSONBlobStore conformance; fire-and-forget
    saveJSONReportingError(_:forKey:) String? call-scoped error, nil on success
    saveDataReportingError(_:forKey:) String? atomic .write(to:options: .atomic)
    removeJSONReportingError(forKey:) String? a missing file counts as success
    removeCanonicalEndgameMiningJSONReportingError(forKey:) String? removes only the routed leaf, never a legacy fallback

    A plain String?/Bool optional can't tell a caller "genuinely absent" apart from "I/O error that happens to look like absent." Backup and recovery code needs that distinction, so every read has a tri-state counterpart: FileJSONBlobReadResult and its byte-preserving twin FileJSONBlobDataReadResult each have exactly .value / .missing / .failure(String). loadJSON(forKey:) (the ordinary protocol method) still collapses .failure into nil, same as .missing — only the ...ReportingError calls let a caller treat them differently.

    saveJSONReportingError/saveDataReportingError return a call-scoped error string rather than setting a process-global "last error" property: two independent progress stores writing concurrently would otherwise race on a shared field, letting one write's success erase another write's failure before anything observes it.

    Bounded enumeration¶

    Method Scope Default maximumKeys
    storedJSONKeysReportingError flat *.json files directly in the blob root maximumEnumeratedJSONKeys
    storedAuthoredJSONKeysReportingError authored-heads/ + authored-revisions/ + flat legacy authored keys maximumEnumeratedJSONKeys
    storedEndgameMiningObjectsReportingError the whole endgame-mining/ subtree maximumEnumeratedJSONKeys
    storedEndgameMiningV1HeadKeysReportingError fixed personalEndgames/head/v1[/<replica>] subtree only EndgameMiningGenerationResolver.maximumHeadCandidates (4,096)
    storedEndgameMiningV2HeadKeysReportingError fixed personalEndgames/head/v2[/<replica>] subtree only EndgameMiningV2GenerationResolver.maximumHeadCandidates (4,096)
    snapshotJSONByKey(excludingKeys:includingAuthoredRecords:) full-directory export, [String: String] derived from the two enumerations above

    maximumEnumeratedJSONKeys = 1_000_000 is the shared safety ceiling behind nearly every one of these. It exists so a hostile or damaged namespace can't turn a bounded inventory pass into an unbounded per-edit decode. Every result type here (FileJSONBlobKeyListResult, FileJSONBlobStoredObjectListResult, FileJSONBlobSnapshotResult) is deliberately all-or-nothing: exceeding the ceiling — or hitting any other structural problem, like a symlink where a directory is expected — fails the entire call rather than returning a truncated list. A truncated list would let a backup or a GC pass believe it had seen everything.

    snapshotJSONByKey is the concrete case that exercises this: it unions storedJSONKeysReportingError with storedAuthoredJSONKeysReportingError (when includingAuthoredRecords is true), excludes the caller's own backup/library envelope keys plus the authored- and endgame-mining infrastructure keys, then reads each remaining key. If a key that was just enumerated disappears before its read (a real race, not a bug), the whole snapshot fails with "file disappeared during backup" — a full backup cannot truthfully claim completeness in that window.

    let store = FileJSONBlobStore()

switch store.loadJSONReportingError(forKey: TacticsRatingStore.blobKey) {
case .value(let json):
    print(json)
case .missing:
    print("no rating blob yet — a fresh Self() is fine")
case .failure(let message):
    print("unreadable, do NOT treat this as missing: \(message)")
}

switch store.snapshotJSONByKey(excludingKeys: ["library.fullbackup.v1"]) {
case .value(let blobsByKey):
    // write blobsByKey into a backup archive — every key it saw is present
    break
case .failure(let message):
    // never write a partial backup
    print("backup aborted: \(message)")
}

    Durability: DurableBlobPersistence¶

    saveJSONReportingError/saveDataReportingError are already atomic (a .write(to:options: .atomic) never leaves a half-written file installed at the canonical path). saveJSONDurablyReportingError / saveDataDurablyReportingError add a second, stronger tier: after the ordinary atomic write succeeds, they fsync until the bytes are proven to be on stable storage, not just handed to the OS page cache.

    saveJSONDurablyReportingError(json, forKey: key):
  1. saveJSONReportingError(json, forKey: key)         — the ordinary atomic write
  2. synchronizeInstalledBlobDurablyReportingError(forKey: key):
       a. fsync the installed file itself
            Android → installed FileJSONBlobStoreDurabilityBridge.syncAfterAtomicReplace
            elsewhere (incl. a native CLI) → FileHandle(forWritingTo:).synchronize()
       b. if the key routes through the endgame-mining namespace, also fsync
          every ancestor directory from the leaf's parent up to the durable
          blob root, deepest first:
            endgameMiningDurabilityDirectories(forKey:)
              = endgameMiningRouteDirectories(forKey:).reversed()
          (flat blob keys have no ancestor chain — step (b) is a no-op)

    Directory fsync is real on Darwin and Glibc; only Windows is a no-op

    synchronizeDirectoryDurablyReportingError(_:) — the call each ancestor directory in step (b) goes through — is real work on every platform except Windows. Under #if os(Android) it goes through the installed bridge's syncDirectory closure. Everywhere else, including the native macOS/Linux binary a CLI builds and runs as, it opens the directory itself (open(path, O_RDONLY | O_DIRECTORY | O_CLOEXEC)), calls fsync on that descriptor, and closes it — POSIX exposes the primitive directly, and canImport(Darwin) || canImport(Glibc) is exactly the native-binary case. Only under canImport(WinSDK) does the call return nil (success) without doing anything: Win32 has no documented, unprivileged equivalent to POSIX directory fsync, and FlushFileBuffers requires a writable file handle and does not document directory-entry synchronization, so the source deliberately validates the directory there and stops rather than call an API that doesn't do what the name suggests.

    The platform bridge¶

    public struct FileJSONBlobStoreDurabilityBridge: Sendable {
    public let syncAfterAtomicReplace: @Sendable (String) -> String?
    public let syncDirectory: @Sendable (String) -> String?

    public init(
        syncAfterAtomicReplace: @escaping @Sendable (String) -> String?,
        syncDirectory: @escaping @Sendable (String) -> String?
    )
}

    Both closures take an absolute filesystem path and return nil on success or a short error description. Android's app shell wraps its Kotlin/JNI fsync helper in these two closures and calls FileJSONBlobStore.installDurabilityBridge(_:) once at process bootstrap, before any durable write can occur — the kit itself never links against JNI. A durable save that needs the bridge before it is installed fails explicitly ("Stable-storage verification failed (...): Android durability bridge is unavailable") rather than silently downgrading to a non-durable write. The test initializer's platformDurabilityEnabled: Bool = false parameter exists because native Android test executables have no Java VM to host the bridge; setting it lets a native test opt out of only that adapter while keeping the same atomic-write and fault-injection behavior as production.

    Atomic same-directory install¶

    replaceInstalledBlobAtomicallyDurablyReportingError(with:forKey:) is the lower-level primitive migration and recovery code use when they've already prepared a complete replacement file next to the routed target, instead of handing raw bytes to saveDataReportingError:

    replaceInstalledBlobAtomicallyDurablyReportingError(with: prepared, forKey: key):
  1. reject unless `prepared` and fileURL(forKey: key) share a parent
     directory and are two distinct paths
  2. canImport(WinSDK) → MoveFileExW(source, target,
       MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)
     else               → POSIX rename(sourcePath, targetPath)
  3. on success, run the same fsync chain as an ordinary durable save

    A single rename/MoveFileExW call is the required primitive, not remove-then-move: a process interruption at any point always leaves either the old file or the complete new file installed at the canonical path — never a missing interval. The two branches exist because they aren't equivalent calls: the UCRT's rename fails with EEXIST when the target already exists, so it can create but never replace, while Win32's MoveFileExW swaps the directory entry in one operation when passed MOVEFILE_REPLACE_EXISTING. MOVEFILE_WRITE_THROUGH additionally asks Win32 not to return until the move has completed on disk — the strongest documented app-level option on that platform, though the kit's own source comment is careful not to call it equivalent to POSIX's parent-directory fsync.

    Deterministic fault injection¶

    Persistence-failure tests need "the 3rd read of key X fails" to be a fact, not a flake. FileJSONBlobStore's test-only initializer exposes two layers of injected faults, both defaulted to off so production code pays nothing:

    public init(
    directory: URL,
    failingReadsForKeys: Set<String> = [],
    failingWritesForKeys: Set<String> = [],
    failEnumeration: Bool = false,
    failingReadCallNumbers: [String: Set<Int>] = [:],
    malformedReadCallNumbers: [String: Set<Int>] = [:],
    failingWriteCallNumbers: [String: Set<Int>] = [:],
    platformDurabilityEnabled: Bool = false
)

    failingReadsForKeys / failingWritesForKeys / failEnumeration are coarse: every access to that key (or every enumeration call) fails, every time. The call-numbered parameters are precise — only a specific, 1-based call number for a specific key faults:

    FileJSONBlobInjectedCallFaults.readFault(forKey: key):
  call = (readCalls[key] ?? 0) + 1; readCalls[key] = call
  call ∈ failingReadCallNumbers[key]    → .failure
  call ∈ malformedReadCallNumbers[key]  → .malformedValue
      (the read returns the literal bytes Data("{ injected malformed JSON".utf8))
  otherwise                             → no fault

    The counter lives behind an NSLock in a private, reference-typed FileJSONBlobInjectedCallFaults (final class, @unchecked Sendable) — reference semantics so a test that constructs one store and hands it to both the code under test and its own assertions observes a single, shared call order, not two independent counters that could diverge. Leave all three [String: Set<Int>] parameters empty (the default) and injectedCallFaults stays nil — production's init(subdirectory:) never even allocates it, so ordinary reads and writes pay no locking cost.

    let store = FileJSONBlobStore(
    directory: scratchDirectory,
    failingReadCallNumbers: ["tacticsRating": [3]],     // 3rd read of this key fails
    malformedReadCallNumbers: ["drillSRS": [1]],        // 1st read returns malformed JSON
    failingWriteCallNumbers: [:]
)

    Conflict resolution: ProgressBlobSemanticMerger¶

    Two replicas can both write the same progress blob offline — two CloudKit-synced devices, say — and land back at the same key with genuinely different attempts recorded. Plain last-writer-wins would silently discard one replica's real progress. ProgressBlobSemanticMerger is a stateless namespace that performs a deterministic, replica-order-independent union for exactly the keys where that's meaningful; everything else stays on the platform's ordinary LWW path.

    public static let mergeableKeys: Set<String> = [
    TacticsRatingStore.blobKey,        // "tacticsRating"
    TacticsPerformanceStore.blobKey,   // "tacticsPerformance"
    DrillSRS.blobKey,                  // "drillSRS"
    RepertoireDrillStats.blobKey,      // "repertoireDrillStats"
    BlunderMasteryStore.blobKey,       // "blunderMastery"
    "endgameHistory",
]
public static func canMerge(key: String) -> Bool

    Menu snapshots and other rebuildable caches are deliberately excluded — a generic JSON-object merge on payloads that don't carry stable record identity or a causal reset tombstone would corrupt them rather than reconcile them.

    Candidate selection and the "more than one" gate¶

    mergedResult(forKey: key, candidates: [ProgressBlobCandidate]):
  ordered      = candidates.sorted(by: updatedAt descending, ties by json ascending)
  contributors = ordered.filter { isConsumerDecodable($0, forKey: key) }
  guard contributors.count > 1 else return nil

    isConsumerDecodable decodes the candidate's JSON against the real type for that key (TacticsRatingStore, DrillSRS, …; blunderMastery and endgameHistory both decode as ConsecutiveCorrectProgress). A candidate that fails to decode is simply not counted in contributors — it can't win the merge, but the caller's original candidates list still has it for conflict-evidence purposes. The > 1 gate is what keeps a single decodable candidate's exact bytes and timestamp untouched: zero or one contributor returns nil ("no merge needed"), so a newer-but-malformed sibling can never lend its timestamp to a synthetic one-row union.

    Per-record tie-break¶

    When two contributing stores supply a record sharing the same Identifiable id — a TacticsAttempt, a rating or SRS Mutation, a RepertoireDrillStats.DrillAttempt — the merger keeps whichever copy's canonical JSON encoding sorts smaller:

    canonical(x) = JSONEncoder(outputFormatting: .sortedKeys).encode(x) → UTF-8 String
winner = canonical(a) < canonical(b) ? a : b

    This is a lexicographic tie-break on encoded bytes, not "keep the newest" — these per-record types don't reliably carry an independent timestamp to compare, and a byte-canonical order is fully deterministic and replica-order-independent, which is the property a merge needs.

    Ledger baseline, compaction, and reset tombstones¶

    TacticsRatingStore, DrillSRS, and the shared ConsecutiveCorrectProgress (behind blunderMastery/endgameHistory) all carry an optional mutation-ledger shape (legacyBaseline, mutations, mutationCompactedAt). Only TacticsRatingStore additionally carries a reset tombstone (resetAt, clearsLegacyBaseline, discardedMutationIDs) — DrillSRS and ConsecutiveCorrectProgress have no resetAt field at all, so they have nothing for a sibling replica's reset to dominate. The compaction step below is shared by all three merges:

    ledgerStores = stores where legacyBaseline != nil || mutations != nil
               (ratings also count clearsLegacyBaseline == true)

selectedCompactedStore =
    ledgerStores.max(by: mutationCompactedAt ?? .distantPast);
    ties favor the LOWER candidate index
    (candidates are pre-sorted newest-updatedAt-first, so a tie favors the
     replica that was already ahead on updatedAt)
compactedAt = selectedCompactedStore?.mutationCompactedAt

    For TacticsRatingStore only, a reset tombstone can still override a compacted baseline:

    resetAt = ledgerStores.compactMap(\.resetAt).max()
resetDominatesBaseline = resetAt.map { $0 >= (compactedAt ?? .distantPast) } ?? false

baseline =
    resetDominatesBaseline               → empty .init()          (tombstone wins)
    else selectedCompactedStore.legacyBaseline
    else first ledgerStore.legacyBaseline (candidate order)
    else a baseline synthesized from the single newest decodable
         candidate's already-materialized fields (`stores.first`)
    else empty .init()

    DrillSRS and ConsecutiveCorrectProgress have no reset step, and their final fallback (once neither selectedCompactedStore nor any ledger store has a legacyBaseline) is a per-key union over every decodable candidate, not one candidate's whole snapshot:

    baseline =
    selectedCompactedStore?.legacyBaseline
    else first ledgerStore.legacyBaseline (candidate order)
    else DrillSRS: union of `entries` over every decodable candidate
         (candidates are pre-sorted newest-first, so the first value seen
         per key wins)
         ConsecutiveCorrectProgress: union of `values` over every decodable
         candidate, keeping the larger count seen per key

    Mutations from every ledger store are then unioned by id (same canonical-JSON tie-break as above), filtered against the union of every store's discardedMutationIDs/discardedAttemptIDs, and finally sorted by id.uuidString (orderedMutations) — never by dictionary iteration order, which Swift doesn't guarantee is stable across runs. TacticsPerformanceStore and RepertoireDrillStats have no compaction ledger; they skip straight to the discard-set/reset-cutoff union over attempts.

    Post-merge caps¶

    Store Cap applied to the merged result Backing constant
    TacticsPerformanceStore .capLast(3_000) on attempts TacticsPerformanceStore.maxAttempts
    RepertoireDrillStats Array(attempts.suffix(200)) per repertoire matches RepertoireDrillStats.maxAttemptsPerRep (private to that type — the merger repeats the same 200)

    Both caps exist so a merge of two already-large histories doesn't itself produce a blob over CloudKit's ~1 MB record limit.

    let merged = ProgressBlobSemanticMerger.mergedResult(
    forKey: TacticsRatingStore.blobKey,
    candidates: [
        .init(json: localJSON, updatedAt: localUpdatedAt),
        .init(json: cloudJSON, updatedAt: cloudUpdatedAt),
    ]
)
if let merged {
    store.saveJSON(merged.json, forKey: TacticsRatingStore.blobKey)
    print(merged.contributors.count, "replicas folded in")
    print(merged.latestContributorUpdatedAt)   // max(updatedAt) over contributors
}

    Supporting identity & namespace types¶

    SavedGameCollectionRole¶

    Stable identity for the three app-generated saved-game collections:

    Case sourceIdentifier defaultCollectionName defaultEventTag
    .otb "fianchetto.otb" "OTB Games" "Over the Board"
    .vsEngine "fianchetto.vs-engine" "vs Engine" "Play vs Engine"
    .boardImports "fianchetto.board-imports" "Board Imports" "Board import"

    init?(sourceIdentifier:) trims whitespace/newlines, lowercases, and requires an exact match against one of the three sourceIdentifier strings above — no prefix or fuzzy matching. owns(sourceIdentifier:) is Self(sourceIdentifier:) == self.

    Two disjoint legacy sets feed one-time migration/auto-promotion for games saved before roles existed:

    Case legacySourceIdentifiers (Android) legacyAppleSourceIdentifiers (Apple)
    .otb ["local", "pgn"] ["local"]
    .vsEngine ["pgn"] []
    .boardImports [] ["local"]

    Note

    The two legacy sets share values ("local", "pgn") but not meaning — a "local" Android source and a "local" Apple source promote to different roles. They're two separate properties instead of one shared set for exactly that reason: collapsing them would let an arbitrary Apple PGN import literally named "OTB Games" be mistaken for OTB provenance.

    if let role = SavedGameCollectionRole(sourceIdentifier: "fianchetto.otb") {
    print(role.defaultCollectionName)   // "OTB Games"
}

    SavedGameTags¶

    One shared PGN-tag builder used by every app-generated saved game (OTB, electronic-board OTB, play-vs-engine), so their persisted tags stay structurally identical:

    public static func make(
    eventTag: String,
    date: String,
    white: String,
    black: String,
    result: String,
    startFEN: String?,
    termination: String? = nil,
    timeControl: String? = nil
) -> PGNGame.OrderedTags

    Event / Date / White / Black / Result are always set, in that insertion order. SetUp / FEN follow, added only when startFEN is non-nil and non-empty; then TimeControl, added only when timeControl is non-nil and non-empty; then Termination, added only when termination is non-nil and non-empty. pgnDateString(from: Date = Date()) formats the date as yyyy.MM.dd using Calendar(identifier: .gregorian) and Locale(identifier: "en_US_POSIX") — the standard PGN-safe, non-localized date form.

    Note

    termination and timeControl are recent additions, and termination closes a real gap rather than a cosmetic one: StatsKernel has always read tags["Termination"] straight into EloEstimator.isTimeEnding, so every app-generated game silently told its own rating estimator that no game ever ended on time until something actually populated the tag. Callers should pass GameResultPresentation.terminationTag(for:) — derived from the same typed GameOutcome that produces result — never a hand-written string.

    pgnTimeControl(secondsBase:incrementSeconds:) is the matching helper for the timeControl argument: "300+3" for a Fischer-increment clock, "300" with no increment, "-" (the standard's own untimed token) when secondsBase is not positive.

    let tags = SavedGameTags.make(
    eventTag: SavedGameCollectionRole.otb.defaultEventTag,
    date: SavedGameTags.pgnDateString(),
    white: "Player",
    black: "Engine",
    result: "1-0",
    startFEN: nil
)

    OTBGameTags¶

    The single home for the over-the-board (electronic-board) saved-game tag roster, shared by both apps' saveOTBGame:

    public static func make(
    eventTag: String,
    date: String,
    outcome: GameOutcome,
    startFEN: String?,
    timeControl: String?
) -> PGNGame.OrderedTags

    It delegates straight to SavedGameTags.make, supplying placeholder white: "White" / black: "Black" player tags (editable afterwards through the game's tag editor) and deriving both result and termination from the one outcome: GameOutcome argument — GameResultPresentation .pgnResultToken(for:) and .terminationTag(for:) respectively — never recovered from display prose and never supplied as two tags that could drift apart. startFEN and timeControl pass straight through to SavedGameTags, so the same conditional SetUp/FEN/TimeControl rules apply: a game that started from a non-initial position reloads its SAN correctly, and a clock session that was actually attached is the only thing that writes TimeControl.

    let tags = OTBGameTags.make(
    eventTag: BoardBrand.pgnEventTag(rawValue: "chessnutAir"),
    date: SavedGameTags.pgnDateString(),
    outcome: .rules(.checkmate, activeColor: .black),
    startFEN: nil,
    timeControl: SavedGameTags.pgnTimeControl(secondsBase: 300, incrementSeconds: 3)
)

    SyncVisibleRetentionStorageKeys¶

    Eight content-addressed key-prefix families for personal-endgame retention sync state, built by string concatenation off one shared root:

    prefix                     = "personalEndgames/retention/v1/"
rosterPrefix                = prefix + "roster/"
capabilityPrefix            = prefix + "capability/"
rootProofPrefix             = prefix + "root/"
proposalPrefix               = prefix + "proposal/"
acknowledgementPrefix       = prefix + "ack/"
sealPrefix                   = prefix + "seal/"
sweepAcknowledgementPrefix  = prefix + "sweepAck/"
completionPrefix             = prefix + "completion/"

    Because every one of these shares the "personalEndgames/" prefix, any concrete key built from them falls under EndgameMiningStorageNamespace.isInfrastructureKey and routes through the endgame-mining namespace described above, not the flat blob namespace. Values are immutable and content-addressed, so a storage adapter is free to tolerate identical physical duplicates rather than treating them as a conflict.
