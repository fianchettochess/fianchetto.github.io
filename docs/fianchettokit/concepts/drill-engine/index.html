    Drill Flow, SRS & Tactics Mining¶

    How FianchettoKit decides what a drill does next: the shared drill state machine, the engine-probe contracts it issues, the spaced-repetition and Elo math that scores an answer, and the pure functions that mine and select tactics puzzles from a game.

    Overview¶

    The Train module splits along one line: the shell (SwiftUI on Apple, Compose on Android) owns the item pool, the board, and the pixels; every type documented on this page owns the decision — what counts as an answer, when to ask the engine, how strict to be, when a position is due again, and which puzzles a drill hands out. Every type here imports only Foundation and ChessCore — no SwiftUI, no UIKit, no platform concurrency. DrillFlowCore in particular never suspends: it is a pure event in → [Effect] out state machine, and every asynchronous step (an engine probe, a paced auto-advance, a scripted reply) is requested as an effect and reported back later as an event, never awaited inside the core.

    Five drills (Tactics, Traps, Punish, Study, Endgames) and the game-review quiz sit on this shared spine. TacticsRatingStore, TacticsPerformanceStore, BlunderMasteryStore, TrainProgressCache, and PracticeMode are covered from the persistence side in Stores & the storage seam; this page covers the algorithms and flow/selection logic layered on top.

    DrillFlowCore: the drill state machine¶

    DrillFlowCore is a Sendable struct that walks a pool of Items against the moves a user plays. It keeps score, owns every generation counter, and returns the exact board/engine work the shell must perform as [Effect].

    Item and Goal¶

    An Item is one drill question: a FEN, a board orientation, the ply the answer is expected at (answerPly, 0 for a freshly loaded root), and a Goal that says what answers it:

    public struct Item: Equatable, Sendable {
    public enum Goal: Equatable, Sendable {
        case knownAnswer(expectedUCI: String, expectedDisplay: String)
        case discoveredBestMove
        case mateIn(Int)
        case keepTheWin(playOutToMate: Bool)
    }
}
    Goal Used by How it grades
    .knownAnswer(expectedUCI:expectedDisplay:) Tactics, Traps, Punish; Study's replay/find-better drills Instant exact-UCI accept; a miss runs the two-FEN leniency probe
    .discoveredBestMove Study's best-move puzzles The engine's best move at the item FEN, probed once and cached per item load; a terminal position after the played move is an instant solve
    .mateIn(Int) Study's mate-in-N puzzles Mid-line moves are budget-checked against the remaining mover moves; on-track earns a scripted opponent reply and the line continues with no verdict
    .keepTheWin(playOutToMate:) the Endgame trainer The composite endgame probe is the whole grade — membership, leniency, and (with playOutToMate) the defense continuation all arrive in one transport hop; only a delivered checkmate is graded by the core alone

    Configuration¶

    Sampled once when the core is created for a run:

    public struct Configuration: Equatable, Sendable {
    public let marginBase: Int              // base cp margin before DrillStrictness scales it
    public let autoAdvance: Bool
    public let missRetriesSameItem: Bool    // default false
    public let dynamicItemSupply: Bool      // default false
    public let endlessSupply: Bool          // default false — forces dynamicItemSupply = true
}

    marginBase is the drill's unscaled acceptance margin before DrillStrictness scales it — 50cp for Tactics/Trap/Punish, 80cp for Study, 150cp for the Endgame trainer (see Grading primitives below). endlessSupply implies dynamicItemSupply in init regardless of what the caller passes — a custom endgame drill that never exhausts also, necessarily, deals each item's FEN itself.

    The flow: boardChanged → beginGrading → probe → commit¶

    Every cursor change on the board — including ones the drill caused itself, like a scripted reply landing — goes through boardChanged(_:strictness:). Filtering echoes is the core's job, not the caller's: it only reacts when board.cursorPly == answerPly, i.e. exactly the ply it is waiting on for a user answer.

    boardChanged(board, strictness)
  ├─ cursorPly != answerPly, or a verdict is already showing → [] (ignored echo)
  ├─ .knownAnswer && played == expectedUCI → instant .correct, no engine hop
  └─ else: capture PendingAttempt (uci, afterFEN, afterSafeFEN, isCheckmate,
           isStalemate, marginCp, requiresExact, showsCloseEnough)
       → beginGrading(attempt, item, restoreFirst: false)

beginGrading dispatches on item.goal:
  .knownAnswer         requiresExact ? commitRejected : runProbe (leniency)
  .discoveredBestMove  terminal position → commitAccepted (instant)
                       cachedBaselineUCI present → gradeAgainstBaseline
                       else → runBestMoveProbe, then cache the result
  .keepTheWin          isCheckmate ? commitAccepted (instant) : runEndgameProbe
  .mateIn(N)           isCheckmate ? commitAccepted (instant)
                       isStalemate || remaining <= 0 → runBestMoveProbe
                         (hint only — the grade is already .wrong)
                       else → runMateProbe

*ProbeFinished handlers → commitAccepted / commitRejected / surfaceUnavailable
  .onTrack / .continueLine → scheduleLineContinuation → .scheduleReply effect
    → scriptedReplyPlayed(_:) commits the line advance (answerPly += 2,
      userMovesPlayed += 1, no verdict shown)

    gradeAgainstBaseline is the one place an exact match short-circuits a second engine query: matching the cached baseline commits immediately, so an unavailable redundant probe can never reject the engine's own best move.

    The Effect vocabulary¶

    Effect is Equatable on purpose — golden tests assert the exact array a transition returns. Every case is a command the core issues; the shell never asks the core anything, it only reports events back (boardChanged, probeFinished, bestMoveProbeFinished, mateProbeFinished, endgameProbeFinished, scriptedReplyPlayed, itemSupplied, beatElapsed, retryProbe, advance, skip, effectFailed, suspend/resume, exit).

    Effect What the shell must do
    .loadItem(index:fen:flipped:ticket:) Load a fresh drill board. Failable — report ticket via effectFailed on failure
    .supplyItem(index:) Generate the FEN for item index (dynamic supply) and answer with itemSupplied(index:fen:flipped:) synchronously
    .restoreAttempt(ply:uci:ticket:) Put the captured attempt back on the board ahead of a probe verdict. Failable
    .runProbe(DrillProbeRequest, ProbeTicket) Run the leniency probe; report probeFinished(ticket:verdict:)
    .runBestMoveProbe(fen:ticket:) Ask the engine's best move at fen; report bestMoveProbeFinished(ticket:uci:)
    .runMateProbe(DrillMateProbeRequest, ProbeTicket) Run the composite mate-line check; report mateProbeFinished(ticket:verdict:)
    .runEndgameProbe(DrillEndgameProbeRequest, ProbeTicket) Run the composite endgame grade; report endgameProbeFinished(ticket:verdict:)
    .scheduleReply(attemptPly:attemptUCI:replyUCI:delayNs:ticket:) After delayNs, restore the attempt, play replyUCI, report scriptedReplyPlayed(ticket:) (or effectFailed)
    .cancelReply Cancel the outstanding scripted-reply task
    .presentMissComparison(playedUCI:expectedUCI:) Draw played-vs-expected arrows (expectedUCI nil when it could not be discovered)
    .clearMissComparison Remove the comparison — emitted explicitly on every transition that leaves one presented
    .recordOutcome(DrillOutcome) Persist the result (SRS / mastery / rating / hub progress)
    .scheduleBeat(delayNs:ticket:) Start the auto-advance timer; report beatElapsed(ticket:)
    .cancelBeat Cancel the outstanding beat
    .reportUnavailable(message:) Surface a probe/board failure — an explicit, assertable effect twinned with the .unavailable verdict
    .completed(score:attempts:) The run finished — payload matches the completion card

    DrillOutcome is the persisted record: DrillOutcome(kind: .correct \| .wrong \| .skipped, itemIndex: Int), emitted exactly once per completed verdict — and always after that verdict's board-work effects (see effect ordering below).

    Probe seams¶

    The core mandates only the shape of each engine question; how a shell transports it (broker one-shots, resilient retries, movetime vs. depth) is its own business.

    Leniency probe — DrillFlowProbe = @Sendable (DrillProbeRequest) async -> DrillProbeVerdict. DrillProbeRequest(puzzleFEN:afterPlayedFEN:marginCp:) is a two-FEN question: is afterPlayedFEN within marginCp centipawns of puzzleFEN's best line? POV contract: puzzleFEN is evaluated from the side to move (the drill mover); afterPlayedFEN is evaluated from the opponent of that side, so both scores land oriented to the mover. Both FENs are stockfishSafeFEN — the request shape itself forces the sanitization, so no transport can forget it at the engine boundary.

    Mate-line probe (Study's .mateIn) — one composite question per move. DrillMateProbeRequest(questionFEN:afterPlayedFEN:remainingMateBudget:) asks whether the position still forces mate within remainingMateBudget mover moves (always ≥ 1 — the core grades exhausted budgets itself and never asks the engine about them). DrillMateProbeVerdict answers with .onTrack(replyUCI:) (still forces mate; the scripted reply to play), .offTrack(expectedUCI:) (a nil hint degrades the miss copy to "?", never the grade), or .unavailable.

    Endgame probe (.keepTheWin) — the endgame's "probe" is its grader; the shell's transport holds the tablebase/engine evidence and answers the whole chess question in one hop:

    public struct DrillEndgameProbeRequest: Equatable, Sendable {
    public let questionFEN: String
    public let playedUCI: String
    public let afterPlayedFEN: String       // engine-safe
    public let isStalemate: Bool            // a certain miss, no engine consult needed
    public let playOutToMate: Bool          // end-to-end: a kept win continues with a defense
    public let marginCp: Int
    public let requiresExactBestMove: Bool  // strict can't short-circuit — the accepted set
                                             // itself IS the transport evidence
}

public enum DrillEndgameProbeVerdict: Equatable, Sendable {
    case won(dtm: Int?)
    case wonSuboptimal(dtm: Int?, bestDisplay: String?)
    case lostWin(expectedUCI: String?, expectedDisplay: String?)
    case continueLine(replyUCI: String)
    case voidItem                          // never winnable — withdraw, zero score movement
    case unavailable(message: String?)
}

    .voidItem is not a grade — the shell supplies a replacement item through the same itemSupplied path dynamic supply uses, and score/attempts don't move.

    Generations, tickets, and failure handling¶

    Opaque tickets over one monotonic counter¶

    ProbeTicket, AutoAdvanceTicket, and EffectTicket are each a one-field wrapper (let generation: UInt64) around a RunGeneration — a small Sendable counter (begin() -> UInt64, invalidate(), owns(_:) -> Bool) that the core keeps three independent copies of: probeGeneration, beatGeneration, effectGeneration. The field isn't public, so a shell can never construct or inspect a ticket — it can only hold the one the core handed it and pass it back unchanged. Any transition that invalidates in-flight work calls invalidate(), so a late-arriving result from a retired generation is silently dropped by the owns(_:) check at the top of every event handler. probePurpose (.leniency, .baseline, .mateCheck, .endgame, .hint) rides alongside probeGeneration so a probe launched for one reason can never be misinterpreted as another's answer, even while sharing the same counter.

    NO SILENT FALLBACK

    An unavailable probe is never converted into a grade, a failure never auto-skips, and .checking is never left unrecoverable. Probe failure, probe interruption mid-flight, an unplayable scripted reply, and a failed board effect all surface as the typed, retryable .unavailable(message:) verdict plus .reportUnavailable — score, attempts, and the item cursor move only when a completed verdict lands.

    The V4 rollback/retry channel¶

    Every batch that contains failable board work (.loadItem, .restoreAttempt, .scheduleReply) arms an internal Rollback: a captured token, the provisional scoreDelta/attemptsDelta, a failureMessage, a RetryAction (.grade re-runs the retained attempt; .reload re-issues the item load), and the pending/missShown state to restore. Effect ordering is load-bearing — every emitted batch places its failable board effects before .recordOutcome — so a shell that applies effects in order and calls effectFailed(ticket) on the first failure un-does the provisional commit exactly, re-arming the same retry retryProbe() triggers. An outcome can therefore never be persisted for a verdict whose board presentation never actually landed.

    Pacing constants¶

    Constant Value Where
    DrillFlowCore.scriptedReplyDelayNanoseconds 400,000,000 ns (0.4s) pause between an accepted mid-line move and the scripted opponent reply
    DrillAutoAdvancePolicy.correctDelayNanoseconds 900,000,000 ns (0.9s) auto-advance delay after .correct
    DrillAutoAdvancePolicy.reviewDelayNanoseconds 1,600,000,000 ns (1.6s) auto-advance delay after .closeEnough / .wrong

    DrillAutoAdvancePolicy.delayNanoseconds(for:) returns nil — no schedule at all — for .checking, .unavailable, .done, and nil.

    DrillAutoAdvanceTicket is the public counterpart to the core's own internal AutoAdvanceTicket (above), for a caller that paces its own advance directly against DrillAutoAdvancePolicy instead of driving it through DrillFlowCore's effect vocabulary. It carries the same two facts an ownership check needs — an itemIndex and a feedbackGeneration UUID — captured before the delay and compared after it:

    let ticket = DrillAutoAdvanceTicket(itemIndex: index, feedbackGeneration: generation)
guard let delay = DrillAutoAdvancePolicy.delayNanoseconds(for: verdict) else { return }
try await Task.sleep(nanoseconds: delay)
guard ticket.isCurrent(itemIndex: currentIndex, feedbackGeneration: currentGeneration)
else { return }

    Checking cancellation alone is not enough — a cancelled task can already be resuming, which is precisely when it would advance past an item the user has since moved on from; isCurrent is the check that catches that case.

    Usage: driving a single-move drill¶

    var core = DrillFlowCore(configuration: .init(marginBase: 50, autoAdvance: true))

let items = puzzles.map {
    DrillFlowCore.Item(
        fen: $0.fen, expectedUCI: $0.correctMoveUCI,
        expectedDisplay: $0.correctMoveSAN, flipped: $0.userColor == .black
    )
}
var effects = core.start(items: items)          // apply(effects): shell loads item 0

// The user plays a move; the shell reports the resulting board facts.
effects = core.boardChanged(
    DrillFlowCore.BoardFacts(cursorUCI: playedUCI, cursorSAN: playedSAN,
                             cursorPly: core.answerPly, position: afterMove),
    strictness: .normal
)

for effect in effects {
    switch effect {
    case .runProbe(let request, let ticket):
        let verdict = await probeTransport(request)              // DrillFlowProbe
        effects += core.probeFinished(ticket, verdict: verdict)
    case .recordOutcome(let outcome):
        persist(outcome)                                         // SRS / mastery / rating
    default:
        apply(effect)
    }
}

    Grading primitives (DrillTypes.swift)¶

    DrillTypes.swift is the platform-free grading vocabulary shared by every puzzle drill (extracted 2026-06-16 from the app's DrillKit.swift).

    DrillVerdict — the per-attempt result:

    public enum DrillVerdict: Equatable, Sendable {
    case checking
    case correct
    case closeEnough(expected: String, played: String)
    case wrong(expected: String, played: String)
    case unavailable(message: String)
    case done
}

    DrillProbeVerdict — the three-state lift of an optional completed decision (nil means no reliable chess judgment was made):

    public enum DrillProbeVerdict: Equatable, Sendable {
    case accepted, rejected, unavailable
    public init(completed decision: Bool?)   // true→.accepted, false→.rejected, nil→.unavailable
    public var completedAttemptDelta: Int    // 1 for accepted/rejected, 0 for unavailable
}

    DrillStrictness — the Settings → Practice knob, @AppStorage key "drillStrictness":

    marginScale:  lenient = 2.0   normal = 1.0   strict = 0.3
scaledMargin(base) = max(1, Int((Double(base) * marginScale).rounded()))
showsCloseEnough        == (self == .normal)
requiresExactBestMove    == (self == .strict)

    Lenient accepts generously (a winning-but-imperfect move still reads "Correct"); Normal is the only strictness with a "Close enough" middle ground; Strict demands the engine's exact rank-one move and — critically — requiresExactBestMove lets DrillFlowCore.beginGrading reject a miss without ever issuing a probe, so a smaller-margin probe can never relabel a near-best move as correct under Strict.

    DrillMastery — aggregate counts against the shared BlunderMasteryStore history map:

    public static func counts<Item>(
    _ items: [Item], history: [String: Int],
    threshold: Int,
    key: (Item) -> String
) -> (total: Int, due: Int, mastered: Int)

public static func distinctCounts<Item>(
    pools: [[Item]], history: [String: Int],
    threshold: Int,
    key: (Item) -> String
) -> (total: Int, due: Int, mastered: Int)

    threshold has no default, deliberately. It used to be = BlunderMasteryStore.masteryThreshold, and that expression was a trap: the Apple app separately declares its own enum literally named BlunderMasteryStore whose masteryThreshold reads the user's "Mastery streak" setting out of UserDefaults, so the character-identical source text BlunderMasteryStore.masteryThreshold meant the user's chosen streak in Fianchetto/Views and meant the kit's floor of 3 in FianchettoAndroid/Sources/Fianchetto — and, because a Swift default argument is evaluated in the module that declares it, any call that simply omitted the argument got 3 on both faces regardless of what the user had chosen. Nine live defects came out of that one construct kit-wide, including two that wrote disagreeing mastered/due counts into the synced TrainProgressCache. The floor now lives on MasteryStreak, which nothing shadows; a caller without the user's stored preference gets it through MasteryStreak.resolve(stored:) so the fallback is visible at the call site instead of hidden in a default argument:

    let threshold = MasteryStreak.resolve(stored: storedMasteryThreshold)
let counts = DrillMastery.counts(items, history: history, threshold: threshold) { $0.masteryKey }

    distinctCounts exists because tactics pools overlap — one position can be nominated by several TacticsExtractionModes (an opponent blunder that is also a critical position) — so summing per-mode counts would inflate the Train hub's total by however much the modes happen to overlap. It counts each distinct mastery key once, regardless of pool iteration order.

    Spaced repetition: DrillSRS¶

    DrillSRS is the repertoire drill's SRS state, a Codable, BlobBackedStore keyed by blobKey = "drillSRS". Per key it tracks nextReview, interval (days), and streak:

    correct → streak += 1;  interval = min(interval * 2, 30)   // days, doubling, capped
wrong   → streak  = 0;  interval = 1                        // days
nextReview = mutation.timestamp + interval days   (UTC Gregorian calendar,
                                                     secondsFromGMT: 0)
isDue(key) == entries[key] == nil  ||  entry.nextReview <= now

    A key with no entry at all counts as due — an unseen position is always served. There is no partial credit and no separate "ease factor": the interval only ever doubles or resets, so the entire schedule is captured by interval and streak.

    var srs = DrillSRS.load(from: blobStore)

if srs.isDue(key: position.positionKey) {
    // serve this position in today's drill
}

srs.recordCorrect(key: position.positionKey, to: blobStore)
// srs.recordWrong(key: position.positionKey, to: blobStore)

let entry = srs.entry(for: position.positionKey)
entry?.interval    // Int, days
entry?.streak      // Int
entry?.nextReview  // Date

    recordCorrect/recordWrong persist through save(to:) themselves — no separate save call is needed.

    Android migration

    DrillSRS.load(from:migrationStore:) is an Android-only convenience: if the canonical "drillSRS" blob decodes with empty entries, it falls back to the legacy "repertoireDrillSRS" key, and on a successful migration immediately re-saves under the canonical key so every subsequent load takes the normal path. The old key and the new key share the identical algorithm and JSON shape — this is a rename, not a format migration.

    Cross-replica mutation ledgers¶

    ConsecutiveCorrectProgress (backing BlunderMasteryStore), DrillSRS, and TacticsRatingStore all persist through the same pattern, so that two devices syncing the same CloudKit-mirrored blob can union their concurrent answers instead of one whole-blob write clobbering the other's:

    1. First write:  legacyBaseline := current materialized state
                 mutations := []
2. Each answer:  append an immutable Mutation { id: UUID, timestamp, key, correct }
3. Rebuild:      state := legacyBaseline
                 replay mutations where timestamp > mutationCompactedAt
                   ordered by (timestamp asc, then id.uuidString asc)
4. Compaction:   once mutations.count >= 1,000 (maxRetainedMutations):
                   legacyBaseline := current materialized state
                   mutations := []
                   mutationCompactedAt := now

    A wrong answer is therefore an ordinary ordered operation — one more Mutation — not a destructive whole-blob reset. record(key:correct:) / recordCorrect/recordWrong / recordAttempt all follow the same four steps: prepareMutationLedgerIfNeeded(), compactMutationLedgerIfNeeded(), append, rebuildFromMutationLedger(). Two replicas that both append a mutation and later merge just get a longer, still-deterministically-sorted list — timestamp order, with the UUID string as a tiebreaker for same-instant concurrent writes.

    ConsecutiveCorrectProgress.decode(_:) also accepts a pre-ledger legacy shape directly — a raw [String: Int] — and lifts it into legacyBaseline with an empty mutations array, so an older build's blob decodes exactly like a freshly-compacted one.

    reset() only tombstones the future

    TacticsRatingStore.reset(in:) does not just wipe the ledger: it tombstones only mutations with a future timestamp into discardedMutationIDs — a defense against a replica whose wall clock runs ahead — then sets clearsLegacyBaseline = true and resetAt = now. The replay lower fence becomes max(mutationCompactedAt, resetAt), so a concurrent mutation with a badly skewed earlier clock can still land on the wrong side of it — the ledger is a bounded, best-effort merge window, not an unbounded event log. TacticsPerformanceStore.reset(in:) guards its own capped attempt array the same way, tombstoning only future-timestamped attempts into discardedAttemptIDs.

    Tactics puzzle mining: TacticsExtractor¶

    TacticsExtractor is a pure PGN + eval arrays → [TacticsPuzzle] function over Sendable value types — no Game/MoveNode traversal, so extraction can run from a Task.detached without blocking the main actor.

    The four extraction modes¶

    public enum TacticsExtractionMode: String, Sendable, CaseIterable, Codable {
    case opponentBlunders   // "Punish"   — the opponent erred; find the punishing reply
    case userBlunders       // "Improve"  — you erred; find what you should have played
    case criticalPositions  // "Critical" — either side; any sharp eval swing
    case missedMate         // "Mates"    — you had a forced mate and let it slip
}

    extract(from:mode:mateMaxN:swingThreshold:) requires mainline.count >= 4 and evals.count == moves.count + 1; anything short of that yields []. Neither mateMaxN nor swingThreshold has a default — each used to (mateMaxN: Int = 5, swingThreshold: Int = 150), and Android's Tactics view called this exact overload with the arguments left off, so it silently graded every account at the kit's floor no matter what the user had chosen in Settings (mateMaxN) or a value that had never actually been correct at extraction time in the first place (swingThreshold — see TacticsSensitivity). A caller without the user's mate-cap preference reaches the floor through MissedMateCap.resolve(stored:); both shipping Tactics views extract at TacticsSensitivity.minimum — the kit's loosest offered sensitivity — and apply the person's actual preference afterward with TacticsSensitivity.filteredPools, rather than varying swingThreshold per call. extractAll(from:modes:mateMaxN:swingThreshold:) parses the PGN and decodes the three eval JSON arrays exactly once and fans them out across every requested mode — the dominant cost (the PGN token walk plus three JSON decodes) is paid once regardless of how many modes are requested. Every mode's result list is sorted descending by |evalAfter - evalBefore|.

    swingForUser = white user:  evalAfterCp - evalBeforeCp
               black user:  evalBeforeCp - evalAfterCp

.opponentBlunders  qualifies:  !isUserMove  &&  swingForUser >= swingThreshold
.userBlunders      qualifies:   isUserMove  &&  swingForUser <= -swingThreshold
.criticalPositions qualifies:  |swingForUser| >= swingThreshold
.missedMate        qualifies:   isUserMove
                    && a forced mate favoring the user existed before the move
                       (|mateDistance| <= mateMaxN)
                    && that forced mate is gone after the move

    .opponentBlunders poses the puzzle after the blunder (find the punishing reply, taken from the engine's recommendation at the next node); the other three modes pose it before the erring move (find what should have been played there).

    isHighQuality and the difficulty ladder¶

    puzzleEvalCp = mode == .opponentBlunders ? evalAfter : evalBefore
contested    = |puzzleEvalCp| <= 600                    // contestedBandCp
isHighQuality = contested && (bestVsSecondGapCp ?? nil) >= 100   // uniquenessThresholdCp
                                                          // nil gap => false

    A decisively-won or decisively-lost position makes a poor puzzle — many moves "win" and the recorded best is arbitrary — so isHighQuality requires the position to still be genuinely contested (within ±600cp) and to have a clear best move (at least 100cp ahead of the second-best alternative). A nil gap — a legacy game annotated before second-best tracking shipped — is never high-quality, but stays eligible at lower priority rather than being dropped.

    swing = |evalAfter - evalBefore|
isSharp = (bestVsSecondGapCp ?? nil) >= 100, or true when the gap is nil (legacy fallback)

swing >= 500  →  isSharp ? .easy   : .medium
swing >= 250  →  isSharp ? .medium : .hard
otherwise     →  .hard

    cacheFingerprint¶

    TacticsInput.cacheFingerprint is a 64-bit FNV-1a-style hash — offset basis 14_695_981_039_346_656_037, prime 1_099_511_628_211 — folded over ["tactics-cache-v4", white, black, username, moveText, startingPositionFEN, annotationEvalsJSON, secondBestEvalsJSON, mateDistancesJSON]. Swift's built-in Hasher is process-randomized and unsuitable for a persisted cache key, so each component is explicitly length-framed (its UTF-8 byte count folded in 8 bytes at a time) before its own bytes are mixed in — without that framing, ["ab", "c"] and ["a", "bc"] would hash identically at the component boundary.

    annotate feeds this directly

    fianchetto-cli's annotate subcommand emits exactly the per-ply, white-POV centipawn array (white_pov_evals, forced mates flattened to the ±100000 sentinel) that TacticsInput.annotationEvalsJSON expects and that MissedMateCandidate's offline scan checks against (mateMarker = 100_000.0). Puzzle mining over an arbitrary PGN can therefore run entirely headless downstream of annotate, with no app involved.

    TacticsDrillSelection¶

    Which puzzles a tactics drill serves, and in what order — extracted because both shells had independently written the same ranking and disagreed on exactly one edge case.

    ranked(subset):
  unmastered = subset.filter { history[key] < masteryThreshold }
  source = unmastered.isEmpty ? subset : unmastered   // fallback, not a filter
  sort source by:
    1. mastery count ascending      (fewest attempts first)
    2. |evalAfter - evalBefore| descending

prioritized(from: pool, count):
  high = ranked(pool.filter { $0.isHighQuality })
  low  = ranked(pool.filter { !$0.isHighQuality })
  return (high + low).prefix(max(1, count))

    The mastered-drop in ranked is a fallback, not a filter: a player who has mastered every puzzle in a tier still gets that tier back, rather than an empty pool. prioritized's max(1, count) is the same never-empty discipline one level up — Settings' "puzzles per drill" picker defaults to 20, but if it were ever read as 0 (a fresh key, a bad restore, a foreign value), a naive prefix(count) would start a drill with no puzzles. max(1, count) guarantees a user who asked to drill always gets at least one.

    let byMode = TacticsExtractor.extractAll(
    from: input,
    modes: [.opponentBlunders, .criticalPositions, .missedMate],
    mateMaxN: MissedMateCap.resolve(stored: storedMateMaxN),
    swingThreshold: TacticsSensitivity.minimum
)
let pool = byMode[.opponentBlunders] ?? []

let drill = TacticsDrillSelection.prioritized(
    from: pool,
    count: 20,
    masteryHistory: BlunderMasteryStore.history(in: blobStore),
    masteryThreshold: MasteryStreak.resolve(stored: storedMasteryThreshold)
)

    ReviewQuizKernel¶

    The shared review-quiz selection engine: which mainline plies become quiz questions, and what answer choices each one offers. Lifted from Android's ReviewQuizView, which handled a case iOS's pre-set node.moveQuality check missed entirely — batch-annotated library games that carry evals but no per-node quality labels.

    Annotations-first, eval-derived fallback¶

    public static func quizMoveQuality(
    plyIndex k: Int, evalCps: [Double], mainLineCount: Int,
    annotations: [Int: MoveAnnotation], startIsWhite: Bool
) -> MoveQuality?

    startIsWhite reflects who moves first — a FEN-setup / black-to-move game flips ply parity, and therefore flips who the quiz is about. It carried = true until 2026-08-08, and that default is exactly what let the Android quiz view drop the argument entirely: for a black-to-move game Android inverted the mover on every ply and quizzed the user on the opponent's mistakes, while its own entry-button count — which did pass the flag — advertised a different set of questions than the quiz actually asked (divergence register C8). A defaulted correctness argument makes "forgot to pass it" indistinguishable from "meant true", so the only durable fix was to make the compiler ask every caller.

    A non-empty annotations dictionary means the caller has authoritative per-ply labels: the eval path is disabled entirely, and only a stored .blunder or .mistake at ply k qualifies (this is what reproduces the interactive-review behavior exactly). When annotations is empty — the batch-annotated library path — quality is derived instead from the win-probability drop across evalCps (both before/after probabilities oriented to the mover via AccuracyAggregator.winProbability, then classified with AccuracyAggregator.classifyMoveQuality(wpDrop:playedBestMove:)); only a resulting .blunder/.mistake qualifies.

    quizablePlies(mainLine:evalCps:annotations:moveText:startIsWhite:) walks every mainline ply, keeps the ones quizMoveQuality accepts, and resolves each one's best move — engineBestMoveUCI first, else a PGN-embedded snapshot built lazily (at most once, only on the first miss, and only kept if it aligns 1:1 with the mainline) — dropping any ply whose best move still can't be resolved. QuizablePly { index, quality, bestUCI } is the result element.

    choices() distractor assembly¶

    public static func choices(
    bestUCI: String, bestSAN: String,
    actualUCI: String, actualSAN: String,
    legalMoves: [Move], positionBefore: Position,
    limit: Int = 4
) -> [Choice]

    The engine's best move always appears first. The move actually played is added only when it differs from best — the whole point of the question is to contrast the two, so a quiz that omits the played move teaches nothing. Remaining slots up to limit are filled with legal-move distractors, shuffled and deduplicated by UCI. The result is returned unshuffled — best (and maybe played) first, then the distractors in their shuffled order — so the caller decides presentation order; both shells shuffle again themselves before display, which keeps this function deterministic and directly testable:

    let plies = ReviewQuizKernel.quizablePlies(
    mainLine: game.mainLine, evalCps: evalCps,
    annotations: perPlyAnnotations, moveText: pgn.moveText
)
let options = ReviewQuizKernel.choices(
    bestUCI: plies[0].bestUCI, bestSAN: bestSAN,
    actualUCI: actualUCI, actualSAN: actualSAN,
    legalMoves: legalMoves, positionBefore: positionBefore
).shuffled()   // caller owns presentation order

    Combination puzzles: CombinationDrillCore¶

    A combination — a multi-move tactic with a scripted opponent reply after each solver move — cannot be graded against a single expected UCI the way DrillFlowCore grades a puzzle, because the "answer" is a tree: several solver moves can be equally correct, and the opponent's reply differs by branch. CombinationDrillCore is that tree's own Sendable state machine, lifted out of CombinationDrillView for the same reason DrillFlowCore was extracted from the shells — every bug it had shipped was an ordering bug (an undo re-triggering the check it was undoing from; a move scored before its consequence was known playable; a completion written one line before another assignment overwrote it), and none of the three was reachable by any test that had to go through a SwiftUI view to exercise them. It owns no board: every board mutation comes back as an Effect the shell applies, and every board fact it needs arrives as a BoardSnapshot — the same input/output split this page's other cores use.

    var core = CombinationDrillCore(puzzle: puzzle)
apply(core.start())                       // [.loadPosition(fen:), .setBoardFlipped(_)]

// On EVERY cursor change — including the ones the drill caused itself.
let effects = core.boardChanged(CombinationDrillCore.BoardSnapshot(
    cursorUCI: cursorUCI,     // the move under the cursor; nil at the start position
    cursorPly: cursorPly,     // its ply index; -1 at the start position
    position: livePosition    // WITH cursorUCI already on the board
))
apply(effects)

core.solved; core.wrongAttempts; core.attempts; core.totalSolverMoves; core.isFinished

    Its re-entrancy guard is the same shape as DrillFlowCore's: a board change only counts as an answer when board.cursorPly == waitingPly + 1, a value recorded when the core decides, before the shell has applied anything — so the scripted reply landing at waitingPly, a take-back returning the cursor there, or the user browsing the move list all grade nothing, regardless of what order the shell delivers them in. Effect is loadPosition(fen:), setBoardFlipped(Bool), takeBack(TakeBackReason), playReply(uci:move:), and completed(solved:attempts:); TakeBackReason distinguishes a scored .wrongMove from an unscored .replyUnplayable (a malformed or exhausted tree), so a shell can eventually word the two differently without the core tracking anything more than it already does.

    The tree CombinationDrillCore walks is built by CombinationPuzzleKernel from engine lines, fed by two small value types:

    • NodeEvaluation — engine evaluations for the legal moves at one position, mover-POV centipawns: moveEvals: [String: Int] plus a computed bestCp (the max). buildPuzzle's evaluations parameter is keyed by FEN; a solver node accepts every move within dualSolutionToleranceCp (50cp) of bestCp, not only the engine's top pick, because a drill that accepted just one of two winning moves would reject a correct dual solution. A position with no entry falls back to accepting only the move the supplied line actually played — conservative rather than wrong.
    • UnresolvedBranch — an opponent reply a real player might choose that the tree has no scripted continuation for: the FEN, the solver-relative UCI path to it, the reply itself, lossVsBestCp, an optional humanProbability from a Maia policy, and reachProbability (the product of the opponent choices above it in the tree). Its expectedFrequency ((humanProbability ?? 1) * reachProbability), not lossVsBestCp alone, is what decides whether a gap is worth scripting — a reply nobody plays costs nothing to leave unresolved. A non-empty unresolvedBranches list does not block drilling: CombinationDrillCore always plays a scripted reply, so the walk can never strand on one; it is reported so the miner can go probe the gap, not so the solver refuses to start.
