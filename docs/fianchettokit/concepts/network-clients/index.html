    Network Clients¶

    Three REST clients: a Lichess tablebase probe, the Lichess opening explorer, and Chess.com / Lichess game import. All identify as User-Agent: "Fianchetto-ChessApp/1.0" and surface failures as ChessAPIError.

    dataResult portability shim

    All three clients call an internal URLSession.dataResult(for:) / dataResult(from:) pair instead of the native async data(for:) / bytes(for:), wrapping the completion-handler dataTask in a checked continuation. FianchettoKit's own floor is iOS 18 / macOS 15 — already past the iOS 15 / macOS 12 the native async APIs require — so this isn't an OS back-deployment; it's kept for Android portability, since the completion-handler dataTask is broadly available on swift-corelibs-foundation (including Android's SkipFoundation), where the async bytes(for:) is not. A lock-guarded state object (URLSessionDataResultState) guarantees the continuation resumes exactly once even when cancellation races task creation or a completion callback fires after cancellation.

    Errors¶

    public enum ChessAPIError: LocalizedError {
    case invalidUsername     // 404
    case networkError(String)
    case noGamesFound
    case rateLimited         // 429
    case unauthorized        // 401
}

    ChessAPIError is LocalizedError with user-facing errorDescriptions (e.g. unauthorized → "Authentication required — add your Lichess API token…").

    TablebaseService — Syzygy probe¶

    A cached actor over the Lichess tablebase endpoint (https://tablebase.lichess.ovh/standard). Results are cached by FEN, with no eviction — unlike LichessExplorer's 200-entry cap — since a session probes a comparatively small set of distinct endgame FENs.

    public actor TablebaseService {
    public static let shared: TablebaseService
    public init()
    public static func pieceCount(for position: Position) -> Int
    public func probe(fen: String) async throws -> TablebaseResult
    public func clearCache()
}

    import ChessCore
import FianchettoKit

if TablebaseService.pieceCount(for: position) <= 7 {   // tablebase is <= 7 pieces
    let result = try await TablebaseService.shared.probe(fen: position.stockfishSafeFEN)
    print(result.category)            // .win / .loss / .draw / .cursedWin / ...
    print(result.dtm ?? -1, result.dtz ?? -1)
    print(result.bestMove ?? "—")

    for move in result.moves {
        switch move.userVerdict {
        case .keepsWin: print("\(move.uci) keeps the win")
        case .draws:    print("\(move.uci) only draws")
        case .losesWin: print("\(move.uci) throws the win")
        case .unknown:  break
        }
    }
}

    Use userVerdict, not category

    Lichess reports each move's category from the opponent's perspective — the side to move after your move. So a move whose category is loss means the opponent is losing after your move, i.e. your move keeps the win. TablebaseMove.userVerdict is the single source of truth for the from-your-POV mapping; route every consumer through it instead of mapping categories inline.

    public struct TablebaseResult: Sendable {
    public let category: Category    // win, loss, draw, cursedWin, blessedLoss, unknown
    public let dtm: Int?             // depth to mate
    public let dtz: Int?             // depth to zeroing
    public let bestMove: String?
    public let moves: [TablebaseMove]
}

public struct TablebaseMove: Sendable, Identifiable {
    public let uci: String
    public let san: String?
    public let category: TablebaseResult.Category
    public let dtm: Int?
    public let dtz: Int?
    public var userVerdict: UserVerdict   // .keepsWin | .draws | .losesWin | .unknown
}

    Category.isDecisive is true for .win, .loss, .cursedWin, and .blessedLoss (not .draw or .unknown).

    LichessExplorer — opening explorer¶

    A cached actor over the Lichess opening explorer. Pick the database and (for the Lichess database) the rating bands.

    public actor LichessExplorer {
    public static let shared: LichessExplorer
    public init()
    public func explore(fen: String,
                        database: ExplorerDatabase = .lichess,
                        ratings: [Int] = [1600, 1800, 2000, 2200, 2500],
                        speeds: [String] = ["blitz", "rapid", "classical"],
                        token: String? = nil) async throws -> ExplorerResult
    public func clearCache()
}

public enum ExplorerDatabase: String, CaseIterable, Identifiable, Sendable {
    case lichess = "Lichess"   // https://explorer.lichess.org/lichess
    case masters = "Masters"   // https://explorer.lichess.org/masters
}

    let result = try await LichessExplorer.shared.explore(
    fen: position.fen,
    database: .lichess,
    ratings: [1600, 1800, 2000, 2200, 2500],
    speeds: ["blitz", "rapid", "classical"],
    token: nil                 // optional Lichess API token (Bearer)
)

print(result.totalGames, result.white, result.draws, result.black)
for move in result.moves.prefix(5) {
    print(move.san, move.totalGames, move.averageRating ?? 0)
}

    Results are cached per "<database>:<fen>", or "<database>:<fen>:r=<ratings>:s=<speeds>" for the Lichess database (.masters ignores ratings/speeds, so its key drops them). ratings is filtered against the allowed set {1000, 1200, 1400, 1600, 1800, 2000, 2200, 2500}, falling back to the default list if nothing survives; speeds is filtered against ["bullet", "blitz", "rapid", "classical", "correspondence"] the same way. The cache holds at most 200 entries with oldest-first eviction; only non-empty results (white + draws + black > 0) are cached, and a malformed top-level JSON body throws .networkError rather than caching an empty result. A 401 surfaces as .unauthorized; a 429 as .rateLimited.

    ChessAPIService — game import¶

    A fully nonisolated, Sendable class whose fetch+parse pipeline runs off the main actor. Its fetch methods are @concurrent — under the project's Approachable Concurrency settings, a plain nonisolated async method would run on the caller's actor, silently pulling a multi-month Chess.com sweep or a byte-by-byte Lichess decode back onto the main thread. The optional progress callback is @MainActor @Sendable and fires once per archive month, not per byte.

    public final class ChessAPIService: Sendable {
    public init()

    @concurrent public func fetchChessComGames(
        username: String, since: Date? = nil, filters: ImportFilters? = nil,
        onProgress: (@MainActor @Sendable (Int, Int) -> Void)? = nil
    ) async throws -> ChessComFetchResult

    @concurrent public func fetchLichessGames(
        username: String, since: Date? = nil, token: String? = nil,
        filters: ImportFilters? = nil
    ) async throws -> [PGNGame]

    @concurrent public func fetchLichessGameSnapshot(
        username: String, since: Date? = nil, token: String? = nil,
        filters: ImportFilters? = nil
    ) async throws -> LichessFetchResult

    @concurrent public func fetchLichessHistoryPages(
        username: String, since: Date? = nil, token: String? = nil,
        filters: ImportFilters? = nil,
        pageSize: Int = ChessAPIService.defaultLichessHistoryPageSize,
        resumingFrom cursor: LichessHistoryPageCursor? = nil,
        onPage: @Sendable (LichessHistoryPage) async throws -> Void
    ) async throws -> LichessHistoryCompletion
}

    The service owns two URLSessions: session (30 s per-request / 180 s total-resource timeout) for the Chess.com archive walk, and streamSession (60 s per-request / 7,200 s / 2 h total-resource timeout) for the Lichess export, a single long-lived stream rather than bounded requests. A second, internal init(session:streamSession:) exists only as a test seam.

    LichessExplorer and TablebaseService each own their own private session too, but with a simpler budget: a flat 10 s per-request timeout and no timeoutIntervalForResource override at all. Neither client needs a resource-timeout ceiling — each request is one bounded lookup (an opening-book query, a FEN probe), never a multi-month sweep or an hours-long stream, so the per-request idle timer alone is enough to bound it.

    This capability is not currently exposed headlessly — fianchetto-cli ships exactly six subcommands (annotate, estimate, maia, accuracy, project, track) and none of them touch import. An import-shaped subcommand is only a proposal on the CLI's own expansion notes; everything below is the underlying policy such a command would eventually have to drive.

    Chess.com — monthly archive sweep¶

    fetchChessComGames walks GET https://api.chess.com/pub/player/<username>/games/archives, filters and reverses the archive list to newest-first, then fetches and parses each archive's /pgn text. Per-archive failures are collected, never abort the sweep:

    archives = GET .../games/archives -> { "archives": [String] }
kept     = chessComArchiveURLs(archives, notBefore: since)
walk     = kept.reversed()                     // newest month first

for each archive URL in walk:
    require url.scheme == "https" && url.host == "api.chess.com"   // else: failedArchives += url; continue
    pgn = GET url + "/pgn"
    games = PGNParser.parse(pgn)
    require isStructurallyValidChessComArchive(games)               // else: failedArchives += url; continue
    allGames += games
    onProgress(index + 1, total)   // @MainActor, once per archive

    public struct ChessComFetchResult: Sendable {
    public let games: [PGNGame]
    public let failedArchives: [String]     // archive URLs that errored
    public var isPartial: Bool { !failedArchives.isEmpty }
}

    .invalidUsername is thrown only for a 404 on the archive list; .rateLimited can surface from either that request or any per-archive PGN request. .noGamesFound is thrown only when finalGames.isEmpty && failedArchives.isEmpty — a genuinely empty account, never a partial sweep. CancellationError and any ChessAPIError thrown mid-sweep propagate immediately; every other per-archive failure is recorded and the sweep continues.

    Archive-month boundary filter. Chess.com's archive URLs are UTC-calendar- month paths (.../YYYY/MM). chessComArchiveURLs(_:notBefore:) builds its own Calendar pinned to TimeZone(secondsFromGMT: 0)! — never Calendar.current — because deriving the boundary from the device's local time zone can make a positive-UTC-offset device consider itself already in the next month and permanently skip the still-current UTC archive:

    given since: (sinceYear, sinceMonth) = UTC calendar components of since
keep archive iff:
    trailing "/year/month" path components are unparseable   // KEEP — malformed URLs are
                                                                // reported as failures, not silently dropped
    OR year > sinceYear
    OR (year == sinceYear AND month >= sinceMonth)

    Structural validation gate. PGNParser is deliberately permissive for hand-authored imports — any non-empty token text becomes a PGNGame — so a network archive needs a stricter boundary: an HTML error page or truncated body must not be mistaken for a successful, if game-less, month. isStructurallyValidChessComArchive requires the parsed archive to be non-empty and every game to have non-empty trimmed White/Black tags and a Result tag drawn from {"1-0", "0-1", "1/2-1/2", "*"}.

    Client-side filters. Chess.com has no server-side filter API, so ImportFilters are applied per game, after parsing — see the mapping table under ImportFilters below.

    Lichess one-shot fetch — fetchLichessGames / fetchLichessGameSnapshot¶

    fetchLichessGames is a thin convenience over fetchLichessGameSnapshot that throws .noGamesFound when games is empty. Prefer the snapshot form for anything persisting an incremental cursor — an empty terminal-game list is a valid snapshot (it can mean "no new games" or "the only matching game is still in progress"), which the convenience form can't distinguish from a truly empty account.

    public struct LichessFetchResult: Sendable {
    public let games: [PGNGame]                    // terminal games only
    public let earliestOngoingGameDate: Date?
    public let serverDate: Date?
    public var hasOngoingGames: Bool { earliestOngoingGameDate != nil }
    public func safeSyncWatermark(fetchStartedAt: Date) -> Date?
}

    Both methods first issue a separate ongoing-game probe: the same account/filters request, but with since, until, max, sort, rated, perfType, color, opening, and pgnInJson/ongoing/finished stripped and re-added as pgnInJson=true&ongoing=true&finished=false. Excluding the caller's cursor and filters means the probe always reflects the account's true earliest in-progress game. Only after the probe completes is the requested finished-history slice fetched and merged with the probe's records.

    Safe sync watermark — the rewind rule. Lichess delays ongoing games by up to 60 s in the export, so a cursor computed purely from request time can land after a game that started before the response but isn't visible in it yet:

    lichessSafeSyncWatermark(fetchStartedAt, serverDate, earliestOngoingGameDate):
    if serverDate == nil: return nil                       // no trustworthy clock — do not advance
    candidate = min(fetchStartedAt, serverDate) - 61s       // 60s export delay + 1s overlap margin
    if earliestOngoingGameDate != nil
       && earliestOngoingGameDate <= candidate:
        return earliestOngoingGameDate - 1s                 // rewind the cursor to just before that game
    return candidate

    LichessFetchResult.safeSyncWatermark(fetchStartedAt:) and LichessHistoryCompletion.safeSyncWatermark() both forward to this one private algorithm — the completion form treats snapshotUntilMilliseconds / 1000 as fetchStartedAt.

    Never derive a Lichess watermark by any other means

    A missing serverDate must disable cursor advance entirely — that's why the function returns nil instead of falling back to the local clock. Publishing a locally-computed cursor when the remote clock is unknown is exactly the failure OnlineImportWatermarkPolicy (below) exists to rule out.

    ImportFilters / ImportTimeControl / ImportColor¶

    The shared filter vocabulary across both platforms. All fields default to nil (no restriction).

    public struct ImportFilters: Sendable {
    public var ratedOnly: Bool?              // nil = any, true = rated only, false = unrated only
    public var timeControls: Set<ImportTimeControl>?   // nil/empty = all classes
    public var color: ImportColor?           // nil/.any = either color
    public var since: Date?                  // nil = no lower bound
    public init(ratedOnly: Bool? = nil, timeControls: Set<ImportTimeControl>? = nil,
                color: ImportColor? = nil, since: Date? = nil)
    public var isActive: Bool   // true iff any field imposes a real restriction
}

public enum ImportTimeControl: String, CaseIterable, Codable, Sendable, Hashable {
    case bullet, blitz, rapid, classical
    public var displayName: String
    public var chessComTimeClass: String   // "standard" for .classical, else rawValue
}

public enum ImportColor: String, CaseIterable, Codable, Sendable {
    case any, white, black
    public var displayName: String
}

    ImportTimeControl raw values match Lichess perfType values exactly, while Chess.com names classical games "standard" in its TimeClass tag — the one case chessComTimeClass translates.

    Filter field Chess.com mapping Lichess mapping
    ratedOnly !event.contains("(Unrated)") (client-side) rated=true\|false query param
    timeControls TimeClass tag vs. chessComTimeClass (client-side) perfType=<comma-joined sorted raw values>
    color White/Black tag vs. username (client-side) color=white\|black (omitted for .any)
    since Date tag "YYYY.MM.DD" vs. since (client-side) since=<ms>, = max(since, filters.since)

    Lichess applies filters server-side via query parameters built by the shared lichessBaseRequest; Chess.com applies them client-side, after parsing.

    Lichess bounded history walk — fetchLichessHistoryPages¶

    The producer for a complete, resumable, newest-first account history. It has no total game cap — a full page always produces a strictly older continuation, and the walk ends only when Lichess returns a short page. pageSize must be in 1...maximumLichessHistoryPageSize (5,000) or it throws .invalidPageSize; the default is defaultLichessHistoryPageSize (1,000).

    if resuming from a cursor:
    validate cursor.hasValidIntegrityAndShape
    validate cursor.matches(requestSignature, pageSize)   // else .resumeCursorRequestMismatch
    snapshotUntilMilliseconds = cursor.snapshotUntilMilliseconds   // fixed, carried forward unchanged
    nextUntilMilliseconds     = cursor.nextUntilMilliseconds
    previousPageIDs           = Set(cursor.overlapGameIDs)
else:
    probe ongoing games once (no filters/cursor) -> serverDate, earliestOngoingGameDate
    snapshotUntilMilliseconds = floor((serverDate ?? now).timeIntervalSince1970 * 1000)
    nextUntilMilliseconds     = snapshotUntilMilliseconds
    previousPageIDs           = {}

loop:
    GET .../games/user/<username>?until=nextUntilMilliseconds&max=pageSize&sort=dateDesc&finished=true&...filters
    (novelRecords, nextUntil?, nextOverlapIDs) = LichessNewestFirstPageAccumulator(
        pageSize, currentUntilMilliseconds: nextUntilMilliseconds, previousPageIDs
    ).consume(page)
    games  = terminal games in novelRecords
    cursor = nextUntil.map { LichessHistoryPageCursor(snapshotUntilMilliseconds, nextUntilMilliseconds: $0,
                                                        ..., overlapGameIDs: nextOverlapIDs) }
    await onPage(LichessHistoryPage(games, resumeCursor: cursor))   // durability handshake
    if cursor == nil: return LichessHistoryCompletion(...)          // short/partial page = terminal
    nextUntilMilliseconds = cursor.nextUntilMilliseconds
    previousPageIDs        = Set(cursor.overlapGameIDs)

    One-millisecond overlap rule. A full page (page.count == pageSize) can't assume the next page starts strictly after this page's oldest game — Lichess may treat until inclusively, and games can share a millisecond-resolution createdAt. LichessNewestFirstPageAccumulator handles this by computing nextUntil = pageMinimum(createdAtMilliseconds) + 1 and requiring nextUntil < currentUntilMilliseconds, else it throws .cursorDidNotAdvance — the guard against an infinite loop or a silently-skipped timestamp cluster. The previous page's full ID set is carried forward as previousPageIDs/overlapGameIDs so records reappearing at the shared boundary millisecond are filtered from novelRecords instead of re-yielded. A short page (page.count != pageSize) is unambiguously the end of history: nextUntilMilliseconds is nil.

    onPage is a durability handshake: persist page.games and then page.resumeCursor before returning. Nothing older is requested until that closure returns, so replaying an already-acknowledged page after a crash between those two writes is safe — stable Lichess IDs make re-persisting idempotent.

    let completion = try await service.fetchLichessHistoryPages(
    username: "DrNykterstein",
    token: lichessToken,          // optional; changes throughput, not which games match
    pageSize: 5_000,
    resumingFrom: savedCursor     // nil on a fresh import
) { page in
    try await persistGamesAndThenCursor(page.games, cursor: page.resumeCursor)
}
print(completion.acknowledgedGameCount, "acknowledged games")
if let watermark = completion.safeSyncWatermark() {
    // safe to advance the account's incremental-sync cursor
}

    public struct LichessHistoryPage: Sendable {
    public let games: [PGNGame]
    public let resumeCursor: LichessHistoryPageCursor?
    public var isTerminal: Bool { resumeCursor == nil }
}

public struct LichessHistoryPageCursor: Sendable, Codable, Equatable {
    public let schemaVersion: Int                  // = lichessHistoryCursorSchemaVersion (1)
    public let snapshotUntilMilliseconds: Int64     // fixed upper bound of the whole walk
    public let nextUntilMilliseconds: Int64
    public let serverDate: Date?
    public let earliestOngoingGameDate: Date?
    public let overlapGameIDs: [String]             // boundary-page IDs, for de-dup on resume
    public let integritySHA256: String              // checksum, not a secret-keyed auth proof
    public func isValid(for identity: LichessHistoryImportIdentity) -> Bool
}

public struct LichessHistoryCompletion: Sendable {
    public let snapshotUntilMilliseconds: Int64
    public let serverDate: Date?
    public let earliestOngoingGameDate: Date?
    public let acknowledgedPageCount: Int
    public let acknowledgedGameCount: Int
    public var hasOngoingGames: Bool { earliestOngoingGameDate != nil }
    public func safeSyncWatermark() -> Date?
}

    Request-signature and integrity-proof hashing. Because the cursor is Codable and meant to be persisted, it carries two SHA-256 digests (via PortableSHA256.Hasher, each domain-separated by a literal version string):

    lichessHistoryRequestSignature = SHA256(
    "fianchetto.lichess-history-request-signature.v1",
    normalizedUsername, String(pageSize),
    <every base-request query item, sorted by (name, value)>   // order-independent
)

lichessHistoryCursorIntegrityProof = SHA256(
    "fianchetto.lichess-history-page-cursor.integrity.v1",
    schemaVersion, snapshotUntilMilliseconds, nextUntilMilliseconds,
    dateField(serverDate), dateField(earliestOngoingGameDate),   // "none" | "some:<hex bitPattern>"
    requestSignature, pageSize, overlapGameIDs.count, <each overlapGameIDs entry>
)

    dateField encodes a Date as "none" or "some:" plus the hex bitPattern of timeIntervalSinceReferenceDate — the exact IEEE-754 bits — so a Codable round-trip is lossless while sub-millisecond mutation is still detected. Both digests are integrity checksums, not secret-keyed authenticity proofs.

    isValid(for:) re-derives the expected request signature from a LichessHistoryImportIdentity (below) and checks it, the integrity proof, and the schema version — with the API token deliberately excluded, since a token changes throughput, not which public games match. hasValidIntegrityAndShape additionally requires: schemaVersion == lichessHistoryCursorSchemaVersion (1); snapshotUntilMilliseconds > 0; nextUntilMilliseconds > 0; nextUntilMilliseconds < snapshotUntilMilliseconds; overlapGameIDs non-empty, with no duplicates or empty strings, and count <= pageSize.

    Crash-safe resumption — LichessHistoryImportIdentity + LichessHistoryImportCheckpoint¶

    A cursor alone is enough to resume a walk mid-flight, but crash recovery also needs to know whose walk a saved cursor belongs to and how much of it has reached durable storage. LichessHistoryImportIdentity is the canonical request identity — the API token is excluded for the same reason as above:

    public struct LichessHistoryImportIdentity: Codable, Hashable, Sendable {
    public static let currentSchemaVersion = 1

    public let schemaVersion: Int
    public let normalizedUsername: String
    public let ratedOnly: Bool?
    public let timeControlRawValues: [String]     // sorted
    public let colorRawValue: String?              // nil unless white/black (.any collapses to nil)
    public let sinceMilliseconds: Int64?
    public let pageSize: Int

    public init?(username: String, since: Date? = nil, filters: ImportFilters? = nil,
                 pageSize: Int = ChessAPIService.defaultLichessHistoryPageSize)

    public var isValid: Bool
    public var filters: ImportFilters?      // reconstructed, or nil if not .isActive
    public var storageToken: String         // SHA-256 digest — a stable cache/file key, not a secret
}

    The failable initializer normalizes the username (trim + lowercase) and rejects an out-of-range pageSize or a since that doesn't scale losslessly to milliseconds within Int64. storageToken is a domain-separated SHA-256 digest ("fianchetto.lichess-history-import-identity.v1"), a stable filesystem/blob-store key derived from the request shape.

    public struct LichessHistoryImportCheckpoint: Codable, Equatable, Sendable {
    public static let currentSchemaVersion = 1

    public let schemaVersion: Int
    public let identity: LichessHistoryImportIdentity
    public let cursor: ChessAPIService.LichessHistoryPageCursor
    public let acknowledgedPageCount: Int
    public let acknowledgedGameCount: Int
    public let insertedGameCount: Int

    public init(identity:cursor:acknowledgedPageCount:acknowledgedGameCount:insertedGameCount:)
    public func isValid(for expectedIdentity: LichessHistoryImportIdentity) -> Bool
}

    isValid(for:) requires: schema match; identity.isValid and exact equality to the caller's freshly-recomputed expected identity (so a changed username, filter, or page size invalidates a stale checkpoint rather than silently resuming the wrong request); cursor.isValid(for: identity); acknowledgedPageCount > 0; acknowledgedGameCount >= 0; and insertedGameCount in 0...acknowledgedGameCount (a page can be acknowledged with fewer games actually inserted after dedup).

    guard let identity = LichessHistoryImportIdentity(
    username: "DrNykterstein", filters: filters, pageSize: 5_000
) else { return }   // invalid username/pageSize/since

if let saved = loadCheckpoint(for: identity.storageToken), saved.isValid(for: identity) {
    // resume: pass saved.cursor as `resumingFrom:`
} else {
    // start fresh: resumingFrom: nil
}

    Update Games: the shared incremental-sync policy¶

    "Update Games" — re-fetching only what changed since the last successful import — has one policy shared verbatim between platforms: a source-agnostic watermark rule plus GameUpdatePlanner, the namespace that drives a single update pass end to end.

    OnlineImportWatermarkPolicy.safeSyncWatermark¶

    public enum OnlineImportWatermarkPolicy {
    public static func safeSyncWatermark(
        candidateSyncDate: Date?, isPartial: Bool,
        filtersAreActive: Bool, allFetchedGamesSelected: Bool
    ) -> Date?
}

    safeSyncWatermark(candidateSyncDate, isPartial, filtersAreActive, allFetchedGamesSelected):
    if isPartial || filtersAreActive || !allFetchedGamesSelected:
        return nil                       // watermark must not advance
    return candidateSyncDate

    Extracted after two app shells independently reimplemented this rule with diverging, less-safe parameter sets. Getting it wrong doesn't crash: it silently makes remote history permanently unreachable, because the next incremental sync starts from the stamped cursor and never looks back. candidateSyncDate must be the request's start time, not the save time, or games published mid-fetch would be skipped; isPartial catches a Chess.com sweep with failed archive months; filtersAreActive catches a filtered batch that can't describe an unfiltered "everything since X" replay; allFetchedGamesSelected catches a shell offering per-game import selection.

    sinceDate picks the fetch lower bound: a full sweep passes nil (re-walks everything, relying on dedup); an incremental update resumes from lastSyncDate. remoteGameID(of:) forwards to GameIdentity.remoteID(link:site:): an explicit PGN Link tag wins outright; a Site tag is accepted only when it's a recognized Chess.com/ Lichess game URL, so a generic PGN venue falls through to content identity.

    newGames dedup. For each fetched game, register it into a GameDedup.KeySet — deduping against both existing and the same fetched batch — preferring a remote ID (remoteGameID(of:)) when present, else the 6-field GameDedup.compositeKey (white, black, date, result, event, opening, plus token-text move export and JSON-encoded tags) as an @autoclosure, so an ID-bearing game never pays for PGN serialization or move-text hashing. newGamesCheckingCancellation is the same policy with a cancellation check before each composite-key fingerprint, so a retired full-history update doesn't keep hashing thousands of games off-screen.

    syncStamp — two overloads:

    syncStamp(isPartial, now):
    if isPartial: return nil
    return floor(now.timeIntervalSince1970 seconds)   // round DOWN — HTTP Date is second-granular;
                                                        // a fractional client time would compare LATER
                                                        // than the authoritative server boundary

    if source == "lichess": return result.exactSyncWatermark   // verbatim — Lichess's own server-clock cursor
    return syncStamp(isPartial: result.isPartial, now: requestStartedAt)   // chess.com path

    NDJSON streaming internals¶

    Internal (non-public) types backing the Lichess fetch paths. Briefly, for contributors working inside FianchettoKit/Network — none of this is public API.

    LichessGameStreamDecoder frames Lichess's NDJSON export one byte at a time via consume(_ byte:) throws -> LichessGameRecord? and finish() throws -> LichessGameRecord?, buffering only the current line's raw bytes and releasing a LichessGameRecord as soon as a 0x0A newline arrives (trailing 0x0D stripped, empty lines ignored). A line over maximumLineByteCount (default defaultMaximumLineByteCount = 8 * 1024 * 1024, 8 MiB) throws .lineTooLarge.

    Each line decodes as {id, createdAt: Int64, status: String, pgn: String?}. status.lowercased() is checked against a fixed set:

    finalStatuses = {
    "aborted", "mate", "resign", "stalemate", "timeout", "draw",
    "outoftime", "cheat", "nostart", "unknownfinish",
    "insufficientmaterialclaim", "variantend"
}

    A status not in that set — including a future Lichess status the decoder hasn't been updated for — yields finishedGame == nil (isOngoing == true): fail toward "not yet final" rather than risk a persisted in-progress snapshot. For a final status, pgn must be non-nil and parse to exactly one game with non-empty White/Black/Result tags, or the line throws .invalidPGN. Both byte-driven decode paths check Task cancellation every 4,096 bytes rather than every byte.

    Two private static helpers on ChessAPIService turn a raw record list into a LichessFetchResult:

    finishedLichessGames(in records: [LichessGameRecord]) -> [PGNGame]
    keep record.finishedGame where record.id has not been seen before
    // first occurrence of an id wins; a later duplicate is dropped even if
    // it too carries a finishedGame

earliestOngoingGameDate(in records: [LichessGameRecord]) -> Date?
    min over records where isOngoing of
        Date(timeIntervalSince1970: createdAtMilliseconds / 1_000)

    The keep-first-id rule matters because the ongoing probe and the requested finished-history slice are two separate requests merged into one record list; if the same id appears in both, only the first copy encountered should survive into games rather than being counted, or silently overwritten, twice.

    Two accumulators sit on top of the decoder, one per pagination strategy:

    Type Used by Overlap rule
    LichessGamePageAccumulator fetchLichessGamesPaged — oldest-first, Android/Linux/Windows fallback (default page size 1,000) full page → nextSince = pageMaximum(createdAt) - 1; throws .cursorDidNotAdvance if pageMaximum <= previousMaximumCreatedAt
    LichessNewestFirstPageAccumulator fetchLichessHistoryPages — bounded newest-first walk full page → nextUntil = pageMinimum(createdAt) + 1, must be < currentUntilMilliseconds else .cursorDidNotAdvance

    Both dedup by stable record id and throw .pageTooLarge if the server returns more records than requested. The Android/Linux/Windows fallback exists because Android's AsyncBytes adapter silently converts a stream read error into ordinary end-of-stream, and swift-corelibs-foundation has no async bytes(for:) at all — all three platforms use finite, overlapping completion-handler pages, which preserve transport errors and bound memory.

    lichessServerDate(from:) parses the HTTP Date header as an RFC 7231 IMF-fixdate (DateFormatter, locale en_US_POSIX, zone GMT+0, format "EEE',' dd MMM yyyy HH':'mm':'ss 'GMT'"). A missing or unparseable header deliberately yields nil, disabling cursor advance per the safe-watermark rule above.
