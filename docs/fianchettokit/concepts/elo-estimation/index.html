    Elo Estimation & Strength Tracking¶

    Turns engine-annotated games into an Elo number, in two senses. A GamePerformance is per-game evidence — what one game's move quality implies about the player's strength, with a deliberately wide confidence interval. A StrengthTracker posterior integrates many games into one tighter estimate via a Kalman filter. Chart domains, provider-scale personalization, and serving-coverage labels are all built from that pair.

    Layering: pure domain logic over Foundation + ChessCore only. No SwiftUI, no SwiftData, no CoreML, no Skip imports — every type here is a value type or a nonisolated enum namespace.

    This is not all of Engine/

    EloEstimator and StrengthTracker are the strength-and-rating slice of Sources/FianchettoKit/Engine/, not the whole directory. A dozen other files there — AnnotationStaleness, GuessEloPolicy, MoveAnnotationSeverityBand, and others covering engine identity, search budgets, and live-analysis publication — have no page in either the reference or superseded set yet. Don't infer their behavior from this page; they need their own pass.

    Two time-control classifiers¶

    TimeControlClass picks the calibration artifact (Lichess-style); TimeSpeed picks the display/rating pool (Chess.com-style). They can disagree.

    TimeControlClass.classify(baseSeconds:incrementSeconds:)
  estimatedSeconds = baseSeconds + 40 × incrementSeconds
  < 180 → .bullet   < 480 → .blitz   < 1500 → .rapid   else → .classical
  baseSeconds == nil → .correspondence

StatsKernel.classifySpeed(tags:event:)          // different thresholds
  1. definitive correspondence TimeControl tag  → .daily  (wins over stale Event)
  2. Event keyword: bullet/ultrabullet/blitz/rapid/classical/
     correspondence|daily|"let's play"          → matching TimeSpeed
  3. empty tag + no keyword                      → .rapid  (NOT .daily —
                                                    no signal ≠ correspondence)
  4. base < 180 → .bullet  base < 600 → .blitz  base ≤ 1800 → .rapid  else classical

    TimeControlClass.classify(fromPGNTag:) parses staged PGN clocks ("40/7200:3600+30") via estimatedSeconds(fromPGNTag:): each :-stage contributes base + moveCount × increment, moveCount defaulting to 40 when no moves/ quota is given, then classifies with incrementSeconds: 0 (the weighting already happened). A lone "1/seconds" single-stage tag is Chess.com's Daily serialization and returns nil.

    Chess.com rates 5|5 as Blitz (300 < 600); the Lichess formula computes 300 + 40×5 = 500, landing in rapid. StatsKernel.estimateEloHistory carries both per candidate — displaySpeed (grouping/chart key, from classifySpeed) and timeControl (artifact selection, from TimeControlClass) — computed once, never re-derived from each other.

    Daily is its own rating pool

    .daily/.correspondence games are excluded from estimated-strength history entirely. Folding Daily into Rapid was tried: on the reference account, 378 Daily games (627–1,225) interleaved chronologically with 2,529 live games (202–1,048) on one axis, reading as "erratic and counterfactual." There is also no v4.1 model for correspondence.

    Accuracy formulas¶

    AccuracyAggregator is the sole home of every accuracy/win-probability constant; EloEstimator and the WinProbability.swift ChessCore extensions delegate here rather than holding their own copy.

    winProbability(cp:)             = 1 / (1 + exp(-0.00368208 × cp))
moveAccuracy(wpBefore:wpAfter:)   drop = max(0, wpBefore−wpAfter) × 100
accuracy(fromMeanLoss:)           raw  = 103.1668 × exp(-0.04354 × loss) − 3.1668
                                   return clamp(raw, 0, 100)

    moveAccuracy and accuracy(fromMeanLoss:) share the same constants but differ in when they're applied: moveAccuracy runs per-move and is then averaged (dashboard, RecentAccuracyKernel); accuracy(fromMeanLoss:) runs once on a pre-aggregated mean loss (EloEstimator, matching the Python calibration pipeline's filter.py). By Jensen's inequality, averaging per-move accuracy yields slightly higher values — a dashboard tile and an EloEstimator accuracy for the same game can differ by a point or two.

    let acc = AccuracyAggregator.moveAccuracy(wpBefore: 0.58, wpAfter: 0.51)

    Move-quality classification, Stockfish-native and Maia-native:

    classifyMoveQuality(wpDrop:playedBestMove:)
  playedBestMove → .best
  wpDrop >= 0.20/0.10/0.05/0.02 → .blunder/.mistake/.inaccuracy/.good
  else → .excellent

maiaMoveQuality(rank:probability:)      // rank -1 = outside Maia's top-K
  rank == 0                              → .best
  rank 0...2                             → .excellent
  rank 0...5  || probability >= 0.05     → .good
  rank 0...15 || probability >= 0.02     → .inaccuracy
  rank 0...30                            → .mistake
  else                                   → .blunder

maiaMoveAccuracy(rank:probability:) = clamp(sqrt(probability) × 100, 0, 100)

    Both return ChessCore's MoveQuality. The sqrt curve keeps mid-probability moves from collapsing to near-zero the way a linear scale would.

    The 12-feature move-level vector¶

    EloEstimator's v3, v4.1-ensemble, and v4.1-no-Maia models all consume the same 12-element vector (assembleV3Features), mirroring the Python pipeline's filter.py exactly:

    # Feature Computation
    0 accuracy accuracy(fromMeanLoss:) of this player's win-% losses
    1–3 blunder/mistake/inaccuracy_rate share of moves with win-% loss ≥ 20 / 10 / 5
    4 acpl_capped mean per-move cp loss, each move capped at 500
    5 eval_volatility population std-dev (÷n) of win-% after every ply, not just this player's moves
    6 opp_punish_rate share of opponent blunders (win-% swing ≥ 20) where the player's next loss ≤ half the gift; 0.5 if the opponent never blundered
    7 mean_abs_eval mean \|win% − 50\| across every ply
    8 n_moves this player's move count
    9 plies total plies
    10 is_checkmate always 0.0 — coefficient is 0 in every fitted model
    11 is_time 1.0 from PGN Termination via isTimeEnding(_:), else 0.0

    isTimeEnding treats Lichess's normalized "time"/"time forfeit" and Chess.com's prose ("won on time") as time endings, while explicitly excluding "timeout vs insufficient material" first. Computing the vector needs ≥ 3 of the player's own moves — stricter than the v2 path's ≥ 1.

    Calibration artifacts (EloCalibrationData)¶

    internal (not public) — generated by Tools/elo-calibration/generate_swift.py from the Lichess Open Database (CC0, May 2026); its header says "DO NOT EDIT." That generator does not live in this package: its header is explicit that it lives in the Fianchetto (Apple app) repository, because regenerating needs a 1 MB research corpus and an SSH compute target that have no business being a dependency consumers resolve. FianchettoKit's own Tools/ directory holds only FianchettoMaiaBackupTool. Because EloCalibrationData is internal, fianchetto-cli cannot read these constants directly today, only through EloEstimator.estimate.

    Quota balancing differs by time control

    Bullet, blitz and rapid were fit with rating-band quota balancing (≤ 15k rows per band) for better sub-1200 coverage. Classical is an unbalanced fit — its corpus was too small to support quotas. That shows up in the fitted numbers: classical's Maia lift is the largest of the four classes (see below), and its ensemble residual bands are tighter than bullet's everywhere except the bottom band (0–800: classical 270.5 vs. bullet 257.6) — exactly where an unbalanced, quota-free corpus would be thinnest on very-low-rated games.

    Version Features Selected when
    v2 (TCModel) accuracy only correspondence, or any TC with no v4.1 model
    v3 (V3TCModel) 12 superseded by v4.1 in production; kept for parity tests
    v4.1 ensemble (V41EnsembleTCModel) 16 (12 + 4 Maia) a valid 11-point Maia log-likelihood vector is available
    v4.1 no-Maia (V3TCModel refit) 12 Maia evidence missing or wrong length — the production fallback 
    v2: binnedLookup(accuracy:model:)          // monotone binned-median, linear interpolation
  accuracy <= centers[0]      → ratings[0]              (clamp low)
  accuracy >= centers[last]   → ratings[last]            (clamp high)
  between centers[i], [i+1]   → linear interpolation
  degenerate table (<2 bins)  → evalPoly(polyCoefficients, accuracy)  // cubic Horner

v3 / v4.1: prediction = intercept + Σᵢ coefficients[i] × (feature[i] − featureMeans[i]) / featureStds[i]

v4.1 Maia features 12–15, from an 11-point log-likelihood vector over
eloGrid = [600,800,...,2600] (step 200):
  llSpread = max(logLikes) − min(logLikes)        // ORIGINAL values
  weights  = softmax(logLikes)                     // stable: subtract max before exp
  meanElo  = Σ eloGrid[i]×weights[i]
  stdElo   = sqrt(Σ weights[i]×(eloGrid[i]−meanElo)²)
  argmaxElo = eloGrid[argmax(weights)]

    v4.1-ensemble cross-validated MAE by TC: bullet 226.5, blitz 200.4, rapid 189.2, classical 159.0. Classical's fit documents a +115.6 Elo contribution from the Maia features versus the no-Maia fallback — the largest lift of the four classes.

    EloEstimator.estimate — routing and confidence intervals¶

    public static func estimate(
    evalsJSON: String, startIsWhite: Bool, color: PieceColor, tc: TimeControlClass,
    isOTBClassical: Bool = false, maiaLogLikes: [Double]? = nil,
    maiaEvidence: MaiaBackfillPolicy.TargetEvidence? = nil, termination: String? = nil
) -> GamePerformance?

    (A whitePovEvals: [Double] overload skips re-decoding an already-parsed eval array.)

    bullet/blitz/rapid/classical
  + valid maiaEvidence (11 finite log-likes, eligibleMoveCount > 0)
      → v4.1 ensemble   servingPath = .exactOpponentMaiaEnsemble
                                    or .neutral1500EvidenceExactArtifact
                                       (per maiaEvidence.opponentConditioning)
  + legacy bare maiaLogLikes (11 doubles, no metadata)
      → v4.1 ensemble   servingPath = .exactOpponentMaiaEnsemble  (always)
  + no usable Maia evidence
      → v4.1 no-Maia    servingPath = .moveQualityFallback
correspondence (or any TC with no v4.1 model)
      → v2 binned lookup   servingPath = .moveQualityFallback

    EloEstimatorServingPath.usesMaiaRefinement is true for every case except .moveQualityFallback. The two Maia paths currently share identical v4.1 coefficients — the split exists so a future neutral-conditioned artifact has somewhere to route without touching today's behavior.

    The four dispatch functions in EloCalibrationData disagree on purpose about the raw value their switch doesn't name — in practice always "correspondence", since TimeControlClass has only five cases and the other four are named explicitly. model(forRawTC:) — the v2 lookup — falls back to rapid as the nearest calibrated neighbor, never returning nil. v3model(forRawTC:), v41ensembleModel(forRawTC:) and v41noMaiaModel(forRawTC:) all return nil instead: for those three, nil is the routing signal that sends estimate down to the v2 lookup, so returning a guessed model there would silently defeat the correspondence fallback in the routing table above.

    servingPathLabel(for:) on StatsChartPresentationPolicy renders exactly three strings, one per EloEstimatorServingPath case — "Exact-opponent Maia", "Neutral-1500 Maia (provisional)", "Move-quality model" — with no "pending" or default case, because a move-quality estimate is a valid result in its own right, not a placeholder for missing Maia evidence. estimatedStrengthServingCoverage(for:) tallies a batch of GamePerformance values into an EstimatedStrengthServingCoverage, which carries exactOpponentMaiaCount and neutral1500MaiaCount as separate fields rather than one merged count. Its init(maiaRefinedCount:gameCount:) compatibility initializer exists for callers written before that split was observable: it files every historical Maia-refined count under exactOpponentMaiaCount and leaves neutral1500MaiaCount at zero, which is the correct backward reading since the legacy API had no conditioning field to have gotten it wrong from.

    belowFloor (v4.1)  = rawElo < 100.0            pointElo = clamp(rawElo, 100...3500)
belowFloor (v2)    = accuracy < binnedCenters[0]   // e.g. 26.0 for blitz

baseHalfWidth = belowFloor ? 2×(floor-band MAE)
              : residual-std band whose bandLow <= pointElo (walk ascending, last match wins)

uncertaintySampleMoves = min(nMoves, maiaEligibleMoveCount ?? nMoves)   // v4.1 path;
                          // v2/correspondence uses sampleMoves directly instead
sampleFactor = min(3.0, sqrt(max(1.0, 20.0 / uncertaintySampleMoves)))
otbFactor    = isOTBClassical ? 1.5 : 1.0
halfWidth    = baseHalfWidth × sampleFactor × otbFactor
ci           = pointElo ± halfWidth

    belowCalibrationFloor fires only for very low accuracy (< 26% for blitz) — most beginners stay inside the calibrated range even though the estimate may overshoot, because the Lichess accuracy formula yields ≥ 60% even for 800-rated players. maiaEligibleMoveCount (positions Maia actually scored, after excluding the opening and forced moves) is smaller than raw move count, so a Maia-refined CI uses that tighter count.

    isOTBClassical should be true only for a genuine over-the-board long control mapped into Lichess's .classical bucket — StatsKernel's isOTBClassicalTC flags this when TimeControlClass.estimatedSeconds(fromPGNTag:) >= 6000 (90+30 → 6600s, 120+0 → 7200s), because the Lichess-classical corpus is dominated by 30+0 (1800s) games.

    let tc = TimeControlClass.classify(fromPGNTag: tags["TimeControl"] ?? "")
guard let performance = EloEstimator.estimate(
    evalsJSON: game.annotationEvalsJSON, startIsWhite: true, color: .white, tc: tc,
    isOTBClassical: false, maiaEvidence: maiaTargetEvidence,   // nil → v4.1 no-Maia
    termination: tags["Termination"]
) else { return }
print(performance.elo, performance.ci, performance.servingPath)

    StrengthTracker — the Kalman filter¶

    Value-semantic: updated(with:) returns a new tracker, the receiver is unchanged.

    predVariance      = posteriorSigma² + processTau²
obsVariance        = max(1.0, ciHalfWidth²)     // ciHalfWidth = (ci.upper − ci.lower)/2
posteriorVariance = 1 / (1/predVariance + 1/obsVariance)
posteriorMean      = posteriorVariance × (posteriorMean/predVariance + performance.elo/obsVariance)
posteriorSigma      = sqrt(posteriorVariance)

    public init(priorMean: Double, priorSigma: Double = 300.0, processTau: Double = 50.0)

    priorSigma = 300 starts "very uncertain"; processTau = 50 lets the posterior drift ~±150 Elo over 9 games even absent new evidence, so genuine improvement is followed rather than smoothed away. A wider GamePerformance CI (fewer moves, OTB widening) contributes proportionally less to the update. StatsKernel seeds every tracker at priorMean: 1_500, priorSigma: 300 and the processTau default.

    var tracker = StrengthTracker(priorMean: 1_500, priorSigma: 300)
for performance in performancesInDateOrder {
    tracker = tracker.updated(with: performance)
}
print(tracker.posteriorMean, tracker.ci)   // 68% interval

    Personalizing onto a provider scale¶

    Two causal calibrators sit downstream of the tracker, both prequential: predict using only strictly-earlier labels, emit, then observe(...) the current game's rating. observe is a separate call from the prediction, so no code path can let today's label leak into today's estimate.

    PersonalizedStrengthCalibrator (the slow trend) is offset-only — a single account rarely spans enough of a rating pool to fit a slope reliably.

    offset = median(residuals)     // residuals: actualRating − baseStrength, window 20
                                // available once residuals.count >= minimumOffsetSamples (20)
mean = baseStrength + offset

fallbackHalfWidth: robustScale = max(50.0, 1.4826 × MAD(residuals))
                    offsetSE    = 1.2533 × robustScale / sqrt(n)
                    = sqrt(baseSigma² + robustScale² + offsetSE²)
conformalHalfWidth(coverage):    // once forecastErrors.count >= minimumConformalSamples (20), window 50
  rank = clamp(ceil((n+1)×coverage), 1, n);  return max(1, sorted(forecastErrors)[rank-1])

half68 = conformalHalfWidth(0.68) ?? fallbackHalfWidth
half95 = conformalHalfWidth(0.95) ?? (1.96 × fallbackHalfWidth)

    prediction(baseStrength:baseSigma:) returns a PersonalizedStrengthPrediction (nil during the offset warm-up): mean, interval68/interval95, the offset that produced mean, calibrationSampleCount/forecastSampleCount (how many residuals/forecast errors the calibrator has banked), and usesEmpiricalIntervals — whether the intervals above came from the split-conformal branch or the warm-up fallback formula.

    ChessComGameProjectionCalibrator (the current-game projection) keeps entirely separate residual/forecast-error state per serving path (usedMaiaRefinement) — Maia-refined evidence and the move-quality fallback have different bias and spread, so mixing them would let fallback noise corrupt Maia calibration.

    offset (per path) = median(residualsByPath)     // needs >= minimumSampleCount (20)
mappedPerformance   = clamp(performance.elo + offset, 100...3500)

weight = ceiling × sampleMoves / (sampleMoves + prior)
  Maia path:     ceiling 1.00 (maiaMaximumEvidenceWeight), prior 5.0 (maiaMoveCountPrior)
  fallback path: ceiling 0.60 (fallbackMaximumEvidenceWeight), prior 15.0 (fallbackMoveCountPrior)

cappedDelta = clamp(weight × (mappedPerformance − anchorRating), ±250.0)  // maximumAnchorDelta
mean        = clamp(anchorRating + cappedDelta, 100...3500)

    A 30-move Maia game reaches weight ≈ 30/35 ≈ 0.86; the same game on the fallback path reaches only 0.60×30/45 ≈ 0.40 — the noisier estimator is trusted less relative to the account anchor. Interval construction: propagated (offsetSE combined in quadrature with the performance CI's model sigma, × 1 or × 1.96) during warm-up, or a split-conformal order statistic (finiteSampleQuantile: sorted[clamp(ceil((n+1)×coverage)-1, 0, n-1)]) once ≥ minimumIntervalSampleCount (20) strictly-earlier forecast errors exist for that path. Its forecastErrorWindow is 100 (vs. 50 for the slow-trend calibrator) — the per-game projection sees more raw observations per account, so it can hold a wider window.

    projection(for:) returns an AnchoredGamePerformanceProjection — the "played like" number, distinct from both GamePerformance.elo (evidence-only) and StrengthTracker.posteriorMean (the slow pool-wide posterior). It carries anchorRating and mappedPerformance (the two inputs to mean above), performanceWeight (the weight computed above), mean with its interval68/interval95, the path's offset/offsetStandardError, sampleCount/intervalSampleCount (residual/forecast-error occupancy for that path), usesEmpiricalInterval, and usedMaiaRefinement — the path key, so a caller can tell which calibration state produced a given projection without re-deriving it from the input GamePerformance.

    tracker = tracker.updated(with: performance)
let gameProjection = projectionCalibrator.projection(for: performance)
let personalized = localCalibrator.prediction(
    baseStrength: tracker.posteriorMean, baseSigma: tracker.posteriorSigma
)
// ... emit the point, THEN:
if let actualRating {
    localCalibrator.observe(
        baseStrength: tracker.posteriorMean, actualRating: Double(actualRating),
        personalizedPrediction: personalized
    )
    projectionCalibrator.observe(
        actualRating: Double(actualRating), rawPerformanceElo: performance.elo,
        usedMaiaRefinement: performance.usedMaiaRefinement, projection: gameProjection
    )
}

    StatsKernel.estimateEloHistory — the end-to-end pipeline¶

    1. Flatten every collection's games into candidates: timeControl (Lichess
   formula, artifact selection), displaySpeed (chess.com-facing, grouping),
   a lexically-sortable timestamp (UTCDate/Time → EndDate/Time → Date → date).
2. Sort chronologically (ties: source, username, speed, stable game ID).
3. Group by (source, username, displaySpeed) — never share a tracker or
   offset across providers, accounts, or speed pools.
4. Skip displaySpeed == .daily entirely. The v3 corpus held ZERO
   correspondence rows — measured against 3,378 games, the v2 correspondence
   model produced a near-constant 1937 ± 98 against an actual 765. A flat
   offset, not a measurement.
5. Per group, seed StrengthTracker(priorMean: 1_500, priorSigma: 300),
   PersonalizedStrengthCalibrator(), ChessComGameProjectionCalibrator().
   An unannotated game still updates the projection anchor but yields no
   EloPoint. An annotated game: estimate → update tracker → compute
   projection + personalized prediction (Chess.com sources only) → emit
   EloPoint → THEN observe the rating into both calibrators.
6. Merge all groups' points, re-sort globally by timestamp.

    EstimatedStrengthCalibration is a 3-state lifecycle: .lichessEquivalent (unmodified tracker output; always the state for non-Chess.com sources) → .chessComCalibrating (Chess.com, < 20 strictly-earlier labels — still Lichess-scale) → .chessComPersonalized (≥ 20 samples: offset-personalized trend, optionally a per-game gameProjection). EloPoint.strengthCI95 defaults, when not explicitly supplied, to strengthMean ± 1.96 × halfWidth(strengthCI).

    let aggregate = StatsKernel.compute(from: snapshot)   // includeEloEstimate: Bool = true
let blitzHistory = aggregate.estimatedEloHistory.filter { $0.speed == .blitz }

    StatsKernel.compute returns more than estimatedEloHistory: each opening the library has been played gets an OpeningStat — name, games, wins, draws, losses, and an accuracy that stays nil rather than 0 when no game in that opening was annotated, so a chart never reads a never-analyzed opening as if it were played with zero skill.

    Chart & UI presentation helpers¶

    EloChartPresentation — pure Y-domain/clipping math shared by the SwiftUI Charts and Compose renderers, extracted after a real divergence: Apple's domain unioned shaded intervals, ratings, and percentile-trimmed evidence dots; Android omitted the dots, so points outside the interval band clamped flat against the axis (measured 2.3%–7.1% of points).

    displayedInterval(point) = (chessComPersonalized && gameProjection != nil)
                            ? gameProjection.interval68 : point.strengthCI
unclippedPerformance(point) = same condition ? gameProjection.mappedPerformance
                                              : point.performance.elo

domain(points:showsComparableRating:)
  values = every displayedInterval bound (+ actualRating if showsComparableRating)
  performances = unclippedPerformance(...).sorted()
  n>=20: extend by performances[n/20] (5th pct) and performances[n×19/20] (95th pct)
  else:  extend by performances.first/.last
  padding = max(30, (upper−lower) × 0.05)

clipped(_:to:)  inset = max(1, domainWidth × 0.01); clamp into [lower+inset, upper−inset]

    StatsChartPresentationPolicy — estimatedStrengthSpeeds = [.bullet, .blitz, .rapid, .classical] (Daily excluded, no calibrated model). normalizedMode(_:) accepts only the literal "estimated"; any other stored value fails safe to "rating". estimatedStrengthChartPoints drops the Lichess-reference warm-up points once any point has gone .chessComPersonalized, so a chart never mixes two rating scales. estimatedStrengthServingCoverage(for:) tallies GamePerformance values by servingPath into .label strings like "Maia-refined: 41 of 50 games (41 exact)".

    AccuracyScaleKit — word grade vs. semantic band, no Color mapping (apps switch over Band themselves):

    Range descriptor(_:) band(_:)
    95–100 "Engine-level" .elite
    90–95 "Excellent" .elite
    80–90 "Good" .good
    70–80 "Solid" .solid
    60–70 "Inconsistent" .inconsistent
    50–60 "Shaky" .shaky
    < 50 "Room to grow" .struggling

    The top cut point differs between the two

    descriptor splits 90–95 from 95+ into two labels; band collapses both into one .elite case at the 90 cutoff. A UI showing the word grade next to a band-derived color chip can legitimately show "Engine-level" and "Excellent" against the identical color.

    RecentAccuracyKernel — candidateLimit = 25 is applied to rows with non-empty annotationEvalsJSON before username/color resolution or accuracy decoding, mirroring Apple's SwiftData query (fetch newest 25 annotated rows, then filter). A malformed-but-annotated row still consumes a budget slot even though it yields no Point. pointLimit = 10; results collected newest-first, reversed to oldest-first for left-to-right display.

    Supporting pure math¶

    MaterialBalance.compute(from:) — kings excluded from both counting and value:

    pieceOrder = [.queen, .rook, .bishop, .knight, .pawn]
startingCounts = [Q:1, R:2, B:2, N:2, P:8]     pieceValues = [Q:9, R:5, B:3, N:3, P:1]
capturedByColor[type] = max(0, startingCounts[type] − currentOnBoard[type])
whiteAdvantage        = whiteTotalValue − blackTotalValue

    StreakMath — callers map attempts to [Bool], most-recent last: current(flags) is the trailing run of true (reversed scan, stop at first false); best(flags) is the longest run anywhere (forward pass, reset on false).

    Headless usage today¶

    fianchetto-cli already exposes estimate (runs EloEstimator.estimate against an annotated PGN), track (threads estimates through a StrengthTracker), project (drives ChessComGameProjectionCalibrator), accuracy (AccuracyAggregator's per-phase/per-bucket breakdown), and maia (Maia-native move-quality/rank scoring). Not yet exposed as their own subcommands, despite being pure and headless-safe: chart-domain (EloChartPresentation.domain/.clipped, for a non-Swift consumer to compute the same Y-axis bounds the app draws); serving-coverage (StatsChartPresentationPolicy.estimatedStrengthServingCoverage, to report Maia-refined vs. fallback fraction without the chart UI); recent- accuracy (RecentAccuracyKernel.points, scripting the sparkline budget policy); tc-classify (TimeControlClass.classify and StatsKernel.classifySpeed side by side, useful precisely because they can disagree); and calibration-dump (a diagnostic dump of EloCalibrationData's fitted constants — this one needs a small public shim first, since the type is internal and unreachable from outside FianchettoKit today).
