    Repertoire, openings & traps¶

    The subsystem that names positions, finds the holes in your preparation, and mines drillable material out of your own games. Every type here imports only Foundation and ChessCore — no engine, no persistence, no @MainActor — so the same walks run in the app, on Android, and in a test.

    Four questions¶

    Question Type
    What is this position called? OpeningBook
    What have I prepared? RepertoireBookKernel
    What have I prepared badly? RepertoireAuditKernel
    What will my opponent actually play that I have no answer for? RepertoireOpponentModelKernel

    Three supporting kernels feed them: PersonalOpeningBookKernel (your own game frequencies), PersonalTrapExtractor (knife-edge misses mined from lost games), and PersonalTrapDrill / RepertoireDrillStats (the drill queue and its history).

    The engine-dependent halves stay outside: the app owns the Stockfish and Maia run loops, the SwiftData rows, and the progress reporting. What lives here is the chess algebra and the decision rules those loops feed results into.

    The position key¶

    Two keying schemes exist, and the difference is load-bearing.

    Function Shape
    OpeningBook.positionKey(_:) forwards to Position.positionKey — the raw FEN-derived key
    OpeningBook.epNormalizedKey(_:) 4 fields: <pieces> <side> <castling> <ep> 
    epNormalizedKey(pos) = "<fenField0> <fenField1> <fenField2> <ep>"
  where ep = pos.capturableEnPassantTarget?.algebraic ?? "-"
  (returns the raw FEN unchanged when it has fewer than 4 space-separated fields)

    A raw FEN records an en-passant target after every double push, even when no pawn can actually take. That phantom target is why 1.d4 e6 2.c4 d5 used to miss the canonical Queen's Gambit Declined entry keyed from 1.d4 d5 2.c4 e6: byte-different keys, identical position.

    Every book lookup therefore tries the raw key first, then the normalized key. The order matters: the fallback can only add a transposition match the raw key missed, never override a position the book keys distinctly.

    OpeningBook.epNormalizedKey(forStoredKey:) is the string-only, idempotent form for callers that hold a key but no live Position — migrating legacy repertoire rows, and importing backup rows. It returns its input unchanged when the key has fewer than 4 fields or its EP field is already -, and otherwise re-parses through Position(fen: key), which accepts both the 4-field key shape and a full 6-field FEN.

    The repertoire stores its moves under epNormalizedKey, so transpositions collapse by construction.

    OpeningBook¶

    An immutable ECO/opening database decoded from precomputed JSON or plist. The Apple app supplies openings_precomputed.json/.plist from its bundle; Android supplies its own asset.

    let data = try Data(contentsOf: bookURL)
guard OpeningBook.configureShared(precomputedData: data, isPlist: false) else {
    // Loud failure — every lookup would otherwise silently return nil.
    throw BootstrapError.openingBookMissing
}

let entry = OpeningBook.shared.lookup(position)      // Entry(eco:name:isTerminal:)
let book  = OpeningBook.shared.continuations(for: position)   // [BookMove]
let line  = OpeningBook.shared.findPath(to: anchorKey)        // "d4 d5 c4 c6"

    configureShared returns true only when a non-empty book decoded. A false result leaves the previously installed book untouched — it never installs an empty book over a good one.

    continuations(for:) re-resolves each stored BookMove against the legal move list and, when the resulting position has its own entry, replaces the stored name/ECO with that entry's. A continuation label therefore describes the position the move reaches whenever the book names that position; a move that doesn't resolve against the legal list, or that reaches a position with no entry, keeps its precomputed label.

    ECO family names¶

    openingName(forECO:) answers "what is D00 called?". Picking the answer is not obvious, because dozens of entries share an ECO code.

    load():
  BFS from Position.initial() through the continuation graph,
  stamping a ply depth on every reachable entry key
  (both the raw positionKey and the epNormalizedKey variant at each position).
  Entries unreachable via book continuations get depth Int.max.

ecoNames[eco] = the entry with MINIMUM ply depth,
                ties broken by lexicographically first name.

    This replaced a shortest-name heuristic. "Amazon Attack" (13 chars, 1.d4 d5 2.Qd3, depth 3) is a shorter string than "Queen's Pawn Game" (17 chars, 1.d4 d5, depth 2), so D00 was named after a sideline. Depth gets it right.

    The continuations cache¶

    Each OpeningBook value owns its own NSLock-guarded memo — deliberately not process-global, because an early query against the empty bootstrap book would otherwise poison a position after configureShared installed real data.

    countLimit = 4096
on overflow: drop max(1, storage.count / 10) arbitrary keys

    That ~10% drop is a cheap eviction chosen over true LRU bookkeeping, because opening-book lookups are dominated by hot positions. Empty results are cached too, so a non-book position costs one dictionary probe once.

    Warning

    findPath(to:) is an uncapped BFS. On a miss it walks the entire book to exhaustion. That is why RepertoireBookKernel.anchorPly(searchBook:) defaults to false and coverageIndex must never enable it.

    RepertoireMoves¶

    One in-memory representation serves every walk:

    public typealias RepertoireMoves = [String: [String: String?]]
//                                  ^key    ^san    ^comment

    Keys are epNormalizedKey. A single repertoire's map and a whole-colour union have the same shape, so every lookup is identical for both.

    RepertoireBookKernel.moves(at: position, in: whiteUnion)           // [MoveInfo], SAN-sorted
RepertoireBookKernel.isRepertoireMove("Nf3", at: position, in: whiteUnion)
RepertoireBookKernel.colorUnion(of: [slav.moves, semiSlav.moves])  // last writer wins per (key, san)
RepertoireBookKernel.crossSuggestions(at: position, own: white, opposite: black)

    crossSuggestions surfaces "you also study this from the other side": the opposite colour's moves at this key that this colour has not prepared.

    subtreeEntries(fromMove:at:in:) enumerates the subtree one prepared response roots, walking only that map. It returns [] unless the (rootKey, san) pair actually exists, seeds visited with the root key, then walks from the position after the move.

    Note

    subtreeEntries does no dominator analysis. A position also reachable via a different line in the same map still contributes its entries. Acceptable within one repertoire, where distinct branches rarely share positions.

    Move numbering and anchors¶

    plyIndex(of: position) = (fullmoveNumber - 1) * 2 + (activeColor == .black ? 1 : 0)
position(_, restatedAtPly: ply) sets fullmoveNumber = ply / 2 + 1

numberedLine(moves, startPly:) renders element `offset` at ply = startPly + offset:
  ply even            -> "\(ply/2 + 1).\(san)"      e.g. "4.Nf3"
  ply odd, offset == 0 -> "\(ply/2 + 1)...\(san)"   e.g. "4...Nf6"  (Black leads)
  ply odd, offset > 0  -> "\(san)"                  (Black mid-pair)

    An anchor FEN's own move counters are not trustworthy. An anchor is captured from whatever the board held, and a board loaded from a bare four-field position key carries fullmoveNumber == 1. A real 3...c6 Semi-Slav anchor can therefore claim to be move 1, and everything derived from it reads a full opening too early.

    anchorPly resolves it in strict priority order:

    1. the replayed ply of anchorLineSAN — accepted ONLY when replaying it from the
   game start actually reaches the anchor's epNormalizedKey
2. only when searchBook: true — the replayed ply of OpeningBook.shared.findPath(to:)
3. plyIndex(of: anchoredPosition)   (the FEN's own counters)

    Step 2 is opt-in because it fires the uncapped BFS. Only the iOS gap scan opts in; export, punish generation, and the Android surfaces are main-actor and take the FEN fallback.

    Gap analysis¶

    computeGaps walks a move map looking for uncovered lines. It is an explicit-stack pre-order walk — cooperative-pool threads have ~512 KB stacks, and a 1000+-ply line at the 10⁴ design target overflowed the recursive form. The conversion preserves recursive semantics exactly:

    • visited is claimed on pop (= recursion entry), not on push;
    • children are pushed reversed, so sorted-SAN order pops first;
    • the book-gap emission item is pushed beneath the children, so it pops only after every rep-move subtree has finished updating visited.

    Together those three keep visited-first-wins transposition claims and gap-suppression order identical to the recursion they replaced.

    Three gap sources¶

    (a) USER-TURN gap
    activeColor == color, repMoves.isEmpty, moveSequence not empty
      -> you reached a position of your own and wrote nothing down

(b) BOOK gap  (at an opponent-turn node)
    every OpeningBook continuation SAN not in your SAN set,
    skipped when the resulting key is already visited,
    skipped when repertoire[nextKey] is non-empty (self-transposition)

(c) PERSONAL gap  (at an opponent-turn node)
    replies from personalStats.continuations(atKey:), SAN-sorted, requiring
      faced >= personalGapEncounterThreshold   (= 2)
      not prepared
      NOT listed in the book
      same visited / self-transposition guards
      -> fromPersonalGames = true

    The threshold is 2 because one game is an anecdote and two is a pattern. A personal gap whose own position the book does not name is labelled "<deepest named ancestor> sideline". The unanchored root is excluded from that ancestor chain — the book names the initial position "Starting Position", and a sideline named after it would be noise.

    The self-transposition guard is tested against repertoire directly, never through the sibling index, so a sibling repertoire can never outvote your own prep.

    theoryDepth on a gap is literally OpeningBook.shared.continuations(for: position).count.

    Ordering¶

    1. uncovered before covered   (coveredByRepertoireID == nil first)
2. gamesEncountered  descending
3. theoryDepth       descending
4. moveSequence.count ASCENDING   (shallower first)

    Key 1 is load-bearing, not decoration. Gaps sort by gamesEncountered next, and transpositions into a well-played sibling carry the highest counts — they are exactly what would otherwise float to the top of a list of work you do not owe. On the whole-colour overview every gap is untagged, so key 1 is a no-op there.

    Scoping and coverage¶

    An unanchored repertoire walked from move 1 flags every un-prepared opponent first move as an uncovered line: a 1.d4 e6 repertoire surfaces 1.c4, 1.e4, and friends, none of which pass through its line at all.

    forcedRootAnchor(repMoves:color:):
  position = initial, ply = 0
  while repMoves[key] has EXACTLY ONE prepared move that parses:
      apply it; ply += 1
      if the move just applied was the player's OWN:
          return (position.fen, ply) when an opponent move was seen earlier, else nil
  -> nil when the line is not forced, when there is no own move, or when the
     player is on move at the very root (a White repertoire)

    Scoping only helps when the opponent moves first, which is precisely the case that leaks pre-repertoire lines. scopedWalkRoot picks the repertoire's own anchor when it has one, else this derived root, else the game start — and carries the ply along, because it cannot be recovered from the FEN alone.

    Sibling coverage¶

    A RepertoireTerritory is the set of positions a repertoire answers — its move map's keys plus its reaching line — not the single position its anchor names. Measured on the shipped book: within 6 plies of the Slav root (1.d4 d5 2.c4 c6) there are 24 book edges reaching genuine Semi-Slav positions. One anchor cannot name them all.

    coverageIndex(of: territories):
  rank by  anchorPly DESCENDING     (anchor ply IS specificity; unanchored = 0)
        then caller order ascending
        then id.uuidString ascending
  pass 1: claim every key of every territory's own `moves`   (first claim wins)
  pass 2: for anchored territories only, claim anchorPrefixMap(line:) keys
          — ranked strictly below real prep

    The UUID tie-break is load-bearing: two synced devices can carry equal orderIndex and dateCreated, and Swift's sorted(by:) is not stable. Pass 2 exists because an anchored sub-repertoire stores nothing before its anchor, so its on-ramp positions are absent from pass 1 and a gap one ply before a sibling's anchor would stay untagged.

    anchorPly is called here without searchBook by explicit instruction — enabling it would fire the uncapped BFS once per sibling.

    Coverage is not ownership. coveredByRepertoireID is orthogonal to repertoireID, which stays the repertoire that was scanned; re-filing a covered line under the covering repertoire would hide it from the book that needs no work while the list header still counted it.

    assignGap attributes an overview gap instead:

    normalise each anchor FEN to an epNormalizedKey;
replay the gap's moveSequence from Position.initial(), collecting keysByPly;
iterate plies ascending, replacing the winner only on a STRICTLY greater ply
  -> deepest anchor on the path wins; at equal depth the earliest anchor in the
     caller's sorted order wins (deterministic)
no anchor on the path -> mainID

    let coverage = RepertoireBookKernel.coverageIndex(of: sameColorTerritories)

let root = RepertoireBookKernel.scopedWalkRoot(
    repMoves: slav.moves,
    color: .black,
    anchorFEN: slav.anchorFEN,
    anchorLineSAN: slav.anchorLineSAN,
    searchBook: true          // off-main scan only — this is the uncapped BFS
)

let gaps = RepertoireBookKernel.computeGaps(
    color: .black,
    repMoves: slav.moves,
    anchorFEN: root.fen,
    anchorPly: root.ply,
    owningRepertoireID: slav.id,
    personalStats: PersonalOpeningBookKernel.gamesSnapshot(from: personalBook),
    siblingCoverage: coverage
)

for gap in gaps where gap.coveredByRepertoireID == nil {
    print(RepertoireBookKernel.numberedLine(gap.moveSequence, startPly: gap.startPly),
          gap.openingName ?? "—",
          "faced \(gap.gamesEncountered)×")
}

    Anchor suggestions¶

    suggestAnchors clusters main-assigned gaps and proposes a sub-repertoire for each cluster that is dense by the player's own games.

    defaults: minGaps = 5, minEncounters = 10, minAnchorPly = 3

consider only rooted gaps (startFEN == nil && !moveSequence.isEmpty)

family key = opening name up to the first ":" with " sideline" removed,
             or the first TWO SANs of the move sequence when unnamed

a cluster qualifies when
    members.count >= minGaps  ||  totalEncounters >= minEncounters

its anchor = the LONGEST COMMON PREFIX of the members' move sequences,
    rejected when shorter than minAnchorPly,
    when it fails to replay,
    or when its FEN is already in existingAnchorFENs

eco = the first non-nil member ECO
sort: totalEncounters desc, gapCount desc, name ascending

    The || is deliberate. Prompting off book breadth alone would nag broad-theory players into a dozen repertoires; prompting off what their opponents actually play only suggests structure where their games demand it. minAnchorPly = 3 stops a cluster from anchoring "everything after 1.e4".

    Auditing prepared moves¶

    The audit asks the opposite question from gap analysis: of the moves you did write down, which are weak?

    Both audit walks consume a frozen MovesIndex (typealias MovesIndex = [String: Set<String>]) built up front by movesIndex(from:), so the tree walk needs no store query.

    Config fingerprints¶

    Cached per-position results are only reused when the config fingerprint matches. Swift's Hasher is per-process seeded and would never match across launches, so the kernel folds its own:

    salt   = "maia3-policy-serving-v2"        // maiaServingContractSalt
offset = 1469598103934665603
prime  = 1099511628211

fingerprint = offset
for byte in salt.utf8:  fingerprint = (fingerprint ^ Int(byte)) &* prime
fingerprint = (fingerprint ^ 0) &* prime          // namespace separator
for value in values:    fingerprint = (fingerprint ^ value) &* prime

AuditConfig  folds [movetime, cpLossThreshold, alternativeMustBeWithin, maiaElo]
PunishConfig folds [movetime, topK, opponentElo, swingThreshold,
                    maxExtraPly, maxExtendedNodes]

    The salt is deliberately separate from the Elo estimator's persisted target-evidence contract: audit and punish caches consume Maia through the live serving adapter and must invalidate when that adapter's semantics change, even if the estimator envelope does not.

    AuditConfig Default Meaning
    movetime 1500 Stockfish ms per position
    cpLossThreshold 80 flag threshold — ≈ a third of a piece
    alternativeMustBeWithin 120 max acceptable loss for the engine's #2; beyond it the position has no good alternative
    maiaElo 1500 rating Maia is conditioned on

    Candidates¶

    buildPositionIndex recurses from the anchor (or the standard start) with a hard depth < 40 ply cap, first-visit-wins, keyed by epNormalizedKey — so a candidate builder can recover a full Position from a stored key alone. auditCandidates then keeps only positions where position.activeColor == color (a colour bucket also holds opponent replies, which are not actionable), skips dismissed entries keyed "<positionKey>:<san>", and sorts by (positionKey, userMoveSAN) so an interrupted run resumes predictably.

    AuditCandidate.moveNumber is position.fullmoveNumber, which is only correct because the walk seeds through position(_:restatedAtPly:) when an anchorPly is supplied.

    Scoring¶

    The engine's post-move eval is from the OPPONENT's POV, so:

  userMoveCP = -postEvalCP
  cpLoss     = engineBestCP - userMoveCP

cleanFinding (engine prefers your own move):
  cpLoss = 0, userMoveCP == engineMoveCP == engineBestCP
  — recorded so the position is cached and never re-probed

flaggedFindings(_:threshold:) keeps cpLoss >= threshold, sorted worst-first

    let index = RepertoireAuditKernel.movesIndex(from: whiteUnion)
let candidates = RepertoireAuditKernel.auditCandidates(
    color: .white,
    moves: index,
    anchorFEN: anchorFEN,
    anchorPly: anchorPly,
    dismissed: dismissedKeys      // "<positionKey>:<san>"
)

var findings: [RepertoireAuditFinding] = []
for candidate in candidates {
    let best = await engine.evaluate(fen: candidate.position.fen)   // your adapter
    if best.uci == candidate.userMoveUCI {
        findings.append(RepertoireAuditKernel.cleanFinding(
            for: candidate,
            engineBestMoveUCI: best.uci,
            engineBestCP: best.cp
        ))
    } else {
        var after = candidate.position
        MoveGenerator.applyMoveUnchecked(&after, candidate.userMove)
        let post = await engine.evaluate(fen: after.fen)
        findings.append(RepertoireAuditKernel.flaggedFinding(
            for: candidate,
            engineBestMoveUCI: best.uci,
            engineBestCP: best.cp,
            postEvalCP: post.cp
        ))
    }
}

let flagged = RepertoireAuditKernel.flaggedFindings(
    findings, threshold: config.cpLossThreshold
)

    Counterintuitive prep¶

    A second, quieter result falls out of the same run:

    isCounterintuitive(soundBelow: threshold)
  == cpLoss < threshold        (the move is sound)
  && maiaRank != nil           (Maia actually ran)
  && maiaRank >= 2             (outside Maia's top 2, or absent from the policy)

    A sound move a human at that rating would not naturally find is prep you have to memorise rather than reconstruct — worth flagging even though nothing is wrong with it. maiaRank and maiaTopSAN are var and optional so older cached JSON blobs still decode.

    Punish generation¶

    Where the audit inspects your moves, punish generation inspects the opponent's — specifically the natural-but-unsound replies a repertoire hands you a winning refutation against.

    collectOpponentNodes walks stored moves in sorted() SAN order from the anchor (or Position.initial()), claims each epNormalizedKey in a visited set, and emits a PunishNode at every position where activeColor != color.

    punishSwing(oppBestCP:userBestReplyCP:) = oppBestCP + userBestReplyCP

  The reply position's eval is from the USER's POV, so the reply's value to the
  opponent is its negation: oppBest − (−userBest).

A reply is a punishable blunder at swing >= PunishConfig.swingThreshold (120).

rankedPunishItems sorts by facedCount DESCENDING, then swingCP descending
  — most-faced first, not biggest-swing first.
    PunishConfig Default
    movetime 1500 ms
    topK 4 Maia replies per node
    opponentElo 1500
    swingThreshold 120 (roughly a clean pawn)
    maxExtraPly 4 ply past the stored lines
    maxExtendedNodes 40

    PunishNodeSnapshot is the Codable record of an extended (multi-ply) node, so a resumed generation reuses the engine-discovered node set instead of re-exploring it.

    The drill key is namespaced:

    RepertoirePunishItem.masteryKey = "rep:\(replyPositionKey):\(refutationUCI)"

    That is the third namespace in the shared blunder-mastery store, alongside "trap:" (see PersonalTrapDrill.masteryKey) and the un-prefixed blunder-queue keys. It is keyed on the EP-normalized reply key, so mastery is transposition-aware.

    Opponent modelling¶

    A repertoire can pass both the gap scan and the audit — no unfinished lines, no weak moves — and still collapse the first time somebody plays a natural, unbooked move on move 6, because nothing ever asked what will a human actually do here?

    Maia answers that: a policy trained on human games at a rating band returns what players at that level play, not what an engine prefers.

    The kernel is split in two so it stays pure, and because the node set is bounded by the repertoire — which is what makes running a neural policy over it affordable at all.

    // Phase 1 — which nodes need a policy.
let nodes = RepertoireOpponentModelKernel.opponentTurnNodes(
    color: .white,
    repMoves: whiteUnion
)

// The caller runs Maia. `node.positionKey` is the key the table must use.
var policy: RepertoireOpponentModelKernel.PolicyTable = [:]
for node in nodes {
    policy[node.positionKey] = await maia.topMoves(fen: node.positionFEN, elo: 1500)
        .map { MaiaReply(san: $0.san, probability: $0.probability) }
}

// Phase 2 — the replies you have no answer for, most-often-faced first.
let unprepared = RepertoireOpponentModelKernel.unpreparedReplies(
    color: .white,
    repMoves: whiteUnion,
    policy: policy,
    minimumProbability: 0.05,
    minimumExpectedFrequency: 0.01
)

    Ranking is the point¶

    A raw "Maia likes this and you lack it" list is nearly useless — it is dominated by deep, rare positions. What matters is how often you will actually face the move.

    reach starts at 1.0 at the walk root. Descending a move costs:

  your own move                                -> 1.0
      (your moves are chosen, not sampled, so they cost no probability)
  an opponent move listed in policy[key]       -> its policy mass
  an opponent move absent from Maia's top-K    -> unlistedReplyProbability = 0.01
  policy == nil (phase-1 enumeration)          -> 1.0

emit a reply when it is not prepared and
  probability        >= minimumProbability          (0.05)
  expectedFrequency  >= minimumExpectedFrequency    (0.01)
where expectedFrequency = replyProbability * reachProbability

sort by expectedFrequency descending

    A 40% reply at move 2 outranks a 73% reply down a line reached 5% of the time, and only expectedFrequency expresses that.

    Constant Value Raise it / lower it
    defaultMinimumProbability 0.05 raising shortens the list; lowering surfaces rarer sidelines out of Maia's noisy tail
    defaultMinimumExpectedFrequency 0.01 "fewer than 1 in 100 games" — this is what keeps deep-and-rare noise out
    unlistedReplyProbability 0.01 absence from a truncated top-K means rare, not impossible; using 0 would zero out the subtree and hide every gap beneath a sideline you prepared against

    The walk descends through prepared moves only. Unprepared replies are the output, not paths to follow — by definition there is nothing beyond them to audit.

    Note

    Known limit: visited makes the first path to a transposition win, so a node reachable two ways is scored on one path's reach rather than the sum. That under-states such nodes. Summing would mean abandoning the visited set and risking exponential blow-up on a densely transposing repertoire, so first-path-wins is the deliberate trade — and it matches computeGaps rather than inventing a second behaviour.

    The personal opening book¶

    PersonalOpeningBookKernel turns opted-in collections of your games into a per-position move-frequency tree.

    let tree = PersonalOpeningBookKernel.build(from: [
    PersonalOpeningBookKernel.CollectionGames(
        username: "yourhandle",              // already lowercased
        games: games.map {
            PersonalOpeningBookKernel.GameSnapshot(
                white: $0.white, black: $0.black,
                result: $0.result, moveText: $0.pgn
            )
        }
    )
])

let stats = PersonalOpeningBookKernel.stats(for: position, in: tree)
for move in stats.moves {                     // sorted by games descending
    print(move.san, move.games, move.percentage, move.score)
}

// The Sendable feed into gap analysis.
let snapshot = PersonalOpeningBookKernel.gamesSnapshot(from: tree)

    build:
  walk from startFEN (or the standard start), stopping at plyIndex >= maxPly (30)
  or at the first unparseable SAN;
  at each ply increment the CHILD leaf's games and one of wins/draws/losses
  (result .unknown increments nothing), keyed by the SAN re-canonicalized through
  MoveGenerator.algebraicNotation, under the current epNormalizedKey.

A game is SKIPPED — and does not count toward gameCount — when:
  its move list is empty
  its custom startFEN fails to parse
  PieceColor.ofUser(white:black:username:) cannot resolve the account owner's side

    The 30-ply cap is a bounded-performance decision: deep endgame positions are not useful in a personal book and cost significant memory.

    Counts live on the child leaf, not the parent. build only ever populates children, so a node's own counters stay 0 and stats(for:in:) derives the position total as node.children.values.reduce(0) { $0 + $1.games }.

    percentage = games / totalGames * 100        (0 when total is 0)
winRate    = wins / games                    (0 when games == 0)
score      = (wins + 0.5 * draws) / games    // points per game, 0...1

    stats(for:in:) looks the position up by OpeningBook.epNormalizedKey and returns an empty PositionStats() when the key is absent.

    Cache identity¶

    contentFingerprint(for:) is the deterministic digest over the complete value input build(from:) consumes:

    FNV-1a-64: offset 0xcbf2_9ce4_8422_2325, prime 0x0000_0100_0000_01b3

coalesce collections by normalized username first
  (games moving between equivalent included collections must not change the digest)

mix, in order:
  the schema salt "personal-opening-book-v3"
  the username count
  per sorted username: the username, its game count, and per game
      white, black, result, moveText, startFEN
  (games sorted by white, black, result, moveText, startFEN)

every string is LENGTH-FRAMED — its UTF-8 count is mixed first, byte-by-byte
little-endian over 8 bytes — so component boundaries cannot collide

output: zero-padded to 16 hex characters

    Duplicate games stay duplicated, because their multiplicity genuinely affects move counts.

    Personal traps¶

    The mining premise is narrow on purpose: lost games only, opening phase only, knife-edge positions only. "I picked the wrong move" is the whole feature, so wins and draws are skipped.

    eligibleUserColor(for:collection:alreadyScanned:) requires all four:
  1. a non-empty game.gameID that has not been scanned
  2. a collection with includeInOpeningBook == true and a non-empty username
  3. PieceColor.ofUser(white:black:username:) resolves a colour
  4. the user LOST — result == "0-1" as White, "1-0" as Black

    Stage 1 — the storage-first prefilter¶

    The annotation pass already scored the top two moves per ply. When those persisted scores show a gap comfortably below threshold, the ply cannot be a trap and its expensive live probe is skipped.

    usable only when BOTH
  EvalJSON.decode(annotationEvalsJSON)          .count == mainLine.count + 1
  EvalJSON.decodeOptional(secondBestEvalsJSON)  .count == mainLine.count + 1

skip a ply WITHOUT probing when
  the persisted second score is non-nil
  abs(best)   < 100_000.0     (the mate sentinel)
  abs(second) < 100_000.0
  abs(best - second) < Double(max(0, minGapCp / 2))

    The cut is lenient — half the threshold — because the stored evals come from a deeper search than the trap probe, so a borderline ply is re-probed rather than dropped. The arrays are White-POV centipawns and |best − second| is POV-invariant, so no re-orientation is needed. Unannotated or partially annotated games fall through to the full live probe unchanged, and the skip is behaviorally identical to a probed ply that turned out sub-threshold — so the completeness contract below is unaffected.

    Stage 2 — the authoritative emit rule¶

    per half-move of the main line:
  stop at halfMove >= maxHalfMove                       (default 30 = move 15)
  skip unless node.positionBefore.activeColor == userColor
  probe(fenBefore)
  require BOTH secondMoveUCI and secondScoreCp
  require both scores inside -1_000_000...1_000_000
  require both PV moves to resolve against the legal move list, and to be DISTINCT
  gap = abs(bestScoreCp - secondScoreCp)
  require gap >= minGapCp                               (default 200 ≈ a minor piece)
  require node.move.uci != bestMove.uci
    -> emit PersonalTrapData(gapCp: gap, halfMoveIndex: halfMove + 1, ...)

    A score without its PV move is not evidence that MultiPV 2 completed. That is why both fields are required and the two root moves must be distinct: a truncated engine response must never become a durable negative witness.

    Two entry points, and the difference is the whole safety story:

    Method Behaviour
    extract(from:userColor:detectedAt:probe:) permissive. Swallows errors, returns []. Preview and tests only — must never create a durable scan marker.
    extractCompleted(from:collectionUsername:detectedAt:probe:) authoritative. Throws PersonalTrapExtractionCompletionError instead of skipping, keeping the source retryable.

    Under extractCompleted, the three failure classes throw probeUnavailable / incompleteEvaluation / invalidEvaluation at halfMoveIndex: halfMove + 1 (1-based). Task.checkCancellation() runs at loop top, after each probe, and once more before returning.

    Durable mining witnesses¶

    The problem: a scan performed with one threshold must not suppress work requested with another, and a projection row that arrived late or vanished in a restore must be repairable without re-running the engine.

    let extractor = PersonalTrapExtractor(minGapCp: 200, maxHalfMove: 30)

let completed = try await extractor.extractCompleted(
    from: game,
    collectionUsername: collection.username,
    detectedAt: .now,
    probe: { fen in await stockfish.topTwo(fen: fen) }
)

let witness = try PersonalTrapScanWitness(
    sourceDigest: completed.sourceDigest,
    policy: completed.policy,
    engineRevision: try PersonalTrapProbeRevision.stockfish18(movetimeMs: 1500)
)

let manifest = try PersonalTrapScanManifest(completedScan: completed, witness: witness)
let record = try PersonalTrapScanRecordData(scannedAt: .now, manifest: manifest)

    PersonalTrapCompletedScan's init is fileprivate. The only way to obtain one is extractCompleted — that is the type-level guarantee stopping an empty legacy array from becoming an authoritative noTraps.

    Bound Value
    PersonalTrapExtractionPolicy.currentRevision / PersonalTrapScanManifest.currentSchemaVersion 1
    maximumSupportedGapCp 1 000 000
    maximumSupportedHalfMove 128 (64 full moves)
    PersonalTrapProbeRevision.maximumMovetimeMs 60 000
    PersonalTrapScanWitness.maximumEngineRevisionBytes 256
    maximumCanonicalJSONBytes 512 KiB
    maximumOutputTraps (128 + 1) / 2 = 64

    The 128-ply ceiling is also what guarantees a worst-case result fits the 512 KiB canonical envelope. The policy's throwing init requires revision > 0, minGapCp in 0...1_000_000, maxHalfMove in 1...128; init(from:) routes through the same validating init, so an out-of-range persisted policy fails to decode rather than being trusted.

    engineRevision is a string because a numeric counter cannot express Stockfish/Reckless provenance plus probe configuration without collisions:

    PersonalTrapProbeRevision.stockfish18(movetimeMs:) returns exactly

  stockfish:sf_18;swiftstockfish:18.0.11@a0db83c6ba55ad8ccabe1b5dba67b22840a8d5f0;
  nnue:c288c895ea92+37f18f62d772;multipv:2;movetime-ms:<movetimeMs>

(one line, no wrapping). Throws invalidProbeMovetime outside 1...60_000.

    It must be non-empty, already trimmed, ≤ 256 UTF-8 bytes, and every unicode scalar in 0x20...0x7E — printable ASCII only. sourceDigest must satisfy ExactByteProof.isCanonicalSHA256.

    Canonicalisation and digest¶

    PersonalTrapScanManifest's public init takes a completed scan and checks source identity twice — sourceDigest and policy must both equal the witness's — so output from one snapshot cannot be paired with a witness for another.

    canonicalTraps:
  reject when traps.count > (policy.maxHalfMove + 1) / 2
  per trap require:
    canonical source id == the manifest's
    fen <= 512 bytes; both UCIs <= 16 bytes; sourceOpeningName <= 4_096 bytes
    gapCp >= policy.minGapCp  and  gapCp <= 2_000_000
    halfMoveIndex in 1...policy.maxHalfMove
    correctMoveUCI != userActualMoveUCI
    the FEN parses, and BOTH UCIs resolve to legal moves in that position
  re-quantise timestamps to whole milliseconds:
    Int64((seconds * 1000).rounded()), rejecting non-finite/out-of-range dates
  sort by halfMoveIndex; reject DUPLICATE half-move indices
  every trap must share the first trap's detectedAt and sourceOpeningName

digest = PortableSHA256 over length-prefixed UTF-8 of, in order:
  "personal-trap-manifest:v1", schemaVersion, sourceGameID,
  witness.sourceDigest, policy.revision, policy.minGapCp, policy.maxHalfMove,
  witness.engineRevision, outcome.kind.rawValue, outcome.traps.count,
  then per trap: fen, correctMoveUCI, userActualMoveUCI, gapCp, halfMoveIndex,
                 sourceGameID, sourceOpeningName, epoch-millisecond detectedAt

    Decoding re-derives the digest through the same canonicalising init and rejects on mismatch, so a tampered or drifted stored digest cannot be trusted. The Outcome decoder enforces (.noTraps, empty) or (.traps, non-empty) and refuses to decode past maximumOutputTraps mid-stream rather than materialising an unbounded array; encoding omits the traps key entirely when empty.

    The codec makes the JSON itself canonical:

    encodeCanonical: JSONEncoder with
  outputFormatting  = [.sortedKeys, .withoutEscapingSlashes]
  dateEncodingStrategy = .millisecondsSince1970
  throws manifestJSONTooLarge above 512 KiB

decodeCanonical: reject empty/oversized input, decode with .millisecondsSince1970,
  then require encodeCanonical(manifest) == source BYTE-FOR-BYTE

    That exact re-encode is what rejects unknown fields, alternate key order, and alternate date spellings (nonCanonicalManifestJSON).

    Admission and reconciliation¶

    PersonalTrapScanManifestState classification order:
  trapsFound < 0                                        -> .malformed
  manifestJSON == nil                                   -> .legacy
  canonical decode fails, OR validateRecord fails       -> .malformed
  otherwise                                             -> .versioned(manifest)

isProcessed(matching:rebuildingLegacy:):
  .legacy     -> !rebuildingLegacy
  .versioned  -> manifest.witness == current
  .malformed  -> false        (never suppresses mining)

    PersonalTrapScanManifestContainer supplies that behaviour to both the native DTO (PersonalTrapScanRecordData) and the backup row, so the two format boundaries cannot drift.

    PersonalTrapScanReconciliation.resolve(currentWitness:records:projection:):
  ignore .malformed records
  .legacy sets a flag
  .versioned records whose witness != current are ignored;
     matching ones increment currentRecordCount and select a canonical manifest
     by manifestPrecedes (smaller manifestDigest wins; on identical digests,
     smaller canonical JSON wins)

  if a canonical current manifest exists:
      .processed  only when currentRecordCount == 1
                       && records.count == 1
                       && manifest.validatesProjection(projection)
      else .repair(manifest)
  else:
      .processed when any legacy record exists, else .extract

    Time-bounded engines can produce two different but individually valid outputs under the same release witness. Re-running the engine would manufacture a third conflict — so the resolver selects one validated, content-addressed result and replaces every sibling and projection row with it. The JSON tie-break is retained purely so the resolver stays mathematically deterministic even for a hypothetical digest collision.

    validatesProjection re-canonicalises candidate rows into a fresh manifest with the same sourceGameID and witness and requires full equality with self. Input order is irrelevant, because construction restores chronological order before the digest is taken.

    Drilling and stats¶

    // One read of the shared consecutive-correct counters, then a pure ordering pass.
let mastery = BlunderMasteryStore.history(in: blobStore)        // [String: Int]

let sections = PersonalTrapDrill.groupByOpening(traps)          // encounter order preserved
for (name, familyTraps) in sections {
    let queue = PersonalTrapDrill.prioritized(familyTraps, skipMastered: true) { trap in
        (mastery[PersonalTrapDrill.masteryKey(for: trap)] ?? 0)
            >= BlunderMasteryStore.masteryThreshold
    }
    print(name,
          "worst miss \(PersonalTrapDrill.worstGap(familyTraps))cp",
          "\(queue.count) to drill")
}

    groupByOpening preserves encounter order, so the family that produced the most recent trap sits at the top; traps with an empty sourceOpeningName bucket under "From your game". Section names run through displayOpeningName(for:), which resolves a bare ECO code to a family name when the book knows one — without it the menu reads as a wall of codes.

    isBareECOCode(s):  s.count == 3
                && chars[0] in "A"..."E"
                && chars[1] and chars[2] are ASCII digits
  — no regex, cheap enough to inline at every section render

prioritized(_:skipMastered:isMastered:):
  skipMastered defaults to true (mastered traps are dropped);
  when false they stay but sink to the bottom.
  Within each bucket, gapCp sorts DESCENDING.

worstGap: returns 0 for empty input, so callers render unconditionally

    PersonalTrapDrill.masteryKey(fen:correctMoveUCI:) is the kernel's single definition of the "trap:<fen>:<correctMoveUCI>" format, so a bridge that needs the key can read it from here — the same discipline as RepertoirePunishItem.masteryKey above.

    RepertoireDrillStats records the repertoire drill history — accuracy, streaks via StreakMath, and a last-10 sparkline — capped at 200 attempts per repertoire on every record, with a resetAt fence that unions post-reset attempt IDs into discardedAttemptIDs so attempts already evicted by the cap cannot resurrect a reset history. See Stores & the storage seam for its API.

    Curated opening traps¶

    OpeningTrap is the shipped, Lichess-sourced counterpart to a mined personal trap — a hand-curated knife-edge puzzle from Resources/opening_traps.json.

    The move-list convention comes straight from Lichess:

    moveList[0] = setupMoveUCI    the opponent's auto-played move that creates the puzzle
moveList[1] = correctMoveUCI  the solver's correct reply

fenAtTrap = `fen` advanced by the setup move,
            falling back to the raw `fen` when the setup move is missing or unparseable

ecoFamily                 = first space-separated token of openingTags
openingFamilyDisplayName  = ecoFamily with "_" replaced by " "

difficulty:  ..<1200 -> .easy
             1200..<1600 -> .medium
             default -> .hard

    The thresholds are intentionally generous — most of the shipped puzzles are rated below 1700.

    Headless usage¶

    fianchetto-cli does not yet expose the repertoire walks directly, but two of its commands produce inputs this subsystem consumes:

    • annotate emits the per-ply White-POV centipawn array in exactly the shape the trap prefilter reads from annotationEvalsJSON — [0] is the start position, [i+1] is after ply i, and forced mates are flattened to ±100000, the same sentinel stage 1 tests against. Available from the command line: fianchetto-cli annotate. (The second-best array the prefilter also needs has no CLI producer today, so a CLI-annotated game falls through to the live probe.)
    • maia runs the same Maia3Encoding policy path headless, scoring the played move's log-probability. It does not emit a full top-K PolicyTable, so RepertoireOpponentModelKernel's phase-2 input still has to come from a caller-supplied Maia adapter. Available from the command line: fianchetto-cli maia.

    Warning

    Any command that touches gaps, audits, or opening names must call OpeningBook.configureShared(precomputedData:isPlist:) before its first lookup and check the returned Bool. Against an unconfigured book every lookup returns nil, every continuations returns [], and the whole subsystem degrades silently: every gap's openingName comes back nil, theoryDepth is 0 everywhere, and the entire book-gap source (b) emits nothing at all.
