    Importing user-supplied puzzles¶

    BUILT — the design record, not a recommendation. Raised 2026-08-19 (users should be able to bring puzzles from Lichess or other public sources) and shipped: this package carries PuzzleLink, PuzzleLinkImport, LichessPuzzleLinkDecoder, LichessPuzzleCSVParser, ImportedPuzzleRecord, ImportedPuzzleWidening and PuzzleImportCopy, and the Apple app drives them through its Fianchetto/Engine/PuzzleLinkImportService.swift. Both the recommendation below and the by-link/by-file scope are what the code does.

    This page lived in the Apple app repository as docs/PUZZLE_IMPORT.md until 2026-08-22. Six files in this package cited it and none of them could resolve it, because the design it records governs code that is here, not there.

    The reasoning is kept because it is why the import is shaped this way — the set -versus-line problem in particular does not stop being true. The open questions at the end stand as written; they were never blocking.

    The gap is not the file format¶

    The instinct is to ask "PGN or something else?". That is the second question.

    A puzzle's answer is a SET; every interchange format stores a LINE.

    Fianchetto already knows this. PuzzleNode in FianchettoKit/Sources/FianchettoKit/Train/Combinations/CombinationPuzzleKernel.swift models a solver node as:

    case solverToMove(
    accepted: Set<String>,      // every move that keeps the win within tolerance
    expected: String,           // the one used for hints and length display
    continuations: [String: PuzzleNode]
)
case opponentToMove(replies: [String: PuzzleNode], mainReply: String)

    That is a richer representation than any public puzzle source publishes. It carries several equally-correct solver moves, scripted opponent replies, and — via unresolvedBranches — an explicit record of where the tree does not yet answer. The mined-combination pipeline builds these by probing an engine.

    So the import problem is not "parse a file". It is: a source gives us one line, and a drillable puzzle needs a tree. Everything below follows from that.

    What each source actually carries¶

    PGN¶

    Carries: the position (FEN + SetUp tags), a mainline, variations (RAVs), comments, NAGs.

    Does not carry, under any convention a parser can rely on:

    • Which line is the answer. A RAV is "another line". Nothing distinguishes an equally good solution from a plausible try that loses. Treating RAVs as accepted answers would teach users that inferior moves are correct.
    • Who solves. Puzzle sources conventionally start the position before an opponent move, which is then played for you. PGN has no tag for that.
    • Where the puzzle ends. A game's PGN continues past the tactic.
    • Rating, themes, provenance, licence.

    PGN is a game format. A puzzle is a game fragment plus a claim about it, and the claim is the part PGN has nowhere to put.

    The Lichess puzzle database¶

    A CSV export, published CC0. Columns are approximately PuzzleId, FEN, Moves, Rating, RatingDeviation, Popularity, NbPlays, Themes, GameUrl, OpeningTags.

    Verify before building. The column list and the licence above are from memory and must be confirmed against the current export before any parser is written. Getting the licence wrong is the expensive mistake here, not getting a column wrong.

    Its convention is explicit and machine-readable, which PGN's is not: the FEN is the position before the opponent's move, the first entry in Moves is played for the user, and the rest alternate. It also carries the metadata we have no source for today — a rating and themes.

    Its limitation is the mirror of PGN's: exactly one accepted move per solver node and one scripted opponent reply. High fidelity about a solution, silent about alternatives.

    We already hold a Lichess personal-access token (Fianchetto/Models/LichessTokenStore.swift), so the account plumbing exists; the puzzle database itself is a public file and needs no token.

    Recommendation¶

    1. Do not invent a third puzzle model. Import targets the existing CombinationPuzzle tree. Endgames keep their own archetype model (FianchettoKit/Sources/FianchettoKit/Train/Endgames/EndgameTrainerKernel.swift) because they are generated, not authored — imported puzzles are authored, and that is the combination shape.

    2. Accept the Lichess CSV as the first-class source. Its conventions are stated rather than inferred, and its metadata is real. Map one line into the tree as accepted = [theMove], with every solver node past the first recorded in unresolvedBranches — because we genuinely have not probed the alternatives. That field already means exactly this, and using it keeps the honesty automatic.

    3. Support PGN, but only with a declared convention. Ask the user which side solves and where the puzzle starts, rather than guessing. Treat RAVs as candidates, never as accepted answers.

    4. Widen accepted with the engine, reusing the miner's tolerance rule. This is the step that converts a lossy single-line import into a real puzzle, and it is the reason not to write a second grading path: if imported puzzles graded answers differently from mined ones, the same move would be correct in one drill and wrong in another. One rule, one place.

    5. Make provenance and licence required fields, not optional metadata. CC0 for the Lichess database, unknown for a user's own PGN. A puzzle whose licence we cannot state is one we must not redistribute in a backup, a shared repertoire, or anything else that leaves the device.

    6. Put the whole thing in FianchettoKit, so the Apple, CMP desktop, Android and CLI faces import identically. A per-face importer is four subtly different answers to "is this move correct?".

    Imported puzzles join the existing vendored set¶

    Owner decision, 2026-08-19. They are not a separate pool and not a separate row.

    A first draft of this document called the imported rating "a rating we cannot compare to ours". That was wrong, and backwards. TacticsRatingStore is a PAIRED Elo: every puzzle carries its own rating, and a scored attempt moves the user rating and the puzzle rating by equal-and-opposite amounts. A puzzle rating is not decoration — it is the input that decides how much a solve is worth.

    Our seeds are a three-bucket heuristic:

    case .easy:   return 1200
case .medium: return 1500
case .hard:   return 1800

    A Lichess puzzle rating is on the same Elo scale and is derived from millions of real attempts. So an imported puzzle should seed its rating from the imported value, and it will be better calibrated than the puzzles we mined ourselves. Importing is a rating upgrade, not a rating hazard.

    Three consequences worth stating before anyone builds this:

    • The pool becomes mixed-precision, and that is fine. Both numbers are only priors; the Elo update corrects them from real attempts either way. An imported puzzle simply starts closer to the truth.
    • Filter on rating deviation, not just rating. Lichess publishes Glicko-2 with an RD, and our model has no RD field. Dropping it means treating a barely-attempted puzzle's shaky rating as confidently as a settled one. Importing only puzzles below an RD threshold is a cheap quality gate and the cheapest place to get this right.
    • An imported puzzle's rating will drift away from Lichess's, because our attempts move it. That is correct and wanted: it becomes our rating, for our users. It also means the imported value is a SEED and must never be re-synced from source later, which would silently discard real evidence.

    Scope: by link or by file, never a bundled database¶

    Owner decision, 2026-08-20, and it narrows the feature considerably.

    We do not ship any of the Lichess database, and we do not offer it. No bulk import, no themed subset, no rating band. The earlier framing in this document — "how much of the database?" — asked the wrong question. What users get is the ability to bring puzzles THEY have:

    • By link. A user shares a puzzle URL into the app. This is the natural companion to the existing Share Extension, and it is the primary path.
    • By file. A user opens a file they already hold.

    WHY THIS IS THE BETTER SHAPE, beyond scope. A bundled database would make every licence and provenance question OURS to answer for content we redistribute; a link or a file the user supplies keeps us a reader of what they already have. It also removes the "how much" question entirely, and with it the RD-threshold quality filter this document previously recommended — a filter only matters when you are choosing puzzles on the user's behalf, and now we never are.

    WHAT SURVIVES from the CSV work: the parser is still how a supplied FILE is read, and ImportedPuzzleRecord's required provenance/licence fields matter MORE under this model, not less — a puzzle arriving by link carries whatever the source says, and "unknown" must stay an explicit, auditable answer rather than an absence.

    Engine probing is REQUIRED, and it is affordable. Owner decision: modest probing, which is fast because the position is fixed and the solution is typical. This is what widens accepted from the source's single line into the set a drill can fairly grade — see recommendation 4 above. One line imported and never probed is a puzzle that marks a correct alternative wrong.

    Open questions for the owner¶

    • What does a link import do when the source is unreachable or the URL is not a puzzle? It must fail visibly rather than importing an empty puzzle.
    • Does a link import require network at drill time, or is the puzzle materialised once and stored? Materialised once is the offline-first answer and matches the rest of the app.
    • Do imported puzzles show their provenance in the drill? They are now indistinguishable from ours in the pool, which is the point — but a user who hits a puzzle they dislike may reasonably want to know where it came from.
