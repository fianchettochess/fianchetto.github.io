    Engine & Annotation¶

    How FianchettoKit turns a game into per-move glyphs, quality labels, accuracy numbers, and an eval chart — and how it does that without ever naming a concrete engine.

    The four stages¶

    Stage Owner Input → output
    Collect evals AnnotationDriver.collectEvals(positions:evaluator:onProgress:) [Position] → [AnnotationEval]?
    Normalize UCI AnnotationKernel.extractEval(fromRankedInfos:bestMoveUCI:) [Int: UCIInfo] rank map → AnnotationEval?
    Classify per ply AnnotationKernel.computeAnnotations(inputs:evals:startIsWhite:) inputs + evals → [NodeAnnotationResult]
    Write back AnnotationKernel.applyAnnotations(_:to:game:) results → MoveNode fields

    The rule that makes this portable: the pipeline depends on the role of a position evaluator — the PositionEvaluator protocol — never on a concrete engine. Stages 2 and 3 are pure functions over Sendable value types, so they can run on a detached task and the whole classification is testable without a running engine; only stage 4 touches the non-Sendable MoveNode / Game.

    Choosing an engine¶

    AnnotationEngineKind (String, CaseIterable, Codable, Sendable) is the registry of engines a user may pick to drive annotation: .stockfish → displayName "Stockfish", .reckless → "Reckless".

    AnnotationEngineKind.settingsKey            // "annotationEngine"
AnnotationEngineKind.resolve(nil)           // .stockfish
AnnotationEngineKind.resolve("reckless")    // .reckless
AnnotationEngineKind.resolve("maia")        // .stockfish — unknown values fall back

    resolve(_:) never fails: nil, an unknown raw value, or a value naming an engine that no longer qualifies all resolve to .stockfish.

    Membership is a capability boundary, not a taste: only evaluating search engines — those producing a best move plus a centipawn or mate score per position — belong here. Maia is deliberately absent, because a human-move predictor (policy + WDL) cannot produce the centipawn deltas blunder-grading is built on. Playing against an engine has no such requirement, which is why PlayConfig.Engine is the wider set .maia / .stockfish / .reckless. Its isAvailable currently returns true for every case and exists as the single future home for platform gating.

    Search budget¶

    The two budget functions take the same persisted "annotation thoroughness" preference string and scale differently, because Stockfish is driven by movetime while Reckless anneals by fixed depth.

    annotateMovetime(batch:thoroughness:)      annotateDepth(thoroughness:)
    base = batch ? 500 : 1000  // ms           "fast"     → 10
    "fast"     → base * 6  / 10                "thorough" → 14
    "thorough" → base * 16 / 10                otherwise  → 12   // ply
    otherwise  → base          // incl. nil

    Integer arithmetic throughout, so the six movetimes are exact:

    thoroughness batch: true batch: false
    "fast" 300 ms 600 ms
    nil / anything else 500 ms 1000 ms
    "thorough" 800 ms 1600 ms

    Available from the command line: fianchetto-cli annotate — a request that omits the movetime_ms field falls back to annotateMovetime(batch: true, thoroughness:).

    AnnotationEval — the neutral per-position DTO¶

    Every engine's output maps onto this one struct before entering the kernel:

    public struct AnnotationEval: Sendable {
    public var bestCp: Int              // engine-POV; mate → ±100_000
    public var secondBestCp: Int?       // nil when MultiPV < 2
    public var isMate: Bool
    public var mateIn: Int?             // signed distance, or nil
    public var bestMoveUCI: String      // "" = no move (terminal)
}

    Three conventions carry the design. Engine POV: positive is good for the side to move, in every field; White-POV orientation happens later, once, at the display boundary. The ±100 000 mate sentinel: bestCp flattens a forced mate to +100_000 or -100_000 by sign, so every downstream comparison — win probability, consensus gap, glyph thresholds — works on one Int axis with no special-casing. mateIn is carried separately precisely because bestCp destroys the distance; it is the only place the signed N survives (the missed-mate tactics category needs it) and is nil when the engine did not surface it.

    The memberwise initializer defaults secondBestCp and mateIn to nil, isMate to false, and bestMoveUCI to "".

    Collecting evals¶

    public protocol PositionEvaluator: Sendable {
    func evaluate(fen: String) async -> AnnotationEval?
}

    Only non-terminal positions reach a conformer — the driver fills terminal positions itself. Returning nil means the engine failed or went silent, and aborts the whole sweep.

    Indexing contract for collectEvals(positions:evaluator:onProgress:)

    positions[0]     = the game's start position
    positions[i + 1] = the position AFTER ply i
    result.count     = positions.count      (or the whole call returns nil)

Per position:
    if Task.isCancelled                → return nil
    if terminalEval(for:) is non-nil   → append it, no engine probe
    else if evaluator returns nil      → return nil          (engine gave up)
    if Task.isCancelled                → return nil
    onProgress(i + 1, positions.count)

    Cancellation is checked twice per position — before the potentially second-long probe and again after appending — so a cancelled batch stops promptly rather than at the next position boundary.

    Warning

    onProgress is @Sendable (completed, total) and may run off the caller's actor. A caller updating actor-isolated UI state must marshal explicitly (Task { @MainActor in … }). It defaults to a no-op.

    Terminal positions¶

    AnnotationKernel.terminalEval(for:) returns nil when MoveGenerator.legalMoves(for:) is non-empty — the caller's signal to probe the engine. Otherwise:

    Position bestCp isMate mateIn bestMoveUCI
    Checkmate (no legal moves, in check) -100_000 true 0 ""
    Stalemate (no legal moves, not in check) 0 false nil ""
    Has legal moves — — — returns nil

    Checkmate is mate in 0 from the mated side's POV, matching the engine's own score mate 0 line.

    From raw UCI to a normalized eval¶

    UCI parsing is foundational chess logic, so ChessCore owns it. FianchettoKit keeps two compatibility aliases so every call site — and the Android port — compiles unchanged:

    public typealias UCIInfoLine   = ChessCore.UCIInfo
public typealias UCIInfoParser = ChessCore.UCIOutputParser

    The former FianchettoKit kernel copies were collapsed onto ChessCore's after the FianchettoKit parser's improvements (nps parsing, no mandatory pv token, bestmove (none) handling, bestInfoByRank) were folded into ChessCore. ChessCore.UCIInfo is a strict superset of the old line type — it keeps depth, multipv, scoreCp, mateIn, nps, pv, bestMoveUCI, centipawns, winProbability, displayText, whitePovCentipawns, and the whitePovCp / whitePovMate statics, and adds the .score enum view and .multiPV.

    extractEval(fromRankedInfos:bestMoveUCI:) resolves a [Int: UCIInfo] rank map (as produced by UCIOutputParser.bestInfoByRank) into an AnnotationEval:

    rank 1 missing, or carries no score → return nil   (evaluation unavailable)
rank 1 .mate(m)  → isMate = true,  mateIn = m,   bestCp = ±100_000 by sign of m
rank 1 .cp(cp)   → isMate = false, mateIn = nil, bestCp = cp
rank 2 scored    → secondBestCp = rank2.score.centipawns  (a mate also ±100_000)
rank 2 absent, or present without a score → secondBestCp = nil

    Note the asymmetry: the rank-1 guard is what makes an evaluation available, while rank 2 is optional and its absence simply zeroes the MultiPV gap later.

    EngineScoreAdapter¶

    The sibling conversion boundary between a raw UCIInfo.Score and product logic, producing a mate-aware centipawn value at an explicit point of view. The annotation sweep does not use it — extractEval above is the annotation path's normalizer — but DrillLeniency.leniencyVerdict(best:played:marginCp:) and the repertoire audit take their evaluations through it:

    public enum PointOfView { case sideToMove, opponentOfSideToMove }
public struct Evaluation { public let centipawns: Int; public let mateIn: Int?
                           public var isMate: Bool }   // mateIn != nil

EngineScoreAdapter.evaluation(from: score, pointOfView: .sideToMove)           // Evaluation
EngineScoreAdapter.evaluation(from: info,  pointOfView: .opponentOfSideToMove) // Evaluation?

    Both overloads default to .sideToMove (the UCI convention). The UCIInfo overload returns nil for a score-less line rather than fabricating a cp 0. .opponentOfSideToMove negates both centipawns and mateIn, through a saturating negation that maps Int.min to Int.max — a malformed cp Int.min line must not turn a sign flip into an arithmetic trap.

    MultiPV carriers¶

    Type Shape Notes
    PositionEval bestMoveUCI, scores: [Int: UCIInfo.Score], moves: [Int: String] 1-based rank keys; bestScore falls back to .cp(0); secondBestScore / secondBestMoveUCI return rank 2 or nil. moves defaults to [:] — rank 2's move is only needed as evidence the second PV completed
    RecklessLine rank, evalText, bestMoveSAN, bestMoveUCI Identifiable on rank (1 = best); evalText is pre-formatted White-POV. Origin/target squares are derived by the caller, not stored

    Classifying a ply¶

    computeAnnotations(inputs:evals:startIsWhite:) produces one NodeAnnotationResult per ply. For ply i:

    guard i < evals.count - 1 else break   // short eval array truncates, never crashes

moverIsWhite = (i % 2 == 0) == startIsWhite
wpBefore     = winProbability(evals[i].bestCp)
wpAfter      = 1 - winProbability(evals[i + 1].bestCp)  // after-position is the OPPONENT's POV
wpDrop       = max(0, wpBefore - wpAfter)

gap          = winProbability(evals[i].bestCp) - winProbability(evals[i].secondBestCp)
               or 0 when secondBestCp is nil

opponentMissed = i > 0
              && (winProbability(evals[i - 1].bestCp) - (1 - wpBefore)) >= 0.10
              && wpBefore > 0.55

matchedBestMove = !bestMoveUCI.isEmpty
               && UCIParser.uciToMove(bestMoveUCI, in: positionBefore) == move

winProbability(cp) = 1 / (1 + exp(-0.00368208 * cp))

    The complement on wpAfter is the step worth remembering: the engine evaluated the position after the move, where it is the opponent's turn, so its score is already from the opponent's POV. Subtracting from 1 puts both numbers back in the mover's frame, the only frame wpDrop is meaningful in.

    gap is the single input separating the positive glyphs from "no annotation": with MultiPV 1 it is always 0, and .brilliant, .great, .best, .excellent and .good all become unreachable — every row in the positive band requires gap >= 0.03 or more. opponentMissed fires when the previous mover let a winning position slip and the current mover is still comfortable — it upgrades a .mistake or .dubious to .miss, and is always false at ply 0. An unparseable or empty best-move UCI silently yields matchedBestMove == false.

    Each ply also borrows two numbers from AccuracyAggregator:

    classifyMoveQuality(wpDrop:playedBestMove:)     moveAccuracy(wpBefore:wpAfter:)
    playedBestMove → .best  (overrides all)         drop = max(0, wpBefore - wpAfter) * 100
    wpDrop >= 0.20 → .blunder                       raw  = 103.1668 * exp(-0.04354 * drop)
    wpDrop >= 0.10 → .mistake                              - 3.1668
    wpDrop >= 0.05 → .inaccuracy                    →      min(100, max(0, raw))
    wpDrop >= 0.02 → .good
    otherwise      → .excellent

    The glyph cascade and the quality cascade share the 0.20 / 0.10 / 0.05 / 0.02 thresholds but are separate outputs written to separate fields.

    Available from the command line: fianchetto-cli accuracy.

    The glyph cascade¶

    classifyGlyph(wpDrop:wpBefore:wpAfter:gap:playedBestMove:opponentMissed:involvesSacrifice:absEvalCp:) is an ordered decision table. The first matching row wins.

    ── error band (worst first) ────────────────────────────────────────────
 1  wpDrop >= 0.20                                       → .blunder
 2  wpDrop >= 0.10                → opponentMissed ? .miss : .mistake
 3  wpDrop >= 0.05                → opponentMissed ? .miss : .dubious

── positive band ───────────────────────────────────────────────────────
    notAlreadyWinning = wpBefore < 0.75

 4  wpDrop < 0.02 && gap >= 0.15 && absEvalCp < 50_000
    && notAlreadyWinning && involvesSacrifice            → .brilliant
 5  wpDrop < 0.02 && gap >= 0.08 && wpBefore < 0.40      → .great
 6  wpDrop < 0.02 && gap >= 0.08 && wpBefore < 0.55
    && wpAfter > 0.60                                    → .great
 7  playedBestMove && gap >= 0.03                        → .best
 8  wpDrop < 0.02 && gap >= 0.03                         → .excellent
 9  wpDrop < 0.05 && gap >= 0.06                         → .good
10  otherwise                                            → nil

    Note

    The ordering is part of the contract, not just the thresholds. Row 7 precedes row 8, so a played best move with a 0.05 gap is .best and not .excellent; the error band precedes everything, so a sacrifice that also drops 0.25 win probability is a .blunder, never a .brilliant. The absEvalCp < 50_000 guard on row 4 excludes mate-sentinel positions, and notAlreadyWinning excludes flashy moves in already-won games.

    classifyGlyph never returns .interesting; that case exists for hand annotation and is handled by the consensus severity ladder below.

    Sacrifice detection¶

    involvesSacrifice(positionBefore:positionAfter:) is the Sendable-safe home of the logic; the involvesSacrifice(node:) overload delegates to it.

    moverColor    = positionBefore.activeColor
opponentColor = moverColor.opposite

for index in 0..<64:
    sq = Square.fromIndex(index)
    skip unless positionAfter[sq] is a moverColor piece
    skip if piece.type is .king or .pawn
    skip unless MoveGenerator.isSquareAttacked(sq, by: opponentColor, in: positionAfter)

    if NOT MoveGenerator.isSquareAttacked(sq, by: moverColor, in: positionAfter)
        → true                     // attacked and undefended

    pawnDir = (opponentColor == .white) ? -1 : 1
    for df in [-1, 1]:
        pawnSq = Square(file: sq.file + df, rank: sq.rank + pawnDir)
        if pawnSq.isValid and holds an opponentColor pawn
            → true                 // capturable by a less-valuable piece

→ false

    Kings are excluded because they cannot be sacrificed; pawns because a hanging pawn is too common to be evidence of anything. The second branch catches the defended-but-pawn-attacked case: a defended knight en prise to a pawn is still material down after the exchange. pawnDir points back toward the opponent pawn that would capture — the inverse of that pawn's push direction.

    Point of view¶

    engineEval is stored White-POV: positive means White is better, regardless of whose turn it is. Two helpers move between frames, both applying moverIsWhite = (plyIndex % 2 == 0) == startIsWhite — no-op for White, negate for Black:

    AnnotationKernel.whitePovCpToMoverPov(whitePovCp, plyIndex: i, startIsWhite: true)
AnnotationKernel.whitePovEvals(evals, startIsWhite: true)  // [Double], same length, [0] = start

    Because the ±100 000 mate sentinel carries only a sign, cp values and mate values round-trip through the negation identically. The first is what ConsensusKernel.compare needs; the second builds the eval chart.

    The eval string comes from EvalFormat.formatCentipawnsNoDistance(cp:isMate:):

    isMate → cp >= 0 ? "M" : "-M"          // bare, no distance
else   → sign + (|cp| / 100) + "." + zero-padded (|cp| % 100)
         e.g. +1.34, -0.21             // pure integer arithmetic

    The mate distance is omitted on purpose: bestCp encodes only that a forced mate exists, so printing M5 there would be a fabrication.

    Writing results back¶

    public struct AnnotationComputeInput: Sendable {
    public let positionBefore: Position
    public let positionAfter: Position
    public let move: Move
}

public struct NodeAnnotationResult: Sendable {
    public let glyph: MoveAnnotation?
    public let moveQuality: MoveQuality
    public let moveAccuracy: Double        // 0…100
    public let engineBestMoveUCI: String?  // nil when the before-position had none
    public let engineEval: String?         // White-POV, e.g. "+1.34" / "-M"
}

    AnnotationComputeInput exists purely so the classify pass never touches the non-Sendable MoveNode: extract on the node's actor, cross the boundary with value types, come back with NodeAnnotationResult values.

    applyAnnotations(_:to:game:) clears before it writes — it first nils setAnnotation(nil, on:), moveQuality, moveAccuracy, engineBestMoveUCI, and engineEval on every node in mainLine, then writes results in order, breaking at i >= mainLine.count. Re-annotating therefore always starts from a clean slate, even when the new result array is shorter than the old one.

    annotateNodes(mainLine:evals:game:startIsWhite:) wraps extract → compute → apply in one call. Use the split form whenever the classify pass must run off the main actor.

    End to end¶

    import ChessCore
import FianchettoKit

struct StockfishAnnotator: PositionEvaluator {
    let session: MyUCISession    // your transport; the kernel never sees it

    func evaluate(fen: String) async -> AnnotationEval? {
        var infoByRank: [Int: UCIInfo] = [:]
        var bestMoveUCI = ""
        for await line in session.search(fen: fen, multiPV: 2, movetimeMs: 500) {
            if let info = UCIInfoParser.parseInfo(line) {
                guard info.score != nil else { continue }
                infoByRank[info.multiPV] = info
            } else if line.hasPrefix("bestmove") {
                bestMoveUCI = UCIInfoParser.parseBestMove(line) ?? ""
                break
            }
        }
        return AnnotationKernel.extractEval(fromRankedInfos: infoByRank,
                                            bestMoveUCI: bestMoveUCI)
    }
}

// positions[0] = start, positions[i+1] = after ply i
let mainLine = game.mainLine
let positions = [game.startPosition] + mainLine.map { $0.positionAfter }
let startIsWhite = game.startPosition.activeColor == .white

guard let evals = await AnnotationDriver.collectEvals(
    positions: positions,
    evaluator: StockfishAnnotator(session: session),
    onProgress: { done, total in print("\(done)/\(total)") }
) else { return }   // cancelled, or the engine stopped responding

// Pure classify pass — safe off the main actor.
let inputs = mainLine.map {
    AnnotationComputeInput(positionBefore: $0.positionBefore,
                           positionAfter: $0.positionAfter,
                           move: $0.move)
}
let results = AnnotationKernel.computeAnnotations(inputs: inputs,
                                                  evals: evals,
                                                  startIsWhite: startIsWhite)

// Write pass, on the model's actor.
AnnotationKernel.applyAnnotations(results, to: mainLine, game: game)

// The eval chart uses the White-POV projection of the same array.
let chart = AnnotationKernel.whitePovEvals(evals, startIsWhite: startIsWhite)

    Two-engine consensus¶

    ConsensusKernel is the pure logic behind the Stockfish + Reckless features: higher-confidence annotations, and "critical moments".

    public struct EngineRead: Sendable, Equatable {
    public let cp: Int
    public let isMate: Bool
    public let bestMoveUCI: String
    public var winProbability: Double   // mates clamp to 1.0 / 0.0 by sign
}

    The mate clamp is what makes two engines comparable when they disagree about mate distance: both reads collapse to the same 1.0 or 0.0, so "mate in 4 vs mate in 6" contributes no gap at all. The caller must supply both reads in the same POV — both White-POV or both mover-POV — which is what whitePovCpToMoverPov(_:plyIndex:startIsWhite:) is for.

    compare(a, b, criticalGap: 0.15)

gap      = |a.winProbability - b.winProbability|
sameMove = a.bestMoveUCI == b.bestMoveUCI && !a.bestMoveUCI.isEmpty
critical = gap >= criticalGap                        // 0.15 by default
        || (!sameMove && gap >= criticalGap * 2/3)   // 0.10 when they differ
confidence = (sameMove && gap < 0.05) ? .high : (critical ? .low : .medium)

    Confidence is high | medium | low; Verdict carries agreeOnBestMove, winProbGap, confidence, and isCriticalMoment. Disagreeing on the move lowers the bar for "critical" by a third, because a move disagreement is itself evidence the position is double-edged.

    Glyph reconciliation runs on a signed severity ladder:

    Annotation .brilliant .great .best, .excellent .good, .interesting nil .dubious .miss, .mistake .blunder
    Severity +4 +3 +2 +1 0 −1 −2 −3 
    reconcileAnnotation(a, b)
    severity(a) == 0 or severity(b) == 0 → nil   // one engine finds it unremarkable
    signs differ (one good, one bad)     → nil   // no confident call
    otherwise → abs(sa) <= abs(sb) ? a : b       // the LESS emphatic one; ties keep a

    An emphatic !! or ?? survives only when both engines are that emphatic, which is exactly what cuts single-engine false positives.

    Verdicts persist per ply through ConsensusRecord(ply:agree:winProbGap:confidence:critical:) — ply is 0-based, and confidence is a plain String holding Confidence.rawValue so a decoder does not need FianchettoKit. ConsensusJSON is the plain-array codec in the EvalJSON style: encode returns "[]" on any failure, decode returns [] for empty or malformed input. Neither throws.

    Why raw centipawns are comparable here

    Both Stockfish and Reckless emit normalized centipawns — Reckless's normalize_to_cp mirrors Stockfish's NormalizeToPawnValue — so the single AccuracyAggregator.winProbability(cp:) logistic applies to both on the same win-expectancy scale and no engine-specific calibration is needed. Comparing on win probability rather than raw cp is still the robust axis, because it compresses the tails where cp scales diverge most.

    Provenance and cache validity¶

    Evaluation arrays alone do not record which engine produced them or how much search was spent, so treating any non-empty array as current silently reused Stockfish results after a switch to Reckless. AnnotationProvenance is the durable identity of one primary annotation run:

    Field Meaning
    schemaVersion envelope version — stamped by init, currently 1
    contractVersion version of the orientation / MultiPV / classification / persistence contract owned by AnnotationKernel, currently 1
    engine AnnotationEngineKind
    engineRevision engine + wrapper + network identity, as a string
    searchKind .movetimeMilliseconds or .depth
    searchLimit the numeric budget for that kind
    multiPV lines requested
    includesConsensus whether glyphs were reconciled with a second engine

    Both version fields are stamped by init, never supplied by the caller.

    satisfies(required) — true only when ALL hold

    schemaVersion   == 1  and  required.schemaVersion   == 1
    contractVersion == 1  and  required.contractVersion == 1
    engine          == required.engine
    engineRevision  == required.engineRevision
    searchKind      == required.searchKind
    searchLimit     >= required.searchLimit          ← the only inequality
    multiPV         == required.multiPV
    includesConsensus || !required.includesConsensus  ← one-way superset

    A deeper or longer search may stand in for a weaker request; nothing else relaxes. Results never cross engine, network-revision, search-kind, MultiPV, or contract boundaries. Consensus is a strict superset of a primary-only run, so a consensus result satisfies a primary-only requirement but not the reverse — and recordingConsensus() returns a copy with includesConsensus set to true once reconciliation succeeds.

    let required = AnnotationProvenance(
    engine: .stockfish,
    engineRevision: "sf17-nnue-b1a57f",
    searchKind: .movetimeMilliseconds,
    searchLimit: AnnotationKernel.annotateMovetime(batch: true, thoroughness: "fast"),
    multiPV: 2,
    includesConsensus: false
)

// storedProvenanceJSON is whatever String? your persistence layer kept next to
// the eval array.
if let stored = AnnotationProvenanceCodec.decode(storedProvenanceJSON),
   stored.satisfies(required) {
    // Cached evals are honest for this request — skip the sweep.
} else {
    // Missing, malformed, over 4 096 bytes, a future schema, or a different
    // configuration: all treated as stale, never as current.
    let json = AnnotationProvenanceCodec.encode(required.recordingConsensus())
}

    Structural validity is enforced by the codec at both ends: versions exactly 1, engineRevision non-empty, at most 512 UTF-8 bytes and entirely printable ASCII (0x20...0x7e), 0 < searchLimit <= 60_000, and 0 < multiPV <= 32. encode uses JSONEncoder with .sortedKeys — a stable string for equality and diffing — and returns "" for a structurally invalid value or an encode failure. decode returns nil for nil/empty input, input over 4 096 UTF-8 bytes, malformed JSON, or a decoded value that fails structural validity.

    Display mapping¶

    The glyph, name, and tint live in FianchettoKit so the two apps cannot drift again — they already had, once, on "Dubious" vs "Inaccuracy".

    MoveAnnotation displayGlyph displayName displayRGB
    .brilliant !! Brilliant (0.0, 0.67, 0.67)
    .great △ Great (0.35, 0.55, 0.71)
    .best ✓ Best (0.55, 0.72, 0.30)
    .excellent ✓ Excellent (0.55, 0.72, 0.30)
    .good ! Good (0.45, 0.65, 0.50)
    .interesting !? Interesting (0.45, 0.70, 0.45)
    .dubious ?! Inaccuracy (0.90, 0.64, 0.45)
    .miss ✕ Miss (0.85, 0.55, 0.30)
    .mistake ? Mistake (0.90, 0.50, 0.15)
    .blunder ?? Blunder (0.80, 0.20, 0.20)
    MoveQuality .best .excellent .good .inaccuracy .mistake .blunder
    displayName Best Excellent Good Inaccuracy Mistake Blunder
    displayRGB (0.0, 0.67, 0.45) (0.30, 0.72, 0.40) (0.60, 0.72, 0.30) (0.95, 0.70, 0.20) (0.95, 0.50, 0.20) (0.80, 0.20, 0.20)

    .dubious renders as "Inaccuracy" deliberately: the glyph stays ?! in move lists, but the word users read matches the MoveQuality.inaccuracy band it corresponds to. Blunder red is 0.80 in both tables, on purpose.

    displayRGB is a plain (red: Double, green: Double, blue: Double) triple in 0…1 — no SwiftUI import — so the values are usable from tests, from a headless tool, and from a non-Apple port. Each app wraps it in its own Color.

    Companion value types¶

    MaterialBalance.compute(from:) derives captured material and White's point advantage from a Position, kings excluded:

    pieceOrder     = [.queen, .rook, .bishop, .knight, .pawn]   // canonical display order
startingCounts = queen 1, rook 2, bishop 2, knight 2, pawn 8
pieceValues    = queen 9, rook 5, bishop 3, knight 3, pawn 1

missing(type, color) = max(0, startingCounts[type] - present(type, color))
capturedByWhite = missing for Black,  capturedByBlack = missing for White
whiteAdvantage  = Σ whiteCount·value − Σ blackCount·value

    The max(0, …) clamp is what makes it promotion-safe: three queens on the board produce zero captured queens, not −2. Only non-zero entries are stored.

    ClockCore holds the precise remaining times; the display throttle, Timer, and @Observable wrapper stay per-platform.

    var clock = ClockCore(minutes: preset.minutes, increment: preset.increment)
clock.start(color: .white)
clock.advance(byElapsed: 0.1)     // @discardableResult -> isExpired
clock.switchTurn()                // increment to the mover, THEN flip
clock.stop()
clock.reset()                     // both sides to initialSeconds, .white to move

    switchTurn() and advance(byElapsed:) are both no-ops unless isRunning. Increment lands on the side that just moved, before the flip. advance subtracts from the active side clamped by max(0, …). loser checks White first, so a double-flag reports .white. forceRemaining(white:black:) exists only under #if DEBUG and writes the precise fields — the wrappers' observable display fields are lagging copies and cannot expire the clock.

    Maia-side results. GameAnalysis holds MoveResult(moveIndex:playerMoveRank:playerMoveProbability:) values with 0-based ranks and derives accuracy (share with rank 0), top3Accuracy (share with rank in 0..<3), and averageProbability — all three return 0 for an empty moveResults. GuessEloResult carries whiteElo and blackElo as Int?, where nil means no estimate was produced for that side. EloKernel.bestElo(from:) is the argmax over a [Float: Double] map of Elo bucket → per-game average log-likelihood, returning Int(best.key) and nil for an empty map; the key is Float to match the CoreML output key type, and dictionary iteration order leaves ties unspecified. The Maia scoring path these summarize is reachable headlessly through fianchetto-cli maia, but the CLI emits its own JSON rows — these three types have no CLI surface today.
