    Strength, Elo & accuracy¶

    How FianchettoKit turns an array of engine evaluations into a rating number: per-game accuracy, an offline-calibrated per-game Elo estimate, a Kalman posterior over true strength, and an account-local projection onto a provider's rating scale.

    The subsystem produces three numbers and never collapses them into one, because they answer different questions and carry different uncertainty:

    Number Type Scope What it means
    Performance GamePerformance.elo one game Evidence-only, from this game's moves. Wide CI — single-game accuracy is a weak predictor of rating.
    Strength StrengthTracker.posteriorMean one account pool Slow Bayesian posterior over true Elo, updated game-by-game, shrunk toward the trailing estimate.
    Projection AnchoredGamePerformanceProjection.mean one game "Played like" — this game's mapped performance blended with the most recent strictly earlier provider rating.

    Every type here is pure domain logic: no SwiftUI, no SwiftData, no CoreML, no persistence. Value in, value out, so the whole pipeline runs off the main actor, in a test, or in a command-line tool.

    Accuracy foundations¶

    AccuracyAggregator is the single home of every win-probability and accuracy constant in the codebase. Its library-scale entry point works directly on the white-POV centipawn array the annotation pipeline stores (annotationEvalsJSON), with no Game / MoveNode graph to walk, so accuracy aggregates across a whole library cheaply. (perSideAccuracy(mainLine:) and aggregateAccuracy(for:color:) are separate [MoveNode] helpers, for a game already parsed into memory.)

    Two aggregation orders exist, and the difference is not a rounding artifact:

    winProbability(cp) = 1 / (1 + exp(-0.00368208 * cp))

per-move average  (accuracy(evalsJSON:startIsWhite:color:))
    drop_i   = max(0, wpBefore_i - wpAfter_i) * 100          // mover POV
    acc_i    = clamp(103.1668 * exp(-0.04354 * drop_i) - 3.1668, 0, 100)
    accuracy = mean(acc_i)

mean loss         (accuracy(fromMeanLoss:))
    meanLoss = mean(clamp(drop_i, 0, 100))
    accuracy = clamp(103.1668 * exp(-0.04354 * meanLoss) - 3.1668, 0, 100)

    By Jensen's inequality the per-move average is the higher of the two. The Review pane shows the per-move average; EloEstimator and the calibration corpus use the mean-loss form, because that is how the training rows were labeled. Mixing them would silently bias every estimate.

    whiteFraction(cp:mateIn:) is the eval-bar variant: mate pins to 1.0 (mateIn >= 0) or 0.0, a nil cp with no mate returns 0.5, and everything else delegates to winProbability(cp:).

    Move quality has two independent classifiers measuring different things:

    classifyMoveQuality(wpDrop:playedBestMove:)     // Stockfish, win-prob drop 0…1
    playedBestMove   -> .best      (overrides everything below)
    wpDrop >= 0.20   -> .blunder
    wpDrop >= 0.10   -> .mistake
    wpDrop >= 0.05   -> .inaccuracy
    wpDrop >= 0.02   -> .good
    else             -> .excellent

maiaMoveQuality(rank:probability:)              // Maia, human-move rank/prob
    rank == 0                             -> .best
    rank in 0...2                         -> .excellent
    rank in 0...5  or probability >= 0.05 -> .good
    rank in 0...15 or probability >= 0.02 -> .inaccuracy
    rank in 0...30                        -> .mistake
    else                                  -> .blunder   // rank == -1, outside top-K

maiaMoveAccuracy(rank:probability:) = clamp(sqrt(clamp(p, 0, 1)) * 100, 0, 100)

    The sqrt is deliberate: a linear probability scale collapses every mid-probability human move toward zero.

    GameAccuracy returns three windows, each with its own real sample count — overall / overallSampleCount, phases / phaseSampleCounts, and moveBuckets / moveBucketSampleCounts. Phase is .opening (move ≤ 10), .middlegame (≤ 30), .endgame, by full-move number rather than piece count so the PGN never has to be re-parsed. Buckets are 5 moves wide, keyed on the first move number in the window: bucketStart(forMoveNumber:) snaps to 1, 6, 11, … and bucketLabel(start:) renders "6–10". An absent entry means the side made no moves in that window — callers skip it rather than counting it as 0.

    AccuracyScaleKit grades a 0–100 value. Note the extra split at 95 that the band scale does not have; color mappings are intentionally absent, so apps switch over Band themselves.

    Value descriptor(_:) band(_:)
    95+ "Engine-level" .elite
    90–95 "Excellent" .elite
    80–90 "Good" .good
    70–80 "Solid" .solid
    60–70 "Inconsistent" .inconsistent
    50–60 "Shaky" .shaky
    < 50 "Room to grow" .struggling

    ChessCore cannot depend on FianchettoKit, so the ergonomic accessors on its engine types live here as extensions that delegate to the one logistic: UCIInfo.Score.winProbability / .whiteWinProbability, UCIInfo.winProbability (nil when the line reported no score), and EngineAnalysis.Evaluation.whiteWinProbability. Mate maps to 1.0 / 0.0; .winDrawLoss(w, _, l) returns w / (w + l) — draws are excluded from the denominator — and 0.5 when w + l == 0.

    Available from the command line: fianchetto-cli accuracy.

    Time-control routing¶

    Two classifiers exist and they are supposed to disagree. TimeControlClass selects which calibration artifact serves a game; StatsKernel.classifySpeed selects which provider rating pool it belongs to.

    TimeControlClass.classify(baseSeconds:incrementSeconds:)   // artifact selection
    total = baseSeconds + 40 * incrementSeconds
    total <  180 -> .bullet      total < 1500 -> .rapid
    total <  480 -> .blitz       else         -> .classical
    baseSeconds == nil -> .correspondence

TimeControlClass.classify(fromPGNTag:)
    "", "-", or a non-numeric base -> .correspondence
    otherwise split on "+" (maxSplits: 1); a missing increment is 0

StatsKernel.classifySpeed(tags:event:)                     // rating pool
    1. a definitive correspondence clock in the TimeControl tag -> .daily
    2. event contains "bullet"/"ultrabullet" -> .bullet; "blitz" -> .blitz;
       "rapid" -> .rapid; "classical" -> .classical;
       "correspondence"/"daily"/"let's play"/"lets play" -> .daily
    3. empty TimeControl tag -> .rapid        (no signal is not evidence)
    4. raw base seconds only: < 180 .bullet, < 600 .blitz, <= 1800 .rapid,
       else .classical

    A 5|5 game is the canonical divergence: 300 + 40 × 5 = 500 routes it through the rapid artifact, while Chess.com rates it in the Blitz pool. Both are correct for their own purpose, and StatsKernel carries them side by side on each candidate (timeControl vs displaySpeed). When the TimeControl tag is absent entirely, the estimator's class is derived back from the chart speed rather than being forced to .correspondence.

    TimeSpeed.daily exists because correspondence is a separate rating pool. Folding it into .rapid cost real accuracy: 378 daily games rated 627–1,225 were plotted on the same curve as 2,529 live games rated 202–1,048, and because the two interleave chronologically the chart showed repeated vertical jumps. A chart cannot average two rating systems and mean anything.

    One more clock rule feeds the CI rather than the routing: the private StatsKernel.isOTBClassicalTC(tag:tc:) fires only when tc == .classical and base + 40 × inc >= 6000 seconds. 90+30 (6600) and 120+0 (7200) qualify; 30+0 (1800) does not. The Lichess classical corpus is dominated by 30+0, so genuine OTB long time controls are out of distribution and get a 1.5× wider interval.

    The per-game estimator¶

    EloEstimator is a namespace, not a stateful object. estimate(...) returns nil when the eval array has fewer than 2 entries, or when the player made fewer than 3 moves on the v4.1 path (the v2 path needs at least 1).

    Route Condition Model
    v4.1 ensemble bullet / blitz / rapid / classical and a valid 11-point Maia log-likelihood vector 16-feature standardized ridge
    v4.1 no-Maia the same time controls without usable Maia evidence 12-feature standardized ridge, refit on the v4.1 corpus
    v2 correspondence monotone binned-median lookup on accuracy alone

    The 12 move-level features¶

    Assembled in the fitted CSV column order:

    # Feature Definition
    0 accuracy mean-loss form, via accuracy(fromMeanLoss:)
    1 blunder_rate fraction of this side's moves with win-% loss ≥ 20
    2 mistake_rate … ≥ 10
    3 inaccuracy_rate … ≥ 5
    4 acpl_capped per-move centipawn loss capped at 500, averaged over this side's move count
    5 eval_volatility population std-dev of the post-ply win-% values (divide by n, matching Python)
    6 opp_punish_rate see below
    7 mean_abs_eval mean |win% − 50| over the post-ply values
    8 n_moves this side's move count
    9 plies total plies in the game
    10 is_checkmate hardcoded 0.0 — coefficient 0.0 and std 1.0 in every TC, so the value is moot
    11 is_time 1.0 when the game ended on time 
    opp_punish_rate
    for each opponent ply whose win-% swing in our favor is >= 20:
        find our FIRST subsequent move
        count it "punished" when our own loss on that move <= oppLoss / 2
    rate = punished / opportunities
    no opponent blunder at all -> 0.5      (training-set mean imputation)

EloEstimator.isTimeEnding(termination)                      // module-internal
    trimmed+lowercased == "time" or "time forfeit"           -> true
    contains "timeout vs insufficient material"              -> false  (a draw)
    contains "won on time" / "lost on time" / "time forfeit" -> true
    otherwise                                                -> false

    The is_time rule covers both representations: Lichess's normalized token and Chess.com's prose ("Alice won on time").

    The four Maia posterior features¶

    The ensemble appends a summary of Maia's posterior over the 11-point Elo grid [600, 800, …, 2600] at indices 12–15, mirroring fit_v41_ensemble.py exactly — including the detail that the spread uses the original vector:

    llSpread        = max(logLikes) - min(logLikes)             // before shifting
weights         = softmax(logLikes - max(logLikes))
maia_mean_elo   = Σ eloGrid[i] * w[i]
maia_std_elo    = sqrt(Σ (eloGrid[i] - maia_mean_elo)² * w[i])
maia_argmax_elo = eloGrid[argmax w]

degenerate input (empty, or count != eloGrid.count)
    -> (mean 1200, std 400, argmax 1200, spread 0)

    maia_mean_elo carries by far the largest weight in the fitted vector — 484.47 for bullet, against a 1519.5309 intercept.

    Prediction and routing¶

    standardized ridge (12- and 16-feature alike)
    prediction = intercept + Σ coefficients[i] * (x[i] - featureMeans[i]) / featureStds[i]
    the loop runs over min(x.count, coefficients.count)

eligibility for the ensemble
    candidate log-likes count == eloGrid.count (11)
    AND typed evidence, when supplied, is valid:
        eligibleMoveCount > 0  AND  every log-like finite
    otherwise -> v4.1 no-Maia ridge, servingPath = .moveQualityFallback,
                 maiaEligibleMoveCount = nil

    Typed MaiaBackfillPolicy.TargetEvidence takes precedence over the legacy bare maiaLogLikes vector, and its conditioning survives into the result:

    Evidence EloEstimatorServingPath servingPathLabel
    .exactLichess .exactOpponentMaiaEnsemble "Exact-opponent Maia"
    .neutralLichessPrior .neutral1500EvidenceExactArtifact "Neutral-1500 Maia (provisional)"
    legacy bare vector .exactOpponentMaiaEnsemble "Exact-opponent Maia"
    none / invalid / correspondence .moveQualityFallback "Move-quality model"

    The legacy vector reports as exact-opponent because that API carried no conditioning metadata. Neutral-1500 evidence is currently served by the exact-opponent-trained coefficients — usesMaiaRefinement is true for both Maia cases, and the separate case exists to make that compatibility behavior observable and to give a future neutral-conditioned artifact a routing seam.

    import ChessCore
import FianchettoKit

let tc = TimeControlClass.classify(baseSeconds: 300, incrementSeconds: 5)  // .rapid

guard let performance = EloEstimator.estimate(
    evalsJSON: game.annotationEvalsJSON,   // white-POV centipawns, plies + 1 entries
    startIsWhite: true,
    color: .white,
    tc: tc,
    isOTBClassical: false,
    maiaEvidence: MaiaBackfillPolicy.TargetEvidence(
        logLikes: maiaLogLikes,            // 11 values, one per grid point
        eligibleMoveCount: 17,
        opponentConditioning: .exactLichess
    ),
    termination: tags["Termination"]
) else { return }                          // < 2 evals, or < 3 owner moves

performance.elo                    // clamped point estimate
performance.ci                     // ClosedRange<Double>
performance.accuracy               // mean-loss form, 0–100
performance.sampleMoves
performance.servingPath            // .exactOpponentMaiaEnsemble here
performance.maiaEligibleMoveCount  // 17 — nil on the fallback path
performance.belowCalibrationFloor

    Available from the command line: fianchetto-cli estimate (and fianchetto-cli maia to produce the evidence).

    Confidence intervals and calibration floors¶

    pointElo   = clamp(rawElo, 100.0, 3500.0)
belowFloor = rawElo < 100.0                          // v4.1 paths

baseHalfWidth =
    belowFloor     -> 2.0 * floor-band MAE           (300.0 if the table is empty)
    Maia ensemble  -> residual std for pointElo      (200.0 if empty)
    no-Maia / v2   -> residual std for pointElo      (150.0 if empty)

sampleFactor = min(3.0, sqrt(max(1.0, 20.0 / nMoves)))
otbFactor    = isOTBClassical ? 1.5 : 1.0
ci           = pointElo ± baseHalfWidth * sampleFactor * otbFactor

    The residual-band walk is identical for v2, v3 and v4.1: start at bands[0].std, walk the ascending table, keep the last band whose bandLow <= elo. That makes the top band open-ended and the bottom band the below-all-bands default.

    Two details of the arithmetic are worth knowing. sampleFactor is 1.0 for any game of 20+ owner moves, and on the v4.1 paths it reaches at most sqrt(20/3) ≈ 2.58, so the 3.0 cap never binds there — a game with fewer than 3 owner moves returns nil first. Only the v2 path, which accepts as few as one owner move, can drive it to the cap. And the CI is not re-clamped after the point estimate is, so a floored estimate legitimately reports a lower bound below 100.

    Warning

    belowCalibrationFloor does not mean "this player is weak". On the v4.1 paths it fires only when the raw ridge output lands below 100 Elo. On the v2 path it means accuracy fell below the first bin center — 54.0 for correspondence, 26.0 in the blitz table, 30.0 in the bullet table — and the lookup clamped silently. Most beginners never trip it: the Lichess accuracy formula returns 60 %+ even for 800-rated play, so the model can overestimate a weak player without any flag firing.

    Calibration data¶

    EloCalibrationData is generated — DO NOT EDIT, regenerate with Tools/elo-calibration/generate_swift.py. Its source is the Lichess Open Database (CC0, May 2026). It is module-internal; EloEstimator owns the public API.

    Artifact Shape Contents
    TCModel (v2) accuracy → Elo cubic polyCoefficients [a3, a2, a1, a0], binnedCenters / binnedMedianRatings, residualBands
    V3TCModel 12-feature ridge coefficients, featureMeans, featureStds (12 each), intercept, residualBands — serves v3 and the v4.1 no-Maia fallback
    V41EnsembleTCModel 16-feature ridge the above plus eloGrid (11 points) and cvMAE

    Dispatch is by TimeControlClass.rawValue, and the fallbacks differ on purpose: model(forRawTC:) returns rapid for an unknown key (nearest calibrated neighbor), while v3model, v41ensembleModel and v41noMaiaModel return nil — which is exactly what routes correspondence to the v2 lookup:

    binnedLookup(accuracy:model:)
    fewer than 2 centers, or lengths mismatched -> evalPoly(polyCoefficients)  (Horner)
    accuracy <= centers.first  -> ratings.first
    accuracy >= centers.last   -> ratings.last
    otherwise, between centers[i] and centers[i+1]:
        t   = (accuracy - centers[i]) / (centers[i+1] - centers[i])
        elo = ratings[i] + t * (ratings[i+1] - ratings[i])

    Fitting notes that change how the numbers should be read:

    • Bullet, blitz and rapid were fit with rating-band quota balancing (≤ 15 k rows per band) for better sub-1200 coverage. Classical is an unbalanced fit — its corpus was too small for quotas.
    • Classical v4.1 credits +115.6 Elo of Maia contribution, which is why classical is eligible for Maia backfill at all.
    • v4.1 residual bands are 0–800 / 800–1200 / 1200–1600 / 1600–2000 / 2000+. Classical band MAEs run 270.5 / 155.7 / 147.0 / 150.5 / 168.9; the bullet no-Maia refit, for contrast, runs 400.8 / 363.0 / 238.8 / 296.7 / 536.0.
    • Correspondence has no ridge model at any version, and its lowest v2 band (1200–1400) has an MAE of 591.4. That number is why the stats pipeline refuses to chart daily games at all.

    Tracking strength over time¶

    StrengthTracker is a Gaussian posterior over true Elo with pure value semantics — updated(with:) returns a new tracker and leaves the receiver alone.

    predVariance      = posteriorSigma² + processTau²
ciHalfWidth       = (ci.upperBound - ci.lowerBound) / 2
obsVariance       = max(1.0, ciHalfWidth²)                 // guards a zero-width CI
posteriorVariance = 1 / (1/predVariance + 1/obsVariance)
posteriorMean     = posteriorVariance * (priorMean/predVariance + performance.elo/obsVariance)
posteriorSigma    = sqrt(posteriorVariance)

defaults: priorSigma 300.0, processTau 50.0 (≈150 Elo of drift over 9 games)
StatsKernel seeds every pool at StrengthTracker(priorMean: 1500, priorSigma: 300)

    Because the observation variance is the squared CI half-width, everything that widens an interval — few moves, OTB classical, a below-floor estimate — automatically reduces that game's influence on the posterior. There is no second weighting scheme to keep in sync.

    var tracker = StrengthTracker(priorMean: 1500, priorSigma: 300)   // processTau defaults to 50
for performance in performancesInGameOrder {
    tracker = tracker.updated(with: performance)
}
tracker.posteriorMean    // best single-number strength estimate
tracker.ci               // 68%: mean ± 1σ

    Available from the command line: fianchetto-cli track.

    Account-local calibration¶

    Both calibrators are causal and account-local: they use only strictly earlier labels, and they refuse to answer until they have enough of them.

    PersonalizedStrengthCalibrator — the slow trend¶

    Offset-only by design. One account spans too little of a rating pool to identify a stable slope, while a robust rolling offset removes persistent platform bias without pretending to be a population calibration. A 20-residual window beat 50 across three fast-improving accounts.

    residualWindow 20   forecastErrorWindow 50
minimumOffsetSamples 20   minimumConformalSamples 20

offset = median(trailing 20 residuals of actualRating - baseStrength)
         nil until 20 labels exist -> prediction(...) returns nil
mean   = baseStrength + offset

warm-up intervals (fewer than 20 prior forecast errors)
    robustScale         = max(50.0, 1.4826 * median|residual - median|)
    offsetStandardError = 1.2533 * robustScale / sqrt(n)
    half68 = sqrt(baseSigma² + robustScale² + offsetStandardError²)
    half95 = 1.96 * half68

calibrated intervals (>= 20 prior forecast errors) — split conformal
    rank = clamp(ceil((n + 1) * coverage), 1, n)
    half = max(1, sortedAbsoluteErrors[rank - 1])

    PersonalizedStrengthPrediction.usesEmpiricalIntervals reports which of the two produced the interval.

    ChessComGameProjectionCalibrator — the per-game dot¶

    Here the provider rating is an anchor, not the target. The current game's move count decides how far its mapped performance may pull away from it.

    weight            = 0.60 * moveCount / (moveCount + 15.0)     // 30 moves -> 0.40
mappedPerformance = clamp(performance.elo + pathOffset, 100, 3500)
weightedDelta     = weight * (mappedPerformance - anchorRating)
cappedDelta       = clamp(weightedDelta, -250.0, +250.0)
mean              = clamp(anchorRating + cappedDelta, 100, 3500)

propagated interval arms
    offsetStandardError = 1.2533 * max(50.0, 1.4826 * median|residual - median|) / sqrt(n)
    lowerSigma = sqrt((elo - ci.lowerBound)² + offsetStandardError²)
    upperSigma = sqrt((ci.upperBound - elo)² + offsetStandardError²)
    bound      = mean ± multiplier * weight * sigma      // 1 for 68%, 1.96 for 95%

empirical interval arms (>= 20 strictly earlier projection errors) — conformal
    index = clamp(ceil((n + 1) * coverage) - 1, 0, n - 1)
    half  = sortedAbsoluteErrors[index]

    The weight factor inside the propagated interval keeps uncertainty from collapsing when the ±250 cap binds. The 0.60 ceiling is a deliberate utility-first choice: the previous 0.40 yielded only 27 % evidence on a 30-move game and made the chart a redraw of the provider rating.

    Residual and forecast-error windows are kept separately per serving path, keyed on usedMaiaRefinement, so a partial Maia backfill can never calibrate one path with the other's residuals. A projection is emitted only when an anchor exists, the path-matching window holds ≥ 20 residuals, and the performance passes the validity gate: finite Elo within 100…3500, finite CI bounds bracketing the point, finite accuracy in 0…100, and sampleMoves > 0.

    Prequential order

    Predict, emit, then observe — always. projection(for:) and prediction(baseStrength:baseSigma:) take no current-rating parameter at all, so the current label physically cannot leak into its own estimate. One consequence is easy to miss: a valid rating always advances the anchor, even for an unannotated game or one whose estimate returned nil. Such a game supplies no residual but still gives the next game the right anchor.

    var tracker = StrengthTracker(priorMean: 1500, priorSigma: 300)
var trend = PersonalizedStrengthCalibrator()
var projections = ChessComGameProjectionCalibrator()

// One account pool, oldest first. `performance` is nil when the game is
// unannotated or its estimate returned nil; `rating` is the PGN Elo tag.
for (performance, rating) in chronologicalGames {
    guard let performance else {
        if let rating { projections.observe(actualRating: Double(rating)) }
        continue
    }

    let projection = projections.projection(for: performance)   // strictly earlier ratings
    tracker = tracker.updated(with: performance)
    let personalized = trend.prediction(                        // nil during warm-up
        baseStrength: tracker.posteriorMean,
        baseSigma: tracker.posteriorSigma
    )
    // … emit the chart point here, and only then observe this game's label.

    if let rating {
        trend.observe(
            baseStrength: tracker.posteriorMean,
            actualRating: Double(rating),
            personalizedPrediction: personalized
        )
        projections.observe(
            actualRating: Double(rating),
            rawPerformanceElo: performance.elo,
            usedMaiaRefinement: performance.usedMaiaRefinement,
            projection: projection
        )
    }
}

    Available from the command line: fianchetto-cli project, which wires exactly this order for one account pool.

    The stats pipeline¶

    StatsKernel.compute(from:includeEloEstimate:) turns a GameStatsSnapshot — a persistence-free mirror of the stored games — into AggregateStats. Passing includeEloEstimate: false skips the per-game estimation pass entirely and leaves estimatedEloHistory empty.

    GameStatsSnapshot.Game carries the scalar fields the pass reads, three of which matter here: cachedMoveCount (-1 means unknown and forces PGN tokenization), maiaLogLikesJSON (legacy, deliberately ignored by the estimator), and maiaTargetEvidenceV1JSON (the corrected owner-side-only evidence actually used).

    Accuracy aggregation is sample-weighted everywhere, never an average of averages: each overall / phase / speed / opening / move-bucket accumulator adds value × sampleCount and divides by the summed counts, so a 60-move game outweighs a 30-move one. Two other rules are pre-computed by the kernel so view bodies never re-filter per render:

    weakOpenings     games >= 5 AND wins > 0 AND wins/games < 0.45,
                 sorted ascending by win rate
repertoireGaps   walk the first 12 plies of each game, key positions by
                 OpeningBook.epNormalizedKey, surface any uncovered position
                 hit >= 5 times, labeled with its most frequent opening name

    estimateEloHistory(from:) is the strength pass:

    grouping   (source, username, displaySpeed) — never shared across providers,
                                              accounts, or rating pools
sort       timestamp, source, username, displaySpeed.rawValue, stableID, inputOrdinal
timestamp  "<UTCDate|EndDate|Date|date>T<UTCTime|EndTime|StartTime|00:00:00>"

per group  tracker = StrengthTracker(priorMean: 1500, priorSigma: 300)
           personalization enabled only when source == "chesscom"
per game   projection -> tracker update -> personalized prediction
           -> emit EloPoint -> observe this game's rating

    The entire .daily group is skipped. There is no v4.1 model for correspondence, the v3 corpus contains zero correspondence rows, and measured across 3,378 real games the v2 curve returned a near-constant 1937 ± 98 against an actual 765. That is a flat offset, not a measurement, so it is withheld rather than drawn. Skipping is safe precisely because displaySpeed is part of the group key — daily games only ever anchor each other.

    Which number an EloPoint displays follows one rule:

    Condition strengthMean / intervals calibration
    a personalized prediction exists its mean, interval68, interval95 .chessComPersonalized
    Chess.com pool still warming up tracker.posteriorMean, tracker.ci, mean ± 1.96σ .chessComCalibrating
    any other provider the same tracker values .lichessEquivalent

    Alongside those, each point carries the untouched performance, the optional gameProjection, actualRating (emitted for comparison — it becomes a label only after the point exists), calibrationSampleCount, usesEmpiricalIntervals, and pool identity (speed, source, username, and accountID, which is "source|username" lowercased). timestamp falls back to date when the PGN has no UTC time, keeping calibration deterministic within a day, and an omitted strengthCI95 is derived as mean ± 1.96 × (CI68 half-width).

    let snapshot = GameStatsSnapshot(
    collections: [.init(username: "alice", source: "chesscom", games: games)],
    whiteRepertoireKeys: whiteKeys,
    blackRepertoireKeys: blackKeys
)

let stats = StatsKernel.compute(from: snapshot)   // includeEloEstimate defaults to true
stats.overallAccuracy                  // sample-weighted, not an average of averages
stats.accuracyByPhase[.middlegame]
stats.accuracyByMoveBucket[11]         // the "11–15" window
stats.weakOpenings.first?.name         // pre-filtered and pre-sorted
stats.estimatedEloHistory.last?.strengthMean

// Or just the strength pass, plus a label for which artifact served it:
let points = StatsKernel.estimateEloHistory(from: snapshot)
let coverage = StatsChartPresentationPolicy.estimatedStrengthServingCoverage(
    for: points.map(\.performance)
)
coverage.label   // "Maia-refined: 7 of 10 games (5 exact, 2 neutral-1500 provisional)"

    OpeningStat.accuracy stays nil when no game in that opening was annotated, so the UI never shows a misleading 0 %. AggregateStats.hasChessComGames is set from a PGN Site tag containing "chess.com" and drives the scale-caveat footnote — Lichess and Chess.com ratings are not directly comparable.

    Presentation policies¶

    StatsChartPresentationPolicy holds the tiny decisions that Apple and Android must not answer differently. It imports nothing at all — not even Foundation. Only the exact string "estimated" selects that mode; legacy, malformed, or future values fail safe to "rating" rather than leaving a segmented control with no selection, and effectiveMode(storedMode:canShowEstimated:) additionally forces "rating" when no estimate is available. estimatedStrengthSpeeds is [.bullet, .blitz, .rapid, .classical]; normalizedEstimatedSpeed(_:) folds .daily to .rapid. servingPathLabel(for:) returns the three strings in the routing table above — a non-Maia estimate is described as the move-quality model, never as "pending", because some games can never produce eligible Maia evidence and their engine-derived estimate is still valid.

    EstimatedStrengthServingCoverage counts the paths behind a chart series: maiaRefinedCount is exact + neutral, moveQualityFallbackCount is max(0, gameCount - maiaRefinedCount), and the compatibility initializer init(maiaRefinedCount:gameCount:) files all historical values under the exact-opponent path.

    RecentAccuracyKernel is the Review sparkline's selection policy, and its budget rule is subtle:

    candidateLimit 25   pointLimit 10        rows arrive newest-first

empty annotationEvalsJSON  -> skip, does NOT consume the budget
budget exhausted (25 rows) -> stop
otherwise charge 1, then resolve username/color (lowercased against white/black)
and compute accuracy; failures still consume their charge
10 successful points       -> stop
finally reverse to oldest-first for left-to-right display

    A non-empty but malformed payload does consume the budget: that row passed the storage-level annotation predicate but cannot safely produce a point. StreakMath.current(_:) / best(_:), which back the drill streak counters, are documented on the Analysis math page.

    Reproducing it from the command line¶

    fianchetto-cli links the same FianchettoKit build the app ships, so its numbers cannot drift from the serving path.

    Kit surface Subcommand
    the Stockfish annotation path that produces white_pov_evals annotate
    AccuracyAggregator formulas, per-move labels, phase split accuracy
    MaiaBackfillPolicy grid / conditioning / qualification + scoring maia
    EloEstimator.estimate — all three routes, CI, floor flag estimate
    StrengthTracker Kalman over a sequence track
    the StatsKernel serving order: projection → tracker → personalization project

    A whole account pool, end to end:

    fianchetto-cli annotate < games.jsonl       > evals.jsonl
# annotate emits only id / white_pov_evals / engine, so join each row with its
# start_is_white, color and clock fields before estimating
fianchetto-cli estimate < estimate-in.jsonl > estimates.jsonl
fianchetto-cli track    < estimates.jsonl   > posterior.jsonl

    estimate output is directly compatible with track input (id, elo, ci_low, ci_high) — the one hop in the chain that needs no join — and track defaults to the app's own priors: prior mean 1500, prior sigma 300, --process-tau 50. project takes one account pool per run and expects games in chronological order — grouping by provider × account × speed stays with the caller, exactly as StatsKernel does it.

    Several surfaces on this page have no subcommand: the full snapshot → AggregateStats pass, StatsKernel.classifySpeed, the raw 12-feature vector (EloEstimator.v3Features is module-internal, exposed only for parity tests), EstimatedStrengthServingCoverage, AccuracyScaleKit, and RecentAccuracyKernel. Use the kit API directly for those.
