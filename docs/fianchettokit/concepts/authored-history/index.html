    Authored History & the Mutation Journal¶

    How user-authored notes and board marks survive concurrent edits across devices, backup/restore, and legacy migration — a small causal CRDT kernel (Sources/FianchettoKit/Authored), not generic last-write-wins.

    Overview¶

    Everything else in the library — imported games, engine evaluations, cached analysis — can be recomputed or re-fetched. A user's notes and board-mark annotations cannot, so they're reconciled by a purpose-built kernel instead of the ordinary "newest updatedAt wins" merge that suffices for everything else. The kernel tracks causality with a bounded vector clock per (logicalGameID, field) pair, never a timestamp: two edits are either causally ordered (one observed the other) or concurrent (neither did), and concurrent edits are never silently discarded, only surfaced as a conflict. The two independently reconciled fields are AuthoredField.notes and .boardMarks.

    The rest of this page follows data through five layers: the causal model (vector clock, immutable revision, canonical values); the reconciliation algorithm, AuthoredReconciler, called by every platform and every backup/restore path; the edit path, turning one keystroke into a crash-safe committed revision; backup, restore, and recovery; and supporting infrastructure — the frontier cache, promotion-stable game identity, and retention/migration policy.

    The causal model¶

    AuthoredReplicaID and AuthoredVectorClock¶

    AuthoredReplicaID is a validated installation identity — commonly a lowercase UUID, though the format isn't UUID-specific so a legacy importer can own a separately-namespaced synthetic head. It's capped at maximumUTF8Bytes = 96 bytes, ASCII charset [0-9A-Za-z\-._].

    AuthoredVectorClock is a [AuthoredReplicaID: UInt64] map bounded at maximumReplicaEntries = 32 replicas. Its relation(to:) is the whole of CRDT causality for this kernel:

    relation(lhs, rhs):
    for each replica present in lhs OR rhs:
        hasGreater |= lhs[replica] > rhs[replica]
        hasLess    |= lhs[replica] < rhs[replica]
        if hasGreater && hasLess: return .concurrent   // short-circuits
    if hasGreater: return .dominates
    if hasLess:    return .dominated
    return .equal

    A zero counter is invalid, not normalized away

    validate() rejects any counter of 0 outright instead of dropping the entry. Silently dropping a zero-valued replica entry would make a real concurrent edit look like dominance.

    AuthoredHead — the immutable per-replica revision¶

    AuthoredHead<Value> is the causal fact itself: schemaVersion, logicalGameID, authorReplicaID, clock, value, authoredAtMilliseconds. currentSchemaVersion = 1, maximumLogicalGameIDBytes = 512, and maximumEncodedBytes = 900 * 1_024 — deliberately under CloudKit's 1 MiB record ceiling, checked after JSON escaping (encoded()), not estimated from raw text length.

    New heads are never built directly by editors — authoring(observing:) is the one place a new clock entry gets minted:

    authoring(logicalGameID, authorReplicaID, value, observing: heads, authoredAtMilliseconds):
    guard heads.count <= 32                              // maximumReplicaHeads
    guard every head.logicalGameID == logicalGameID
    guard heads have distinct (replicaID, logicalGameID, field) storage keys
    joined = merge(heads.map(\.clock))                   // per-replica max()
    clock  = joined.incrementing(authorReplicaID)         // +1 for this replica
    → the resulting head causally dominates every branch the editor actually saw

    Every head also carries a revisionProof, a stable SHA-256 tie-break for otherwise-indistinguishable candidates — explicitly documented as "never used as a substitute for the vector clock":

    revisionProof = SHA256(length-prefixed concat of:
    logicalGameID, field.rawValue, authorReplicaID.rawValue,
    value.sha256, String(authoredAtMilliseconds),
    "replica=counter" for each clock entry, sorted by replica)
    Type Kind Key facts
    AuthoredReplicaID validated string 96-byte ceiling, [0-9A-Za-z\-._]
    AuthoredVectorClock bounded map 32 replicas max, zero counters rejected
    AuthoredHead<Value> immutable fact schema 1, 512-byte game ID, 900 KiB encoded ceiling
    AuthoredHeadStorageKey (replicaID, logicalGameID, field) identity of one mutable compact-head row
    AuthoredHeadCandidate<Value> {copyID, isAnnotatedCopy, head} one physical copy's context; annotation never affects dominance
    AuthoredFieldIdentity Comparable (logicalGameID, field) the coarser identity one field's entire causal history is grouped under — ordered by logicalGameID, then field.rawValue, so backup, health, and restore adapters share one grouping instead of each inventing their own

    AuthoredNotesHead and AuthoredBoardMarksHead are the two field-specialized typealiases actually threaded through the reconciler and edit path — AuthoredHead<AuthoredNotesValue> and AuthoredHead<AuthoredBoardMarksValue> respectively. AuthoredMutationPlanner.makeIntent and the edit-path examples below traffic in these, not the bare generic AuthoredHead<Value>.

    Canonical values¶

    AuthoredCanonicalValue is the protocol every reconciled payload implements: a static field, a static maximumPayloadBytes, a canonicalPayload, and a sha256. Two conformers exist today:

    Value type Field Ceiling Canonicalization
    AuthoredNotesValue .notes 256 * 1_024 (256 KiB) exact UTF-8 bytes; U+0000 rejected
    AuthoredBoardMarksValue .boardMarks 768 * 1_024 (768 KiB) BoardMarkDocument.decodeStrict(source).encoded()

    Notes preserve Unicode normalization and whitespace exactly — the proof is over the exact bytes shown to the user. U+0000 is rejected on every platform because Apple's SwiftData/SQLite bridge truncates strings at that scalar; rejecting it everywhere keeps the portable value lossless instead of allowing a snapshot an Apple store can't reproduce. Board marks decode/re-encode through BoardMarkDocument before hashing, so two physically different JSON strings meaning the same marks hash identically; their 768 KiB ceiling is a raw parser bound, while the authoritative CloudKit safety net is AuthoredHead's 900 KiB encoded-bytes ceiling (nesting this JSON inside a head can expand quotes and control characters substantially).

    let notes = try AuthoredNotesValue(text: "Missed 23...Qxh7+ here.")
let marks = try AuthoredBoardMarksValue(source: boardMarksJSON)

notes.sha256            // hex SHA-256 over the exact UTF-8 bytes
notes.canonicalPayload   // the exact text

    AuthoredReconciler — the reconciliation algorithm¶

    AuthoredReconciler<Value> is the one piece of logic every platform, both backup paths, and restore all call, so replica capacity, conflict classification, and tie-break ordering can never drift between adapters. Causality always outranks annotation quality: isAnnotatedCopy only ever selects a projection representative among causally maximal, SHA-equivalent copies — never dominance, never a divergent branch.

    selectSameReplicaHistory¶

    Collapses one replica's own head history down to its causal maximum:

    selectSameReplicaHistory(heads, limit: 64):
    guard heads.count <= limit                     // maximumCandidates
    guard all heads share one AuthoredHeadStorageKey
    dedupe by revisionProof
    detect corruption: two heads with an *identical* clock but different
        values → hasRelationFailure = true (independent of scan order)
    reduce to the causally-maximal subset (drop anything another head dominates)
    if maximal.count != 1 OR hasRelationFailure:
        hasCausalConflict = true
        active = lexicographically-least maximal head,
                 ordered by (revisionProof, then full encoded JSON bytes)
    else:
        active = the sole maximal head
    → {active, alternates: other maximal heads, superseded, hasCausalConflict}

    reconcile¶

    Reconciles across replicas — answers "what is this field's value right now, across every device":

    reconcile(candidates):
    guard candidates.count <= 64                   // maximumCandidates
    guard all candidates share one logicalGameID, distinct copyIDs
    drop dominated candidates → causally-maximal set
    group the maximal set into AuthoredValueBranch<Value>s by SHA-equivalence
        (sha256 AND canonicalPayload both match)
    each branch's representative: isAnnotatedCopy wins first,
        then stable (copyID, storageKey, revisionProof) ordering
    preferred = first branch's representative (display choice only)
    hasConcurrentConflict = branches.count > 1

    AuthoredValueBranch<Value> is just {representative, equivalentCandidates} — one causally-maximal, SHA-equivalent value plus every physical copy that carries it, so a branch is a projectable value, not a single head. Every branch stays in valueBranches even when hasConcurrentConflict is true — nothing is discarded; the caller decides whether to surface a conflict-resolution UI.

    planDirectProjection — the witnessed-value rule¶

    What a live app or a restore actually applies to a visible row. Its central invariant: every direct value must be historically witnessed by a known compact head or immutable revision, or the call fails with .unexplainedDirectValue rather than accepting an unexplained byte string as fact.

    planDirectProjection(frontierCandidates, historicalWitnesses, directCopies):
    guard directCopies have distinct copyIDs
    guard frontierCandidates.count <= 64     // maximumDirectProjectionFrontierCandidates
    guard historicalWitnesses.count <= 512   // maximumDirectProjectionHistoricalWitnesses
    guard every directCopy.value is witnessed by some known head's value
          (else: .unexplainedDirectValue)

    select each replica's active frontier head (selectReplicaHistories)
    historical witnesses NOT causally covered by that compact frontier
        rejoin reconciliation instead of being hidden
    reconcile the union →
        .noCausalState        (no history at all for this field)
        .converge(value:, changedCopyIDs:)   (unique non-conflicting branch)
        .concurrentConflict   (more than one branch survives)

    Each element of directCopies is an AuthoredDirectValueCopy<CopyID, Value> — {copyID, value, isAnnotatedCopy}. It plays the same role as AuthoredHeadCandidate above but for a physical row that carries a value with no causal head of its own yet, which is exactly the shape a live import or a restored backup copy starts from.

    The "rejoin" step matters: a physical copy can legitimately still show an older value after another copy advances the shared compact head — export retains that copy's exact immutable revision, and if the compact frontier doesn't causally cover it, that older fact stays part of the live decision instead of being quietly overwritten.

    let candidates = try [headFromPhone, headFromDesktop].map {
    try AuthoredHeadCandidate(
        copyID: $0.authorReplicaID.rawValue,
        isAnnotatedCopy: false,
        head: $0
    )
}
let reconciliation = try AuthoredReconciler<AuthoredNotesValue>.reconcile(candidates)

if reconciliation.hasConcurrentConflict {
    // present reconciliation.valueBranches for the user to pick a winner
} else if let preferred = reconciliation.preferred {
    display(preferred.head.value.canonicalPayload)
}

    Storage key grammar — AuthoredBlobRecordCodec¶

    Two namespaces exist because a single generic row can't support both "what does this replica currently say" (mutable, rewritten in place) and "prove exactly what was ever said" (append-only, never overwritten):

    compactHeadNamespace       = "authoredHead.v1."
immutableRevisionNamespace = "authoredRevision.v1."

compact head key (one row per replica, rewritten on every edit):
  authoredHead.v1.<field>.<base64url(logicalGameID)>.<base64url(replicaID)>

immutable revision key (one row per revision, never rewritten):
  authoredRevision.v1.<field>.<base64url(logicalGameID)>.<base64url(replicaID)>.
      <20-digit zero-padded authorCounter>.<valueSHA256>.<revisionProof>

    Tokens are base64url (+→-, /→_, = stripped). decodeToken() bounds any incoming key token to 683 UTF-8 bytes before decoding — the exact base64url expansion of the 512-byte logicalGameID ceiling — so a hostile or corrupted key can't amplify parsing cost. maximumCompactHeadCandidates = 64 bounds how many same-key compact siblings any adapter reconciles at once; a backup sidecar excludes the active row, so its ceiling is maximumCompactHeadAlternates = 63.

    DecodedRecord case Storage role Mutable?
    .notesHead / .boardMarksHead compact per-replica projection yes — replaced on edit
    .notesRevision / .boardMarksRevision append-only causal fact no — write-once

    Because both shapes wrap the identical AuthoredHead<Value> payload, AuthoredBlobRecordCodec.relation(_:_:) compares any two decoded records regardless of role. immutableRevisionProjection(for:) derives the canonical immutable row for any validated compact head, and rekeying(_:to:) losslessly moves a causal fact from a deterministic pre-marker alias key to its promoted canonical logicalGameID — clock, author, value, and timestamp stay byte-identical; only the key and proof regenerate. That's what lets game identity promotion fold a duplicate copy's causal history into its canonical lineage losslessly.

    The edit path¶

    One user edit becomes a durable, causally-sound revision through four cooperating pieces, each owning one safety property:

    AuthoredMutationPlanner.makeIntent   → builds the CAS intent (pure, no I/O)
AuthoredSemanticCAS.plan             → decides commit / repair / conflict
AuthoredMutationBlobWriter           → the actual two-phase durable write
AuthoredMutationIntentJournal        → single-slot WAL bridging the two writes

    AuthoredMutationPlanner.makeIntent builds a LibraryData.PendingAuthoredMutation from an expected/desired field projection plus the visible causal frontier. Ordinary edits advance exactly the value branch the editor's own direct row showed (expected); if another copy already advanced past that branch, the planner falls back to the exact witnessed historical revision instead of manufacturing a precursor, and if the local replica's own head diverged onto a branch not superseded by this edit, planning fails with .localReplicaBranchWouldBeLost rather than clobbering it. An explicit conflict resolution instead passes resolvingFrontierToken — a PortableSHA256 hash over the exact reviewed frontier rows, sorted by (key, dataJSON) — proving the resolution applies to precisely that state; a changed frontier throws .directValueChanged.

    let intent = try AuthoredMutationPlanner.makeIntent(
    incarnation: incarnation,
    logicalGameID: logicalGameID,
    replicaID: replicaID,
    field: .notes,
    expected: expectedProjection,
    desired: desiredProjection,
    frontierRows: frontierRows,
    authoredAtMilliseconds: Int64(Date().timeIntervalSince1970 * 1_000)
)

try AuthoredMutationIntentJournal.admit(intent, to: blobStore)
try AuthoredMutationBlobWriter.writeImmutableFacts(intent, to: blobStore)
try AuthoredMutationBlobWriter.writeCompactHead(intent, to: blobStore)
try AuthoredMutationIntentJournal.clear(intent, from: blobStore)

    AuthoredSemanticCAS.plan is the exact decision table every storage adapter applies to a direct-value write — persistence-neutral, no I/O:

    plan(current, expected, desired, mode):
    if current == desired:
        if mode == .resolveKnownFrontier AND current != expected:
            → .conflict(currentValue: current)
        → .repairMetadata(base: mode == .ordinaryEdit ? desired : expected)
    else if current != expected:
        → .conflict(currentValue: current)
    else:
        → .commitDirectValue

    AuthoredMutationBlobWriter writes in two phases and read-back-verifies every byte — no last-write-wins. Immutable rows first: a pre-existing row at the same key with a different decoded value throws .immutableFactConflict; a byte-different but semantically identical row is rewritten to canonical bytes so SHA manifests don't retain two physical representations of one fact. The compact head second, and only if AuthoredBlobRecordCodec.relation(desired, existing) == .lhsDominates and the existing head's own immutable revision is already among the intent's own immutable rows from phase one — writeCompactHead checks this, it does not backfill; an intent that omits that revision fails closed with .compactHeadConflict instead.

    AuthoredMutationIntentJournal is the single-slot WAL bridging those two writes (blobKey = FileJSONBlobStore.pendingAuthoredMutationKey). admit(_:to:) refuses to overwrite a different pending intent — only the byte-identical intent may be rewritten, to re-prove durability after an uncertain prior write. clear(_:from:) only removes the slot when the caller's expected intent still matches what's stored, then verifies removal. Android's replica identity is guarded the same way: AuthoredReplicaIdentity.loadOrCreate(in:key:) generates a fresh UUID().uuidString.lowercased() only when the blob is entirely absent, and returns .failure for anything malformed or unreadable rather than silently regenerating it — two devices sharing one compact replica head would erase history.

    fianchetto-cli does not drive this edit surface: its annotate subcommand produces per-ply engine evaluations from a live Stockfish session, not authored notes or board marks, and none of the CLI's six implemented subcommands (annotate, estimate, maia, accuracy, project, track) touch this pipeline. An authored subcommand appears in the CLI's expansion proposals for offline inspection and fuzzing of the reconciler, but it is unimplemented and, even as proposed, reads and replays history rather than editing it — a scripted note or board-mark edit still has to go through this exact planner/CAS/writer/journal pipeline on a real platform shell.

    Backup and restore¶

    AuthoredBackupReconciler — the mutation-free merge kernel¶

    AuthoredBackupReconciler.plan(_:) produces one complete merge plan from live rows, an existing backup envelope, and/or an incoming backup, without writing anything. Input combines primaryRows: [BlobRow] (duplicate keys intentional — the kernel merges them), conflictSidecars, and allowedLogicalGameIDs; any decoded record outside that ID set throws .orphanedLogicalGameID, fencing orphans out of a category-limited backup. Physical duplication is bounded at maximumPhysicalCandidatesPerKey = 256 per key before any semantic decoding, so repeated identical payloads can't become a CPU/memory amplification vector.

    The output Plan holds immutableRevisionRows (every compact candidate becomes an immutable fact first, so a dominated compact projection can never be discarded without a permanent record) and compactHeadGroups — causally maximal compact rows per key, {active, alternates}.

    syncedBlobs is not exclusively authored data

    A backup's syncedBlobs array is the same progress-category row list every ordinary BlobBackedStore rides in — combinationPuzzles (CombinationPuzzleStore), tacticsRating, drillSRS, and the rest sit in it beside the authored compact-head and immutable-revision rows. plan(_:) decodes every primaryRows entry as an authored record and throws .invalidRecord on the first one that isn't, so a real caller must pre-filter with AuthoredBlobRecordCodec.isAuthoredKey(_:) before calling in — never pass a raw syncedBlobs array through unfiltered. Those non-authored progress rows reconcile very differently on conflict: they have no vector clock at all, so two offline replicas are folded with a plain typed union instead of causal reconciliation. That union's return value is a ProgressBlobMergeResult — the merged json plus the exact contributors that fed it, so a caller can derive backup precedence without re-deciding which rows counted. See the file store guide for the merge rules themselves; it isn't this page's kernel.

    let plan = try AuthoredBackupReconciler.plan(.init(
    primaryRows: (backup.syncedBlobs ?? []).compactMap { row in
        guard AuthoredBlobRecordCodec.isAuthoredKey(row.key) else { return nil }
        return .init(key: row.key, dataJSON: row.dataJSON)
    },
    conflictSidecars: (backup.syncedBlobConflicts ?? []).compactMap { conflict in
        guard AuthoredBlobRecordCodec.isAuthoredKey(conflict.key) else { return nil }
        return .init(
            key: conflict.key,
            // Each alternate `Candidate` carries only `dataJSON`; it repeats
            // the parent conflict row's key rather than owning one itself.
            alternates: conflict.alternates.map {
                .init(key: conflict.key, dataJSON: $0.dataJSON)
            }
        )
    },
    allowedLogicalGameIDs: allowedIDs
))

    A DirectProjectionIndex(from:) built once over a validated Plan gives O(1) per-game notesDirectProjection(logicalGameID:directCopies:) / boardMarksDirectProjection(...) lookups without re-decoding history for every game — the same witnessed-value rule above, applied per field.

    AuthoredRestoreJournal — the four-slot crash-safe handoff¶

    Android library restore spans several durable phases; AuthoredRestoreJournal (currentSchemaVersion = 2) survives a crash between them. Four fixed large payload keys hold the prepared targets — targetLibraryBlobKey, targetBackupBlobKey, restoreWriteSetBlobKey, recoverySnapshotBlobKey — and one small canonical head, headBlobKey = "local.authoredRestoreJournal.v1" (maximumHeadBytes = 16 * 1_024), is written last and is the sole active-transaction marker:

    prepare(...)                        → build + validate every byte, no writes
installBeforeCausalPublication(_:)  → write 4 payloads (read-back-verified),
                                        recheck ownership, THEN write the head
recoveryRead()                      → startup: read head, decide AggregateState
clearIfCommitted()                  → retire the journal once everything durable

    Because the head is written last and the four payload slots are fixed and reused rather than accumulated, a crash at any point leaves at most four inactive, overwriteable payloads. Recovery compares the durable aggregate library's ExactByteProof against head.expectedLibrary (unchanged since prepare → AggregateState.needsCommit) or head.targetLibrary (already replaced → .targetCommitted) — the only two AggregateState cases. Any other observed value is never overwritten: it surfaces as RecoveryReadResult.stale, not as an AggregateState case, and the journal is retained rather than risking an unrelated newer library getting clobbered.

    let journal = AuthoredRestoreJournal(store: blobStore)
switch journal.prepare(
    restoreCategoryRawValue: LibraryBackupCategories.games.rawValue,
    authoredPublicationMode: .completeFrontier,
    restoreWriteSet: writeSet,
    targetLibrary: targetLibrary,
    targetBackupJSON: incomingBackupJSON
) {
case .value(let prepared):
    _ = journal.installBeforeCausalPublication(prepared)
case .failure(let message):
    break   // targets rejected; nothing was written
}

    AuthoredRestoreProjector¶

    AuthoredRestoreProjector.project(_:onto:boardMarksProjectionExclusions:) applies one validated AuthoredBackupReconciler.Plan onto a live LibraryData snapshot. It installs the identity marker (AuthoredGameIdentity.installingMarker) on every physical copy of a logical game, but overwrites a field's bytes only on the copies named in decision.changedCopyIDs. A move-sequence-incompatible copy is excluded from board-mark projection but still receives notes and identity.

    AuthoredRecoveryPlanner — the inverse of restore¶

    A normal restore projects the causal winner into direct storage. AuthoredRecoveryPlanner.plan(reconciling:to:authorReplicaID:authoredAtMilliseconds:) is the inverse: after observing every current causal branch, it authors an explicit new revision converging to a target backup value. It never manufactures tracking for a field with no existing causal state; recovery only touches fields already represented.

    When a game's target copies disagree, recovery authors one concurrent branch per distinct value, each on a deterministic sub-replica ID:

    recoveryReplicaID = "recovery.v1." + SHA256(seed head's encoded bytes)

    so re-running the same recovery advances the same branches instead of consuming new vector-clock slots on every retry.

    The frontier inventory cache — AuthoredBlobInventory¶

    Rescanning every append-only immutable revision to answer "what does this field currently say" would make routine reads scale with history depth. AuthoredBlobInventory sits in front of AuthoredReconciler as a bounded, resumable cache with two tiers, bound together by a SHA-256/byte-count proof:

    generation (a UUID)
  → FrontierCatalog (schemaVersion 2): sorted indexKeys, isComplete flag
      → per-(logicalGameID, field) FrontierManifest (schemaVersion 4,
        maximumRows = maximumCompactHeadCandidates * 2 = 128)

    A complete, proof-bound catalog that omits a field's key is itself proof that field has no causal state — the first edit on a brand-new game is O(1) instead of a full rescan. frontierRows(...) returns one field's rows; allFrontierRows(...) returns everything for backup export, falling back to a full rebuild only if the catalog is missing, incomplete, or unbound.

    Full rebuilds (the exceptional path) checkpoint via FrontierRebuildCheckpoint (schemaVersion 1), keyed on a rolling SHA-256 digest of the exact sorted authored-key sequence (sequenceSHA256) plus the backup envelope's own SHA-256, so an interrupted rebuild resumes per already-completed field group. The actual per-field reduction, one AuthoredHistoricalReducer<Value, Element> per (logicalGameID, field), streams that field's immutable revision rows in storage-key order and folds them down to the retained frontier — capped at AuthoredBlobRecordCodec.maximumCompactHeadCandidates — without ever materializing every decoded revision at once, which is what keeps a rebuild's memory footprint independent of how deep a game's edit history runs.

    garbageCollectInfrastructure only deletes a manifest or witness proven unreachable from a fully validated, complete generation; on any doubt — an unreadable manifest, an unbound catalog — it leaks the row rather than guessing ownership.

    Game identity — AuthoredGameIdentity¶

    Every storage key above is keyed on logicalGameID, a promotion-stable identity distinct from any platform row ID. It lives inside game tags under reservedTagKey = "_FianchettoAuthoredLogicalID" — deliberately not a valid PGN tag name, stripped at every generic PGN import/export boundary (externalTags(from:)) so it never leaks into a shared or exported game.

    A marker is markerPrefix ("stable.v1.") + 64 lowercase hex characters (isValidMarker). Before any marker exists, the deterministic alias is AuthoredBlobRecordCodec.logicalGameID(forIdentitySource:) = "stable.v1." + SHA256(identitySource). The first authored write on an unmarked game stamps that deterministic value as an explicit marker:

    let resolution = try AuthoredGameIdentity.resolveOrCreate(
    tagsJSON: game.tagsJSON,
    identitySource: game.authoredIdentitySource
)
game.tagsJSON = resolution.tagsJSON
let logicalGameID = resolution.logicalGameID   // stable across future promotion

    Once a marker exists on one physical copy, ownership resolution (ownership(for:) / replayingOwnership(...)) propagates it to every other copy sharing the same content seed or semantic remote game ID — so promoting an imported game to a synced one doesn't orphan its existing notes. Two different valid markers on the same seed or remote ID is a hard failure, .conflictingMarkers, thrown before any adapter mutates a row.

    Retention and migration¶

    Why AuthoredRevisionRetentionPolicy retains everything today¶

    AuthoredRevisionRetentionPolicy.currentGarbageCollectionDecision is hardcoded to .retainAll(blocker: .acknowledgedEpochUnavailable), and permitsDeletion is hardcoded false for every case that exists. The kernel's reasoning: an old vector-clock counter, a dominated value, elapsed time, or total row count are all observations, not deletion authority. Safe reclamation needs a sync-visible checkpoint epoch that every active replica has acknowledged, plus proof each candidate revision is covered by it — records that don't exist yet in the persistence protocol. The policy is deliberately one-sided: a deletion-authorizing case is meant to arrive as part of a future acknowledged-epoch protocol, not a local heuristic that quietly widens this API.

    AuthoredStorageMigration — restartable legacy-file migration¶

    Migrates Android's original flat authored filenames into the routed authoredHead.v1. / authoredRevision.v1. hierarchy, bounded at maximumEntriesPerLaunch = 512 entries per pass. Discovery uses BoundedCandidateSelection, a capacity-bounded max-heap retaining only the lexicographically smallest capacity sortTokens seen across an unbounded directory scan — O(directory entries × log budget) time, O(budget) memory.

    Each candidate is migrated verify-copy-then-delete: the legacy source is never removed until the exact same bytes are durable and directly readable at the canonical path, and both paths are re-read and re-compared immediately before the delete call.

    The checkpoint is diagnostic-only, not the safety mechanism

    Unlike the frontier rebuild checkpoint above, every migration pass re-enumerates every physical legacy candidate regardless of what an earlier checkpoint claims was .complete. If an Android system restore brings back old legacy rows alongside a checkpoint saying migration finished, the next pass still finds and repairs them — the checkpoint only rotates the resume cursor for a bounded per-launch batch.

    let result = blobStore.migrateLegacyAuthoredStorage()
result.migratedCount
result.retainedCount
result.isComplete   // remainingCandidateCount == 0 && failureDescription == nil
