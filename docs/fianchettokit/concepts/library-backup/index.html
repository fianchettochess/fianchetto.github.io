    Library Backup: Format, Streaming Encoder & Exact-Byte Proofs¶

    The library-backup subsystem defines the on-disk JSON that the iOS app and the Android (Skip/SkipFuse) port read and write byte-compatibly, plus everything needed to produce, validate, stream, and prove that JSON without ever loading an unbounded amount of it into memory at once.

    Overview¶

    A backup is one JSON document: games, repertoires, traps, caches, synced progress blobs, and settings. Both platforms must agree on every field name, type, and optionality, because the JSON keys come directly from the Swift struct's stored properties — a renamed or reordered field breaks a lossless cross-platform restore. The source comments describe this format as mirroring a shared docs/BACKUP_FORMAT.md, kept outside this package.

    There is exactly one hard rule that everything else in this page exists to enforce:

    Warning

    Always encode and decode through LibraryBackupCodec, never a bare JSONEncoder/JSONDecoder. A bare JSONEncoder emits reference-date Doubles for every Date instead of ISO-8601 strings and silently corrupts a cross-platform restore. LibraryBackupCodec is also the only place that runs schema-version gating and semantic/resource validation, so a file that a bare encoder would happily write might be a file the app later refuses to restore.

    File Role
    LibraryBackup.swift The envelope model, LibraryBackupCategories, LibraryBackupAncillaryOverlay, and LibraryBackupCodec (config + validate/encode/decode entry points)
    LibraryBackupStreamingEncoder.swift Bounded-memory incremental encoder (streamSupported, ValidatedStream)
    LibraryBackupReplayableSource.swift ReplayableSource, the actor-confined streaming input, and the game replay-fingerprint machinery
    ExactByteProof.swift The {byteCount, sha256} proof type
    BackupFileProofReader.swift Chunked, change-detecting proof of a file already on disk
    LibraryBackupSettingPolicy.swift The portable settings kind/rule/registry and RatingChartWindow
    LibraryBackupAuthoredAdapter.swift Canonicalizes game-owned causal rows against marker-derived identity
    MaiaBackupEvidenceReplayer.swift Rejoins an offline Maia evidence corpus back onto its source backup
    StoredBackupOverlayHead.swift Android's compact backup-overlay storage format + migration reader

    The LibraryBackup envelope¶

    LibraryBackup.currentSchemaVersion is 1. It is a monotonically increasing Int bumped only for a breaking shape change; anything additive is expressed as an Optional field instead, which is the pattern nearly every field below follows.

    public struct LibraryBackup: Codable, Sendable, Equatable {
    public let schemaVersion: Int
    public let exportedAt: Date
    public let collections: [Collection]
    public let personalTraps: [PersonalTrapRow]
    public let trapScanRecords: [TrapScanRecord]
    public let repertoires: [Repertoire]?          // nil = older build, no repertoires yet
    public var auditCaches: [AuditCacheRow]? = nil
    public var punishCaches: [PunishCacheRow]? = nil
    public var syncedBlobs: [SyncedBlobRow]? = nil
    public var syncedBlobConflicts: [SyncedBlobConflictRow]? = nil
    public var settings: [SettingRow]? = nil
}

    Only collections, personalTraps, and trapScanRecords are required, non-optional arrays that were present since schema v1. Everything from repertoires onward is Optional with a nil default so that:

    • an older build's export, which never wrote the key, still decodes (Codable treats a missing key as nil for an Optional property with no custom init(from:));
    • a newer reader can tell "zero rows" ([]) apart from "this build didn't know about this category yet" (nil) — syncedBlobConflicts, for example, is lossless recovery data for CloudKit duplicate rows, and a nil there means "no conflicts were even tracked," not "no conflicts existed."

    LibraryBackup's memberwise init reflects the same split: repertoires has no default value (callers must pass nil or an array explicitly) while every field after it defaults to nil.

    Collection, Game, and Enrichment¶

    Collection holds name, source, username, an optional lastSyncDate, orderIndex, dateCreated, and its games: [Game]. One flag does double duty: includeInOpeningBook: Bool also gates which games can receive a Maia-replay ordinal (see below).

    Game mirrors StoredGame's persisted, non-derived fields — note that date is a PGN yyyy.MM.dd string, not an ISO-8601 Date, and stays opaque all the way through this subsystem. A Game carries its own portable enrichment fields directly (annotationEvalsJSON, userNotes, maiaTargetEvidenceV1JSON, …); Game.Enrichment is the same data factored out as a standalone value so an adapter can reason about "just the enrichment" without touching PGN identity:

    public struct Enrichment: Sendable, Equatable {
    public var annotationEvalsJSON: String
    public var secondBestEvalsJSON: String
    public var annotationMateDistancesJSON: String?
    public var annotationProvenanceJSON: String?
    public var userNotes: String
    public var boardArrowsJSON: String?
    public var consensusJSON: String?
    public var maiaLogLikesJSON: String?
    public var maiaTargetEvidenceV1JSON: String?

    public func overlayingNonEmpty(from backup: Self) -> Self
}

    overlayingNonEmpty(from:) is the merge rule used whenever a backup is reconciled against already-live data: a non-empty incoming (backup) value wins, but nil/empty backup data never erases something already present live. annotationProvenanceJSON is a deliberate exception — it is treated as inseparable from the eval payload it describes, so it is only overlaid when the incoming annotationEvalsJSON or secondBestEvalsJSON is itself non-empty; otherwise a live envelope is preserved rather than falsely attributing existing numbers to the incoming engine/configuration. maiaTargetEvidenceV1JSON instead delegates to MaiaBackfillPolicy.preferredTargetEvidence(live:incoming:).

    LibraryBackupCategories¶

    Selective import/export is driven by an OptionSet whose bit positions are part of the persisted cross-platform contract — a saved restore journal stores rawValue directly, so these must never be renumbered:

    Category Bit
    .games 1 << 0
    .repertoires 1 << 1
    .traps 1 << 2
    .caches 1 << 3
    .progress 1 << 4
    .settings 1 << 5
    .all union of the six above

    LibraryBackupAncillaryOverlay¶

    A game-free projection of a backup — schemaVersion, exportedAt, and every field from personalTraps onward except collections and repertoires — for an adapter that only needs to enrich a fresh live projection without materializing the whole game graph. init(projecting: LibraryBackup) derives one from a complete backup so platform adapters don't repeat the category field list. Going the other way, var ancillaryEnvelope: LibraryBackup re-wraps it as a LibraryBackup with collections: [] and repertoires: nil, purely so the existing envelope-level validation and merge kernels can run against it unchanged.

    Warning

    ancillaryEnvelope's result is a game-free compatibility value for reuse of merge kernels, not a complete backup — the doc comment is explicit that it must never be published directly. Authored rows carried by an overlay still require reconciliation against live game ownership before a caller persists or publishes them, exactly as for a complete backup.

    SettingValue and the setting policy¶

    SettingRow pairs a key: String with a SettingValue, a three-case enum covering the value kinds carried by a backup:

    public enum SettingValue: Codable, Sendable, Equatable {
    case bool(Bool)
    case int(Int)
    case string(String)
}

    Its Codable conformance is hand-written rather than synthesized, and it reproduces the exact shape Swift's synthesizer would produce for an associated-value enum: a single-key object whose payload is nested one level down under the key "_0".

    SettingValue.string("blue")  →  {"string":{"_0":"blue"}}
SettingValue.int(42)         →  {"int":{"_0":42}}
SettingValue.bool(true)      →  {"bool":{"_0":true}}

    The doc comment is explicit about why: Skip/SkipFuse transpilation of a synthesized associated-value-enum Codable conformance is a known portability risk, and the natural alternative shape a naive hand-write might produce — {"string":"blue"} — would fail to decode on iOS. Hand-writing both init(from:) and encode(to:) pins the byte shape deterministically on both platforms; the shape is also asserted directly in tests.

    The setting registry and policy¶

    LibraryBackupSettingRule is a per-key validation rule with three cases — .bool, .int(minimum:maximum:), .string(maximumUTF8Bytes:) — and an accepts(_:) method that checks a SettingValue against it. LibraryBackupSettingRegistry.definitions curates every key the backup format understands: 20 bool settings, 9 bounded-int settings, and 11 bounded-string settings (40 definitions total), each independent of whatever physical UserDefaults/SharedPreferences key a platform stores it under. A representative slice of the bounded numeric ranges:

    Key Rule
    drillSessionSize .int(minimum: 1, maximum: 100)
    checkmateIntensity .int(minimum: 0, maximum: 3)
    missedMateMaxN .int(minimum: 2, maximum: 10)
    punishTopK .int(minimum: 2, maximum: 8)
    punishOpponentElo .int(minimum: 800, maximum: 2_400)
    autoICloudBackupRetention .int(minimum: 1, maximum: 30)
    masteryThreshold .int(minimum: 2, maximum: 10)
    tacticsSwingThreshold .int(minimum: 50, maximum: 1_000)
    stockfishDepthLimitPersisted .int(minimum: 0, maximum: 128)

    Every one of the 11 curated string settings (boardTheme, pieceSet, explorerDatabase, annotateThoroughness, annotationEngine, tacticsMode, drillStrictness, evalDisplayFormat, libraryGameSort, ratingChartWindow, otbLastTimeControl) uses the same bound: .string(maximumUTF8Bytes: 256).

    LibraryBackupSettingPolicy.accepts(_ row: LibraryBackup.SettingRow) -> Bool is deliberately forward-compatible: a key with no registered definition passes automatically (?? true), so a future build's new setting doesn't fail validation on an older reader; a known key must satisfy its registered rule or the row is rejected — .int(minimum: 2, maximum: 8) on punishTopK rejects a stored 9, for instance, while an unrecognized key like someFutureFlag passes regardless of its value.

    RatingChartWindow¶

    Older Apple builds stored the rating-history window preference in lowercase; Android stored the display label. RatingChartWindow(storedValue:) bridges both by trimming whitespace and lowercasing before matching a raw value:

    Case Raw value shortLabel monthOffset
    .threeMonths "3m" "3M" -3
    .sixMonths "6m" "6M" -6
    .oneYear "1y" "1Y" -12
    .all "all" "All" nil

    LibraryBackupSettingPolicy.normalizedPortableRow(_:) runs accepts(_:) first, then — only for the ratingChartWindow key — replaces whatever spelling arrived with the canonical lowercase raw value via RatingChartWindow(storedValue:). If the stored string doesn't match any case, the row is dropped (returns nil) rather than persisted as a value no segmented-picker UI could represent.

    Canonical JSON encoding contract¶

    LibraryBackupCodec.makeEncoder() and .makeDecoder() are the single source of truth for wire configuration on both platforms:

    encoder.outputFormatting   = [.withoutEscapingSlashes, .sortedKeys]
encoder.dateEncodingStrategy = .iso8601
decoder.dateDecodingStrategy = .iso8601

    .sortedKeys is what makes the encoding canonical: without it, swift-foundation emits object keys in hash-seed-dependent order that can vary across processes (and, on an older Foundation runtime, even across separate encode() calls within one process). Any consumer that treats the encoded bytes' SHA-256 as a payload identity — publication dedup/retention being the motivating case — needs that hash to be a true content identity, not an artifact of key ordering.

    LibraryBackup.exportedAt is canonicalized at construction time, independent of encoding:

    canonicalExportDate(date) = Date(timeIntervalSince1970: date.timeIntervalSince1970.rounded(.down))

    Rounding down to the whole second matches .iso8601's whole-second string output, so an exact-byte proof taken over the in-memory value can never imply sub-second precision the JSON itself doesn't carry.

    Schema-version gate¶

    validateSchemaVersion(schemaVersion):
    schemaVersion < 1                         → throw .invalidSchema(found:)
    schemaVersion > currentSchemaVersion (1)  → throw .unsupportedSchema(found:supported:)
    otherwise                                 → accept

    Codable silently ignores unknown JSON fields, which — absent this gate — would let a future-schema backup appear to restore successfully while quietly discarding data it doesn't understand yet. Every decode path in LibraryBackupCodec runs this check before any semantic validation.

    Resource ceilings¶

    maxPayloadBytes is checked before JSONDecoder ever runs (validatePayloadSize), so a malformed multi-gigabyte file can't multiply its footprint inside the decoder and take down the process. Every other ceiling is enforced after decode, in validateResourceLimits / validateEnvelopeResourceLimits, against the already-structured value:

    Ceiling Value
    maxPayloadBytes (public) 512 × 1024 × 1024 (512 MiB)
    maxCollections 4,096
    maxGames 250,000
    maxGamesPerCollection 100,000
    maxRepertoires 10,000
    maxRepertoireMoves 500,000
    maxAuxiliaryRows (traps / trap-scan records) 250,000
    maxSyncedBlobRows 1,000,000
    maxSyncedBlobConflictRows 500,000
    maxSyncedBlobAlternates (total, across all conflict rows) 1,000,000
    maxGenericSyncedBlobAlternatesPerKey 10,000
    maxSettings 512
    maxSmallFieldBytes (names, tags, PGN metadata) 65,536
    maxGameTextBytes (move text, evals, notes, Maia payloads) 8 × 1024 × 1024
    maxBlobBytes (one synced-blob row/alternate) 16 × 1024 × 1024

    A conflict row's own alternate count is bounded per key, and the per-key limit depends on what kind of key it is: an authoredHead.v1.… compact-head key uses the much smaller AuthoredBlobRecordCodec.maximumCompactHeadAlternates (63 — one less than the 64-candidate compact-frontier ceiling, since a sidecar excludes the active row), while every other key uses the generic 10,000-alternate ceiling. maxSyncedBlobRows in particular is sized around a documented rationale: a 250k-game backup can plausibly carry roughly one compact head plus one exact immutable revision per authored field, so 1,000,000 keeps that arithmetic in bounds without letting the old, unrelated 10k-repertoire cap reject a valid compact frontier.

    The streaming encoder¶

    encodeSupported(_:) and makeEncoder().encode(_:) both return one payload-sized Data. For a 250,000-game backup that is a real cost — the caller ends up holding the whole encoded document in memory at once, on top of whatever in-memory model it was built from. LibraryBackupCodec.streamSupported(_:emit:) avoids that: it emits the same bytes encodeSupported(_:) would, incrementally, through a callback.

    Shell-and-splice¶

    The technique (writeShell) exploits JSONEncoder's determinism on an empty array:

    For a value with N array-typed properties:
  1. Build a "shell" copy of the value with every array-typed property
     replaced by [].
  2. encoder.encode(shell) → shellData (one small Data).
  3. For each array property, search shellData for the literal byte
     sequence  "<property>":[]
     — the insertion point is the byte offset just before the closing `]`.
  4. Sort every insertion point by byte offset (multiple arrays on one
     shell — e.g. Collection has only "games", but the top-level envelope
     has up to seven — must be spliced in stream order, not declaration
     order).
  5. Walk shellData once, writing the bytes up to each insertion point,
     then writing that array's real elements one at a time (encoding each
     element individually and joining with a literal `,`), then resuming
     at the shell byte just after that point.

    If a marker isn't found — i.e. if JSONEncoder ever stops emitting a bare [] for an empty array — the encoder throws LibraryBackupCodec.StreamingError.incompatibleArrayShell(property:) rather than silently producing wrong JSON. Nested shells compose: the envelope shell splices in "collections":[], and writeCollection runs the identical technique one level down for each collection's "games":[].

    Chunking and the running hash¶

    Every write — shell bytes, a comma separator, one encoded element — passes through BackupJSONStream.write(_:), which splits it into pieces of at most maximumStreamingChunkBytes (64 * 1_024, 64 KiB) before handing each piece to the caller's emit closure:

    for each chunk (≤ 64 KiB):
    byteCount += chunk.count   // via addingReportingOverflow; throws .payloadTooLarge on overflow
                                //   or if byteCount would exceed maxPayloadBytes (512 MiB)
    emit(chunk)                 // caller writes it — e.g. to a staging FileHandle
    hasher.update(chunk)        // folded into a running PortableSHA256.Hasher

    Only bytes actually accepted by emit participate in the final ExactByteProof — a throwing sink owns disposal of whatever partial staging target it already wrote.

    let handle = try FileHandle(forWritingTo: stagingURL)
defer { try? handle.close() }

let proof = try LibraryBackupCodec.streamSupported(backup) { chunk in
    try handle.write(contentsOf: chunk)
}
// proof.byteCount / proof.sha256 describe exactly what landed in stagingURL —
// publish stagingURL only after this call returns successfully.

    Validation runs to completion before the first byte is emitted (validatedStream(for:) calls validateSupported(_:) up front), but a sink failure or a late aggregate payload-size overflow can still leave a partial stream on disk — production callers target a discardable staging file and publish it only once streamSupported returns.

    Streaming a ReplayableSource¶

    LibraryBackupCodec.ReplayableSource is the other streaming input: an envelope LibraryBackup plus, per collection, a ReplayableSource.Collection(name:source:username:lastSyncDate:includeInOpeningBook:orderIndex:dateCreated:gameCount:replayGames:) whose replayGames: (_ visit: (LibraryBackup.Game) throws -> Void) throws -> Void closure can capture live persistence-actor model objects instead of a fully materialized [Game] array.

    ReplayableSource is marked @available(*, unavailable, message: "ReplayableSource is actor-confined") extension LibraryBackupCodec.ReplayableSource: Sendable {} — it is actor-confined by construction and must be built and consumed synchronously by the actor that owns the live models its closures capture. streamSupported(_:emit:) walks it twice in spirit but once in practice: validateReplayableSource(_:) replays every game once to compute a ReplayProofAccumulator digest (the expected proof), then the actual write pass (writeBackup(_:expectedReplayProof:...)) replays the same source again while accumulating a second digest, and the two must match exactly:

    ReplayProofAccumulator, seed "library-replay-games:v1":
    hash(collectionCount)
    for each collection: hash(collectionIndex), hash(gameCount)
    for each game:       hash(collectionIndex), hash(gameIndex),
                          then replaySemanticFingerprint's field list (below)

    If replaying the source a second time produces a different game count for some collection, StreamingError.replayCollectionCountMismatch(collectionIndex:expected:actual:) is thrown; if the accumulated digest itself differs, StreamingError.replaySourceChanged is thrown. Either way, the write fails into the caller's discardable staging file rather than publishing a document that doesn't match what was validated.

    LibraryBackup.Game.replaySemanticFingerprint is the field-framed digest shared by that accumulator and by persistence adapters as one review point for the wire projection:

    replaySemanticFingerprint, seed "library-backup-game-replay:v2":
    hash(orderIndex)
    hash(white, black, date, event, result, opening, moveText, tagsJSON,
         gameID, annotationEvalsJSON, secondBestEvalsJSON, userNotes)
    for each of [annotationMateDistancesJSON, annotationProvenanceJSON,
                 boardArrowsJSON, consensusJSON, maiaLogLikesJSON,
                 maiaTargetEvidenceV1JSON]:
        present → hash("some"), hash(value)
        nil     → hash("nil")

    Every hashed piece goes through update(lengthPrefixedUTF8:) — an 8-byte big-endian length prefix followed by the UTF-8 bytes — not through JSON encoding, so a harmless key-order difference between two encodings of the same value can never look like a semantic change.

    Exact-byte proofs¶

    ExactByteProof is {byteCount: Int, sha256: String} — Codable, Equatable, Sendable — constructible via init(byteCount:sha256:), init<Bytes: Sequence>(bytes:) where Bytes.Element == UInt8, or init(utf8 source: String), the last two hashing incrementally without retaining a second payload-sized copy. isCanonicalSHA256 requires exactly 64 UTF-8 bytes, each in the ASCII ranges 48...57 ('0'–'9') or 97...102 ('a'–'f') — uppercase hex is rejected. isStructurallyValid additionally requires the bounds themselves to be sane (minimumByteCount >= 0, maximumByteCount >= minimumByteCount) and byteCount to fall within them. Decoding deliberately preserves a structurally invalid proof rather than failing to decode, so a persistence boundary can quarantine a damaged record without being unable to even read it back.

    Both ExactByteProof and the streaming encoder's running hash are built on PortableSHA256.Hasher (Support/PortableSHA256.swift) — a small, dependency-free, incremental SHA-256 implementation chosen specifically because CryptoKit is unavailable on the native Android build and Swift's built-in Hasher is intentionally process-randomized, so neither can serve as a stable cross-platform or cross-process content identity.

    BackupFileProofReader — proving a file already on disk¶

    public enum BackupFileProofReader {
    public static let readChunkBytes = 64 * 1_024

    public static func proof(
        of url: URL,
        expectedProof: ExactByteProof? = nil,
        maximumBytes: Int = LibraryBackupCodec.maxPayloadBytes,
        hooks: ReadHooks = ReadHooks()
    ) throws -> ExactByteProof
}

    It reads a local regular file only (SAF/content URLs must first be copied into private storage) in 64 KiB chunks, and detects a file that changed underneath the read even when the change happens to leave the size unchanged mid-read:

    1. Reject non-file URLs (.nonFileURL) and missing paths (.missing).
2. attributesOfItem(atPath:)[.size] → initialByteCount   (before opening the handle)
3. Reject non-regular files (.notRegularFile).
4. Read in chunks of min(readChunkBytes, remaining + 1) bytes —
   the "+1" makes a file that grew past maximumBytes overshoot the cap
   and get caught by .payloadTooLarge, instead of silently reading a
   truncated prefix.
5. Fold every chunk into a running PortableSHA256.Hasher; call
   hooks.afterChunk(index, byteCount) after each one (a deterministic,
   test-only seam — production callers use the no-op default).
6. attributesOfItem(atPath:)[.size] → finalByteCount     (after the last read)
7. Require initialByteCount == finalByteCount == (bytes actually read),
   else throw .changedDuringRead.
8. If expectedProof was supplied and it doesn't equal the observed
   proof, throw .proofMismatch(expected:observed:).

    The before/after size comparison is the reader's sole detector of a same-size content mutation — the doc comment notes explicitly that Skip's Android Foundation layer exposes no inode/mtime identity to lean on instead.

    // After staging a backup file, prove it matches what streamSupported wrote.
let stagedProof = try BackupFileProofReader.proof(
    of: stagingURL,
    expectedProof: streamingProof
)

    StoredBackupOverlayHead — Android's compact storage path¶

    Instead of retaining a complete portable backup in app storage, the Android port can retain a compact head at the same blob key:

    public struct StoredBackupOverlayHead: Codable, Equatable, Sendable {
    public static let formatIdentifier = "fianchetto.android.stored-backup-overlay-head"
    public static let currentFormatVersion = 1

    public let format: String
    public let formatVersion: Int
    public let completeEnvelopeProof: ExactByteProof
    public let overlay: LibraryBackupAncillaryOverlay
}

    StoredBackupOverlayReader is the single fail-closed reader for the shared library.fullbackup.v1 blob key (StoredBackupOverlayReader.blobKey), and it distinguishes the legacy shape from the compact one with a format discriminator rather than a try/catch fallback:

    decode(data):
    probe = decode({ format: String? })   // container.contains(.format), then a
                                           // non-optional decode(String.self) —
                                           // a *present* null value therefore fails
                                           // to decode rather than being treated as absent
    if probe.format is present:
        format must equal formatIdentifier, else throw .unsupportedFormat
        decode as StoredBackupOverlayHead, validate formatVersion == 1
          and completeEnvelopeProof.isStructurallyValid(...)
        → .compactOverlayHead
    else (no "format" key at all):
        decode as the legacy LibraryBackupAncillaryOverlay envelope
          via decodeSupportedAncillaryOverlay(_:)
        → .legacyCompleteEnvelope

    Any mismatch on the compact-head branch — wrong identifier, wrong version, an invalid proof — fails closed rather than being silently retried as a legacy envelope. This is what lets one JSON blob key safely serve both an old install (writes/reads the legacy shape) and a migrated one (writes/reads the compact head) during rollout: the presence of a top-level format key alone decides which namespace a given payload belongs to.

    Authored-row reconciliation at a glance¶

    Rows keyed under authoredHead.v1.… / authoredRevision.v1.… in syncedBlobs/syncedBlobConflicts are not an opaque progress namespace — they are game-owned causal state (things like move annotations and notes), and LibraryBackupAuthoredAdapter exists because a backup restore must never trust that namespace at face value. Every decode and encode path in LibraryBackupCodec routes through it (validateSupported, decodeSupportedWithAuthoredProjection, validateReplayableSource) before persisting anything.

    At a high level, the adapter:

    1. Builds a GameOffset-indexed (collectionIndex, gameIndex) identity candidate for every game in the backup via gameCandidates(in:), using each game's PGN tags and move text.
    2. Resolves those candidates — plus any caller-supplied live AdditionalID candidates — into a canonical alias map through AuthoredGameIdentity.
    3. Canonicalizes every authored SyncedBlobRow/SyncedBlobConflictRow onto that map (canonicalized(_:canonicalLogicalIDByAlias:)).
    4. Runs the shared AuthoredBackupReconciler semantic plan against the canonicalized rows, producing a Projection<AdditionalID> — the ownership, the canonicalized rows, the reconciliation plan, and the resulting allowedLogicalGameIDs.
    public static func project(_ backup: LibraryBackup)
    throws -> Projection<NoAdditionalCandidate>

public static func project<AdditionalID: Hashable>(
    _ backup: LibraryBackup,
    additionalCandidates: [AuthoredGameIdentity.LogicalIDCandidate<AdditionalID>]
) throws -> Projection<AdditionalID>

    A validated projection can be cheaply reused via reprojectValidated(_:validatedBase:additionalCandidates:) instead of re-running the whole plan against live candidates — but only if a narrow authoredSource(in:) SHA-256 (seed "library-authored-source:v1") still matches exactly. That hash covers only the fields that can affect authored ownership — white/black/date/result/event/opening/moveText/tagsJSON/ gameID/annotationEvalsJSON, plus authored-keyed synced-blob rows and sidecars — and deliberately excludes progress, repertoire, and cache fields, since the doc comment states plainly that "they cannot affect authored ownership." If the backup passed to reprojectValidated doesn't hash to the proof captured at first validation, it throws AdapterError.validatedProjectionSourceMismatch rather than silently skipping re-validation of a backup that was mutated after it was first checked.

    This page only sketches the shape of that reconciliation; the identity markers, alias promotion, revision retention, and CAS semantics it builds on are covered in depth in the Authored History & the Mutation Journal page.

    Maia evidence replay¶

    MaiaBackupEvidenceReplayer rejoins a privacy-reduced, offline Maia inference corpus — produced by a MaiaHarness aggregate step outside this package — back onto the exact backup it was derived from, without ever exporting player names, game IDs, PGN text, URLs, or notes into that corpus in the first place. Each corpus row is a MaiaBackupReplayRecord:

    public struct MaiaBackupReplayRecord: Codable, Equatable, Sendable {
    public let sourceBackupSHA256: String
    public let sourceGameOrdinal: Int
    public let timeControl: String
    public let trueElo: Int
    public let opponentElo: Double
    public let opponentConditioning: String
    public let targetEvidenceContractID: String
    public let logLikes: [Double]
    public let eligibleMoveCount: Int
    public let positionSequenceSHA256: String
    public let modelArtifactSHA256: String
}

    Its CodingKeys map every field to a short snake_case wire name (source_backup_sha256, source_game_ordinal, tc, true_elo, oppo_elo, opponent_conditioning, target_evidence_contract_id, log_likes, n_maia_moves, position_sequence_sha256, model_artifact_sha256) — this is the JSON-lines shape the offline aggregation step actually emits.

    let result = try MaiaBackupEvidenceReplayer.enrich(
    sourceBackupData: backupData,
    with: records,
    exportedAt: .now
)
result.backup             // the same backup, with maiaTargetEvidenceV1JSON filled in
result.enrichedGameCount  // how many games actually matched a record

    sourceGameOrdinal is a global ordinal across every game in every collection with includeInOpeningBook == true, assigned in collection/game iteration order — a collection outside the opening book contributes no ordinals at all, so a game inside it can never be a replay target. enrich enforces, in order: ordinals are strictly increasing with no duplicates (.sourceOrdinalsNotStrictlyIncreasing / .duplicateSourceOrdinal); every record's modelArtifactSHA256 is a canonical lowercase-hex SHA-256 and identical across the whole batch (.modelArtifactMismatch); every ordinal falls inside the backup's actual eligible-game count (.sourceOrdinalOutsideBackup); and every record in the batch is actually consumed (.recordsNotConsumed(expected:actual:)).

    Per record, evidenceJSON(for:collection:record:) then independently re-derives the scoring context from the game's own PGN tags — via MaiaBackfillPolicy.scoringContext, GameTagCodec, and TimeControlClass.classify — and cross-checks it against the record before trusting a single number in it:

    targetEvidenceContractID == MaiaBackfillPolicy.targetEvidenceContractID       (.contractMismatch)
logLikes.count == MaiaBackfillPolicy.expectedVectorLength,
    all finite, all <= 1e-6 (log-probabilities are non-positive)              (.invalidLikelihoodEvidence)
eligibleMoveCount > 0                                                        (.invalidLikelihoodEvidence)
opponentConditioning ∈ {"exactLichess", "neutralLichessPrior"}               (.unknownOpponentConditioning)
recomputed opponentElo within < 0.001 of record.opponentElo                  (.gameContextMismatch)
recomputed TimeControlClass matches record.timeControl                       (.timeControlMismatch)
recomputed owner-color rating (by context.playerColor) == record.trueElo     (.ownerRatingMismatch)
recomputed qualifying-move count == record.eligibleMoveCount                 (.eligibleMoveCountMismatch)
recomputed positionSequenceSHA256 == record.positionSequenceSHA256           (.positionSequenceMismatch)

    positionSequenceSHA256 itself hashes, for every qualifying position, the little-endian bit patterns of Maia3Encoding.encodeTokens(position:) followed by the little-endian Maia3Encoding.policyIndex of the move actually played — so the corpus is bound not just to "this game" but to "this exact sequence of encoded model inputs."

    Only when every check agrees does enrich overwrite game.enrichment.maiaTargetEvidenceV1JSON — every other field on that game is preserved byte-for-byte through a hand-rolled copying(_:enrichment:) that deliberately bypasses PreparedGameData's ID-normalizing round trip, so a replay pass can never quietly renormalize a legacy game ID as a side effect of adding evidence to it.

    Headless-ness & CLI angle¶

    Every type on this page lives under Library/Backup, and the whole subsystem depends on Foundation and ChessCore only — there is no import SwiftUI, no import UIKit, and no @MainActor isolation anywhere in these nine files. LibraryBackupCodec.encodeSupported/decodeSupported, the streaming encoder, BackupFileProofReader, ExactByteProof, the authored adapter, and MaiaBackupEvidenceReplayer are all synchronous, non-isolated, and exercisable from a plain command-line binary or a CI job with no simulator involved.

    That makes a handful of fianchetto-cli subcommands a natural fit even though they don't exist today: a backup verify subcommand is barely more than BackupFileProofReader.proof(of:expectedProof:) plus LibraryBackupCodec.decodeSupported; a backup diff subcommand is two decodes and a structural comparison of the resulting LibraryBackup values; and a backup replay-maia subcommand would be a thin argument-parsing wrapper over MaiaBackupEvidenceReplayer.enrich(sourceBackupData:with:exportedAt:), reading a JSON-lines corpus from stdin or a file. None of the three exist today; fianchetto-cli's existing maia subcommand covers other Maia-related surface, but not this join-back step.
