    E-Board Integration: Session Core, Diff Resolution, and Diagnostics¶

    Sources/FianchettoKit/Boards/ (17 files) turns a raw physical-board event stream into game state, shared by the iOS/macOS app and the Android (Skip/SkipFuse) port from one decision core. Every type here except EBoardSessionCore — a plain class that deliberately holds non-Sendable stored state and is never sent across an actor boundary — is Sendable, and all but three files carry no @MainActor — the whole desync-resolution and promotion-disambiguation state machine is a plain value/reference-type decision core a unit test (or a future CLI) can drive with zero UI and zero Bluetooth.

    Overview: BoardKit's primitives vs. what FianchettoKit's Boards layer adds¶

    BoardKit (extracted from FianchettoKit 2026-07-03, a sibling package) owns the wire-level kernel — BoardEvent, BoardCommand, BoardTransport, BoardTransportState, BoardAdapter, BoardCapabilities, BoardExecutionGate, OccupancyMoveInference, BoardDiffResolver, BoardCorrectionPlanner, BoardTakebackDetector, ChessBoardGeometry, BoardReconnectPolicy, BoardSyncGate — plus the four brand codecs (SquareOffAdapter, ChessnutAdapter, ChessUpAdapter, MillenniumAdapter). FianchettoKit re-exports BoardKit and SquareOffAdapter (@_exported import), so import FianchettoKit alone resolves every board kernel type. FianchettoKit's Boards/ layer adds the product decisions BoardKit deliberately doesn't own:

    Concern Type(s)
    Which physical brand is this, and how do I find/name it BoardCatalogKey, BoardCatalog, BoardGATTSpec, BoardBrand
    Is it safe to scan / swap adapters right now BoardTransportLifecyclePolicy
    Who owns this async BLE callback BoardConnectionGeneration
    Deterministic write pacing BoardWriteQueue<Owner>
    Turning BoardEvent into game effects EBoardSessionCore, EBoardEffect
    Running the diff search off-main, applying its result EBoardDiffResolutionCoordinator
    One shared effect-application + orientation re-feed EBoardShellKernel, EBoardShellKernelContext
    UCI (re-)validation, takeback log lines EBoardMoveResolution
    App-to-board write-back move search EBoardPositionTransition
    Sync-sheet/OTB copy BoardSyncPresentation
    Field-bug capture and replay EBoardDiagnosticCapture, EBoardDiagnosticPersistenceCoordinator

    The iOS and Android EBoardSession shells used to hand-mirror this logic in Swift and Kotlin/Skip separately; every type here exists because that mirroring drifted.

    Board identity and the catalog¶

    BoardCatalogKey is the closed identity every board is keyed by, shared by both platforms' local BoardType enums (a FianchettoKit type can't be a Compose @State on Android, so each app maps its own thin BoardType to this key with an exhaustive switch):

    public enum BoardCatalogKey: String, CaseIterable, Sendable {
    case squareOffPro
    case chessnutAir
    case chessUp2
    case millenniumEONE
}

    BoardBrand.displayName(rawValue:) is the single source of truth for what a board is called: squareOffPro → "Square Off Pro", chessnutAir → "Chessnut", chessUp2 → "ChessUp 2", millenniumEONE → "Millennium eONE" (BoardBrand.pgnEventTag(rawValue:) currently mirrors this).

    GATT identity¶

    BoardGATTSpec is the platform-neutral BLE contract for one brand — plain String UUIDs, no CoreBluetooth import, so it stays Linux/Android-compilable. BoardCatalog.gattSpec(key:) returns the real values:

    Key scan filter TX service / char RX service / char dual-service aux notify
    squareOffPro D804B643-…, NUS 6e400001-… 6e400001…/6e400003… 6e400001…/6e400002… false —
    chessnutAir boardStateService, commandService boardStateService/boardStateChar commandService/commandWriteChar true commandResponseChar, fileChar
    chessUp2 NUS 6e400001-…, Device Info 0000180a-… 6e400001…/6e400003… 6e400001…/6e400002… false —
    millenniumEONE MillenniumGATT.serviceUUID serviceUUID/notifyCharUUID serviceUUID/writeCharUUID false —

    Note

    ChessnutGATT.*/MillenniumGATT.* resolve to literal UUIDs inside BoardKit, not FianchettoKit — cited here by symbolic name, not hex this package can't verify.

    BoardGATTSpec.auxiliaryNotifyEndpoints subscription is best-effort: a missing auxiliary endpoint never fails the connection. Chessnut is the only brand that populates it — commandResponseChar (stored-game download replies) and fileChar (the archive itself) — and neither is the primary board-state notify channel, so losing one costs a feature (stored-game import), not the connection.

    serviceUUIDs — a computed property, distinct from scanServiceUUIDs — is the narrower set of services the transport discovers characteristics on: a case-insensitively de-duped [txServiceUUID, rxServiceUUID, advertisedServiceUUID].compactMap { $0 }. It deliberately excludes ChessUp's 0000180a Device Information service even though that UUID is in scanServiceUUIDs (an advertising filter only) — discovering characteristics there costs a round trip for a service the protocol never touches.

    Name and scan matching¶

    BoardCatalog.matchesScan(key:name:advertisedServiceMatches:) =
    !excludes && (serviceMatch || includes)

    Exclusion wins. For .chessnutAir, excludes = ChessnutGATT.isMoveProfile(name:) — the Chessnut Move shares every GATT UUID with the Air/classic profile, so a service-UUID match alone must never pull a Move into .chessnutAir. The other three keys have no shared-UUID sibling: advertisedServiceMatches || matchesName(key:name:).

    scansByName(key:) is false for squareOffPro/chessUp2 (they advertise their service UUID directly) and true for chessnutAir (two 128-bit service UUIDs don't fit a 31-byte advertising packet) and millenniumEONE (advertises only the Local Name "MILLENNIUM CHESS", no service UUID). A scansByName == true board must run a broad withServices: nil scan and filter every discovered peripheral through matchesScan in the callback.

    import FianchettoKit
import BoardKit

let key = BoardCatalogKey.chessnutAir
let adapter = key.makeAdapter()          // ChessnutAdapter()
let spec = key.gattSpec                  // BoardGATTSpec

if key.scansByName {
    let belongsHere = key.matchesScan(
        name: advertisedLocalName,
        advertisedServiceMatches: sawOneOf(spec.scanServiceUUIDs)
    )
}

key.displayName            // "Chessnut"
key.kotlinManagerClass     // "fianchetto/module/ChessnutBleManager"

    BoardCatalog.chessnutBeepData(frequency:durationMs:) forwards to ChessnutAdapter.beepData(frequency:duration:) so the app can drive the one beeper in the fleet without importing ChessnutAdapter directly.

    Transport lifecycle policy and connection ownership¶

    BoardTransportLifecyclePolicy centralizes "is it safe to touch the transport right now" so the iOS and Android radios can't drift into one platform tearing down an adapter the other is still using:

    allowsScan(from:) / allowsBoardTypeChange(from:) — true only for:
    .idle, .disconnected, .poweredOff, .unauthorized
                                        — false for:
    .scanning, .connecting, .connected, .reconnecting

isTerminalConnectionAvailabilityState(_:) — true only for:
    .poweredOff, .unauthorized

statePoweredOn(reconnectIsRunning:attempt:) =
    reconnectIsRunning ? .reconnecting(attempt: attempt) : .idle

resolvesDeferredScanOnPowerOn(reconnectIsRunning:) = true   // always

    .poweredOff/.unauthorized are deliberately allowed for scan/type-change so the platform can still run its native retry/permission flow; any state with a connection attempt in flight blocks both. statePoweredOn keys off whether a reconnect task is alive rather than the last-written state value — a radio bounce during a reconnect loop can otherwise write .poweredOff over .reconnecting, and "don't clobber .reconnecting" can't fire on the way back up if it's reading a state the bounce already overwrote.

    Connection ownership¶

    BoardConnectionGeneration is the monotonic token guarding a delayed async BLE callback against mutating state after its connection attempt is obsolete:

    begin():            current &+= 1; isActive = true      // returns the new token
activate(token):     current  = token; isActive = true   // process-wide token (Android JNI)
invalidate():        isActive = false
accepts(g):          isActive && g == current

    activate(_:) exists because Android's singleton JNI bridge can outlive and retarget multiple transport instances — a per-instance begin() counter starting at 1 isn't sufficient there, since two transports would both start at the same value.

    Write pacing¶

    BoardWriteQueue<Owner: Equatable & Sendable> is a deterministic FIFO for physical writes, combining a per-command delay with the adapter's minimum write interval:

    nextAction(activeOwner:now:):
    drop every queued entry whose owner != activeOwner
    if queue empty: .none
    if first write since reset():  required = delayBefore;                          anchor = enqueuedAt
    else:                          required = max(delayBefore, minimumWriteInterval); anchor = lastWriteAt
    if (now - anchor) < required: .wait(required - elapsed)
    else: dequeue; .write(payload, owner)

    The caller performs the write, then calls didWrite(at:) to record the timestamp nextAction paces off next. reset() drops queued entries and forgets lastWriteAt, for when the transport swaps links.

    The session state machine (EBoardSessionCore, EBoardEffect)¶

    EBoardSessionCore is a final class, not @Observable, never crossing an actor boundary — called synchronously from whichever @MainActor shell owns it:

    public private(set) var awaitingPromotionFromUCI: String?
    public private(set) var lastReportedOccupancy: [Bool]?
    public private(set) var boardPromotionPick: PieceType?
    public private(set) var lastReportedIdentity: [Piece?]?

    public func clearPendingOutbound()
    public func handle(event: BoardEvent, game: GameView, orientationFlipped: Bool) -> [EBoardEffect]
    public func completeBoardDiffResolution(

    public func present(move: Move, positionBefore: Position) -> [EBoardEffect]
    public func forceApply(uci: String, game: GameView) -> [EBoardEffect]
    public func applyResolution(_ resolution: BoardDiffResolver.Resolution, game: GameView) -> [EBoardEffect]
    public func syncAfterPromotion(game: GameView) -> [EBoardEffect]
    public func completePromotion(pieceType: PieceType, game: GameView) -> [EBoardEffect]

    Every call takes a GameView — a closure-free value snapshot the shell builds fresh each cycle, which keeps the core testable without a live Game or a SwiftUI host:

    public struct GameView {
    public let position: Position
    public let currentNodeUCI: String?             // for promotion-completion detection
    public let ancestorPositions: [Position]        // up to 6 plies back, shell-precomputed
    public let legalCastlingRookHomes: Set<String>  // e.g. ["a1", "h1"]
    public init(position:currentNodeUCI:ancestorPositions:legalCastlingRookHomes:)
}

    EBoardEffect is the closed, Equatable vocabulary of everything the core can decide — the shell iterates the returned array and applies each case, which is what lets a golden test assert the exact effect sequence a BoardEvent produces:

    Group Cases
    Observable mirrors setLiftedSquare, setLastAppliedMove, setLastReportedOccupancy, setPendingResolutions, setPendingOutbound, setAwaitingPromotionFromUCI, adoptOrientationFlip
    Deferred reconciliation resolveBoardDiff, scheduleStateConfirmation(afterMilliseconds:)
    Game mutations applyMove(uci:), applyResolution(moves:), retractPlies(_:)
    Physical counters bumpPhysicalMoveApplied, bumpTakeback
    Promotion picker showPromotionPicker(from:to:legalUCIs:), dismissPromotionPicker
    Board hardware indicateSquares(_:)

    handle(event:game:orientationFlipped:) is the single entry point; each call re-binds OccupancyMoveInference.isCastlingStillLegal from game.legalCastlingRookHomes, then switches on BoardEvent. The cases the core acts on: .squareSensed, .occupancySnapshot, .disconnected, .promotionPick, .identitySnapshot. .ready, .connected, .raw, .battery, .storedGameImported are no-ops here — the last is a side-channel import result the app session handles before it reaches the move-inference core at all.

    Execution-gate routing¶

    While an app-dictated move (an engine reply, a tap-move) awaits physical execution, pendingOutbound: BoardExecutionGate? reroutes field events away from OccupancyMoveInference entirely:

    if let gate = pendingOutbound {
    switch gate.feed(square: square, isLift: isLift) {
    case .inProgress: return []
    case .executed:   /* clear gate, reset inference, clear LEDs */
    case .deviated:   /* clear gate, LEDs, fall into the diff resolver */
    }
}

    present(move:positionBefore:) arms the gate — the shell must guard transport.state == .connected first, or arming while disconnected blocks inference forever. It snapshots pre-move occupancy into pendingOutboundPreOccupancy; tryResolveAgainstSnapshot treats the board still showing that exact pre-move state as the expected wait state rather than a desync (the "Go auto-takeback fix" — without it, a streaming board's heartbeat frame kept re-running stash/confirm/BFS and eventually retracted the app's own move).

    Lift/place inference¶

    Outside a gated move, field events go to OccupancyMoveInference.handle(square:isLift:), returning .pieceLifted(square), .moveCandidates([String]), or .noChange. .moveCandidates is matched against MoveGenerator.legalMoves(for:) in tryApply; .noChange (a lift returned to its own square) still re-runs the diff resolver so a stale pendingResolutions clears the instant the board re-agrees. A committed move that doesn't consume the triggering lift square gets that lift re-fed, so the opponent's next pickup isn't swallowed.

    Promotion disambiguation¶

    tryApply collects the inference candidates that resolve to a legal promotion move, deduplicated by promotion piece type:

    2+ distinct legal promotion pieces:
  1. boardPromotionPick already reported (BoardEvent.promotionPick, e.g. a
     ChessUp 0x97 frame) -> auto-commit to that piece, no picker
  2. else, an identity-sensing board's latest identitySnapshot shows a piece
     on the promotion square whose type ∈ {queen, rook, bishop, knight} AND
     whose color equals the promoting side's game.position.activeColor
     -> auto-commit to that piece, no picker
     (a still-standing pawn, a king, or a wrong-color spare piece falls
     through — those are the player's own captured pieces set aside)
  3. else -> .showPromotionPicker(from:to:legalUCIs:), awaitingPromotionFromUCI = from+to

Exactly 1 legal promotion piece survives the candidate filter:
  -> auto-promote directly, no picker

    The identity-consult branch runs after the boardPromotionPick check — a hardware-reported pick always wins. A .promotionPick arriving while the picker is already open (the 0x97 frame can race the pawn-placement events either way) auto-completes the promotion and emits .dismissPromotionPicker so the shell closes its UI without a tap.

    Auto-orientation¶

    An .identitySnapshot on a 64-square identity-sensing board (Chessnut Air family) can prove the board is physically rotated relative to the app's orientationFlipped flag:

    on .identitySnapshot(pieces) where pieces.count == 64:
    expected = identityArray(for: game.position)
    adjusted = orientationFlipped ? pieces.reversed() : pieces
    reversed = adjusted.reversed()

    if adjusted != expected && reversed == expected:
        adopt `reversed`; emit .adoptOrientationFlip(!orientationFlipped)

identityArray(for: position):
    out[file * 8 + rank] = position.board[rank * 8 + file]   // rank-major -> file-major, a1..h8

    A position can never equal its own 180°-reversal (the two kings alone forbid it), so "matches un-reversed" and "matches reversed" are mutually exclusive — once adopted, every following frame matches directly and the flip cannot re-fire, closing the "stale persisted flip" class where a leftover flip silently misread every move 180° with no UI surface to discover it.

    .adoptOrientationFlip must not trigger a re-feed

    The core has already stored the corrected arrays for the frame that produced .adoptOrientationFlip. The shell must persist the new flag without running its normal orientation-change re-feed (EBoardShellKernel.orientationRefeed, below) — re-feeding would reverse an already-reversed array a second time.

    Diff resolution and correction flow¶

    tryResolveAgainstSnapshot(game:fromSnapshot:) is the core's desync classifier, run on every .squareSensed, .occupancySnapshot, and .identitySnapshot, in order:

    1. pendingOutbound != nil && occupancy == pendingOutboundPreOccupancy
       -> expected pre-move wait state; clear stash; []

2. gameOccupancy == occupancy
       -> in sync; clear stash; [.setPendingResolutions([])]

3. lift-in-progress guard (occupancy is a strict subset of gameOccupancy —
   squares only vacated, none newly filled)
       -> pure lift; clear stash; [.setPendingResolutions([])]
       (defer to OccupancyMoveInference, fed by the same frame's deltas)

4. stability gate: occupancy != unconfirmedMismatch
       -> stash it; [.scheduleStateConfirmation(afterMilliseconds: 500)]

5. occupancy == unconfirmedMismatch but !fromSnapshot
       -> still waiting; [.scheduleStateConfirmation(afterMilliseconds: 500)]

6. occupancy == unconfirmedMismatch && fromSnapshot
       -> clear stash; [.resolveBoardDiff(EBoardDiffRequest(position, occupancy))]

    The stability gate (4–6) exists because continuously-streaming boards (Chessnut Go) emit frames during a move — a piece slid across the board, or resting off-centre and crosstalking an adjacent square — producing a one-frame mismatch that is neither in-sync nor a pure lift. It requires the same mismatched occupancy on two consecutive snapshot-originated observations before the depth-3 BFS runs.

    A delta-path re-entry cannot self-confirm

    fromSnapshot distinguishes a full snapshot from a delta-path re-entry (a deviation, a no-change, a failed-candidate fallback) — both observe lastReportedOccupancy, so without this gate a delta-path call re-observing the same physical frame would confirm the stash against itself. This happened once: hand-shadowing crosstalk during 1...e6 self-confirmed and the resolver fabricated [e7e5, d4e5], silently corrupting the game.

    The lift-in-progress guard (3) exists separately because occupancy-only boards (Millennium eONE) auto-report a full frame on every sensor change, including the transient "lifted, not yet placed" instant at the start of a move — occupancy-indistinguishable from a completed capture. Without it, the BFS can fabricate a spurious multi-ply capture chain and auto-apply it: a c7 lift mid 1.d4 d5 2.c4 c6 once resolved to the unique [c7c5, c4d5, c5c4], leaving white pawns on both d4 and d5.

    Resolving and applying¶

    EBoardDiffResolutionCoordinator moves the BFS off @MainActor:

    public init(resolver: @escaping Resolver = { request in
    BoardDiffResolver.resolve(
        from: request.position,
        targetOccupancy: request.targetOccupancy,
        maxDepth: 3,
        limit: 8
    )
})

    It runs the search on a Task.detached, keeps a one-entry (cachedRequest, cachedResolutions) memo so an identical request served twice is free, and tags every request with a generation counter (generation &+= 1 on every invalidation) so a completed-but-stale search can never publish over newer game state. completeBoardDiffResolution re-validates the request against the current position and occupancy first — defense-in-depth layer one, independent of the coordinator's own generation check:

    resolutions.count == 1:
    if first.moves.count > 1 && resolutionContainsCapture(first, from: request.position):
        -> [.setPendingResolutions(resolutions)]     // demoted for user confirmation
    else:
        -> applyResolutionEffects(first)             // auto-applied

resolutions.count > 1:
    -> [.setPendingResolutions(resolutions)]

resolutions.isEmpty:
    if pendingOutbound == nil: try BoardTakebackDetector.pliesToUndo(boardOccupancy:ancestorPositions:)
    else:                      -> [.setPendingResolutions([])]   // gate still armed; not a takeback

    resolutionContainsCapture walks the resolution's UCI moves against a scratch position; a move counts as a capture if its destination is occupied before the move, or it is en passant. An unparseable UCI counts as a capture too, failing toward the safer, user-confirmed path.

    Multi-ply capture chains are demoted, not blocked

    A single-resolution quiet multi-ply catch-up (moves played while the app looked away) still auto-applies. Only a multi-ply resolution containing a capture is demoted — a capture is the only way the BFS can "explain away" a sensor-dropout-vacated square, so a fabricated chain and a genuine quiet catch-up need different defaults.

    Takeback detection only runs when pendingOutbound == nil — while a gate is armed, the board showing an ancestor position is the expected pre-execution state, not proof of a physical takeback.

    Correction-instruction text¶

    BoardSyncPresentation supplies the shared strings both platforms' sync sheet and OTB status strip render:

    State Title Subtitle

    // "Place the White Queen on d1"

corrections.placeSquares    // expected occupied, board empty

    Cross-platform shell glue: EBoardShellKernel¶

    EBoardShellKernelContext is the @MainActor protocol both platform EBoardSession shells conform to — observable mirrors named to match each shell's @Observable stored properties (conformance is automatic), bridged internals (sessionCore, diffResolution, suppressRefeedFlag, …), and platform services (sendBoardCommand, kernelLogNotice, persistDiagnostics, …).

    EBoardShellKernel.apply(_:context:) is an exhaustive switch over EBoardEffect — a new case fails compilation here, in exactly one place, preserving the parity the shells' hand-mirrored switches used to provide only by discipline. Nine cases are applied directly (setLiftedSquare, setLastReportedOccupancy, setPendingResolutions, resolveBoardDiff, scheduleStateConfirmation, setPendingOutbound, setAwaitingPromotionFromUCI, adoptOrientationFlip, indicateSquares); eight are platform-divergent and return false: setLastAppliedMove, applyMove, applyResolution, retractPlies, bumpPhysicalMoveApplied, bumpTakeback, showPromotionPicker, dismissPromotionPicker.

    .setLastReportedOccupancy and .setPendingResolutions are equality-gated before the @Observable write — streaming boards emit identical heartbeat frames continuously, and an ungated assignment fired Observation per BLE frame (the resolver bookkeeping underneath still runs unconditionally). A non-empty .setPendingResolutions only logs/annotates when EBoardDiagnosticDeduplication.desyncKey(positionFEN:occupancyHex:resolutions:) differs from the last-logged key — the same content-key mechanism the diagnostic capture uses to collapse repeated frames.

    Orientation re-feed¶

    EBoardShellKernel.orientationRefeed(context:) replaces ~56 hand-mirrored lines per shell. On an orientation flag change it reverses the shell's lastReportedOccupancy/liftedSquare mirrors (via ChessBoardGeometry.flippedSquare(_:)), then re-feeds the core a synthetic, already-corrected snapshot — .identitySnapshot if core.lastReportedIdentity is non-nil, else .occupancySnapshot — with orientationFlipped: false since the arrays are pre-corrected. Any .adoptOrientationFlip the core would compute on that synthetic feed carries wrong flag semantics, so it (and the fed-back .setLastReportedOccupancy) is filtered from the applied effects: a manual toggle stays manual, and the next real frame still auto-corrects.

    Field diagnostics¶

    EBoardDiagnosticCapture — always-on ring buffer¶

    EBoardDiagnosticCapture is a BlobBackedStore (blobKey = "eBoardDiagnosticCapture") that starts recording as soon as a board session exists — no opt-in toggle, since its content is board-protocol data only (no player names, no device UUID), so always-on is safe by construction.

    cap = 500 entries

appendRaw(bytes:):
    hex = space-separated lowercase hex of the bytes
    if last entry is .rx AND sameState(last.data, hex, keyByteCount: stateKeyByteCount):
        merge: repeatCount += 1; lastOffsetMs = now      // collapse the run in place
    else: append a new EBoardDiagnosticEntry(kind: .rx)

stateKeyByteCount(forBrand:):
    "chessnutAir" -> 34
    everything else -> nil    // compares the WHOLE frame (always safe, never over-merges)

    An entry is a run of identical frames, not one slot per frame. The 34 came from a field capture: a Chessnut Air frame changed only at bytes 21 and 25, byte 34 was a free-running counter cycling through 55 distinct values, and every other trailing byte was static — collapsing on the full 38-byte frame yielded 57 ring entries for 500 raw frames; collapsing on the leading 34 yielded 3. The ring buys state changes, which is what a desync investigation actually reads.

    EBoardDiagnosticEntry.Kind is rx | lifecycle | comment; appendLifecycle(_:) records "connected"/"disconnected", annotate(_:) records free text (FEN, UCI, desync notes — never player names). asReplayText() renders .replay format text, valid input for ReplayScript.parse(text:) and replayable with zero live hardware:

    var capture = EBoardDiagnosticCapture()
capture.startSession(boardBrandRawValue: "chessnutAir")
capture.appendRaw(bytes: frame)
capture.annotate("desync fen=\(fen) choices=\(resolutions.count)")
let text = capture.asReplayText()
// "# board: chessnutAir"
// "# privacy: content-only (board frames + moves; no player names, no device ID, relative timestamps)"
// "rx 4d 43 ..."
// "# repeated x12 over 1100ms"

let steps = try ReplayScript.parse(text: text)
let replay = ReplayTransport(adapter: SquareOffAdapter(), parsedScript: steps)
let events = replay.runSync()
// Feed `events` through EBoardSessionCore.handle(event:game:orientationFlipped:)
// for deterministic decision replay of a field bug.

    Desync deduplication¶

    A board parked in one persistently-mismatched state would otherwise fill the ring with the same annotation on every frame. EBoardDiagnosticDeduplication keys on content, not time, so re-observing the same mismatch is a no-op:

    EBoardDiagnosticDeduplication.desyncKey(
    positionFEN: String, occupancyHex: String,
    resolutions: [BoardDiffResolver.Resolution]
) -> String
// "\(positionFEN)|\(occupancyHex)|" + resolutions
//     .map { $0.moves.joined(separator: ",") }
//     .joined(separator: ";")

    EBoardShellKernel compares this key against context.desyncDedupKey on every non-empty .setPendingResolutions and, only when it differs, logs

    squareoff desync: fen=<fen> choices=<n> board=<hex>

    via context.kernelLogNotice(_:) and annotates desync fen=<fen> choices=<n> into the diagnostic capture — so a board stuck in one mismatched state produces one ring entry, not five hundred.

    EBoardDiagnosticPersistenceCoordinator — debounced writes off-main¶

    Encoding a 500-entry capture and atomically replacing its file is delegated to this @MainActor coordinator plus a private, non-MainActor Worker actor:

    public init(debounceNanoseconds: UInt64 = 250_000_000)   // 250ms
public func schedule(
    _ capture: EBoardDiagnosticCapture,
    immediate: Bool = false,
    writer: @escaping @Sendable (String) -> Bool
)

    let persistence = EBoardDiagnosticPersistenceCoordinator()
persistence.schedule(capture) { json in
    (try? json.write(toFile: diagnosticsPath, atomically: true, encoding: .utf8)) != nil
}
persistence.schedule(capture, immediate: true, writer: writeToDisk)   // lifecycle/takeback boundaries

    Each call bumps a revision counter; the Worker actor only acts on a call whose revision is still the newest it has seen, and skips re-encoding entirely when capture == lastPersisted — an unchanged snapshot never touches JSONEncoder. immediate: true still performs the encode/write on the worker actor; it only collapses the coalescing delay to zero, for boundaries that should survive an abrupt app exit.

    Headless surfaces and CLI opportunities¶

    Everything through "Diff resolution and correction flow" — BoardBrand, BoardGATTSpec, BoardCatalogKey/BoardCatalog, BoardConnectionGeneration, BoardTransportLifecyclePolicy, BoardWriteQueue, EBoardEffect, EBoardSessionCore, EBoardMoveResolution, EBoardPositionTransition, BoardSyncPresentation, EBoardDiagnosticCapture — is headless: no @MainActor, no SwiftUI, no Compose. Only EBoardShellKernelContext/ EBoardShellKernel, EBoardDiffResolutionCoordinator, and the outer EBoardDiagnosticPersistenceCoordinator class are @MainActor-bound (its nested Worker actor is not) — they exist specifically to bridge into each shell's @Observable view state.

    fianchetto-cli's existing subcommands (annotate, estimate, maia, accuracy, project, track) all operate on completed games — PGN, FEN, engine analysis — rather than a live BLE session, so none of them currently drive this subsystem. But EBoardDiagnosticCapture's .replay export plus BoardKit's ReplayScript/ReplayTransport already form a complete, deterministic, hardware-free path from a captured field session back through EBoardSessionCore's exact decision code — the same handle(event:game:orientationFlipped:) entry point a live shell calls. A .replay file captured in the field is a natural fit for a future headless CLI regression command: parse the script, replay it through a fresh EBoardSessionCore, and assert the resulting [EBoardEffect] sequence against a golden file — reproducing (and guarding against a regression of) a desync bug without a phone, a physical board, or a UI in the loop.

    See also the storage seam's BoardSyncGate (the board-agnostic clock-pause/haptic kernel, covered in Stores & the storage seam) for the smaller, adjacent state machine that reacts to a desync once EBoardSessionCore has already reported one.
