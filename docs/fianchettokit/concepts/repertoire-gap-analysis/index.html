    Repertoire Gap Analysis: Book Coverage, Personal-Game Sourcing, and the Maia Opponent Model¶

    The Repertoire subsystem is the pure chess-algebra layer behind opening prep: finding the holes in a repertoire, scoring the moves already in it, aggregating a player's own games into a personal book, and exporting/importing the result as PGN. Everything here is portable value types and enum namespaces over ChessCore's Position/Move — the app owns the SwiftData rows, the @Observable state, and the Stockfish/Maia run loops that feed engine results back in.

    Three kinds of gap — and a fourth question¶

    "Gap" means three distinct things in this subsystem, produced by three independent kernels that never overlap:

    Kernel Finds Driven by
    RepertoireBookKernel.computeGaps Positions with no prepared reply at all — book continuations and the player's own faced games that the repertoire doesn't answer OpeningBook + an optional PersonalGamesSnapshot
    RepertoireAuditKernel Moves the repertoire does prepare, that are objectively weak Stockfish (engine-free kernel; the app supplies the eval)
    RepertoireOpponentModelKernel Replies inside the repertoire's own tree that a human opponent is likely to play, with no prepared answer Maia's move-probability policy

    The first two are inward-looking — they audit what's written down. A repertoire can pass both (no unfinished lines, no weak moves) and still collapse the first time an opponent plays a natural-but-unbooked move on move 6, because nothing ever asked "what will a human actually do here?" That's the question RepertoireOpponentModelKernel answers, using the same Maia policy RepertoireAuditKernel already consults for maiaRank/maiaTopSAN.

    A fourth question sits beside the three, and it is the only one that looks at games the user actually played: RepertoireDeviationKernel asks when you sat down and played, did you follow this, and what happened when you didn't. It has its own section below, as do the verdict types every scan shares (RepertoireScanOutcome/RepertoireScanStatus), the evidence-and-claim rules that decide what a face may print about a number, the guided-expansion walk, the leech aggregation, the editing policy, and the per-repertoire health digest that sums the whole surface up.

    Core data model¶

    Every kernel in this subsystem shares one representation of "what's prepared":

    public typealias RepertoireMoves = [String: [String: String?]]
// positionKey → san → comment?

    The positionKey is always OpeningBook.epNormalizedKey — never a raw FEN — so transpositions collapse into one dictionary entry regardless of move order:

    epNormalizedKey(pos) = first 4 space-separated FEN fields, with the
                       en-passant field replaced by
                       pos.capturableEnPassantTarget?.algebraic ?? "-"

    A raw FEN records an en-passant target after every double pawn push, even when no enemy pawn can actually capture there — a "phantom" EP square. Dropping it means 1.d4 e6 2.c4 d5 and 1.d4 d5 2.c4 e6 — different move orders reaching the same Queen's Gambit Declined position — hash to the identical key. Every gap walk, every coverage index, and the personal book all key off this one function, so a Slav repertoire can recognize a Semi-Slav transposition it never literally walked.

    The lookup surface over RepertoireMoves is small:

    public struct MoveInfo: Sendable, Hashable {
    public let san: String
    public let comment: String?
    public var annotation: String? = nil
}

RepertoireBookKernel.moves(at: position, in: repMoves)              // [MoveInfo], SAN-sorted
RepertoireBookKernel.isRepertoireMove("Nf3", at: position, in: repMoves)  // Bool
RepertoireBookKernel.crossSuggestions(at: position, own: white, opposite: black)

    crossSuggestions surfaces moves the other colour has prepared at the same position that this colour hasn't — "you also study this from the other side."

    OpeningBook: the shared opening database¶

    OpeningBook wraps a precomputed ECO dataset (entries: position → Entry, continuations: position → [BookMove]), loaded once from JSON or plist and installed process-wide:

    OpeningBook.configureShared(precomputedData: data, isPlist: false)  // discardable Bool
let book = OpeningBook.shared

    configureShared only installs a book that decoded to at least one entry — a failed or empty load leaves the previous shared value untouched, so a missing resource fails loudly rather than making every lookup silently return nil/"Unknown".

    Phantom-EP fallback. Because the book is keyed by raw FEN internally, entry(for:) retries with the EP-normalized key before giving up:

    entry(for: position):
    raw = positionKey(position)                 // pos.positionKey, un-normalized
    if entries[raw] exists → return it
    normalized = epNormalizedKey(position)
    if normalized == raw → return nil            // nothing to drop
    return entries[normalized]                   // fallback only ADDS hits, never overrides

    continuations(for:) runs the same fallback and additionally resolves each book SAN's openingName/eco from the position it leads to (not just the raw book row), so a continuation lands on its own canonical name rather than its parent's. Results are cached by a private NSLock-guarded ContinuationsCache — countLimit = 4096, evicting ~10% of entries (storage.count / 10, at least 1) on overflow rather than tracking true LRU, since opening-book lookups are dominated by a small set of hot positions anyway. Empty results are cached too, so a non-book position doesn't repeat the dictionary probe.

    ECO canonical-name resolution. Loading a book runs a BFS from the initial position over its own continuation graph, assigning a ply depth to every reachable entry:

    for each ECO code:
    canonical name = the entry with the MINIMUM BFS ply depth
    ties broken lexicographically by name

orphan entries unreached by BFS get depth Int.max
    (chosen only when they're the sole entry for their ECO code)

    This replaced an older shortest-name-string heuristic, which picked "Amazon Attack" (13 chars, ply 3) over "Queen's Pawn Game" (17 chars, ply 2) for D00 — shorter text, but a deeper, less representative line.

    findPath(to:) is a separate, uncapped BFS reconstructing the shortest book SAN path to a target epNormalizedKey — used to retroactively derive anchorLineSAN for repertoires anchored before that field existed. It walks the whole graph before giving up on an unreachable target, so it's opt-in (searchBook: on RepertoireBookKernel.anchorPly) and only enabled on off-main scans that already traverse the book.

    Gap walk algorithm: computeGaps¶

    computeGaps is a pre-order walk of the repertoire's own move tree, looking for two things at once: user-turn positions with nothing prepared, and opponent-turn positions where the book (or the player's own games) lists a reply the repertoire doesn't have.

    It uses an explicit stack, not recursion — cooperative-pool threads have roughly 512KB stacks, and a line at the subsystem's 10⁴-position design target overflowed the recursive form. The stack holds two item kinds so that book-gap emission can be deferred until every child subtree has finished:

    enum WalkItem {
    case visit(position: Position, moveSequence: [String], lastNamed: (name: String, eco: String?)?)
    case emitBookGaps(position: Position, moveSequence: [String], key: String, lastNamed: (name: String, eco: String?)?)
}

    Children are pushed reversed so sorted-SAN order pops first (matching recursive pre-order exactly), and on an opponent-turn node .emitBookGaps is pushed beneath the children — so it only runs after every rep-move subtree below it has already claimed its visited entries. This preserves "first-reached-wins" transposition semantics and gap suppression order identically to what a recursive walk would produce.

    Three sources feed the gap list:

    1. User-turn dead end. If it's the player's move and the map has no SAN at this key (and the walk didn't just start here), emit a gap with gamesEncountered: 0 and theoryDepth = the book's continuation count at this position.
    2. Book continuation not covered. On an opponent-turn node, for every book SAN not in the repertoire's own SAN set at this key: skip it if the walk already visited the resulting position, or if repertoire[nextKey] already answers it by a different move order (the self-transposition guard — tested against the raw map directly, never through sibling coverage, so a sibling can never silently outvote your own prep).
    3. Personal-game sideline. If a PersonalGamesSnapshot was supplied, a second pass over the same opponent node adds gaps for replies the player has actually faced that the book doesn't list and the repertoire doesn't answer, gated by:
    public static let personalGapEncounterThreshold = 2   // one game is an anecdote

    Such gaps set fromPersonalGames: true, and if the target position has no book name of its own, they inherit the deepest named ancestor seen so far on the walk with a " sideline" suffix (e.g. "Caro-Kann Defense sideline") rather than surfacing unnamed.

    The final sort is:

    1. coveredByRepertoireID == nil first    // an uncovered line always outranks one
                                          // a sibling repertoire already answers
2. gamesEncountered descending
3. theoryDepth descending
4. moveSequence.count ascending

    Rule 1 exists because transpositions into a well-studied sibling carry the highest gamesEncountered counts on the list — left unranked, they'd float to the top of a "study next" view even though they need no work.

    Anchors: why anchorPly doesn't trust the FEN¶

    Everything that numbers or scopes an anchored sub-repertoire — gap moveSequences, exported PGN, sibling-coverage ranking — needs to know how deep its anchor sits. The anchor's own FEN cannot reliably answer that.

    plyIndex(of: position) = (fullmoveNumber - 1) * 2 + (activeColor == .black ? 1 : 0)

    An anchor is captured as whatever the board held at capture time, and a board reloaded from a bare four-field position key — the shape epNormalizedKey produces, and the shape both the opening book and the repertoire store key by — carries fullmoveNumber == 1 no matter how deep the real position sits. A genuine 3...c6 Semi-Slav anchor can therefore claim to be move 1, and everything derived from it — gap lines numbered 1.Nf3, exports numbered from move 1, a pre-anchor guard that lets the whole reaching line through — reads one full opening too early.

    anchorPly(anchorFEN:anchorLineSAN:searchBook:) resolves the true ply in strict priority order, because each source is progressively less trustworthy than the last:

    1. the replayed ply of anchorLineSAN — accepted ONLY when replaying it from
   the game start actually reaches the anchor's epNormalizedKey
2. only when searchBook: true — the replayed ply of
   OpeningBook.shared.findPath(to: anchorKey)
3. plyIndex(of: anchoredPosition)             (the FEN's own counters, last resort)

    Step 1 wins whenever it's available, because the reaching line's length is the ply with no reconstruction needed — every anchor stored since 2026-06-22 carries one. Step 2 exists for older anchors that predate that field: it recovers the same fact by asking the book for its own shortest path to the anchor — which is exactly the uncapped findPath BFS described above, and the reason searchBook defaults to false and is opt-in rather than automatic. Only the iOS gap scan, which already walks the whole book off-main, turns it on; export, punish generation, and the Android surfaces stay on the FEN fallback. Step 3 only fires for the shrinking tail of anchors with neither a reaching line nor a book path, and reads one opening too early exactly as it always did — not a regression, the pre-existing behavior this function narrows down to a last resort.

    RepertoireBookKernel.position(_:restatedAtPly:) sets fullmoveNumber = ply / 2 + 1 on an anchored position once its true ply is known, so every position derived downstream — the walk in computeGaps, buildPositionIndex, the audit's AuditCandidate.moveNumber — numbers correctly too.

    The forced root: forcedRootAnchor and scopedWalkRoot¶

    Ply mistrust is one problem; scope is a different one. An unanchored repertoire walked from move 1 flags every un-prepared opponent first move as an uncovered line: a 1.d4 e6 repertoire surfaces 1.c4, 1.e4, and every other opening the player never intended to study, because nothing about a move-1 walk knows the player is only accountable for positions reachable through 1.d4 e6.

    forcedRootAnchor(repMoves:color:) finds where that accountability starts. It follows the repertoire's forced (single-continuation) prefix from the start position and returns the FEN and ply immediately after the player's own first move — the point the repertoire's identity is actually established. It returns nil in three cases: the prefix isn't forced up to that point (the repertoire genuinely branches across several first moves), there's no own move to reach at all, or the player is on move at the very root (a White repertoire, where nothing precedes their first move, so a move-1 walk already excludes nothing it shouldn't). Scoping only helps when the opponent moves first — precisely the case that leaks pre-repertoire lines.

    scopedWalkRoot(repMoves:color:anchorFEN:anchorLineSAN:searchBook:) picks the actual walk root for one repertoire: its own anchor when it has one (through anchorPly), else the derived forced root, else the game start — carrying the ply alongside the FEN in every case, since the ply cannot be recovered from a restated FEN alone. gapsForRepertoire composes both calls together for exactly this reason: the Apple app and LibraryStoreKernel had each written out the anchor-then-ply pairing separately, and the CMP bridge was about to be a third copy — which is where a pairing like this starts to silently disagree.

    Sibling coverage: coverageIndex and assignGap¶

    A scoped, single-repertoire walk can't see that a position transposes into a different same-colour repertoire's territory. coverageIndex(of:) builds a flat positionKey → UUID map over every sibling's RepertoireTerritory (its own move-map keys, plus its anchorPrefixMap's on-ramp keys):

    rank territories by:  anchorPly descending, then caller order, then UUID string
                       (deeper/more-specific anchor wins a shared position)

pass 1 (real prep):    first claim per key wins, most-specific first
pass 2 (on-ramp only):  anchored territories additionally claim their
                        anchorPrefixMap(line:) keys — the positions BEFORE
                        their anchor that store no real moves — ranked
                        below pass 1 so real prep always wins a shared key

    Pass 2 exists because an anchored sub-repertoire stores nothing before its own anchor, yet the app already displays its reaching line as "prepared" — without it, a gap one ply before a sibling's anchor goes untagged. Passing the resulting map into computeGaps(siblingCoverage:) never changes which gaps are emitted; it only stamps coveredByRepertoireID, which the sort above then uses.

    assignGap does the analogous job for the whole-colour overview scan — attributing each gap to the most specific anchored sub-repertoire on its path:

    public static func assignGap(
    _ gap: RepertoireGap,
    anchors: [(id: UUID, anchorFEN: String?)],
    mainID: UUID?
) -> UUID?

    It replays gap.moveSequence from the initial position, recording the epNormalizedKey at every ply, and returns the id of the anchor whose key appears at the deepest ply on that path — mainID if none match.

    let coverage = RepertoireBookKernel.coverageIndex(of: territories)

let gaps = RepertoireBookKernel.computeGaps(
    color: .white,
    repMoves: mySlavRepertoire,
    anchorFEN: slavAnchorFEN,
    owningRepertoireID: slavID,
    personalStats: PersonalOpeningBookKernel.gamesSnapshot(from: personalTree),
    siblingCoverage: coverage
)

for gap in gaps where gap.coveredByRepertoireID == nil {
    let line = RepertoireBookKernel.numberedLine(gap.moveSequence, startPly: gap.startPly)
    print(line, gap.openingName ?? "—", "faced \(gap.gamesEncountered)×")
}

    Anchor suggestions¶

    suggestAnchors clusters overview gaps (startFEN == nil) by opening family and proposes a new anchored sub-repertoire for any cluster that's dense by the player's own experience:

    familyKey(gap):
    if gap has a book name: substring before the first ':', with any
                             " sideline" suffix stripped
    else:                    the first two plies of moveSequence, joined

keep a cluster only if:
    members.count >= minGaps (default 5)  OR  Σ gamesEncountered >= minEncounters (default 10)

anchorLine = longest common move-sequence prefix across the cluster's members
require anchorLine.count >= minAnchorPly (default 3)     // else "everything after 1.e4"
skip if replay(anchorLine).fen is already in existingAnchorFENs

sort suggestions by: totalEncounters desc, gapCount desc, name asc

    The thresholds are deliberately encounter-weighted rather than book-breadth weighted: prompting off book size alone would nag a broad-theory player into a dozen repertoires, while gating on what opponents actually play only suggests new structure where the player's own games demand it.

    let suggestions = RepertoireBookKernel.suggestAnchors(
    gaps: overviewGaps.filter { $0.repertoireID == mainWhiteID },
    existingAnchorFENs: existingAnchors
)
for s in suggestions {
    print(s.name, s.anchorLine.joined(separator: " "), "\(s.totalEncounters) games")
}

    The audit model: RepertoireAuditKernel¶

    RepertoireAuditKernel is engine-free — it builds candidate lists to probe and turns Stockfish/Maia results the caller supplies into scored findings.

    public struct AuditConfig: Hashable, Sendable {
    public var movetime: Int                  // Stockfish think time, ms
    public var cpLossThreshold: Int           // flag threshold: cp lost vs engine's pick
    public var alternativeMustBeWithin: Int   // max cp loss for engine's #2 to count as "a good alternative exists"
    public var maiaElo: Int                   // rating used to judge how natural a sound move is

    public init(movetime: Int = 1500, cpLossThreshold: Int = 80,
                alternativeMustBeWithin: Int = 120, maiaElo: Int = 1500)
}

public struct PunishConfig: Hashable, Sendable {
    public var movetime: Int          // Stockfish think time, ms
    public var topK: Int              // Maia replies weighed per opponent node
    public var opponentElo: Int       // rating Maia is conditioned on
    public var swingThreshold: Int    // min cp swing (opponent POV) to count as punishable
    public var maxExtraPly: Int       // ply past the repertoire's own lines to explore
    public var maxExtendedNodes: Int  // cap on nodes the extension walk may find

    public init(movetime: Int = 1500, topK: Int = 4, opponentElo: Int = 1500,
                swingThreshold: Int = 120, maxExtraPly: Int = 4, maxExtendedNodes: Int = 40)
}

    cpLossThreshold (80) is roughly a third of a piece; swingThreshold (120) is roughly a clean pawn — both centipawn-scale defaults chosen to flag real mistakes without drowning the list in engine hair-splitting.

    Note

    maxExtraPly/maxExtendedNodes bound the multi-ply Stockfish walk that explores beyond the repertoire's stored lines when hunting for punish material. collectOpponentNodes (below) only walks positions reachable through the repertoire's own moves — but the extension past that boundary, its scoring and ranking, cache identity, cancellation, and the PunishNodeSnapshot checkpoint that lets it resume all live in RepertoirePunishProducer, which is part of this kit, not app code. It runs @MainActor — the one stated exception to this document's headlessness claim (see below) — not because it touches SwiftData or UI itself, but because the Stockfish/Maia transports its Dependencies struct wires in are MainActor-owned on Apple's shipping app; a desktop or CLI caller drives the same producer through an ordinary actor hop rather than a fresh integration.

    Config fingerprint. Both configs hash to a deterministic Int via a shared FNV-1a-style fold, used to invalidate cached findings when the user changes settings (Swift's Hasher is per-process seeded and wouldn't match across launches):

    fingerprint = 1469598103934665603                       // FNV-1a-style offset basis
for byte in "maia3-policy-serving-v2".utf8:              // maiaServingContractSalt
    fingerprint = (fingerprint ^ byte) * 1099511628211    // prime
fingerprint = (fingerprint ^ 0) * 1099511628211           // separates salt from values
for value in [config's Int fields, in declaration order]:
    fingerprint = (fingerprint ^ value) * 1099511628211

    The salt is folded in first so the fingerprint also captures which Maia serving contract produced the cached maiaRank/probabilities — bumping it invalidates every cache without touching AuditConfig/PunishConfig.

    Candidate discovery. buildPositionIndex replays a repertoire's stored moves from its anchor (or the initial position), indexing every reachable position by epNormalizedKey, depth-capped at 40 ply. auditCandidates turns that into one AuditCandidate per user-turn (positionKey, SAN) pair, skipping any "\(positionKey):\(san)" in a caller-supplied dismissed set, sorted by (positionKey, userMoveSAN) for a deterministic resume order.

    Scoring. The post-move Stockfish eval is from the opponent's POV, so the finding constructors negate it:

    cleanFinding    (engine already prefers the user's move):
    cpLoss = 0                                    // no re-probe needed

flaggedFinding  (engine prefers a different move):
    userMoveCP = -postEvalCP                      // postEvalCP is opponent-POV
    cpLoss     = engineBestCP - userMoveCP

    isCounterintuitive(soundBelow: threshold):
    cpLoss < threshold           // the move is actually SOUND
    AND maiaRank exists AND maiaRank >= 2    // but outside Maia's top-2 human picks

    — flags prep that's correct but hard to find over the board.

    punishSwing(oppBestCP, userBestReplyCP) = oppBestCP + userBestReplyCP

    (The reply position's eval is from the user's POV, so the opponent's value for their own reply is its negation: oppBest − (−userBest).)

    let index = RepertoireAuditKernel.movesIndex(from: repMoves)
let candidates = RepertoireAuditKernel.auditCandidates(color: .white, moves: index)

var findings: [RepertoireAuditFinding] = []
for candidate in candidates {
    // engineBestUCI / engineBestCP / postEvalCP come from the app's own
    // Stockfish driver — this kernel has no engine dependency.
    if engineBestUCI == candidate.userMoveUCI {
        findings.append(RepertoireAuditKernel.cleanFinding(
            for: candidate, engineBestMoveUCI: engineBestUCI, engineBestCP: engineBestCP))
    } else {
        findings.append(RepertoireAuditKernel.flaggedFinding(
            for: candidate, engineBestMoveUCI: engineBestUCI,
            engineBestCP: engineBestCP, postEvalCP: postEvalCP))
    }
}

let weak = RepertoireAuditKernel.flaggedFindings(findings, threshold: RepertoireAuditKernel.AuditConfig().cpLossThreshold)

    Two sort helpers finish the punish pipeline — extracted, per the source comment, because both the iOS and Android shells carried the exact same three lines by hand: RepertoireAuditKernel.rankedPunishItems(_:) and RepertoirePunishDrill.prioritized(_:skipMastered:isMastered:) (the latter optionally filters mastered items first, isMastered arriving as a predicate since mastery lives in the shared SRS store). Both sort by:

    (facedCount, swingCP) descending as a tuple   // most-faced first, biggest swing breaks ties

    RepertoirePunishItem.masteryKey is "rep:\(replyPositionKey):\(refutationUCI)" — namespaced with a rep: prefix into the same mastery store as trap: items and the un-prefixed tactics-blunder queue, keyed by the transposition-aware replyPositionKey.

    Audit cache persistence: one contract, two stores¶

    Audit findings survive an interrupted run through a per-colour cache. The CONTRACT is kit-owned and both faces share it; the STORE differs by face, because the faces have different persistence stacks.

    The shared contract¶

    The payload is RepertoireAuditCacheStorage.Payload — the finding list plus engineRevision, the engine build that produced the verdicts:

    public struct Payload: Codable, Sendable, Equatable {
    public let findings: [RepertoireAuditFinding]
    public let engineRevision: String?   // audit provenance; nil for
                                         // pre-provenance audits
}

    engineRevision rides INSIDE the JSON deliberately: on Apple the row is a SwiftData model mirrored to CloudKit, and a new column there is a schema promotion — the same class of promotion that wedged every device's export for a month when four fields went missing from Production. Inside the blob, it needs no schema change at all. It is optional, so audits written before provenance shipped decode to nil rather than failing.

    Reuse is governed by reusableFindings( cached:cachedFingerprint:expectedFingerprint:candidateIDs:):

    let fingerprint = RepertoireAuditKernel.configFingerprint(auditConfig)

let reusable = RepertoireAuditCacheStorage.reusableFindings(
    cached: cached,
    cachedFingerprint: row.fingerprint,
    expectedFingerprint: fingerprint,
    // AuditCandidate has no `id`; a finding's id is "positionKey:userMoveSAN".
    candidateIDs: Set(candidates.map { "\($0.positionKey):\($0.userMoveSAN)" })
)

    It only returns anything when cachedFingerprint == expectedFingerprint — an exact match; there is no partial reuse across a config change, since a changed cpLossThreshold or Maia contract can retroactively flag or clear any cached finding. Reused entries are also pruned to the current candidate set, so moves deleted from the repertoire stop being cached.

    The portable store: RepertoireAuditCacheStorage¶

    The Android/CLI face persists the payload as two independently durable blobs, one per colour, over the FileJSONBlobStore seam:

    key(for: "white") = "local.repertoireAuditCache.v1.white"
key(for: "black") = "local.repertoireAuditCache.v1.black"
maximumBytes = 64 * 1024 * 1024   // 64MB — StorageError.oversized past this

    save(color:fingerprint:findings:store:auditedAt:) de-duplicates findings by id (last one in the list wins), encodes with [.sortedKeys, .withoutEscapingSlashes] for byte-stable output, writes durably, then reads the blob straight back and byte-compares it — a failed round-trip is reported as a verification error rather than silently trusted. The keys are reserved from generic progress discovery and explicitly carried by the library-backup restore journal: mergedRows(store:overlayRows:) lets live per-colour rows override an older exported envelope, so upgrades and cross-platform restores do not discard valid cache state.

    The Apple store: RepertoireAuditCache rows¶

    The Apple face persists the same payload as SwiftData rows — RepertoireAuditCache, one per colour, carrying the payload JSON, the fingerprint and auditedAt. The store is CloudKit-mirrored (it is one of the types the schema-parity gate watches), so a device sees the audit another device ran — the same cross-device rationale the coverage cache's SyncedJSONBlob row has. What the file-backed path does with a read-back byte-compare and a hard size cap, the Apple path gets from SwiftData's own transactional row write; the contract above (payload shape, exact-fingerprint reuse, candidate pruning) is unchanged.

    The auditor's incremental cadence sits on top: every evaluated position — clean OR flagged — is stored keyed by "positionKey:userMoveSAN", flushed every cacheFlushInterval probes, so an interrupted run resumes instead of replaying the whole library.

    Engine provenance: RepertoireAuditProvenance¶

    The engine build behind a stored audit is recorded and REPORTED, never enforced. RepertoireAuditKernel.configFingerprint covers the probe settings and invalidates the cache when they change — a different threshold answers a different question. Engine build is not like that: Stockfish 19 disagrees with 18 by a few centipawns nobody exploits, so an upgrade must not invalidate thousands of audited moves and spend hours of engine time changing almost nothing. RepertoireAuditProvenance.state(recorded:current:) returns .current, .superseded(recorded:) or .unknown — and .unknown is NOT "stale": an unrecorded build is an unknown one, and claiming it is old would invent a fact, exactly as a never-run scan refuses to render as 0. The hub sentence appears only when a rebuild would actually change the engine behind the answer.

    The opponent model: RepertoireOpponentModelKernel¶

    Ranking by raw Maia policy probability is close to useless — it's dominated by deep, rare positions. What matters is expected frequency: the probability of the reply at that node, times the probability of ever reaching that node — a 40% reply at ply 2 outranks a 73% reply five plies down a line only reached 5% of the time, and only expected frequency expresses that.

    The kernel is split into two pure phases so the (expensive) Maia inference runs exactly once, in between:

    // Phase 1 — which FENs need a reply distribution at all.
let nodes = RepertoireOpponentModelKernel.opponentTurnNodes(color: .white, repMoves: repMoves)

// `policy` comes from the app's own Maia driver — run over `nodes`'
// `positionFEN`s and keyed back by their `positionKey`. The kernel has
// no Maia dependency; it only consumes the resulting ReplyTable.
var policy: RepertoireOpponentModelKernel.ReplyTable = [:]
for node in nodes {
    policy[node.positionKey] = await maia.topMoves(fen: node.positionFEN, elo: 1500)
        .map { OpponentReply(san: $0.san, probability: $0.probability) }
}

// Phase 2 — fold the policy back in and rank.
let unprepared = RepertoireOpponentModelKernel.unpreparedReplies(
    color: .white,
    repMoves: repMoves,
    policy: policy,
    rule: .standard,
    observations: [:],           // empty for a model run — see below
    policySource: .model(elo: 1500)
)
for reply in unprepared.prefix(10) {
    print(reply.replySAN, reply.expectedFrequency, reply.openingName ?? "—")
}

    rule: used to be two separately defaulted parameters (minimumProbability/minimumExpectedFrequency). A Swift default argument is invisible across the Kotlin bridge — the CMP face can't see it, can't inherit it, and supplies whatever it decides — so both were folded into one required RepertoireCoverageRule value; .standard is the shipped pair (defaultMinimumProbability/defaultMinimumExpectedFrequency above, plus a topK/nodeBudget scan budget). Omitting rule: is now a compile error instead of a silent divergence between faces.

    observations:/policySource: travel with the call, not with policy itself, because a probability's meaning depends on where it came from — 18% out of four thousand human games and 18% out of a policy are different claims. A Maia-sourced run (above) passes [:] and .model(elo:); a run sourced from observed play instead populates observations per node key and passes .observedPlay(servedRatings:). The two sources must never mix within one call.

    Both phases share one explicit-stack walk (same 512KB-stack reasoning as computeGaps) that descends only through the repertoire's own prepared moves — an unprepared reply is the walk's output, never a path to follow further, since there's by definition nothing beyond it to audit. The per-step cost that accumulates into reachProbability is:

    step cost at this ply:
    user's own move                        → 1.0            // chosen, not sampled
    opponent move, listed in the policy     → its policy probability
    opponent move, unlisted, policy present → unlistedReplyProbability = 0.01
    opponent move, phase 1 (no policy yet)  → 1.0            // full descent, nothing to weigh yet

reachProbability = running product of step costs along the path
expectedFrequency = replyProbability * reachProbability

a reply qualifies only if:
    replyProbability  >= minimumProbability          (defaultMinimumProbability = 0.05)
    expectedFrequency >= minimumExpectedFrequency     (defaultMinimumExpectedFrequency = 0.01)

results sorted by expectedFrequency descending

    unlistedReplyProbability = 0.01 exists because Maia returns a truncated policy — absence means "rare," not "impossible." Using 0 there would zero out an entire prepared subtree the moment one sideline move fell outside Maia's top-K, hiding every gap beneath it; a small constant keeps the subtree reachable while correctly ranking it far below mainline traffic.

    First-path-wins is a deliberate trade-off

    The walk's visited set means a position reachable by two different move orders is scored on whichever path the walk reaches first, not the sum of both paths' reach probabilities — the same under-statement computeGaps accepts. Summing would mean abandoning the visited set and risking exponential blow-up on a densely transposing repertoire, so this is a matched, intentional trade rather than an oversight.

    Coverage cache persistence: RepertoireCoverageCacheState¶

    The scan's answers — findings, verdict, Elo, and the per-node Maia policies — persist in a RepertoireCoverageCacheState, one BlobBackedStore row holding both colours:

    public struct RepertoireCoverageColorCache: Codable, Sendable, Equatable {
    public var findings: [UnpreparedReply]
    public var outcome: RepertoireScanOutcome
    public var elo: Int
    public var scannedAt: Date
    public var nodePolicies: [String: CachedNodePolicy]   // positionKey → policy@elo
}

    Two rules make the cache trustworthy:

    • A couldNotRun verdict is never persisted. "The model is missing right now" must not erase the last real answer the user can still read.
    • Modelled and observed policies never mix. An observed (Lichess) run is cached whole and returns no model policies; a modelled run prunes the stored policy table to the nodes it actually walked and merges its fresh entries. Positions edited out of the tree therefore stop being cached.

    The per-node policy cache is the incremental re-scan spine. A node's Maia reply distribution depends only on its position and the Elo asked — never on the tree around it — so a re-scan after the user edits their repertoire reuses every surviving node whose cached Elo matches and spends model inference only on the nodes the edit created. Reused nodes count as analysed (the model answered them, earlier), which keeps analysedNodes > 0 honest for the "model never answered at all" guard.

    Persistence rides BlobBackedStore (blob key repertoireCoverageCache) through the storage seam described in file-store; the app bridges it onto its CloudKit-mirrored SyncedJSONBlob row, so both devices' caches converge last-writer-wins — the right rule for a cache, and the same one its sibling caches use. The audit cache takes the same shape on Apple, as SwiftData rows instead of a blob (see the audit-cache section above).

    The fourth question: deviations from prep (RepertoireDeviationKernel)¶

    Every other analysis here judges the BOOK. This kernel is the multiplication of two facts the review surface already computes per game: you left your book at move N and here is what that cost you. It runs no engine — every number it needs is persisted on the games by the annotation pass, which is what makes a library-wide sweep affordable. If it ever needs a probe, it has drifted into being the audit.

    The rule is a value (RepertoireDeviationKernel.Rule, .standard shipped):

    Field Meaning Default
    openingPlyHorizon How deep "the opening" runs, in plies 20 (ten moves — the same boundary game review draws)
    minimumWinProbabilityDrop Win-probability drop that stops being noise 0.05 (the app's .inaccuracy band)
    minimumOccurrences Occurrences below which an edge is not reported small-N guard

    Win probability, not centipawns: opening evaluations cluster near zero, exactly where the logistic is steepest, so a fixed centipawn bar would quietly report almost nothing.

    The unit of a finding is the edge — (positionKey, playedSAN) — not the game. Edges aggregate across games into a Finding carrying occurrences, totalPlayedMoveLoss, the earliest ply, and the moveSequence to seat a board there (a finding a user cannot navigate to is a fact they have to go and find by hand). Each finding's Comparison is honest about what is known: .worseThanPrepared(by:), .betterThanPrepared(by:) (not a mistake — books are chosen for playability), or .preparedMoveNotEvaluated (say nothing, do not imply).

    A sweep's Report is as loud about what it did NOT read as about what it found: gamesSkippedUnannotated, gamesSkippedNonStandardStart, deviationsSkippedNoEvaluation, and a Barren outcome whose cases distinguish "you followed prep throughout" (good news) from "nothing cleared the bar" and "found deviations but none could be judged" (unmeasured, not clean).

    Kept deviations: the ledger (RepertoireDeviationDismissal)¶

    "Keep my prep" on a deviation is a durable authored decision, recorded in RepertoireDeviationDismissalLedger — a BlobBackedStore keyed repertoireDeviationDismissals. Three properties carry the design:

    • One row per decision, keyed by (positionKey, preparedSAN, playedSAN) — re-recording replaces, never appends, so the ledger cannot grow by taps.
    • The filter is kit-owned (visibleFindings(in:retiredPreparations:)): kept findings are hidden, findings whose prepared move no longer exists are retired. Both faces filter identically because the rule is here, not in a view.
    • forgetPreparation(positionKey:preparedSAN:) drops every decision about a prepared move that no longer exists — replacing a move means the old "keep" is an answer to a question that is gone, and if the user ever re-adds the move, its old dismissals must not already be silently waving.

    The ledger is authored state, not a cache: it converges by union across devices rather than last-writer-wins, so two devices keeping different deviations both keep theirs.

    Scan verdicts: RepertoireScanOutcome, RepertoireScanStatus, provenance¶

    Every scan reports its conclusion as a RepertoireScanOutcome — a closed Kind set (notRun, couldNotRun(blocker:), clean, cleanBelowCap, findings(count:), incomplete) whose cases exist because the failures they name were once silently conflated:

    • A capped scan that found nothing reports cleanBelowCap, never clean.
    • analysedNodes and selectedNodes are separate numbers. A run that chose 250 nodes and got three answers must not report "scanned 250 of 250" and draw a clean bill of health — that exact bug shipped once.
    • couldNotRun carries a RepertoireScanBlocker (opponentModelUnavailable, engineUnavailable, nothingInScope, cancelled) — "did not look" is a different sentence from "looked and found nothing", and neither may wear the other's words.

    provenance records WHO answered: .observed(servedRatings:) for real Lichess play or .modelled(RepertoireModelFallbackReason) for the Maia estimate. It is orthogonal to the verdict on purpose — folding the two together breaks the no-credential user, who is the majority and is answered by the model on every scan without having failed at anything.

    RepertoireScanStatus adds the staleness half: the question asked, the scope it ran over, the completedAt stamp and moveCountAtRun — so a surface can call hasDrifted(currentMoveCount:) when the repertoire has changed size since the run (a deletion can remove the very move a finding was about) and print "N moves added since" rather than implying the numbers are live.

    Evidence and claims: what a face may print¶

    A percentage in this subsystem is a claim, and the kit decides which claims the evidence supports:

    • RepertoireNodeEvidence travels with every finding: what was observed at the node (.observed(positionGames:listedGames:fetchedAt:), .noGames(fetchedAt:), .notProbed(refusal)) and which source produced the probability (RepertoirePolicySource: .model(elo:) or .observedPlay(servedRatings:)). Provenance rides the number rather than arriving as a separate argument, because a number and its provenance separated by an argument list is a pair that eventually disagrees.
    • RepertoireEvidenceRule prices the negative claim: "nothing common is missing here" requires an actual look with minimumGamesToDeclareNoReply behind it (59 games), and a share may only print as a percentage above minimumGamesToRankReplies with an maximumUnlistedShare ceiling — thousands of games can still be unquotable if most play sits in moves the source never listed.
    • RepertoireFrequencyClaimRule turns an observation into exactly one of RepertoireFrequencyClaim's cases — .share, .seenInAFewGames, .noGamesRecorded, .tooMuchUnlisted — each with its own sentence. A caller must not choose its own wording for a number; the rule's verdict is the wording.

    Guided expansion: RepertoireExpansionKernel¶

    Covering an unprepared reply is a WALK, not a single edit: answering one reply creates a position where the opponent moves again. This kernel owns the whole walk — which replies are worth offering, what the opponent plays, the frontier order, when to stop — as a pure, engine-free ExpansionSession value the faces render. Owning all of it is deliberate: two faces holding their own traversal cursor is how two faces stop at different depths from the same numbers.

    Session-shaped facts worth knowing:

    • RootBasis distinguishes a measured root (the coverage scan measured its share of the user's games) from a conditioned one (picked off a gap list; percentages are shares of the games that reach the line). The two read identically if nobody says so, so RepertoireExpansionKernel.offerWording says so.
    • Every stop is a named TerminationReason the face prints, and .noPolicy must never render as clean — that is the absence of a model presented as a fact about the repertoire.
    • targetRepertoireID is kit-computed by the same deepest-anchor rule that attributes gaps, so the face always knows which chapter a walk is writing into and can say "Saved to X".

    Checkpoints persist per colour through RepertoireExpansionCheckpointStorage (see file-store); a cursor is one device's position in a walk, not library state another device should inherit.

    Leeches: RepertoireLeeches¶

    "Leeches" is the drill-ledger aggregation of the fourth question's cousin: which prepared moves the user keeps getting wrong over time, as opposed to left once. RepertoireLeechPolicy is a value with argued defaults (90-day window, ≥3 attempts, ≥2 lapses, ≥⅓ lapse rate) and RepertoireLeeches aggregates the ledger into Leech rows keyed by positionKey — the same EP-normalized identity everything else keys on. Faces join a leech back to its line and opening through RepertoireDrillSelection.corpus; the aggregation deliberately does not depend on a tree walk it cannot afford on every read. RepertoireLeechVocabulary owns the sentences.

    Editing policy: RepertoireEditingPolicy¶

    Destructive verbs need confirmations, and confirmations need numbers that two faces must not compute differently. RepertoireEditingPolicy owns the rules (moveReplacementNeedsConfirmation, lineDeletionNeedsConfirmation, the scoped-audit tap states) and the copy those rules produce (moveReplacementMessage, deviation adopt/keep titles and hints). When a new verb appears, its threshold and its sentence both land here — a face that computes its own collateral count is a face whose "Replace" warns in one app and deletes silently in another. ReviewCategory (the four review questions) and ScopedAuditState (which of a chapter-scoped audit tap's situations a colour is in) live here too.

    The health digest: RepertoireHealthDigest¶

    The per-repertoire readiness summary the health surfaces render. One component per review category, each either a count or an explicit not-checked:

    public struct RepertoireHealthDigest.Component: Codable, Sendable, Equatable {
    public let category: RepertoireEditingPolicy.ReviewCategory
    public let count: Int?      // nil = the scan has not run for this scope
    public let checkedAt: Date? // where the scan records a date
}

    The honesty rules are the type's reason to exist: nil renders "Not checked." and must never read as 0 — a missing scan drawn as a clean bill of health is the defect this subsystem keeps fighting — while 0 is a real answer that pairs with its freshness stamp. There is deliberately no aggregate score: a weighted readiness number would be the confident-looking figure the evidence discipline exists to prevent. RepertoireHealthVocabulary owns the count sentences, the not-checked sentence, and the freshness stamp, so the Apple and CMP cards render the same words from the same digest.

    Personal opening book: PersonalOpeningBookKernel¶

    The personal book turns a set of the player's own games into a per-position move-frequency tree, feeding two things back into gap analysis: encounter counts for computeGaps's personal-game pass, and stats for the "what do I actually play here" reads.

    public struct GameSnapshot: Sendable, Equatable {
    public let white: String
    public let black: String
    public let result: String
    public let moveText: String
    public let startFEN: String   // "" for the standard start
}
public struct CollectionGames: Sendable, Equatable {
    public let username: String   // resolves which side the user played
    public let games: [GameSnapshot]
}

public struct Node: Sendable, Codable, Equatable {
    public var games, wins, draws, losses: Int
    public var children: [String: Node]   // one ply deep per node
}
public struct BookTree: Sendable, Codable, Equatable {
    public var nodes: [String: Node]      // positionKey → Node
    public var gameCount: Int
}

    build(from:) tokenizes each game's PGN, resolves the user's colour via PieceColor.ofUser(white:black:username:), and skips games with no parseable moves, an unparseable custom start FEN, or an unresolvable account-owner side — such games don't count toward gameCount. Aggregation stops at maxPly = 30 plies per game; deep endgame positions aren't useful in an opening book and are excluded for memory.

    contentFingerprint(for:) is a length-framed FNV-1a-style fold (64-bit offset basis 0xcbf29ce484222325, prime 0x00000100000001b3) salted with "personal-opening-book-v3". Collections are first coalesced by normalized username — so moving a collection's games between two included, equivalent collections doesn't change the digest — then each username's games are sorted by (white, black, result, moveText, startFEN) before folding, so collection/game order never affects the fingerprint. Every string is combined with its own UTF-8 byte length before its bytes, so component boundaries can't collide ("ab" + "c" folds differently from "a" + "bc").

    MoveStats.score = (wins + 0.5 * draws) / games     // standard points-per-game

    gamesSnapshot(from:) is the bridge into gap analysis — it flattens the tree (nodes with children only) into RepertoireBookKernel.PersonalGamesSnapshot, the flat Sendable type computeGaps(personalStats:) consumes:

    let tree = PersonalOpeningBookKernel.build(from: collections)
let stats = PersonalOpeningBookKernel.stats(for: position, in: tree)   // most-played first
print(stats.moves.map { "\($0.san) \(Int($0.percentage))% (\($0.wins)-\($0.draws)-\($0.losses))" })

let snapshot = PersonalOpeningBookKernel.gamesSnapshot(from: tree)
let gaps = RepertoireBookKernel.computeGaps(
    color: .black,
    repMoves: myBlackRepertoire,
    anchorFEN: nil,
    owningRepertoireID: mainBlackID,
    personalStats: snapshot
)

    Personal trap mining¶

    Gap analysis and the audit both ask what's in the repertoire. PersonalTrapExtractor asks a narrower, sharper question about what isn't: which of the player's own lost games hinged on a knife-edge move they didn't find, mined straight out of the games rather than out of prepared theory.

    Personal traps¶

    The mining premise is deliberately narrow: lost games only, opening phase only, knife-edge positions only. "I picked the wrong move" is the whole feature, so wins and draws are skipped entirely.

    PersonalTrapExtractor.eligibleUserColor(for:collection:alreadyScanned:) gates candidacy on all four of:

    1. a non-empty game.gameID that has not already been scanned
2. a collection with includeInOpeningBook == true and a non-empty username
3. PieceColor.ofUser(white:black:username:) resolves a colour
4. the user LOST — result == "0-1" as White, "1-0" as Black

    Stage 1 — the storage-first prefilter. The annotation pass already scored the top two moves at every ply. When those persisted scores show a gap comfortably below threshold, the ply cannot be a trap and the (expensive) live probe is skipped:

    usable only when BOTH
  EvalJSON.decode(annotationEvalsJSON).count         == mainLine.count + 1
  EvalJSON.decodeOptional(secondBestEvalsJSON).count == mainLine.count + 1

skip a ply WITHOUT probing when
  the persisted second score is non-nil
  abs(best)   < 100_000.0     (the mate sentinel)
  abs(second) < 100_000.0
  abs(best - second) < Double(max(0, minGapCp / 2))

    The cut is deliberately lenient — half the real threshold — because the stored evals come from a deeper search than the trap probe itself, so a borderline ply is re-probed rather than dropped. The arrays are White-POV centipawns and |best − second| is POV-invariant, so no re-orientation is needed; a skip here is behaviorally identical to a probed ply that turned out sub-threshold, so it never weakens the completeness contract below. Games with no or partial annotation fall straight through to the full live probe.

    Stage 2 — the authoritative emit rule. For every half-move of the main line where the user was on move:

    stop at halfMove >= maxHalfMove                       (default 30 = move 15)
skip unless node.positionBefore.activeColor == userColor
probe(fenBefore)
require BOTH secondMoveUCI and secondScoreCp
require both scores inside -1_000_000...1_000_000
require both PV moves to resolve against the legal move list, and to be DISTINCT
gap = abs(bestScoreCp - secondScoreCp)
require gap >= minGapCp                               (default 200 ≈ a minor piece)
require node.move.uci != bestMove.uci
  -> emit PersonalTrapData(gapCp: gap, halfMoveIndex: halfMove + 1, ...)

    A score without its own PV move is not evidence that a MultiPV-2 probe actually completed — that's why both fields are required and the two root moves must be distinct: a truncated engine response must never become a durable negative witness (i.e. "this wasn't a trap").

    Two entry points share that walk, and the difference between them is the whole safety story:

    Method Behaviour
    extract(from:userColor:detectedAt:probe:) Permissive. Swallows probe failures and incomplete evaluations, returns [] on error. Preview and tests only — must never create a durable scan marker.
    extractCompleted(from:collectionUsername:detectedAt:probe:) Authoritative. Throws PersonalTrapExtractionCompletionError instead of silently skipping, so the source stays retryable rather than being recorded as a false "no traps here."

    Under extractCompleted, the three failure classes — probeUnavailable, incompleteEvaluation, invalidEvaluation — all carry the 1-based halfMoveIndex: halfMove + 1 at which they occurred. Task.checkCancellation() runs at the top of every loop iteration, again after each probe, and once more just before returning, so cancellation can't land between a completed probe and the array append that records it.

    Durable mining witnesses¶

    A scan performed with one threshold must never suppress work requested with another, and a projection row that arrived late — or vanished in a restore — must be repairable without re-running the engine. PersonalTrapExtractionPolicy, PersonalTrapScanWitness, and PersonalTrapScanManifest exist to make both of those true.

    let extractor = PersonalTrapExtractor(minGapCp: 200, maxHalfMove: 30)

let completed = try await extractor.extractCompleted(
    from: game,
    collectionUsername: collection.username,
    detectedAt: .now,
    probe: { fen in await stockfish.topTwo(fen: fen) }
)

let witness = try PersonalTrapScanWitness(
    sourceDigest: completed.sourceDigest,
    policy: completed.policy,
    engineRevision: try PersonalTrapProbeRevision.stockfish18(movetimeMs: 1500)
)

let manifest = try PersonalTrapScanManifest(completedScan: completed, witness: witness)

    PersonalTrapCompletedScan's initializer is fileprivate. The only way to obtain one is extractCompleted — that's the type-level guarantee that stops an empty legacy array from ever being mistaken for an authoritative "no traps found."

    Bound Value
    PersonalTrapExtractionPolicy.currentRevision / PersonalTrapScanManifest.currentSchemaVersion 1
    maximumSupportedGapCp 1,000,000
    maximumSupportedHalfMove 128 (64 full moves)
    PersonalTrapProbeRevision.maximumMovetimeMs 60,000
    PersonalTrapScanWitness.maximumEngineRevisionBytes 256
    PersonalTrapScanManifest.maximumCanonicalJSONBytes 512 KiB
    maximumOutputTraps (128 + 1) / 2 = 64

    The 128-ply ceiling also guarantees a worst-case result fits the 512 KiB canonical envelope. PersonalTrapExtractionPolicy's throwing initializer requires revision > 0, minGapCp in 0...1_000_000, maxHalfMove in 1...128; decoding routes through that same validating init, so an out-of-range persisted policy fails to decode rather than being trusted.

    engineRevision is a string, not a numeric counter, because it has to express engine family/version, exact build commit, and probe configuration (movetime, MultiPV) all at once without collisions:

    PersonalTrapProbeRevision.stockfish18(movetimeMs:) returns exactly

  stockfish:sf_18;swiftstockfish:18.0.11@a0db83c6ba55ad8ccabe1b5dba67b22840a8d5f0;
  nnue:c288c895ea92+37f18f62d772;multipv:2;movetime-ms:<movetimeMs>

(one line, no wrapping). Throws invalidProbeMovetime outside 1...60_000.

    It must be non-empty, already trimmed, ≤ 256 UTF-8 bytes, and every unicode scalar printable ASCII (0x20...0x7E). sourceDigest must satisfy ExactByteProof.isCanonicalSHA256.

    Canonicalisation and digest. PersonalTrapScanManifest's public initializer checks source identity twice against the witness — sourceDigest and policy must both match — so output from one snapshot can never be paired with a witness for another.

    canonicalTraps:
  reject when traps.count > (policy.maxHalfMove + 1) / 2
  per trap require:
    canonical source id == the manifest's
    fen <= 512 bytes; both UCIs <= 16 bytes; sourceOpeningName <= 4_096 bytes
    gapCp >= policy.minGapCp  and  gapCp <= 2_000_000
    halfMoveIndex in 1...policy.maxHalfMove
    correctMoveUCI != userActualMoveUCI
    the FEN parses, and BOTH UCIs resolve to legal moves in that position
  re-quantise timestamps to whole milliseconds:
    Int64((seconds * 1000).rounded()), rejecting non-finite/out-of-range dates
  sort by halfMoveIndex; reject DUPLICATE half-move indices
  every trap must share the first trap's detectedAt and sourceOpeningName

digest = PortableSHA256 over length-prefixed UTF-8 of, in order:
  "personal-trap-manifest:v1", schemaVersion, sourceGameID,
  witness.sourceDigest, policy.revision, policy.minGapCp, policy.maxHalfMove,
  witness.engineRevision, outcome.kind.rawValue, outcome.traps.count,
  then per trap: fen, correctMoveUCI, userActualMoveUCI, gapCp, halfMoveIndex,
                 sourceGameID, sourceOpeningName, epoch-millisecond detectedAt

    Decoding re-derives the digest through the same canonicalising init and rejects on mismatch, so a tampered or drifted stored digest can never be trusted. The codec makes the JSON itself canonical ([.sortedKeys, .withoutEscapingSlashes], .millisecondsSince1970, ≤ 512 KiB) and decoding requires an exact byte-for-byte re-encode to match — rejecting unknown fields, alternate key order, and alternate date spellings outright.

    Admission and reconciliation.

    PersonalTrapScanManifestState classification order:
  trapsFound < 0                                        -> .malformed
  manifestJSON == nil                                   -> .legacy
  canonical decode fails, OR validateRecord fails       -> .malformed
  otherwise                                             -> .versioned(manifest)

isProcessed(matching:rebuildingLegacy:):
  .legacy     -> !rebuildingLegacy
  .versioned  -> manifest.witness == current
  .malformed  -> false        (never suppresses mining)

    That classification and isProcessed logic lives in exactly one place — default-implemented on the PersonalTrapScanManifestContainer protocol, which requires only sourceGameID, trapsFound, and manifestJSON. The native persistence DTO (PersonalTrapScanRecordData) and the backup row (LibraryBackup.TrapScanRecord) both conform, so admission state, legacy detection, and witness matching behave identically whether a record came from the live store or a restored backup — the two formats cannot drift apart because they share the implementation, not just the shape.

    PersonalTrapScanReconciliation.resolve(currentWitness:records:projection:) ignores malformed records, tracks whether any legacy record exists, and among .versioned records matching the current witness picks one canonical manifest deterministically (smaller manifestDigest wins; identical digests fall back to smaller canonical JSON). Time-bounded engines can legitimately produce two different but individually valid outputs under the same release witness — re-running the engine would only manufacture a third conflict, so the resolver selects one validated, content-addressed result and reports .repair(manifest) to replace every sibling and projection row with it, .processed only when a lone exact row already matches the projection, and .extract when nothing trustworthy exists yet.

    Drilling and stats¶

    // One read of the shared consecutive-correct counters, then a pure ordering pass.
let mastery = BlunderMasteryStore.history(in: blobStore)        // [String: Int]
let threshold = MasteryStreak.resolve(stored: storedMasteryThreshold)

let sections = PersonalTrapDrill.groupByOpening(traps)          // encounter order preserved
for (name, familyTraps) in sections {
    let queue = PersonalTrapDrill.prioritized(familyTraps, skipMastered: true) { trap in
        (mastery[PersonalTrapDrill.masteryKey(for: trap)] ?? 0) >= threshold
    }
    print(name,
          "worst miss \(PersonalTrapDrill.worstGap(familyTraps))cp",
          "\(queue.count) to drill")
}

    isMastered's threshold: has no default, deliberately. It used to (BlunderMasteryStore.masteryThreshold = 3), and because the Apple app separately declared its own type of the same name whose masteryThreshold read the user's live Settings value, the identical source text BlunderMasteryStore.masteryThreshold meant two different numbers on the two faces — nine live defects traced back to that one construct. The floor now lives on MasteryStreak (floor = 3, range = 2...10) where nothing shadows it, and a caller without the user's stored preference must go through MasteryStreak.resolve(stored:) so the fallback is visible in the call site rather than inherited silently.

    groupByOpening preserves encounter order, so the family that produced the most recent trap sits at the top; traps with an empty sourceOpeningName bucket under "From your game". Section names run through displayOpeningName(for:), which resolves a bare ECO code (isBareECOCode: exactly 3 characters, A-E then two ASCII digits, no regex) to a family name when the book knows one — without it the menu reads as a wall of codes.

    prioritized(_:skipMastered:isMastered:):
  skipMastered defaults to true (mastered traps are dropped);
  when false they stay but sink to the bottom.
  Within each bucket, gapCp sorts DESCENDING.

worstGap: returns 0 for empty input, so callers render unconditionally

    PersonalTrapDrill.masteryKey(for:) / masteryKey(fen:correctMoveUCI:) is the kernel's single definition of the "trap:<fen>:<correctMoveUCI>" format — the same discipline as RepertoirePunishItem.masteryKey above, and a separate namespace from it: a trap and a punish drill at the same position keep independent mastery counters.

    RepertoireDrillStats records the repertoire drill history separately — accuracy, streaks, and a last-10 sparkline — capped at 200 attempts per repertoire on every record, with a resetAt fence that unions post-reset attempt IDs into discardedAttemptIDs so attempts already evicted by the cap can't resurrect a reset history. See Stores & the Storage Seam for its full API.

    Export and import¶

    exportPGN(forColorName:...) walks movesAt(_:) — a caller-supplied position → [MoveInfo] lookup, so the same function serves a single repertoire or a colour union — recursively rendering a standard PGN variation tree. Tokens are escaped per §8.1 of the PGN spec (backslash before quote, so a literal backslash in a comment can't accidentally escape the following character), and a stray } inside a user comment is replaced with ) since PGN has no escape for it. Recursion threads a pathKeys set that's scoped to the current path only (not global, unlike the gap walk), so the same transposition can legally appear under multiple PGN variations — exactly what a literal variation tree needs. When anchorFEN is supplied, the PGN also emits [SetUp "1"]/[FEN ...] tags so compliant readers replay from the anchor rather than move 1. An optional evalAt closure attaches a per-move centipawn comment, converted from the mover's POV to White's POV before formatting.

    exportHTML(forColorName:...) renders a fully self-contained HTML page: an SVG move tree plus an "Annotated Lines" prose section, no external assets. The tree layout is fixed-size box-and-connector:

    nodeW = 72, nodeH = 26, colGap = 32, rowGap = 12, padX = 12, padY = 18
column = ply index (shifted so the shallowest node in an anchored export
         still starts flush left)
row    = leaf index for a leaf; for a branch, the midpoint between the
         first and last leaf row reached anywhere in its subtree (not
         the mean of its immediate children's own row values)

    Piece art is optional: pass a [String: String] of canonical two-character keys ("wK", "bP", …) to raw SVG source, and board diagrams reference shared <symbol>/<use> definitions (each piece's internal ids prefixed to avoid collisions between pieces); pass [:] (the default) and diagrams fall back to Unicode glyphs. Board diagrams render inline only at genuine branch points (validMoves.count > 1) through ply 24 (plyIndex <= 24), to keep the export readable rather than papering every move with a board.

    extractImportCandidates(from:) parses PGN text (or an already-parsed [PGNGame], for callers sharing one bounded parser instance) into ImportCandidate values — (positionKey, san, comment) — by mirroring PGNParser.buildTree token-for-token over a value-arena instead of a class graph: an [ImportArenaNode] array with parent/children indices, built from the same sibling-transposition-merge and variation branch-point stack the recursive parser uses, then flattened pre-order via an explicit stack (the same 512KB cooperative-stack concern as the gap walk).

    forColorName: "White",
    movesAt: { position in RepertoireBookKernel.moves(at: position, in: whiteUnion) }
)

for candidate in extraction.candidates {
    // merge candidate.san at candidate.positionKey into the target repertoire
}

    Headlessness and CLI applicability¶

    RepertoireBookKernel, RepertoireAuditKernel, RepertoireOpponentModelKernel, and PersonalOpeningBookKernel — the four kernels this document is built around — are each either a stateless enum namespace or a Sendable value type over ChessCore's Position/Move: no SwiftData model, no @MainActor/@Observable, no platform UI framework. The personal-trap mining types below hold to the same rule — PersonalTrapExtractor and every durable-witness type are Sendable value types with no platform dependency of their own.

    RepertoirePunishProducer is the one stated exception. It owns the checkpointed punish-generation walk described under PunishConfig above — tree ownership, bounded multi-ply exploration, scoring, ranking, cache identity, cancellation, and resume — and it is @MainActor, not because it needs SwiftData or UI, but because the Stockfish/Maia transports its Dependencies struct wires in are MainActor-owned on Apple's shipping app. A CLI or desktop caller still reaches it, just through an ordinary actor hop rather than a fresh integration; Dependencies.saveCheckpoint is a caller-injected persistence seam, not a store this kernel owns.

    The only owned I/O boundary in the whole subsystem is RepertoireAuditCacheStorage, which talks to FileJSONBlobStore — the same storage seam every other FianchettoKit store uses. OpeningBook.shared/ configureShared is the one piece of process-wide mutable state (a NSLock-guarded singleton), and it's explicitly designed to be installed once from precomputed data at process start, which a CLI's main() can do exactly as an app's launch path does.

    That makes this subsystem a natural fit for headless tooling. Three candidate subcommands map directly onto the three kernels:

    • gaps — load a repertoire (a PGN export, or a serialized RepertoireMoves dump) plus the precomputed opening book, call computeGaps, and print the sorted, numberedLine-formatted gap list. Pointing it at a folder of the player's own PGNs additionally builds a PersonalGamesSnapshot via PersonalOpeningBookKernel, so the personal-game-sourced sideline gaps (personalGapEncounterThreshold-gated) come along for free.
    • audit — build auditCandidates, drive them through Stockfish, and print flaggedFindings(threshold:). This reuses the same UCI plumbing the estimate/accuracy fianchetto-cli subcommands already own, since RepertoireAuditKernel needs only raw (uci, cp) pairs back — no new engine integration required.
    • unprepared — run opponentTurnNodes, feed the resulting FENs through the same Maia serving path the maia fianchetto-cli subcommand already exposes, and call unpreparedReplies to print the opponent's likely, unanswered replies by expectedFrequency.

    None of these exist as shipped subcommands today; they're direct applications of kernels that are already engine-agnostic and already take plain values in and out.
