    Electronic board integration¶

    How FianchettoKit drives a physical BLE chessboard: the brand catalog, the transport admission policy, the effect-returning session core that decides what a board frame means, and the always-on diagnostic capture that makes a field bug replayable.

    What this layer owns¶

    The board kernels themselves live in BoardKit — BoardDiffResolver, OccupancyMoveInference, BoardExecutionGate, BoardTakebackDetector, ChessBoardGeometry, BoardCorrectionPlanner, BoardEvent, BoardCommand. BoardKitReexport.swift does nothing but

    @_exported import BoardKit
@_exported import SquareOffAdapter

    so a single import FianchettoKit resolves the kernels, the Square Off codec, and the FianchettoKit types on this page. The Chessnut, ChessUp, and Millennium adapter modules are not re-exported — they stay an implementation detail behind BoardCatalog. FianchettoKit adds the four things a kernel cannot own by itself:

    Concern Types
    Brand identity and BLE wiring BoardCatalogKey, BoardCatalog, BoardGATTSpec, BoardBrand
    Transport policy BoardTransportLifecyclePolicy, BoardConnectionGeneration, BoardWriteQueue
    Decision core EBoardSessionCore, EBoardEffect, EBoardDiffResolutionCoordinator, EBoardShellKernel, EBoardPositionTransition
    Diagnostics and presentation EBoardDiagnosticCapture, EBoardDiagnosticPersistenceCoordinator, EBoardDiagnosticDeduplication, BoardSyncPresentation, BoardMarkDocument

    Everything except EBoardShellKernel (and the @MainActor coordinators) is headless: Foundation + ChessCore + BoardKit — plus the four adapter modules, which only BoardCatalog imports — no SwiftUI, no CoreBluetooth.

    The catalog¶

    BoardCatalogKey is the closed shared identity for every board implementation. Each app keeps its own BoardType enum — a FianchettoKit type cannot be a Compose @State on Android — and maps onto this key with an exhaustive switch, so adding a board cannot compile until adapter, GATT, and JNI parity are all explicit.

    public enum BoardCatalogKey: String, CaseIterable, Sendable {
    case squareOffPro
    case chessnutAir
    case chessUp2
    case millenniumEONE
}
    Function Returns
    BoardCatalog.makeAdapter(key:) any BoardAdapter — SquareOffAdapter(), ChessnutAdapter(), ChessUpAdapter(), MillenniumAdapter()
    BoardCatalog.gattSpec(key:) BoardGATTSpec (below)
    BoardCatalog.matchesName(key:name:) advertised-name predicate
    BoardCatalog.matchesScan(key:name:advertisedServiceMatches:) full discovery predicate
    BoardCatalog.scansByName(key:) true when the scan must be broad
    BoardCatalog.kotlinManagerClass(key:) JNI class for the Android transport
    BoardCatalog.chessnutBeepData(frequency:durationMs:) Data for BoardCommand.custom(_:)

    BoardBrand holds the two drift-prone strings so the two app-local enums cannot disagree on what a board is called: displayName(rawValue:) maps "squareOffPro" → "Square Off Pro", "chessnutAir" → "Chessnut", "chessUp2" → "ChessUp 2", "millenniumEONE" → "Millennium eONE", and returns the raw value for anything unknown. pgnEventTag(rawValue:) currently forwards to it, kept separate so the PGN Event tag can diverge from the UI label without touching callers.

    GATT specs, verbatim¶

    BoardGATTSpec carries plain UUID strings — no CoreBluetooth import, so the same value serves the iOS CBUUID conversion and the Android transport. Case is not normalized: the NUS and ChessnutGATT UUIDs are lower-case, while Square Off's proprietary UUID and the MillenniumGATT constants are upper-case, so comparisons must be case-insensitive.

    Key Scan filter TX (board → host) RX (host → board) Dual service
    .squareOffPro D804B643-6CE7-4E81-9F8A-CE0F699085EB, 6e400001-…dcca9e 6e400001-…dcca9e / 6e400003-…dcca9e 6e400001-…dcca9e / 6e400002-…dcca9e no
    .chessnutAir ChessnutGATT.boardStateService, ChessnutGATT.commandService boardStateService / boardStateChar commandService / commandWriteChar yes
    .chessUp2 6e400001-…dcca9e (NUS), 0000180a-0000-1000-8000-00805f9b34fb (Device Information) 6e400001-…dcca9e / 6e400003-…dcca9e 6e400001-…dcca9e / 6e400002-…dcca9e no
    .millenniumEONE MillenniumGATT.serviceUUID serviceUUID / notifyCharUUID serviceUUID / writeCharUUID no

    Only Square Off sets advertisedServiceUUID (D804B643-6CE7-4E81-9F8A-CE0F699085EB); it advertises both the NUS service and a proprietary UUID, and including both lets retrieveConnectedPeripherals surface a board already paired with the vendor app.

    Chessnut is the only brand with requiresDualServiceDiscovery: true and the only one with auxiliaryNotifyCharUUIDs — [ChessnutGATT.commandResponseChar, ChessnutGATT.fileChar]. Stored-game download replies on the command-response channel and streams the archive on the file channel, so neither is the primary board-state TX channel and both must be subscribed for requestStoredGames to work. Subscription is best-effort: a missing auxiliary characteristic never fails the connection.

    Discovery and scan rules¶

    Two boards cannot be found by a service-filtered scan at all. The Millennium eONE advertises only its Local Name; Chessnut's two 128-bit service UUIDs (32+ bytes) do not fit a 31-byte advertising packet. Both must scan with withServices: nil and filter in the discovery callback — that is exactly what scansByName(key:) reports:

    Key scansByName matchesName predicate
    .squareOffPro false name.lowercased().contains("square")
    .chessnutAir true ChessnutGATT.isClassicProfile(name:)
    .chessUp2 false ChessUpGATT.isChessUp(name:)
    .millenniumEONE true MillenniumGATT.isMillennium(name:)

    matchesScan is the predicate that callback must use. Its shape is !excludes && (serviceMatch || includes) — exclusion wins:

    matchesScan(key:name:advertisedServiceMatches:)

.chessnutAir:
    !ChessnutGATT.isMoveProfile(name: name)
    && (advertisedServiceMatches || ChessnutGATT.isClassicProfile(name: name))

.squareOffPro, .chessUp2, .millenniumEONE:
    advertisedServiceMatches || matchesName(key: key, name: name)

    The Chessnut Move shares every Chessnut GATT UUID with the Air/classic profile, so without the leading exclusion a service match would pull a Move into .chessnutAir. The service branch is what still recognizes a Chessnut advertising its service under an unhelpful LocalName (a truncating board, a macOS emulator reporting "Mac").

    // Discovery callback, either platform.
let key = BoardCatalogKey.chessnutAir
let spec = BoardCatalog.gattSpec(key: key)
// UUID strings are compared case-insensitively — Square Off's proprietary UUID
// is upper-case in the spec, the NUS UUIDs are lower-case.
let filter = Set(spec.scanServiceUUIDs.map { $0.lowercased() })
let serviceHit = advertisedServiceUUIDs.contains { filter.contains($0.lowercased()) }

if BoardCatalog.matchesScan(key: key, name: peripheralName, advertisedServiceMatches: serviceHit) {
    let adapter = BoardCatalog.makeAdapter(key: key)
    // …connect, then discover spec.txServiceUUID / spec.rxServiceUUID
}

    Transport lifecycle¶

    BoardTransportLifecyclePolicy is the shared admission decision. The two shells use different radio APIs, but starting a scan or swapping the protocol adapter is safe in exactly the same states:

    BoardTransportState allowsScan allowsBoardTypeChange isTerminalConnectionAvailabilityState
    .idle, .disconnected yes yes no
    .poweredOff, .unauthorized yes yes yes
    .scanning, .connecting, .connected, .reconnecting no no no

    .poweredOff and .unauthorized are admitted for scanning so the platform can surface its own retry or permission-request flow; they are simultaneously terminal for an in-flight attempt, because permission denial before Android creates a BluetoothGatt produces no native disconnect callback at all.

    BoardConnectionGeneration is the ownership token delayed callbacks check before touching transport state. begin() does current &+= 1 and activates; activate(_:) adopts a token from a process-wide allocator — Android needs this because its singleton JNI bridge outlives and retargets transport instances, so two per-instance begin() calls would both return 1. invalidate() leaves activeToken == nil, and accepts(_ generation:) is isActive && generation == current.

    BoardWriteQueue<Owner> paces the writes. It is generic over an Owner: Equatable & Sendable (the connection identity) and returns .none, .wait(Duration), or .write(payload:owner:):

    nextAction(activeOwner:now:)

  drop head entries while head.owner != activeOwner
  no head -> .none

  if a previous write exists:              // steady state
      anchor        = lastWriteAt
      requiredDelay = .seconds(max(head.delayBefore, head.minimumWriteInterval))
  else:                                    // first write after reset()
      anchor        = head.enqueuedAt
      requiredDelay = .seconds(head.delayBefore)

  elapsed = anchor.duration(to: now)
  elapsed < requiredDelay -> .wait(requiredDelay - elapsed)
  otherwise               -> pop head, .write(payload:owner:)

    The first-write exception matters: after reset() there is no lastWriteAt to anchor against, so the adapter's pacing floor would otherwise be measured from an arbitrary instant. enqueue(_:owner:delayBefore:minimumWriteInterval:now:) clamps both intervals with max(0, …), and didWrite(at:) records when the platform write actually went out.

    The session core¶

    EBoardSessionCore is a plain final class that owns the decision state and never owns the Game. Every branch that would mutate observable state or the game returns [EBoardEffect] for a shell to apply, which makes the whole decision graph testable with no SwiftUI host and no live game object.

    Core-owned state: the OccupancyMoveInference slot machine, pendingOutbound: BoardExecutionGate?, awaitingPromotionFromUCI, lastReportedOccupancy: [Bool]?, lastReportedIdentity: [Piece?]?, boardPromotionPick: PieceType?, plus two private fields — pendingOutboundPreOccupancy and unconfirmedMismatch — that the algorithms below turn on.

    Input is a GameView: a closure-free, read-only snapshot.

    public struct GameView {
    public let position: Position
    public let currentNodeUCI: String?          // game.currentNode?.move.uci
    public let ancestorPositions: [Position]    // index 0 = 1 ply back, shell pre-computes ≤ 6
    public let legalCastlingRookHomes: Set<String>   // of "a1","h1","a8","h8"
}

    legalCastlingRookHomes is re-bound into inference.isCastlingStillLegal on every handle call, so the inference can defer rook-first castling detection without holding a closure over the game.

    The effect vocabulary¶

    Every case is Equatable, so a golden test asserts the exact array a decision path returns.

    Effect Meaning
    .setLiftedSquare(String?) the "piece in the air" highlight
    .setLastAppliedMove(String?) last committed UCI (write-back guard)
    .setLastReportedOccupancy([Bool]?) replace the 64-element occupancy mirror
    .setPendingResolutions([BoardDiffResolver.Resolution]) resolver candidates; empty = in sync
    .setPendingOutbound(Bool) dictated-move gate armed / cleared
    .setAwaitingPromotionFromUCI(String?) mirror the open-picker base UCI
    .adoptOrientationFlip(Bool) an identity snapshot proved the board is rotated
    .resolveBoardDiff(EBoardDiffRequest) run the depth-bounded search off-main
    .scheduleStateConfirmation(afterMilliseconds: Int) re-ask the board after the delay
    .applyMove(uci: String) apply one UCI to the game
    .applyResolution(moves: [String]) apply a validated multi-ply sequence
    .retractPlies(Int) roll back N plies (physical take-back)
    .bumpPhysicalMoveApplied counter: a board-sourced commit landed
    .bumpTakeback counter: a physical take-back landed
    .showPromotionPicker(from:to:legalUCIs:) open the piece picker
    .indicateSquares([String]) light these squares (.highlight style implied)
    .dismissPromotionPicker close the picker; the board already chose

    Thread model

    The core is neither actor- nor @MainActor-isolated, and holds non-Sendable state. It is called synchronously from a @MainActor shell by convention and is never sent across an actor boundary. Call it from the main actor.

    Orientation¶

    Two different corrections apply, and mixing them up is the classic bug here:

    inbound event                          correction when orientationFlipped
--------------------------------------------------------------------------
.squareSensed(square:isLift:piece:)    ChessBoardGeometry.flippedSquare(square) ?? square
.occupancySnapshot([Bool])             Array(payload.reversed())
.identitySnapshot([Piece?])            Array(payload.reversed())

    A square flips through geometry; a file-major array flips by reversal.

    An identity snapshot can also prove the orientation, which kills the stale-persisted-flip failure class — a leftover flip silently mis-read every move 180° with no reachable UI to discover or fix it:

    identityArray(for: position):            // rank-major -> file-major
    for file in 0..<8, rank in 0..<8:
        out[file * 8 + rank] = position.board[rank * 8 + file]

on .identitySnapshot(pieces) where pieces.count == 64:
    adjusted = orientationFlipped ? Array(pieces.reversed()) : pieces
    expected = identityArray(for: game.position)
    if adjusted != expected && Array(adjusted.reversed()) == expected:
        adjusted = Array(adjusted.reversed())
        emit .adoptOrientationFlip(!orientationFlipped)

    The two matches are mutually exclusive: a position can never equal its own 180° reversal (the kings alone forbid it). So the rule cannot flip-flap — after adoption every frame matches directly and it never re-fires. Mid-move frames (piece in hand) and garbage frames (invalid nibbles → nil holes) match neither way and fall through to the stability gate below.

    The re-feed double-reverse

    A manual orientation toggle goes through EBoardShellKernel.orientationRefeed(context:), which reverses the shell's occupancy mirror and flips liftedSquare through ChessBoardGeometry.flippedSquare, then feeds the core a synthetic snapshot with orientationFlipped: false because the arrays are already corrected. The resulting .setLastReportedOccupancy and .adoptOrientationFlip effects are filtered out — their flag semantics are wrong for a manual toggle, and applying them would reverse an already-reversed array.

    Reconciling app and board¶

    tryResolveAgainstSnapshot(game:fromSnapshot:) is the desync ladder. Six gates run in order, and only a frame that survives all six may reach the diff resolver:

    1  lastReportedOccupancy == nil                    -> []
2  pendingOutbound != nil
   && occupancy == pendingOutboundPreOccupancy     -> clear stash; []
3  BoardDiffResolver.occupancyArray(for: game.position) == occupancy
                                                   -> clear stash; [.setPendingResolutions([])]
4  counts equal && no i where occupancy[i] && !gameOccupancy[i]
                                                   -> clear stash; [.setPendingResolutions([])]
5  occupancy != unconfirmedMismatch                -> stash it;
                                                      [.scheduleStateConfirmation(afterMilliseconds: 500)]
6  !fromSnapshot                                   -> [.scheduleStateConfirmation(afterMilliseconds: 500)]

otherwise -> clear stash;
             [.resolveBoardDiff(EBoardDiffRequest(position: game.position,
                                                  targetOccupancy: occupancy))]

    Each gate exists because a real board produced a real corruption:

    • Gate 2 — while an app-dictated move awaits physical execution, a board still showing the pre-move position is the expected wait state. Without it, every heartbeat frame from a streaming board re-ran stash → confirm → search and ended up retracting the app's own move.
    • Gate 4, lift-in-progress — occupancy-only boards (Millennium eONE) report a full frame on every sensor change, including "piece lifted, not yet placed". A pure lift is occupancy-indistinguishable from a completed capture, so the depth-3 search can fabricate a capture chain. Because gate 3 already returned on equality, "no square is newly filled" here means a strict subset, i.e. mid-move. Defer to the inference, which sees the settled place delta.
    • Gates 5 and 6, stability — require the same mismatched occupancy on two consecutive frames, and only a genuinely distinct snapshot may confirm a stash. A delta-path re-entry re-observes the same physical frame; letting it self-confirm is what allowed one transient Chessnut Go frame to fabricate [e7e5, d4e5].

    .scheduleStateConfirmation(afterMilliseconds: 500) is the backstop for change-driven reporters: a streaming board confirms or denies via its next natural frame, but a board that sends one frame per change would otherwise never produce a second observation.

    The search itself is handed to EBoardDiffResolutionCoordinator, a @MainActor class with no UI dependency whose default resolver is

    BoardDiffResolver.resolve(from: request.position,
                          targetOccupancy: request.targetOccupancy,
                          maxDepth: 3,
                          limit: 8)

    run on Task.detached(priority: .userInitiated). It keeps a one-entry cache (EBoardDiffRequest is the exact key, and an empty result is cached too), ignores an identical in-flight request, bumps generation &+= 1 on every invalidation, and publishes only when owner == generation && activeRequest == request && task?.isCancelled == false. invalidateUnlessMatching(_:) is what keeps repeated identical BLE snapshots sharing a single search.

    Applying a resolution¶

    completeBoardDiffResolution(_:for:game:)

guard request.position == game.position
   && request.targetOccupancy == lastReportedOccupancy       else -> []

exactly one resolution:
    first.moves.count > 1 && resolutionContainsCapture(first, from: request.position)
        -> [.setPendingResolutions(resolutions)]              // demote to user confirmation
    otherwise
        -> pre-validate every ply against the forward simulation, then
           [.applyResolution(moves:), .bumpPhysicalMoveApplied,
            .setLastAppliedMove(moves.last), .setLiftedSquare(nil),
            .setPendingResolutions([])]  (+ dictated-gate cleanup)

two or more:
    -> [.setPendingResolutions(resolutions)]

none, and pendingOutbound == nil, and
BoardTakebackDetector.pliesToUndo(boardOccupancy:ancestorPositions:) == n:
    -> [.retractPlies(n), .bumpTakeback, .setLastReportedOccupancy(occupancy),
        .setLiftedSquare(nil), .setPendingResolutions([])]  (+ gate cleanup)

otherwise -> [.setPendingResolutions([])]

    The equality guard is defense in depth: the coordinator already rejects stale generations, and the core independently refuses a result whose position or physical snapshot has moved on, so a cancelled-but-uncancellable search can never mutate newer state.

    The multi-ply-capture demotion is the sharp rule. A capture is the only way the search can "explain away" a square a dropped sensor vacated, so a multi-ply chain containing one is precisely the misread signature — while legitimate multi-ply catch-up (quiet moves played while the app was not looking) still auto-applies:

    resolutionContainsCapture(_:from:)
    pos = position
    for uci in resolution.moves:
        move = UCIParser.uciToMove(uci, in: pos)      // unparseable -> return true
        if pos.board[move.to.rank * 8 + move.to.file] != nil || move.isEnPassant:
            return true
        MoveGenerator.applyMoveUnchecked(&pos, move)
    return false

    An unparseable ply returns true — fail toward asking the user.

    Take-back adoption is suppressed while a dictated move is armed. A board showing an ancestor position then is the expected pre-execution state; treating it as a take-back silently retracted every app-side move about a second after commit whenever a streaming board was bound but not mirrored. The cost is that a genuine gate-armed physical take-back goes unrecognized until the gate clears, which is the better failure.

    Dictated moves and promotion¶

    present(move:positionBefore:) arms the gate for an engine reply or a tap-move, snapshots the pre-move occupancy for gate 2 above, and returns the LED effect. Guard transport.state == .connected before calling — arming a gate while disconnected blocks inference indefinitely.

    let core = EBoardSessionCore()

// Engine (or tap) produced `reply` from `positionBefore`.
for effect in core.present(move: reply, positionBefore: positionBefore) {
    // .setPendingOutbound(true), .setLiftedSquare(nil),
    // .indicateSquares(["e2", "e4"])
}

// Field events now route through BoardExecutionGate instead of the inference.
let effects = core.handle(
    event: .squareSensed(square: "e2", isLift: true),
    game: gameView,
    orientationFlipped: false
)

    while pendingOutbound != nil, each field event feeds the gate:

.inProgress -> []
.executed   -> clear gate; inference.reset()
               [.indicateSquares([]), .setPendingOutbound(false), .setLiftedSquare(nil)]
.deviated   -> clear gate
               [.indicateSquares([]), .setPendingOutbound(false)]
               + tryResolveAgainstSnapshot(game:, fromSnapshot: false)
               + inference.reset(), .setLiftedSquare(nil)

    The empty .indicateSquares([]) is load-bearing. Square Off firmware self-clears on execution, but Millennium (corner grid) and Chessnut keep LEDs lit until told otherwise, so without it the last dictated move stays illuminated for the rest of the game. clearDictatedMoveIfPending() mirrors that cleanup for the snapshot path, where the move reconciles through the resolver and the gate never sees its own field events.

    Promotion resolves in three tiers when two or more distinct legal promotion pieces match:

    1  hardware pick — boardPromotionPick (BoardEvent.promotionPick, e.g. ChessUp 0x97)
   matches a legal promotion piece  -> auto-commit, no picker
2  identity consult — lastReportedIdentity at the promotion TO-square holds a
   piece whose type is queen/rook/bishop/knight AND whose color ==
   game.position.activeColor        -> auto-commit, no picker
3  otherwise -> clear the stash; awaitingPromotionFromUCI = from + to;
   [.showPromotionPicker(from:to:legalUCIs:), .setAwaitingPromotionFromUCI(_), .setLiftedSquare(nil)]

exactly one legal promotion match  -> auto-promote, no picker
completePromotion(pieceType:game:) -> queen "q", rook "r", bishop "b", knight "n", default "q"

    Tier 2 rejects a pawn, a king, or a wrong-color piece: those are almost certainly captured pieces the player set aside on the edge of the board, not a promotion choice. Requiring an exact type-and-color match keeps the identity path as strict as the hardware path. A .promotionPick arriving while the picker is already open completes it and appends .dismissPromotionPicker.

    syncAfterPromotion(game:) is the iOS callback, distinguishing completion from cancellation by whether currentNodeUCI is a 5-character UCI prefixed by the armed base — on completion the game already applied the move, so it emits .bumpPhysicalMoveApplied and deliberately no .applyMove.

    The shell kernel¶

    EBoardShellKernelContext is the @MainActor protocol both platform shells conform to, in three groups: observable mirrors the kernel writes (liftedSquare, lastReportedOccupancy, pendingResolutions, awaitingPromotionFromUCI, orientationFlipped, pendingOutbound, diagnosticCapture), bridged internals (sessionCore, diffResolution, suppressRefeedFlag, confirmationTask, desyncDedupKey), and platform services (currentPosition, compactOccupancyHex(), makeGameView(), sendBoardCommand(_:), isTransportConnected, kernelLogNotice(_:), kernelLogError(_:), persistDiagnostics(immediate:), applyKernelEffects(_:), completeDiffResolution(_:_:)).

    EBoardShellKernel.apply(_:context:) -> Bool switches exhaustively, so a new EBoardEffect case fails compilation in exactly one place. It returns false for the platform-divergent set the shells keep: .setLastAppliedMove, .applyMove, .applyResolution, .retractPlies, .bumpPhysicalMoveApplied, .bumpTakeback, .showPromotionPicker, .dismissPromotionPicker.

    Two writes inside it are equality-gated on purpose. Streaming boards emit identical heartbeat frames continuously, and the core emits .setPendingResolutions([]) on every in-sync snapshot; an ungated @Observable assignment fired Observation and re-rendered every reader once per BLE frame. So lastReportedOccupancy and pendingResolutions are written only when the value actually changed — the resolver bookkeeping still runs either way.

    Diagnostics¶

    EBoardDiagnosticCapture is a BlobBackedStore (blobKey = "eBoardDiagnosticCapture") holding a drop-oldest ring buffer capped at cap = 500 entries. It is always on: the content is board-protocol data only, which makes always-on safe by construction.

    Entry kind Payload Export line
    .rx hex frame, space-separated octets rx <hex>
    .lifecycle "connected" / "disconnected" event <name>
    .comment FEN, UCI, or desync note # <text>

    startSession(boardBrandRawValue:) resets the buffer and seeds a comment eboard-diag v1 brand=<raw> at offset 0. appendRaw(bytes:) hex-encodes and skips an empty frame; appendLifecycle(_:) and annotate(_:) take strings. Timestamps are relative by construction — sessionStartTimestamp is stored but never exported.

    asReplayText()

# eboard-diag capture (field diagnostics)
# board: <boardBrandRawValue>          (line omitted when empty)
# privacy: content-only (board frames + moves; no player names, no device ID, relative timestamps)
<blank line>

per entry, in capture order:
  .comment   -> "# <data>"                          (does not advance lastOffsetMs)
  .lifecycle -> ["delay <delta>"] then "event <data>"
  .rx        -> ["delay <delta>"] then "rx <hex>"

delta    = max(0, entry.offsetMs - lastOffsetMs), emitted only when > 0
offsetMs = max(0, Int((Date().timeIntervalSinceReferenceDate - sessionStartTimestamp) * 1000))
           and 0 while no session has started
hex      = bytes.map { String(format: "%02x", $0) }.joined(separator: " ")
output   = lines.joined(separator: "\n") + "\n"

    That output is valid input for ReplayScript.parse(text:), so a field capture replays deterministically against the same kernels that produced it.

    Desync annotations are deduplicated by content, not by time:

    EBoardDiagnosticDeduplication.desyncKey(positionFEN:occupancyHex:resolutions:)
    = "\(positionFEN)|\(occupancyHex)|"
      + resolutions.map { $0.moves.joined(separator: ",") }.joined(separator: ";")

    The shell kernel logs squareoff desync: fen=<fen> choices=<n> board=<hex> and annotates desync fen=<fen> choices=<n> only when this key differs from context.desyncDedupKey, so a board parked in one mismatched state fills the ring with one entry rather than five hundred.

    Encoding a 500-entry capture and atomically replacing its file are delegated to EBoardDiagnosticPersistenceCoordinator, a @MainActor facade over a private actor:

    let persistence = EBoardDiagnosticPersistenceCoordinator()   // 250 ms debounce

capture.annotate("uci e2e4")
persistence.schedule(capture, immediate: false) { json in
    blobStore.saveJSON(json, forKey: EBoardDiagnosticCapture.blobKey)
    return true            // false = writer failed; the snapshot is not marked durable
}

// Lifecycle and take-back boundaries skip the delay but still encode off-main.
persistence.schedule(capture, immediate: true, writer: writer)
persistence.cancelPending()      // session shutting down

    schedule bumps a monotonic revision &+= 1; immediate: true uses delay 0 rather than the 250 ms default. The worker persists only when revision == newestRevision, the capture differs from the last persisted value, JSONEncoder succeeds, and the writer returns true.

    Board marks¶

    BoardMarkDocument is the shared arrow/circle document, bounded so a corrupt or hostile blob cannot blow up either platform:

    Constant Value
    currentVersion 1
    maximumEncodedBytes 1 * 1_024 * 1_024
    maximumPositions 4_096
    maximumMarksPerPosition 128
    maximumTotalMarks 16_384
    maximumPositionKeyBytes 512

    Validation requires version == 1, a non-empty position key within the byte limit, per-position id uniqueness, both indices in 0..<64, and the geometry invariant: an .arrow needs fromIndex != toIndex, a .circle needs fromIndex == toIndex.

    // Editing path: refuse anything this build cannot safely display.
guard let doc = BoardMarkDocument.decodeStrict(rawJSON) else { /* show nothing */ }

// Backup path: never normalize a future document into an empty drawing.
let preserved = BoardMarkDocument.decodePreserving(rawJSON)
preserved.isRecognized           // false when the source was retained verbatim
preserved.encoded()              // the exact original bytes in that case

    encoded() returns the preserved source when unrecognized, "" when every position list is empty (the historical blank sentinel), and otherwise JSON with [.sortedKeys, .withoutEscapingSlashes] after dropping empty position arrays. That last property is what makes a recognized document usable as digest input. BoardMark's decoder treats a missing kind as .arrow for Apple v1 compatibility, while an unknown explicit kind still throws — which is exactly what routes it to the byte-preserving path.

    Presentation strings¶

    BoardSyncPresentation is nonisolated and imports no SwiftUI: semantic state and user-facing copy live here once, and each platform maps state to its own colors and symbols.

    Call Result
    SummaryState(hasSnapshot: false, mismatchCount: _) .noSnapshot → "No board snapshot yet"
    SummaryState(hasSnapshot: true, mismatchCount: 0) .inSync → "In sync"
    SummaryState(hasSnapshot: true, mismatchCount: 3) .outOfSync(count: 3) → "3 squares out of sync"

    syncStripMessage(hasPendingResolutions: false, mismatchCount: 1) "1 square out of sync — tap to fix"

    The same file extends BoardCorrectionPlanner.Correction with instruction — "Move the piece on <from> to <square> (<piece.descriptiveName>)", "Place the <piece.descriptiveName> on <square>", or "Remove the piece on <square>" — and [Correction] with placeSquares / removeSquares for lighting the board.

    Headless surface¶

    Everything in the decision path runs in a command-line tool today. A capture, its brand, and a starting position are enough to reproduce a field bug exactly:

    import ChessCore
import FianchettoKit

let core = EBoardSessionCore()
var position = Position.initial()

func gameView() -> EBoardSessionCore.GameView {
    EBoardSessionCore.GameView(
        position: position,
        currentNodeUCI: nil,
        ancestorPositions: ancestors,          // index 0 = 1 ply back
        legalCastlingRookHomes: rookHomes
    )
}

// Feed one decoded board event and run the deferred search inline.
var effects = core.handle(
    event: .occupancySnapshot(occupancy),
    game: gameView(),
    orientationFlipped: false
)

for effect in effects {
    guard case .resolveBoardDiff(let request) = effect else { continue }
    let resolutions = BoardDiffResolver.resolve(
        from: request.position,
        targetOccupancy: request.targetOccupancy,
        maxDepth: 3,
        limit: 8
    )
    effects += core.completeBoardDiffResolution(resolutions, for: request, game: gameView())
}

// Inspect the mismatch without applying anything.
core.occupancyMismatches(game: gameView())   // ["d4", "e5"]
core.corrections(game: gameView()).map(\.instruction)

    EBoardPositionTransition.connectingMove(from:to:) closes the loop in the other direction for write-back: it brute-forces MoveGenerator.legalMoves(for:), applies each candidate with MoveGenerator.applyMoveUnchecked into a copy, and returns the first whose resulting Position equals the target — comparing Position values rather than building a FEN string per candidate.

}

    Command line¶

    No fianchetto-cli subcommand covers the e-board layer yet. The natural downstream step is already there: a game recorded over the board exports as PGN and annotates through the engine path — available from the command line as fianchetto-cli annotate.

    Three e-board subcommands are proposed, each following the suite's JSON-lines contract (one request object per stdin line, one response per stdout line in request order, diagnostics on stderr, and {"id": …, "error": …} for a bad line):

    Proposed Stdin Stdout
    eboard-replay {"id":…,"brand":"squareOffPro","startFEN":…,"replay":"<.replay text>"} one line per decided event: {"id":…,"effects":[…],"fen":…}
    eboard-diff {"id":…,"fen":…,"occupancy":"<64 chars of 0/1>","maxDepth":3,"limit":8} {"id":…,"resolutions":[{"moves":["e2e4"],"depth":1}],"mismatches":["e2","e4"]}
    eboard-catalog none (argument-only) one line per BoardCatalogKey: key, display name, GATT spec fields, scansByName

    eboard-diff is the pure kernel call and needs no transport at all; eboard-replay needs only the capture text, since asReplayText() already encodes the frames and their relative timing.
